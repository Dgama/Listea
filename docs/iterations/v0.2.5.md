# Listea v0.2.5 — Import Before Review

> **Status:** Executable iteration specification, revision 2  
> **Audience:** Coding agent and maintainers  
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)  
> **Implemented by:** [`v0.2.5-plan.md`](v0.2.5-plan.md) revision 2  
> **Depends on:** v0.2 normalized Task/Asset/ListEntry and shared TaskState semantics  
> **Prepares for:** v0.3 PDF and multi-Asset document review

> **Revision 2 (2026-09-16)** settles two places where revision 1 and the implementation plan would have given contradictory instructions. Both are marked **[r2]** where they appear.
>
> - **Content admission versus review eligibility.** "Supported files" now means two different, explicitly named rules for the two importers, and importing material never implies a judgment may be recorded against it.
> - **Presentation-unavailable material is not reviewable.** PDFs and unresolvable Assets are imported and catalogued; they are not review-eligible until a viewer exists or the source returns.

## Outcome

v0.2.5 separates bringing material into Listea from choosing Tasks to review.

At the end of this iteration, a file or folder becomes reviewable only after an explicit importer has created or reconciled normalized Tasks and Assets. Quick Review and List creation then select complete Tasks without redefining them.

The release should make these two real workflows possible through one domain path:

```text
Picture Classification
folder Source → file-as-Task → Tasks → Quick Review or List

Candidate Selection
folder Source → folder-as-Task → multi-Asset Tasks → Quick Review or List
```

PDF rendering itself is not part of v0.2.5. PDF files may be recognized and represented as Assets only if the current app can safely preserve unsupported content without claiming it is reviewable. The PDF viewer belongs to v0.3.

**[r2] What "without claiming it is reviewable" requires.** A Task is **review-eligible** only when the whole Task is contained in the scope, every Asset it needs is currently resolvable, and every Asset it needs has a viewer in this build. A Task that fails any of those is imported, catalogued, explained and navigable, and no new ReviewEvent may be recorded against it — not by a swipe, not by a control, not by any future caller. A placeholder is evidence that the content could not be inspected, and a judgment filed against uninspectable evidence is a judgment about nothing.

Completion by other means is unaffected: a List Detail checkbox, a bulk edit and progress counting are not review submissions and stay exactly as they are.

## Why this release exists

The legacy Select Folder flow combines source selection, file scanning, Task creation, and review-context creation. That was sufficient while every reviewable object was one media file, but it makes the following concepts indistinguishable:

- external file;
- imported Asset;
- judgment target (Task);
- membership in a List;
- an ephemeral Quick Review queue.

Adding candidate packages or PDF on top of that flow would embed `File = Task = ListEntry` more deeply. v0.2.5 introduces the smallest usable creation boundary before content support expands.

## User-facing model

The primary model is:

```text
Import material once
→ browse imported Tasks
→ Quick Review immediately or select Tasks for a List
```

The app may present imported material under headings such as:

```text
Task Groups
├── Picture Classification
└── Candidate Selection
```

For this release, these groups are source-backed catalog entries. They are not new owners of Tasks or review state.

## Vocabulary used by this iteration

- **Source:** registered origin of raw material; v0.2.5 supports a folder Source.
- **Importer:** explicit grouping rule that produces Tasks and Assets from a Source.
- **Import run:** one attempt to discover and reconcile a Source using its configured importer.
- **Catalog scope:** a browsable projection of imported Tasks, normally preserving the Source hierarchy.
- **Complete Task in scope:** every required source-backed Asset of the Task is available within that scope.
- **Quick Review:** ephemeral review context over complete Tasks in the current scope.
- **List:** persistent, named, ordered context over selected existing Tasks.

## In scope

### 1. Folder Source registration

The user can choose a folder, name the resulting catalog entry, and select an import method before Tasks are created.

Source registration stores:

- an opaque Source ID;
- a resolvable root locator;
- display name;
- importer kind and version/configuration;
- latest import status and timestamps;
- sufficient provenance for later reconciliation.

Choosing a folder does not itself create a List.

### 2. File-as-Task importer

This importer preserves the existing media workflow:

- discover files recursively beneath the selected root — **[r2] every file the existing scanner admits, with no content filter**, because that is what the legacy folder-to-List path has always done and this importer exists to preserve it. Admission is not eligibility: a file no viewer supports still becomes a Task, and that Task simply is not review-eligible;
- create one Task per discovered file;
- create one Asset for that file and attach it to the Task;
- retain relative source structure for catalog browsing;
- assign stable opaque Task and Asset IDs;
- store source identity separately for refresh/reconciliation.

Re-running the same importer on the same registered Source must reconcile unchanged material to the same Task and Asset identities. It must not create duplicates merely because the user imports again.

### 3. Folder-as-Task importer

The first folder-as-Task rule is deliberately constrained:

- each immediate child folder of the selected root creates one Task;
- all supported descendant files inside that child folder become Assets of that Task;
- nested folders organize Assets but do not create nested Tasks;
- deterministic relative-path order supplies the initial Asset order;
- a child folder with no supported files produces no reviewable Task and an import notice;
- direct supported files under the selected root become individual one-Asset Tasks;
- unsupported files are reported and skipped, not silently treated as reviewable Assets.

**[r2] Supported, for this importer, means picture ∪ video ∪ PDF.** It is new and has no legacy behaviour to preserve, so it gets the strict rule while file-as-Task keeps the permissive one. PDF Assets are imported and catalogued; the Tasks holding them are not review-eligible until v0.3 supplies a viewer.

Example:

```text
candidates/
├── alice/
│   ├── cv.pdf
│   └── papers/
│       └── sample.pdf
├── bob/
│   └── cv.pdf
└── rubric.txt
```

produces:

```text
Task Alice
├── Asset cv.pdf
└── Asset papers/sample.pdf

Task Bob
└── Asset cv.pdf

# [r2] rubric.txt produces no Task. It sits directly under the import root, so it would
#      have become a one-Asset Task — but .txt is outside picture ∪ video ∪ PDF, so
#      folder-as-Task skips it and reports it instead.
#
#      Tasks Alice and Bob import and catalogue normally, and are not review-eligible
#      in v0.2.5 because no build of Listea can yet render a PDF.
```

The selected import root is part of the importer configuration. Entering `alice/papers/` later does not redefine `sample.pdf` as another Task.

### 4. Source-backed catalog

After a successful import, the user can browse imported Tasks through a catalog projection that preserves useful Source structure.

The catalog must visually distinguish, at least through labels or counts:

- complete Tasks available in the current scope;
- Tasks that intersect the scope but are incomplete there;
- unavailable or unresolved Assets;
- files skipped or rejected during the most recent import.

The exact visual design is not prescribed in this iteration.

### 5. Quick Review from a scope

Quick Review uses the current catalog scope and creates an ephemeral ordered queue from complete Tasks only.

It must:

- use existing Task identities;
- avoid creating a List/ListEntry solely for the session;
- use the same TaskState and ReviewEvent path as List Review;
- exclude partial Tasks;
- **[r2] exclude Tasks that are not review-eligible** — an Asset that cannot be resolved, or that no viewer in this build can render;
- show a concise reason when review cannot start, naming which condition failed: nothing imported here, only part of a Task, content missing, or no viewer yet;
- avoid importing again unless the user explicitly requests refresh/import.

Quick Review is allowed from the Source root or a child scope. A child scope is eligible only to the extent that it contains whole Tasks.

### 6. List creation from Tasks

Create List operates on normalized Task selections.

It must:

- accept complete Tasks selected from one or more catalog scopes;
- create a List and ordered ListEntries;
- leave Task-to-Asset membership unchanged;
- never invoke grouping rules to reinterpret files;
- allow the same Task to appear in another List or Quick Review;
- derive progress from TaskState;
- delete only membership/context when the List is deleted.

**[r3] A folder is a selection unit, not only a place to browse.** Added after v0.2.5 shipped, on the
report that a Source's catalog offers no way to take a whole subtree without ticking every Task in
it. While Select is on, a folder row carries a checkbox to its left that covers every Task beneath
it — itself and its descendants, the same containment browsing descends by, so what the box picks is
exactly what opening the folder would have shown.

The box and the row keep separate jobs. The box's tap only ticks; the row's tap still opens the
folder and nothing else. Folding them together would make browsing to check something a way to
commit to it, which is the one thing a selection must not do.

Ticking a folder and then clearing a Task under it records the Task as *excluded* rather than
unticking the folder: the folder keeps saying the user chose it while no longer claiming a Task they
took back, and ticking that Task again restores it. Clearing the folder drops its exclusions, so a
folder ticked a second time does not silently re-apply a choice already taken back. A Task picked by
hand is unaffected by a folder being ticked and unticked over it.

Selecting inside a folder selects that folder's Tasks; there is no separate "select all" action,
because a folder's own box at the level above already is one.

**[r2] Review eligibility does not gate List creation.** A List is membership, not a judgment, and v0.1 Lists have always been allowed to contain a file no viewer supports or one whose source has gone. Such an entry is listed, counted, checkable and deliverable; it is only blocked from a new review submission. Import completeness *does* gate the composed flow: no List is created from a failed or incomplete import selection.

An “Import and create List” shortcut may remain for continuity, but it must execute separate import and list-creation use cases with separate error handling.

### 7. Explicit refresh/re-import

The Source view provides an explicit refresh or re-import operation.

For v0.2.5:

- unchanged source identities retain Task and Asset IDs;
- new material creates new Tasks/Assets according to the configured importer;
- changed source metadata/content updates source-facing metadata without replacing domain identity by default;
- missing material becomes unavailable and is reported; it does not erase review history;
- changing importer kind or its grouping semantics in place is rejected with an explanation.

Importer changes that merge or split existing reviewed Tasks are deferred until a migration policy is designed.

### 8. Import result and recoverable errors

Every import run reports:

- Tasks created;
- Tasks reconciled unchanged;
- Assets created or updated;
- skipped unsupported files;
- empty Task folders;
- unresolved/conflicting source locators;
- fatal errors.

No List is created from a failed or incomplete import selection. Successfully committed normalized Tasks remain independent of a later failure to create a List.

## Required domain behavior

### Stable identity

- Task, Asset, Source, and import-run IDs are opaque and distinct.
- A path, URI, filename, folder name, or array position is never used as the domain ID.
- Source locators may be indexed for reconciliation without becoming public Task identity.

### Task completeness

- Review selection always includes the whole Task.
- A narrower catalog scope cannot create a partial version of a Task.
- Partial scope membership is explanatory catalog state, not TaskState.
- A missing Asset makes presentation unavailable/incomplete; it does not automatically uncheck or delete the Task.
- **[r2] It does block a new review submission until the source returns.** Containment and source health are different facts, and review eligibility requires both — plus a viewer for every Asset the Task needs. Eligibility is derived, never stored: it is not a column, not a TaskState field, and not something an import run writes down.

### Shared review truth

- Quick Review and all Lists resolve the same Task ID to the same TaskState.
- A review submission from either context appends the same kind of ReviewEvent.
- Pure navigation and catalog browsing do not mutate TaskState or append events.

### Independent lifetimes

- Deleting a List deletes ListEntries, not Tasks or Assets.
- Removing a catalog shortcut does not silently delete review data.
- Revoking Source access does not erase TaskState or ReviewEvents.
- Destructive deletion of imported Tasks, if exposed at all, is a separate explicit operation and is not required in this iteration.

## Migration and compatibility

The existing Select Folder behavior is represented as a composed compatibility flow:

```text
register/reuse folder Source
→ run file-as-Task importer
→ open Source catalog scope
→ start Quick Review or create List
```

Migration must preserve:

- existing review state;
- existing Lists and ordering;
- current file resolution where possible;
- legacy webhook/public item identifiers at the compatibility boundary;
- the ability to reach the same normalized Task from Quick Review and List Review.

Migration must not invent ReviewEvents for historical state changes that were never recorded as submissions.

Existing users may initially see nearly the same one-motion experience. The release is successful only if the underlying operations are separate and the new folder-as-Task workflow uses the same Core path.

## Data and service seams

This is an implementation-neutral specification, but the implementation must expose equivalent responsibilities for:

```text
SourceRepository
ImportSource / RefreshSource
Importer (file-as-Task, folder-as-Task)
TaskCatalogQuery
BuildQuickReviewContext
CreateListFromTasks
ResolveAssetContent
```

These names are illustrative, not mandated. The important condition is that List creation cannot call a raw folder scanner to decide Task boundaries, and the review UI cannot own importer logic.

Physical persistence may reuse or adapt legacy tables during migration. The semantic ownership defined here still applies.

## Out of scope

- PDF rendering, search, annotations, thumbnails, or viewer gestures;
- generic importer plugin framework;
- arbitrary user-authored grouping rules;
- drag-and-drop Task splitting or merging;
- changing importer strategy in place for a reviewed Source;
- automatic identity merge across different Sources;
- shared Asset instances across multiple Tasks;
- general Task CRUD or manual Task authoring;
- durable independent Task Group lifecycle or permissions;
- synchronization with remote/cloud Sources;
- mixed Task Review Templates inside one List;
- deletion policy for purging historical Tasks and review events.

## UX requirements

The UI must make the active verb unambiguous:

- **Import Folder** chooses a Source and importer.
- **Refresh Import** reconciles a registered Source.
- **Quick Review** reviews complete Tasks in the current scope.
- **Create List** selects existing Tasks and creates persistent membership.

The app should not use **Select Folder** as the only explanation for all four actions. A shortcut may keep that label temporarily for compatibility only if the subsequent screen states whether it is importing, reviewing, or adding Tasks.

**[r2] A shortcut over un-imported material must ask before it writes.** The confirmation names the Source root it proposes and the importer it will use, and no `sources`, `tasks`, `assets` or provenance row exists until it is accepted. A progress line reading *Importing 128 files…* is status shown after consent, never in place of it. Once a Source covers the folder, entering Quick Review is immediate again — the question is asked once per folder, not once per review.

When a scope contains only part of a Task, the UI should explain the condition in domain terms, for example:

> This folder contains only part of “Alice.” Open the parent scope to review the complete Task, or start a new import to define different Task boundaries.

It must not offer Create List as a way to repair or redefine the Task.

## Acceptance scenarios

### A. Existing picture workflow

1. Import a nested picture folder with file-as-Task.
2. Confirm every supported image becomes one stable Task with one Asset.
3. Quick Review a child scope containing complete image Tasks.
4. Mark one Task reviewed.
5. Open a List containing that Task and observe the same state.
6. Refresh the Source and confirm unchanged files do not create duplicate Tasks.

### B. Candidate package workflow

**[r2] Run it with images.** Candidate folders holding 2, 3 and 5 pictures exercise every multi-Asset behaviour this release introduces, with a renderer that exists. A PDF candidate folder is imported in the same pass, but only to confirm steps 7–8.

1. Import a candidate root with folder-as-Task.
2. Confirm each immediate child folder produces one Task.
3. Confirm descendant files become ordered Assets of that Task.
4. Browse into a nested asset folder and confirm it does not expose a partial Task for review.
5. Review from the candidate/root scope and confirm the whole Task is the judgment target, whichever Asset is on screen.
6. Add that Task to two Lists and confirm both observe the same TaskState.
7. **[r2]** Import a PDF candidate folder and confirm it appears in the catalog, states that its viewer arrives in v0.3, and is excluded from Quick Review.
8. **[r2]** Confirm no review can be submitted for it from any surface, and that nothing about it is written when the attempt is made.

### C. Independent List lifetime

1. Create a List from imported Tasks.
2. Submit a review for one Task.
3. Delete the List.
4. Confirm the Task, Assets, TaskState, and ReviewEvent remain reachable from the catalog/another context.

### D. Source change

1. Import a Source and review a Task.
2. Remove or make one backing file unavailable.
3. Refresh the Source.
4. Confirm the missing Asset is reported and presentation is unavailable/incomplete.
5. Confirm prior TaskState and ReviewEvents remain intact.

### E. Importer change protection

1. Import a Source with file-as-Task.
2. Attempt to change it to folder-as-Task in place.
3. Confirm the app refuses to silently merge existing Tasks and directs the user to a separate import or future migration flow.

## Definition of done

v0.2.5 is complete when:

- both importers produce the normalized v0.2 domain model;
- Source/import actions are separate from Quick Review and List creation in application logic;
- Quick Review never reviews a partial Task;
- **[r2] no ReviewEvent can be recorded against a Task whose content cannot be presented**, and the refusal lives at the write boundary rather than only in the UI;
- Create List accepts Task IDs rather than raw files;
- repeated import of unchanged material is identity-stable;
- Quick Review and List Review share TaskState and ReviewEvent behavior;
- legacy file-as-Task behavior still works through the compatibility composition;
- the candidate-package acceptance scenario passes without adding candidate-specific behavior to Core;
- architecture and migration tests demonstrate that adding a PDF Asset Viewer will not require changing Task/List/import semantics — **[r2] proven by a PDF-Asset Task behaving identically to an image Task in import, catalog, containment, selection, List membership, TaskState and webhook, and differing only in eligibility**.

## Decisions deferred to later versions

The following need real workflows before becoming architecture:

- whether a durable Task Group entity is necessary;
- whether one Asset may be shared by multiple Tasks;
- cross-Source duplicate detection and identity merge;
- user-controlled Task split/merge with historical review migration;
- automatic cleanup of unavailable imported Tasks;
- editable importer definitions;
- persistent Quick Review sessions beyond ordinary resume state.

## Handoff to v0.3

v0.3 can begin once v0.2.5 proves that content type is independent from Task and review context. Its primary extension should be:

```text
PDF Asset kind
→ PDF Asset Viewer
→ Asset navigation within a multi-Asset Task
```

It must not reopen the meanings of Source, Importer, Task, Quick Review, List, TaskState, or ReviewEvent.
