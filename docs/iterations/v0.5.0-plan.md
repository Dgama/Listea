# Listea v0.5.0 — Implementation plan

> **Status:** Plan, for implementation. **No production code or schema is changed by this document.**
> **Spec:** [`v0.5.0.md`](v0.5.0.md) — the model, and why the middle band is the template
> **Builds on:** v0.4.0 (ownership; a List that spans Todos), v0.3.0 (the Todo), v0.2.5 (the
> three-tier review surface, whose decision log this one is deliberately shaped after)
> **Inspected:** `Settings.kt`, `MediaUi.kt`, `ReviewScreen.kt`, `Webhook.kt`, `MainActivity.kt`,
> `SettingsScreen.kt`, `SourcesScreen.kt`, `ListsViewModel.kt`, `Catalog.kt`, `FileArrange.kt`,
> `MediaSave.kt`, `domain/Templates.kt`, `domain/Domain.kt`, `data/ListEntities.kt`,
> `data/ReviewAsset.kt`, `data/ListeaDatabase.kt` at `773a0d0`

## Framing

The specification's whole claim is that one band of the Review screen varies with two things at
once, and that nothing else about the screen does. Everything here follows from that:

> **The template lookup is keyed by file kind, resolved from the filename, and is per Todo.**

> **The definition of an asset control is built-in, versioned and hashed. Its configuration is the
> Todo's, and is editable.**

> **Three bands are touched by nothing in this plan: the navigator, the task control, and the media
> transport.**

The blast radius is genuinely small and was measured before this plan was written. Everything the
action list feeds is five call sites:

| Site | What it draws |
|---|---|
| `MediaUi.kt:697` | The middle band — the chip row itself |
| `MediaUi.kt:765` | `ItemActionTags` — the task-level badge row in the navigator |
| `ReviewScreen.kt:131` | `ReviewChrome.actionLabel`, used by the Info sheet |
| `MainActivity.kt:2255` | The Info sheet, again |
| `Webhook.kt:312` | `itemJson`'s `actions` array |

All five read `AppSettings.actions` today. All five need the same answer — *what does this Task's
control for this kind define?* — so the plan introduces that one answer once and points all five at
it.

## 0. Decision log

Decisions taken while writing this plan that the specification does not itself settle. Each is
cheap to overturn now and expensive later, which is why they are listed first.

| # | Decision | Why | Where |
|---|---|---|---|

| 2 | The kind is **derived from the filename at read time**, never persisted, and derived **through `mediaKindOf`** (`FileArrange.kt:197`) | `assets` has no kind column by design (`v0.2.5-plan.md` decision 3), and `Catalog.assetViewerAvailable:50-53` is filename-based for a stated reason: a Task nobody is looking at must still be answerable without opening its files. ## 1. The template objects

`domain/Templates.kt` grows a third kind and a third definition. Nothing about
`TemplateDefinition.AssetViewer` or `TemplateDefinition.TaskReview` changes.

```kotlin
enum class TemplateKind { ASSET_VIEWER, TASK_REVIEW, ASSET_CONTROL }

data class AssetControl(
    val compatibleKinds: Set<AssetKind>,
    val favourite: Boolean
) : TemplateDefinition
```

### `AssetKind` needs a derivation, and has never had one

Worth stating before anything else, because it is the one place this plan is not merely extending
what exists. `AssetKind` (`domain/Domain.kt:49`) is declared, and `AssetViewer` already declares
against it — but **nothing in `app/src/main` has ever computed one from a file.** The classifier
review eligibility actually uses is a *different* enum: `mediaKindOf(name): MediaKind?`
(`FileArrange.kt:197`), over `MediaKind { PICTURE, VIDEO, TEXT }` (`FileArrange.kt:23`), driven by
`fileExtension` (`FileArrange.kt:204`).

So this release adds the derivation, and the only correct form of it is a total mapping **through**
the existing classifier:

```kotlin
fun assetKindOf(name: String): AssetKind = when (mediaKindOf(name)) {
    MediaKind.PICTURE -> AssetKind.IMAGE
    MediaKind.VIDEO   -> AssetKind.VIDEO
    MediaKind.TEXT, null -> AssetKind.OTHER
}
```

It must not be a second extension list. A new list would drift from `MediaKind.PICTURE.extensions`
the first time someone adds `jxl` to one of them, and the failure — a file that renders but has no
tag chips, or has chips but will not render — would be found by a user rather than by a test.
Test #1 pins this.

**A same-named trap:** `MediaSave.kt:68` already declares `fun mediaKindOf(mimeType: String?, name: String): SavedMediaKind?`
— same name, different signature, mime-first, returning `SavedMediaKind`. It is for saving to the
album and is not the classifier to reuse. Import the right one deliberately; an accidental
overload resolution here compiles and is wrong.

`compatibleKinds` is load-bearing in two places and must not be decorative:

- **Validation** — a configuration may name a definition for a kind only if the definition accepts
  that kind. This is what stops an `OTHER` row existing.
- **Settings** — the template manager renders exactly the kinds the built-in accepts, which is why
  §4 can say "image and video" without hardcoding a second list.

The built-in, in `object Templates`:

```kotlin
val MediaAssetControl = TemplateVersion(
    ref = TemplateVersionRef("builtin.media.asset-control", 1),
    displayName = "Media Asset Control",
    definition = AssetControl(
        compatibleKinds = setOf(AssetKind.IMAGE, AssetKind.VIDEO),
        favourite = true
    )
)
```

and added to `Templates.all`.

**The compiler enforces half of decision 4.** `TemplateVersion.canonicalText()` (`Templates.kt:90-105`)
is an exhaustive `when` over `TemplateDefinition` with **no `else` branch**, so adding the third
subtype will not compile until the new arm is written — and the arm must fold `compatibleKinds` and
`favourite` into the digest, or two controls differing only in a compatible kind would hash alike.
That is the mechanism that keeps `contentHash` meaningful, and it is why this release can add a
template *kind* without weakening the immutability the audit found was otherwise unreachable.

**`Templates`' own doc comment is now false** (`Templates.kt:110-113`: "two versions, no editor, no
storage" — and it was already wrong about the viewer being two). It must be rewritten to say what
the registry now is: three definitions, still no editor and no storage, with the editable part being
the *configuration* on the Todo rather than the definition (decision 4). A comment that says the
opposite of the code is how the next reader concludes templates are still decorative.

**`compatibleKinds` in `MediaViewer` is deliberately left alone.** It is tempting to make the two
agree — the viewer classifies kinds, the control accepts them — but they are independent facts: a
future control may accept a kind the viewer cannot display (to record "this is a PDF, and here is
its note") and the viewer may display a kind no control governs. Coupling them is a design error
dressed as tidiness, and the plan declines it.

## 2. Room schema v20

Two columns, both `NOT NULL`, and no new tables. A new table was designed first and discarded:
every per-kind value here is a small fixed map, and `sources.contentPolicy` already set the
precedent that such a value is a column, not a relation.

**`sources`** gains:

```sql
ALTER TABLE sources ADD COLUMN assetControls TEXT NOT NULL DEFAULT ''
```

**`task_imports`** gains:

```sql
ALTER TABLE task_imports ADD COLUMN assetControls TEXT NOT NULL DEFAULT ''
```

Both are `String` on the entity (`@ColumnInfo(defaultValue = "")`), matching the migration.

### Encoding

One line per kind, tab-separated: four fixed fields then the tag list.

```text
image	builtin.media.asset-control	1	a1:Price:price|a2:Quality:quality
video	builtin.media.asset-control	1	a3:Fresh:fresh|a4:Cheap:cheap
```

Fields 2 and 3 record **which definition version the configuration was chosen under**. That is not
hashed into anything — decision 4 keeps configurations out of `contentHash` — but it is recorded,
because it is the only way to answer "which control were these tags picked for?" once a v2 exists.

Tags are `id:displayName:wireValue`, `|`-separated. The two-level encoding is the reason
`encodeCustomActions`' rule survives: `sanitizeActionText` already strips `\t` and `\n` from
anything typed, so the line separator is safe; `|` and `:` are added to what it strips, because a
tag's separator must be as untouchable as its record's.

Decoding follows `decodeCustomActions` exactly: a line whose kind is unrecognised is dropped, a tag
whose id is empty or contains `,` is dropped (the comma is what items store with —
`encodeActionIds`), and anything unreadable costs its own entry rather than the whole column.

Two new functions in `Settings.kt` beside the existing codec:

```kotlin
fun encodeAssetControls(controls: Map<AssetKind, AssetControlConfig>): String
fun decodeAssetControls(text: String): Map<AssetKind, AssetControlConfig>
```

`AssetControlConfig` is `data class AssetControlConfig(val ref: TemplateVersionRef, val tags: List<CustomAction>)`.
Reusing `CustomAction` rather than minting a parallel type is deliberate: a tag **is** what a custom
action already is — an id nothing shows, a display name, and a wire value — and the id generators,
the sanitiser and the codec all apply unchanged.

## 3. Migration v19→v20

In `MIGRATION_19_20`, in the shape `MIGRATION_18_19` established: two `ALTER TABLE` statements, both
not-null with a default, no second pass over any table, and a doc comment that says *why* `''` is
the behaviour-preserving value.

The comment has to carry its weight here, because `''` is doing something subtler than `'keep'`
did. It means **"nothing was ever chosen"**, and every reader must resolve it as *the app's current
default* rather than as *no tags*. A future reader who treats `''` as an empty tag set would
silently strip every tag chip off every Todo that predates this version. Say so in the comment.

**No backfill, on purpose.** Decision 9. Two reasons, and the second is the real one:

1. A Room migration runs against SQLite and cannot read DataStore, so the current app-wide tag list
   is not available to it.
2. There is nothing correct to write even if it were. What a pre-v0.5.0 Todo "chose" is *the app
   default, continuously*. Writing a snapshot of today's list onto it would freeze it at upgrade
   time and quietly change its behaviour the next time the user edited Settings — which is the
   opposite of the compatibility this migration is for.

`LEGACY_*` tables and `file_review_state` are untouched.

`exportSchema = true` stays on, and `20.json` must be committed. `ListeaDatabase.kt:1148` gains
`MIGRATION_19_20` in `.addMigrations(...)`.

**A migration test is required** (§10). The v14→v19 tests are the model: open a v19 database with
the fixture's shape, migrate, and assert both columns exist and read as `''` on every row.

## 4. Settings

### The stored keys

Add two, and keep the old one:

```kotlin
val KEY_ASSET_CONTROL_TAGS_IMAGE = stringPreferencesKey("asset_control_tags_image")
val KEY_ASSET_CONTROL_TAGS_VIDEO = stringPreferencesKey("asset_control_tags_video")
val KEY_CUSTOM_ACTIONS = stringPreferencesKey("custom_actions")   // read-only from here on
```

`readAssetControlTags(prefs, kind)` reads its own key and, **absent that, falls through to
`readCustomActions(prefs)`**. Both kinds fall back to the same list, which is why an upgrading
install sees today's tags under both image and video and acceptance #6 holds without a rewrite.
The moment the user edits either section, its new key is written and the fallback stops applying to
that kind — the same "a read rather than a one-off rewrite" argument `readCustomActions` already
makes for the two slots before it.

`AppSettings.customActions` is replaced by:

```kotlin
val assetControlTags: Map<AssetKind, List<CustomAction>> = DefaultAssetControlTags
```

with `DefaultAssetControlTags = mapOf(IMAGE to DefaultCustomActions, VIDEO to DefaultCustomActions)`.
`DefaultCustomActions` stays exactly where it is, now named as both kinds' starting point.

**`AppSettings.actions` is deleted, not kept as a convenience.** Decision 11's point is that a
global accessor with no notion of kind is the bug; leaving one in place would let the next change
reintroduce it by accident. Its three companions — `labelOf`, `wireOf`, `customActionOf` — take an
explicit tag list or config instead of reading `customActions` off `this`.

`AppSettings` also gains the two lookups the rest of the plan calls:

```kotlin
fun actionsFor(config: AssetControlConfig?): List<ItemAction>
fun configOf(tags: Map<AssetKind, AssetControlConfig>, kind: AssetKind): AssetControlConfig?
```

> **As built.** Neither name survives, and the reason is that both were shaping the caller's
> problem rather than the answer's. `actionsFor(config)` splits a value that turns out always to
> have an answer, so the pair landed as one type and one function: `ResolvedAssetControl(favourite,
> tags)` with `actions` derived from it, returned by `AppSettings.controlFor(recorded, kind)`.
> `configOf` was doing the *decode* half of a lookup the callers always wanted whole, so it has no
> separate existence — `controlFor` decodes and resolves in one step, and
> `controlConfigsFor(recorded)` is the other direction, producing the complete configuration a run
> is handed (§5). Both live in `Settings.kt` beside the codec they are built on.

### The screen

`SettingsScreen.kt`'s existing "Review" section keeps its Custom action editor at `:279-325` /
`CustomActionFields` at `:920-974` **exactly as it is**, and is drawn twice — once per kind — inside
a new template section. The rows, the add button, `nextCustomActionDefaults`, the sanitiser and the
empty-value validator are all reused unchanged; the only new thing on screen is a heading per kind.

The two sections write `KEY_ASSET_CONTROL_TAGS_IMAGE` / `_VIDEO`.

Per decision 15, the sections are not hardcoded to image and video: they are generated from
`Templates.MediaAssetControl.definition.compatibleKinds`. That is what makes §1's claim load-bearing
rather than decorative, and it is a two-line difference.

## 5. The Create Tasks dialog, and the run

This is not a new mechanism. The content policy already does exactly this, end to end, and the
plan follows it rather than inventing a parallel path:

| Step | Content policy, today | Asset control, after |
|---|---|---|
| The dialog asks | `ContentPolicyChoice` (`MainActivity.kt:1632`, used at `:1540`) | The same composable, once per kind present |
| It reaches the run | `ImportOptions.contentPolicy`, passed **into** `dao.runImport` (`ListsViewModel.kt:1590`) | `ImportOptions.assetControls`, passed the same way |
| The Todo records it | `dao.registerSource(contentPolicy = …)` (`ListsViewModel.kt:1573`) | `registerSource(assetControls = …)` |
| The card reads it back | `todoContentPolicyLabel(source)` (`SourcesScreen.kt:288-291`) | `todoAssetControlLabel(source)`, same shape |

**Pass it into the run; do not read it back from the row.** `ListsViewModel.kt:1556-1563` explains
why in terms that apply unchanged: the name and the grouping describe what the Todo *is*, so a
failed run must not leave them changed; a policy describes what *this run* should do, so reading it
from a row the write has not reached would make the dialog's answer apply one run late — the user
picks an answer, presses Refresh, and watches the previous answer take effect. Asset control is the
second kind of value, not the first, and belongs on the `runImport` call beside `contentPolicy`.

The dialog then:

- Asks **per kind present in the folder being imported**. A folder of photographs is asked about
  image only; a folder holding both, like the fixture's `Whatsapp`, is asked about both.
- Pre-fills each kind from the app's current tags (§4), offering a tag editor per kind.
- Collects exactly what lands in `sources.assetControls`.

"Which kinds are present" is computed from the scan the dialog already has in hand — the same scan
that determines Task boundaries. It is **not** a second directory walk, and the dialog must not
start one.

The tag editor must be `CustomActionFields` reused, not re-implemented. If it needs a variant
without a remove button, factor the existing composable rather than forking it.

`todoAssetControlLabel` copies `todoContentPolicyLabel`'s one stated rule: **reuse the heading the
dialog asked with**, so a user who answered the question recognises the answer instead of learning a
second name for it. That is also why the two labels belong adjacent on the card — they are the
Todo's two standing answers, and they should read together.

The card is where decision 8's drift becomes visible: a Todo whose Settings have since been edited
shows what its **Tasks** are under, not what Settings would give a new run. If the card shows the
Todo's own recorded value instead, the drift is invisible at exactly the moment it matters.

## 6. The Task's record

`TaskImportEntity` gains `assetControls: String = ""`.

Stamping happens in the import run, at the point the Task is created or re-seen — the same place
that writes `TaskImportEntity` today.

**Both records come from one value, `options.assetControls` in the enclosing `applyImport` call** —
not from two lookups that happen to agree. That is the whole of the guarantee, and it is weaker than
"one transaction": a new Todo's `sources` row is written by `registerSource` *before* `runImport`
runs (`ListsViewModel.kt:1573` then `:1590`), so the two writes are in different transactions on
different sides of the run. What makes them consistent is that neither reads the database to find
out what the answer was. An implementation that stamps the Tasks from the row it just wrote has
reintroduced the one-run-late failure decision 18 exists to prevent, and would still pass a test
that only ever imports once.

**Re-stamping is only on a run.** Editing Settings changes what the *next* run produces. Tasks
already imported keep what they were imported under, which is the behaviour the specification
requires and acceptance #7 tests. A run over an unchanged folder is still a run and still
re-stamps; that is intentional — the user asked for it.

Reading it is the lookup everything else uses:

```
task.assetControls -> decodeAssetControls -> Map<AssetKind, AssetControlConfig>
       absent/''   -> settings.assetControlTags   (decision 9)
```

Centralise this in one function — `resolvedControls(importRow, settings)` — rather than repeating
the fallback at five sites. The fallback is the part most likely to be forgotten.

> **As built, and deliberately not one function.** There are two resolutions, and the plan's single
> `resolvedControls` would have had to be told which one it was answering:
>
> | Function | Resolves over | Used by |
> |---|---|---|
> | `AppSettings.controlFor(recorded, kind)` | one kind | the chip row, the Create Tasks dialog |
> | `AppSettings.controlForTask(recorded)` | the **union** of the Task's kinds | the badge row, the Info sheet, the webhook |
>
> They legitimately disagree — `AssetControlTest` pins a video-only tag being nameable while a
> photograph is on screen (§8) — so collapsing them would have hidden the distinction rather than
> centralised it. The thing actually worth centralising is the `''`-means-never-chosen fallback, and
> it *is* centralised: it is the first branch of `controlFor`, which `controlForTask` is built on.

## 7. The middle band

`MediaUi.kt:673-736`'s `ReviewAssetControls` changes its parameter from `settings: AppSettings` to
the resolved list, and its `:697` loop iterates that instead of `settings.actions`. Its rendering —
the `★` chip at `:699-712`, the custom chips at `:713-728`, Info at `:732-734` — is unchanged.

`★` is rendered only when the control in force has `favourite = true` (decision 5, §1's
`AssetControl.favourite`). For the one built-in that is always, so this release's visible behaviour
is unchanged by it — but the branch exists, and a test asserts it, because the specification's whole
argument is that `★` belongs to the template.

`ReviewScreen.kt` computes the list at the `:635-647` wiring point, where it already has both the
item and `currentAsset`:

```kotlin
val kind = assetKindOf(currentAsset.name)          // `name`, the basename — not `relativePath`
val controls = resolvedControls(item.importRow, settings)
val control = settings.configOf(controls, kind)
assetControls = { ReviewAssetControls(actions = settings.actionsFor(control), ...) }
```

The field is `ReviewAsset.name` (`data/ReviewAsset.kt:14`), which `toReviewAsset` fills with
`relativePath.substringAfterLast('/')` — the basename, which is what a classifier wants, and the
same field `reviewBlockFor` already passes to `assetViewerAvailable` (`Catalog.kt:62`). Using
`relativePath` would still work for a file whose parent has no dot and would silently misclassify
one whose parent does.

`assetKindOf` is the derivation defined in §1 — a total mapping through `mediaKindOf`, not a new
regex and not a new extension list. It is **new code**, not a promotion of something existing:
`mediaKindOf` is already public in `FileArrange.kt`, so nothing needs moving, and the risk is not an
inaccessible private helper but an implementer reaching for the same-named `MediaSave.kt:68`
overload instead.

**Three comments become false and must be rewritten rather than left.** An audit that finds a
comment contradicting its code is how the next reader is led to the wrong change, so these are part
of the work, not tidying:

| Where | What it says now | What is true after |
|---|---|---|
| `MediaUi.kt:747` | "one function reading one `[AppSettings.actions]` is what makes" the badge row and the chip row agree | They agree for a *different* reason: the badge row resolves over the union of the Task's kinds (§8), the chip row over the kind on screen. They can now legitimately differ, and that is the design |
| `ReviewScreen.kt:637-639` | "renaming an action in Settings relabels the chips immediately" | Renaming relabels the chips of Tasks whose control used that tag, via the id→config resolution — but no longer *every* chip on *every* Asset, which is the point of the release |
| `Templates.kt:110-113` | "two versions, no editor, no storage" | §1, above |

**If the resolved control is null** — a kind with no configuration — the chip row renders `★` only,
since a control-less kind still has whatever the built-in carries. That case cannot arise for image
or video in this release; it is defined now so that the code has one answer rather than an
exception, and so that `OTHER` (which cannot be reviewed) never reaches the branch at all.

> **As built, the branch does not exist — and the reason is worth more than the branch was.** The
> fallback is **per kind**, so a kind the record does not name resolves to *that kind's* app default
> rather than to nothing (§4, decision 9). A user configures image, imports, and later adds a video
> to the folder: the video's kind is named by nothing, and it must offer the app's video tags — not
> an empty row, and not `★` alone. That makes the resolution **total**: `controlFor` never returns
> null, so the "no configuration" case the plan provided an answer for cannot be reached from any
> caller, and the `★`-only arm was deleted rather than left as dead code. What the plan *did* get
> right is that the star is read off the control and not drawn as a constant; the false arm of
> `favourite` is asserted in `AssetControlTest` even though no shipped definition reaches it.
>
> The case the plan was reaching for — *a configured kind whose tags all failed to parse* — is real,
> and it resolves as a control offering nothing. It is a different screen from one offering the app
> default, and it is tested as such.

## 8. Badges, labels and the webhook

One new resolver, in `Settings.kt`, beside `itemActionNames`:

```kotlin
fun resolvedActionsForTask(
    controls: Map<AssetKind, AssetControlConfig>,
    settings: AppSettings
): List<ItemAction>
```

It returns the **union**, in a stable order — `★` first, then each kind in `AssetKind` declaration
order, then each control's tags in configured order, de-duplicated by action while keeping first
occurrence. Stability matters because this list drives the webhook's array order.

Then the three signature changes:

```kotlin
fun itemActionNames(decisions: ReviewDecisions, actions: List<ItemAction>): List<String>
fun itemActionLabel(decisions: ReviewDecisions, actions: List<ItemAction>): String?
```

Note that the wire-value resolution moves inside them and therefore needs the config: take the
resolved list of `CustomAction`s, or a `(ItemAction) -> String` resolver, rather than dropping
`settings`. **Do not drop the settings lookup** — that is how a renamed tag would start sending its
id.

Call sites: `MediaUi.kt:765` (union), `MediaUi.kt:697` (the kind on screen), `ReviewScreen.kt:131`
and `MainActivity.kt:2255` (which context each is in — Info sheet is task-level, so union), and
`Webhook.kt:312` (union; the payload is per item, and an item is a Task).

`Webhook.kt:275-294`'s `buildWebhookPayload` stays **pure** — it takes the event, the list, the
items and a resolver, so it remains JVM-testable exactly as `WebhookPayloadTest.kt` needs. Do not
let a database lookup leak into it.

Decision 14 keeps `:171-179`'s behaviour: an id set on an item but defined by nothing the Task is
under is carried in the record and omitted from the payload, unchanged.

## 11. Risks, limitations and accepted debt

- **Two records, one truth (decision 8).** `sources.assetControls` and `task_imports.assetControls`
  can disagree after a Settings edit, by design. The design's answer is that they *should* disagree
  and the Todo card says so; the risk is a reader who assumes the Todo's value is authoritative and
  writes a bug around it. The migration comment and the DAO's doc comment must both say which one
  review reads — `task_imports` — and test #12 is what stops the run reading the other.
- **The two writes are not one transaction** (§6). A new Todo's `sources` row precedes the run that
  writes its Tasks, so the consistency between them rests entirely on both deriving from
  `options.assetControls`. That is a property no compiler checks and no schema enforces; the only
  defence is test #12 and a comment at `runImport` saying why the parameter exists.
- **The `''` fallback is load-bearing and easy to lose** (§3). A future reader who treats it as an
  empty tag set strips every chip from every pre-v0.5.0 Todo, silently, with no test failing unless
  test #7 is written. Write it.
- **Re-stamping only on a run** means a user who edits Settings sees no change until the next import.
  That is the required behaviour, but it is a real friction and the Todo card is the only place that
  explains it. If the card does not communicate it clearly, that is a defect in this release, not a
  follow-up.
- **`OTHER` has no configuration and cannot be reached for one** (decision 15). If PDFs become
  reviewable later, this release's answer — `★` only — is arbitrary rather than designed, and the
  plan should not be read as having decided it.
- **No typed fields** (decision 16). The chef's notebook holds labels only. The definition is shaped
  to grow a field list, and nothing here commits to that shape.
- **`★` is only nominally a template property** in this release, since the one built-in always
  carries it (§7). The branch and its test are what make the claim real rather than aspirational; if
  they are dropped as unnecessary, the specification's claim that `★` belongs to the template is
  unsupported by the code.
- **The Create Tasks dialog's reuse of `CustomActionFields`** is the part most likely to be
  implemented as a copy. A fork is a defect: it re-introduces the divergence the "one codec, one
  sanitiser" arrangement exists to prevent.
- **`AssetKind` gets its first derivation ever in this release** (§1). It has been declared and
  unused since v0.2, so there is no existing behaviour to preserve and no existing test to catch a
  wrong mapping — the enum is `IMAGE, VIDEO, OTHER` while the classifier beneath it is
  `PICTURE, VIDEO, TEXT`, and the two vocabularies do not line up by name. Test #1 is the only thing
  standing between that mismatch and a file that renders but cannot be tagged. Write it first.
- **`TEXT` maps to `OTHER` and so can never be configured** — a text file has a `MediaKind` but no
  viewer, so it is `OTHER` and unreviewable. That is correct today and is *not* a decision about text
  files; if one ever becomes reviewable it will need its own `AssetKind`, not an `OTHER`
  configuration.

3. **The run stamps from `options`, never from the row it just wrote** — §5, §6, decision 18, risk 2's
