## Why this version

Listea already reviews media well. A Task can hold zero, one, or many files; a PDF can be read and
marked; an Add-on can ask questions about the Task as a whole; a round can be exported and the sent
bytes are kept. The v0.7.x series made the Task–Asset pair and the Task layer visible.

What the product cannot yet do is review **content that is not a file package**. A vocabulary card
is a prompt, a set of options, and a pronunciation clip. A questionnaire is a question, a legal
answer shape, and a reference image. Both are Tasks a person can judge, and both currently have to
pretend to be folders, or cannot enter the app at all. The gap is not a missing screen; it is that
several assumptions are still file-shaped:

- `Task` has no stored content kind or payload;
- the importer plans from a `FolderSnapshot` and nothing else;
- catalog selection, decision targets, page counts, and queue entries assume Assets;
- a zero-Asset Task can pass the current presentability check vacuously.

v0.8.x is the framework round that removes those assumptions. It does not ship the vocabulary or
questionnaire products. It makes the review engine able to accept structured content through the
same identity, review, state, history, and export boundaries that media already uses. v0.9.x then
builds those products on the contracts.

## The one-sentence goal

**A payload-only Task should be importable, discoverable, selectable, renderable, reviewable,
reopenable, and exportable through the same contracts as a media Task — without changing the
meaning of Task, Asset, List, Add-on, ReviewEvent, or export history.**

## Final acceptance — the dating-profile fixture

> **Confirmed 2026-10-24.** This is the end-to-end test for the v0.8 arc, implemented in v0.8.2. The
> fixture bytes, assertions, and device walk are in
> [`v0.8.2-plan.md`](v0.8.2-plan.md#10-acceptance-fixture--the-dating-package).

The acceptance run is a small **simulated dating app**, reviewed as a queue:

- An Upstream Package contains, for each candidate, a **Prompt** member JSON with a basic profile
  introduction and one **Resource** — the personal photo. The photo is supporting content: it is not
  an Asset, not a page, and not a judgment target.
- A manifest declares the Package, its Prompt keys, the profile kind/schema, the photo reference,
  and the like/dislike choices. The Prompt body is a separate member file, not inline in the
  manifest.
- A Structured Viewer renders the question — the profile plus its photo — and the two choices.
- A Headless Review Template records the choice through the normal primary submission path. It
  declares commit modality and revisability independently; the dating case uses one tap with
  regret allowed.

The four things this run must prove:

1. **The protocol is extensible.** A new Prompt/content kind and its choices are declared by the
   Package and resolved through a versioned Viewer/template capability, without a workflow-specific
   branch in core.
2. **A JSON Package is importable.** The manifest is validated, keys are reconciled, and the
   payload-only Tasks are discoverable and selectable.
3. **The Viewer renders the question and the choices.** The profile JSON is presented with its
   photo Resource, and like/dislike are the only decisions offered.
4. **The Headless template catches the result.** A choice submitted through the normal path
   produces one primary event and the permitted state — not an Add-on answer and not a side channel.

The chosen result also leaves through the same round/export path. v5 is exported by **both**
Webhook and Txt from one mapping, and carries content identity plus the chosen option id and label
— not the profile body or the photo.

## What changes

| Area | v0.8.x direction |
|---|---|
| **Prompt** | The question-setter's unit: statement, response contract, and materials. Stored in a Package as a member JSON; instantiated by a TaskPart, never stored as a Task. |
| **TaskPart (v0.8.4)** | The taker's instance of one Prompt inside a Task; the decision unit. A Task holds 1..N; a file or folder Task is one degenerate part; a part may be pending, answered, unavailable or detached. |
| **Composition (v0.8.4)** | The taker's rule for which Prompts become TaskParts of one Task: `prompt:<key>`, `section:<key>`, future `custom:<key>`. The protocol declares no Task. |
| **Package** | A directory with a minimal `.listea` manifest and local members. It declares Prompt keys, Assets, Resources, keys, revisions, and diagnostics. It is import provenance, not a durable owner. |
| **Importer** | Typed input: `FolderSnapshot` **or** a validated Package manifest. A pure plan produces Tasks with optional payloads, ordered Assets, and Resource references. |
| **Task payload** | The normalized Prompt description a TaskPart answers: kind, schema version, body, revision. A part may have a payload and no Assets; a one-part Task keeps the older one-payload shape. |
| **Resource** | A declared supporting dependency (audio, illustration, reference) scoped to `(todoId, packageKey, resourceKey)`. Not an Asset, not a page, not a judgment target. Requiredness is per Task use. |
| **Viewer** | A versioned capability declaration plus a platform renderer. It emits named intents; it does not call a DAO, own navigation, or complete a Task. Resolution is by declared compatibility, not a one-to-one id. |
| **Headless Review Template** | A Task Review Template Version whose primary controls come from the Structured Viewer. It declares commit modality and revisability as **independent** policies, plus `completesTask` and `advanceAfterCommit`. |
| **Page model** | One typed list, grouped by TaskPart (v0.8.4): each part's optional content page, then its Asset pages; the optional Add-on page last. It drives rendering, counts, resume, and the queue guide. |
| **Catalog** | A Package scope inside a Todo, identified by provenance. No fabricated file path for a payload-only Task. |
| **Submission** | One `ReviewSubmission` service over the existing atomic transaction. A valid commit appends one event and updates permitted state; a failed validation writes neither. |
| **Provenance** | New primary events record response-encoding version, template version, Viewer capability version, per-Asset control versions, and structured content revision. Old events are not rewritten. |
| **Export** | A pure `ExportMapping(contract version)` stage between the round snapshot and delivery, shared by Webhook and Txt. v2/v3/v4 stay byte-compatible; v5 is only for structured rounds and carries content identity plus the chosen option, not the Prompt body. |

## What does not change

These are not implementation details; they are the boundaries that make the round safe.

- **Add-ons are frozen.** One per Todo, stamped on import, final page, answers as Task-owned current
  state, replace-on-re-answer, hidden-not-deleted, no required flag, no completion gate, existing
  `addOn` export object. No Add-on answer enters `ReviewResponse` or `ReviewEvent`. A primary
  questionnaire is a different thing and uses a Headless Template.
- **Media and PDF behavior is frozen.** Image/video/PDF viewing, gestures, passage marks, detached
  marks, chip rows, Info sheets, and existing controls keep their semantics. The queue guide keeps
  its two levels and its navigation-only rule.
- **Identity is frozen.** Domain IDs, public IDs, `(taskId, rootUri, relativePath)` for file Assets,
  List membership, and the no-path-as-identity rule remain. Keys are never backfilled from
  `groupPath`.
- **History is frozen.** Current state still describes what is true now; events describe what
  happened. Old response encodings are decoded as far as they go; unknown content is preserved as
  unreadable-with-diagnostic; absent provenance stays absent.
- **Export history is frozen.** A resend uses the stored original bytes, never a new mapper.
- **Source remains retired as an entity.** `sources` is an internal table name that holds Todos.
  Package adds no Source model. The word survives only in its plain-English external-material sense.

### v0.8.1 — Stored Task Reviews, viewer events, the sampled-point proof

**Why first:** Headless must stop being a special case before anything has to choose one. Moving
Task Review onto the same stored, versioned path as an Asset Control, and proving it with a viewer
event that no human button fabricated, is the smallest fixture that settles the model.

**Deliverables**

- Task Review as a stored lineage: `template_versions.kind/definition/definitionVersion`, a typed
  `TaskReviewDefinition` with `viewer`, `accepts`, `commit`, `completesTask`, `advanceAfterCommit`,
  and two seeded built-ins (`builtin.media.rapid-review@1`, `builtin.image.sample-review@1`).
  Headless is a definition, not a class.
- Todo ownership: `sources.taskReview` stamped per Task in `task_imports.taskReview`; the List's
  two columns become a legacy fallback and are no longer written. Resolution is per item.
- An explicit commit: `commitOn` names a template `ACTION` control or the built-in `complete`
  checkbox. The submit button belongs to the template, not the viewer.
- A versioned primary response envelope (`PrimaryReview(completed, events)`) with a decoder for
  stored responses; legacy `MediaReview` encodings stay readable byte-for-byte.
- One viewer event, `IMAGE_POINT`: a long press on an image is mapped back through the zoom/pan
  transform to a normalized point, the app samples a 5×5 average of the image there, and an
  explicit Submit records it. The acceptance fixture is a synthetic colour-block PNG.
- Schema 30, additive: three template columns and two reference columns; the two Task Review
  lineages seeded on upgrade and fresh install.

**Exit evidence**

- The fixture's long-press on a named block records exactly that block's `#RRGGBB`, one event, and
  the permitted state; Submit with no sample writes nothing.
- The recorded result is visible after reopening the List, and a refresh does not reinterpret or
  delete older events.
- A plain media List still reviews through the completion checkbox, and its v2/v3/v4 export bodies
  are unchanged.
- Navigation, page movement, zoom, tag toggles and Add-on saves create no primary event.
- Migration 29→30 preserves states, marks, Add-on answers, events, Lists and export history.

**Plan:** [`v0.8.1-plan.md`](v0.8.1-plan.md).

#### The template design, settled

The question this document left open was what a template is. The answers, agreed 2026-10-23:

- **Storage.** A Task Review is a stored lineage with immutable versions, exactly as an Asset
  Control is. `kind` says which kind of payload the version carries; `definition` is the typed
  Task Review payload; `definitionVersion` versions that payload. Headless is *non-special*
  because lineage, versioning, attachment, hashing and resolution are shared, and *special* only
  in what its definition declares.
- **Owner.** The **Todo** holds it, stamped per Task at import. The List organizes and sorts
  Tasks and carries no template of its own; its old columns survive only as a fallback for rows
  written before this round.
- **Compatibility.** Capability is wrapped in the task definition rather than an explicit
  capability layer. One task class → one viewer → one event class → the template catches it. A
  viewer may serve several task classes, as an image viewer serves several image kinds.
- **Commit.** `commitOn` is explicit and belongs to the template. A template naming its own
  `Submit` draws no completion checkbox; the checkbox is just the built-in control named
  `complete`.
- **Version changes.** An answered Task is not reinterpreted: the event row keeps the authored
  template id and version, and the response keeps its own encoding version. A refreshed Task may
  move to a new version; existing events remain history.
- **Package compatibility.** Deferred to v0.8.2, where a Package will name a viewer/template
  requirement rather than a template id, and `TemplateScope` will learn payload kinds.

### v0.8.2 — Package protocol, payload persistence, the structured page

**Why second:** the template can now catch a viewer event; the next question is where structured
content comes from and where it lives. The Package and the first structured page meet here, and the
dating-profile fixture is the acceptance.

**Decisions agreed 2026-10-24**

1. **The stored unit is a Prompt.** A Package stores questions; answering one in a Todo makes a
   Task. The protocol's record key is `promptKey`, and the vocabulary is recorded in
   [ARCHITECTURE — Prompt and Task](../ARCHITECTURE.md#prompt-and-task).
2. **Prompt bodies are member JSON files** referenced by the manifest, not inline objects. The
   envelope stays small while a description's schema evolves.
3. **Commit modality and revisability are independent** template fields: immediate or confirmed,
   each revisable or final. The dating case is immediate and revisable, so a Like may become a
   Dislike without rewriting history.
4. **v5 exports through both Webhook and Txt** from one `ExportMapping`. It carries content identity
   and the chosen option id and label, never the Prompt body or Resource bytes.

**Deliverables**

- The protocol and limits document: manifest filename, version, keys, kinds, member references,
  Resource declarations, diagnostics, canonical encoding, rejection rules, and fixtures —
  [`package-protocol.md`](../package-protocol.md).
- Typed Package planning and reconciliation on `(sourceId, packageKey, promptKey)`; Resource keys on
  `(sourceId, packageKey, resourceKey)`; per-Package checkpoints; payload persistence with a
  revision; schema 32.
- Directory members only; existing file/folder importers unchanged; a new `ImporterKind.PACKAGE`.
- Structured records may import as **unavailable** until a renderer exists. They must not expose an
  empty review surface or claim presentability from zero Assets.
- Typed page list and one structured `DecisionTarget`; Package catalog scope; selection and Quick
  Review over it, with exclusions explained; queue label and two-level guide integration
  (content page, Assets, Add-on in order).
- One Structured Viewer (`builtin.viewer.profile@1`) and one Headless single-choice definition
  (`builtin.structured.single-choice@1`); submission-time composition/revision check, including
  required Resources and unsupported schema/viewer.
- `ExportMapping` pure seam with v2/v3/v4 golden tests and a documented v5 contract; the latest
  valid primary event is the current structured result, and old events remain history.

**Plan:** [`v0.8.2-plan.md`](v0.8.2-plan.md) — schema shape, phases, tests, and the device walk.

**Exit evidence**

- Unknown protocol or malformed envelope writes nothing; an unknown Prompt kind is diagnosed while
  supported records import.
- Re-import preserves IDs, does not duplicate content, and treats an unchanged Package as a no-op
  except for availability and attachment refresh; two Todos over the same Package produce
  independent Tasks.
- Traversal, duplicate keys, symlink escapes, oversize input, and archives are rejected before
  writes.
- A payload-only Task appears in the Package catalog, starts a review, shows one labelled content
  page, accepts a single choice, commits one event, reopens, and exports a v5 body by both writers.
- A second choice on a revisable Task appends a second event and makes it current; a non-revisable
  Task refuses it at the write boundary.
- A stale revision, unsupported schema, or missing required Resource blocks submission.
- Media-only rounds keep their v2/v3/v4 bodies byte-for-byte.

#### Asset semantics for Package Tasks (recorded 2026-10-26, not implemented)

> **Superseded 2026-10-27 by [v0.8.4](v0.8.4.md); retained as history.** This note called the
> decision unit an **Asset** and expected the setter's `.listea` to decide whether a Section or each
> question becomes a Task. v0.8.4 corrects both: the decision unit is a **TaskPart**, and the
> section-to-Task choice is the taker's **Composition**, not a setter declaration. The counts read
> **1 Part + 1 Add-on** for a single-question Task, not "1 Asset + 1 add-on"; a section Task holds
> **several TaskParts**, not several decision-unit Assets. The intent — one question is one
> decision, a group is several — is preserved and scheduled in
> [v0.8.4-plan.md](v0.8.4-plan.md). Read the paragraphs below as the pre-v0.8.4 proposal, not as the
> current model.

Today a Package Prompt imports as its own Task with zero Assets: its body is the Content page, and
the page model deliberately does not count it as an Asset. That is the correct count for the shape
the importer builds — `file-as-task`, one question per Task — but it is not yet the semantics the
`.listea` format should carry.

For a **virtual** Task — a Prompt judged by a headless template, whether `profile`, `vocabulary` or
a later kind — an **Asset is one independent decision unit**. The exam metaphor is the target: one
`.listea` is one paper, divided into sections (single choice, fill-in, short answer); each section
holds several questions. Importing one question per Task is the `file-as-task` shape, and such a
Task must read `1 Asset` (its Prompt) plus `1 add-on` when one is attached. Importing one section
per Task is the `folder-as-task` shape, and that Task holds several decision-unit Assets — one per
question — rather than one Content page.

That shape is not a display change. Delivering it needs:

- a new `.listea` expression that can name a section and the questions inside it, and say whether a
  section becomes one Task or each question does (a protocol version bump, not a new field on
  `listea.package/1`);
- a Package importer that plans section Tasks with several Prompt Assets, preserving each body's
  option order, its Resources and the package's identity rules;
- a page model and submission path for more than one judgment under one Task — part-identified
  events, a template that can commit per Asset, and an export version that carries each answer. The
  single-choice Template and export v5 remain the one-question shape;
- migration and compatibility rules for a Package already imported under v1: an existing Prompt Task
  gains one Asset and keeps its Task id and current judgment, so the count changes without the
  history changing.

This is the same framework step the optional four-question Task in the
[vocabulary round plan](v0.8.0-vocabulary-plan.md#9-the-optional-challenge-acceptance-7) defers. It
is recorded here so the `0 Assets` line on Prompt Tasks is a known, scheduled gap rather than a
drift; until this lands, the catalog's add-on count is the only part of the Task row that changes.

**Deliverables**

- A second fixture: prompt/reveal, declared single-choice grades, shared pronunciation Resource.
- Optional/required Resource diagnostics; compatible payload revision behavior.
- Independent Todo identities over the same Package.
- Both fixtures use the same generic submission and mapping contracts.
- Freeze the protocol and capability contracts used by the fixtures; finish migration/regression
  documentation.

**Exit evidence**

- One shared audio file creates no Task, Asset, or page row.
- Optional loss disables play and allows otherwise valid review; required loss blocks submission.
- A compatible payload revision keeps the Task ID and current judgment; an incompatible one is
  reported and retains prior data.
- The full v0.8.x definition of done below is met.

### v0.8.4 — TaskParts, Section tags, and the taker's Composition

**Why fourth:** v0.8.3 proved a second Prompt family on the same contracts, but the framework still
could not say "a group of questions is one sitting": the importer binds one Prompt to one Task, and
the word *Asset* was doing two jobs. v0.8.4 settles that model and the vocabulary around it.

**Status: implemented and device-verified 2026-10-27; accepted and pushed 2026-10-28 as
`0.8.4-preview` (804), no release published.** Schema 33 and export v6 ship in that build. The
design is [v0.8.4.md](v0.8.4.md), the implementation plan is
[v0.8.4-plan.md](v0.8.4-plan.md), and the gate with its implementation acceptance is
[v0.8.4-design-check.md](v0.8.4-design-check.md#gate-7--implementation-acceptance).

**Decisions**

1. **A Task is 1..N TaskParts.** A TaskPart is one Prompt instantiated in a Task and the new
   decision unit; it owns its current response, part events, requiredness, availability and pages.
   A file or folder Task is one degenerate part. A one-part Task behaves exactly as today.
2. **A Prompt may contain internal steps, fields and conditions.** A conditional chain is one
   Prompt and one TaskPart. Cross-Prompt conditions were out of scope for this round; v0.8.5
   supersedes that inside one Task, and a condition across Tasks remains a producer follow-up Task.
3. **Section is a tag; Composition is the taker's rule.** `sections[]` is a declaration registry;
   the Composition (`prompt:<key>`, `section:<key>`, future `custom:<key>`) decides Task boundaries
   and order. The protocol declares no Tasks.
4. **Part-level state, Task-level completion.** Part states are `pending`, `answered`,
   `unavailable`, `detached`. Completion is aggregated by a Template policy (`singlePart`,
   `allRequiredParts`, `anyPart`, `explicitOnly`) or set explicitly, with provenance. The Add-on
   stays Task-level, after all parts.
5. **Protocol v2.** `listea.package/2` adds `prompts[].files` (replacing `assets`),
   `prompts[].section` and `sections[]`, and `response: "structured"`. Conditions live only inside
   the Prompt body. The reader accepts v1 and v2; a v1 reader rejects v2 whole.
6. **Schema 33.** `task_parts`, per-part payloads, part state, part Resource uses, composition
   provenance, `partKey` on Assets and primary events, structured field identity, and per-part
   dissolved records. The migration is additive and gives every existing Task one part.
7. **Export v6.** `parts[]` with per-part results and explicit partial completion: pending is
   `null`, answered-empty is `""`. A compatible single-part Task still exports v5; v5 history is
   kept.
8. **Identity and reconciliation.** The Task id stays opaque; `compositionKey` is provenance;
   re-import matches `(todoId, packageKey, compositionKey)`, keeps the Task id across membership
   changes, and detaches removed parts without deleting their answers or history.
9. **Naming.** TaskPart and Composition are new independent terms. Asset keeps its file/page
   meaning and is never the decision unit. Section is narrowed to a tag. Item is retired for the
   decision unit. The canonical page is [the two vocabularies](../vocabulary.md).

**Out of scope:** cross-Prompt conditions, custom-composition UI/storage, per-part revisability,
mixed-contract parts, multiple Add-ons, a `.listea` archive, and webhook/n8n grading.

**Exit evidence (met 2026-10-27):** the scenarios and invariants in the
[design check](v0.8.4-design-check.md) pass; the schema-32 fixture migrates with one part per Task
and unchanged v5 bytes; the media page list is unchanged; a v1 Package imports as before; a Section
Task holds N parts and exports v6; two Todos over one Package are independent.

### v0.8.5 — Conditional parts, per-part judgments and the mixed Task

**Why fifth:** v0.8.4 could hold several questions in one Task but a branch had to live inside one
Prompt body, which forces one Viewer to draw every branch step. The business case the model was
built for — "did you eat? — if yes, review this PDF, pick from this menu, and answer this
vocabulary card" — needs the branch to choose between different Viewers, not to stack them in one.

**Status: implemented and device-accepted 2026-10-29; delivered as `0.8.5-preview` (805),
unreleased.** The design is [v0.8.5.md](v0.8.5.md), the plan is
[v0.8.5-plan.md](v0.8.5-plan.md), and the walk, its results and every deviation are recorded in
[v0.8.5 → Acceptance record](v0.8.5.md#acceptance-record). Schema 34, protocol
`listea.package/3` and export v7 ship in that build.

**Decisions**

1. **A condition is declared between parts.** Protocol v3 adds one `when` per Prompt
   (`prompt`, `field`, `equals`/`in`). Its source is an earlier required part in the same Task;
   conditions compose down a chain and never cross a Task boundary.
2. **Applicability is derived, not stored.** Every part is `pending`, `active` or `inactive` from
   its condition, its source's answer and the source's own applicability. The page list is stable:
   conditional pages always exist and are masked with an explanation, never removed. A TaskPart
   never becomes a counter level.
3. **Stale answers and reopening.** An answered part that goes inactive keeps its answer as
   **stale**; it is shown, exported and not counted. A required part that goes inactive → active
   reopens a completed Task, explicit completion included, and is recorded as
   `task_state.completionSource = "reopened"`, not as a submission event.
4. **Completion is over active required parts.** `allRequiredParts` is vacuous when none is active;
   `anyPart` needs an active answer; `explicitOnly` still completes only from its control.
5. **A part may carry its own judgment.** `task_parts.partJudgment` names the template that governs
   that part's answer sheet, commit and revisability; null inherits the Task's. The Task-level
   definition keeps the completion policy. A missing reference fails closed.
6. **Mixed Tasks and a media part.** A media Prompt (`media`/1, freeform, stem body, files as
   Assets) gets `builtin.media.part@1` with a Done control. A Task that mixes kinds, or holds a
   condition, gets the internal `builtin.structured.mixed@1` container (`allRequiredParts`).
   Homogeneous v0.8.4 Tasks write no part judgment and keep their behavior and v6 export.
7. **Protocol v3.** v3 is v2 plus `when`, `kind: "media"` and `response: "freeform"`; the source
   field is validated through the source Viewer's capability. v1/v2 stay readable and unchanged;
   the v3-only words are diagnosed under them.
8. **Schema 34 and export v7.** Three additive columns (`condition`, `partJudgment`, `stale`).
   Export v7 adds per-part `judgment`, `when`, `applicability` and `stale`; v6/v5 remain for
   compatible bodies. Dissolution part records move to v2 and recovery re-derives applicability.
9. **Composition closure.** Conditions default to one Task per Section; one Task per question
   imports the conditioned part unavailable (`condition-source-outside-task`), and the dialog says
   why before the choice.

**Out of scope:** conditions across Tasks, Packages or Todos; optional condition sources; an
expression language; editing conditions in the app; a general custom-composition editor.

**Exit evidence (met 2026-10-29):** the conditional-mixed fixture walks from `1(1/12)/1` to
`1(12/12)/1` with the page and Task counts stable; the gate closing masks five pages and the Task
still completes on its open required parts; reopening marks the five answers stale and records
`completionSource = "reopened"` with no event; export v7 carries `judgment`, `when`,
`applicability` and `stale`, while the v0.8.4 fixtures stay v5 and v6; the one-Task-per-Prompt
composition reports five `condition-source-outside-task` lines; schema 33 → 34 migrates without
rewriting old rows. The full record, including every deviation, is
[v0.8.5 → Acceptance record](v0.8.5.md#acceptance-record).

## Cross-cutting rules for every sub-version

1. **Add-on is never part of the work.** Regression checks may run; no refactor, no snapshot, no
   requiredness, no new key, no export authority change.
2. **No invented history.** A state edit is not a submission. An old aggregate selection is not
   reconstructed into per-Asset choices. Missing provenance is recorded as absent.
3. **One composition rule, one source.** Page count, page entries, resume identity, and queue-guide
   entries come from the same typed page list.
4. **Write-boundary validation.** Unsupported schema/viewer, missing required Resource, and stale
   revision are rejected where the event and state would be written, not only in the UI.
5. **JVM-testable contracts.** Domain contracts and planners must not need Android, Compose, Room,
   or platform `org.json`.
6. **Migration discipline.** Additive tables/columns where possible; no `DROP COLUMN`; schema JSON,
   migration test, and fixture subtraction for every schema step. Load fixtures with state, marks,
   Add-on answers, events, Lists, and export history populated.
7. **Device walk.** Every sub-version installs with `adb install -r` and is walked on the OnePlus
   PGP110; never `connectedDebugAndroidTest`.
8. **Commit layering.** Docs, then implementation, then tests; whole-file staging. No release tag
   without an explicit decision.

## Definition of done for v0.8.x

The arc is complete when:

- Upstream and Todo ownership remain recognizable, with Package protocol and provenance added at
  import;
- payload-only Tasks are discoverable, selectable, renderable, and protected by write-boundary
  compatibility checks;
- a Task can hold several decisions as **TaskParts**, with per-part answers and Task-level
  completion, and an export that distinguishes a pending part from an answered-empty one;
- a later part may depend on an earlier part's answer across different Viewers, with derived
  applicability, stable masked pages, stale answers and reopening;
- Resources resolve as supporting dependencies outside Asset and page counts;
- the v0.8.1 sampled-point fixture, the single-choice fixture and the reveal/audio fixture use the
  same generic review capabilities and submission path;
- new primary events preserve known meaning while old events retain honest absent provenance;
- Add-on structure, final-page placement, answer state, attachments, and export projection retain
  shipped behavior;
- existing media/PDF behavior, content policies, export choices, and v2/v3/v4 bodies pass regression
  checks;
- the protocol, structured export contract, migration fixtures, JVM tests, and device walks are
  documented and pass.

## Relationship to v0.9

v0.9.x can then build the vocabulary and primary-questionnaire experiences on these contracts:
structured prompts, declared option sets, reveal/play interactions, recall grades, and a
product-level scheduler integration. The existing Add-on remains available in its current form. If
v0.9 needs multiple Add-ons, required answers, or Add-on snapshots in events, that is a separate
product decision with its own architecture review — not a consequence of this framework round.
