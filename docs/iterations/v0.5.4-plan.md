> **Status:** Plan, **executed in full.** All six steps are in the working tree and every one has been
> walked on the maintainer's device; what the passes found is recorded in
> [`v0.5.4.md`](v0.5.4.md), and §8 says where the plan and the code came apart. **No production code
> or schema is changed by this document** — it is the plan the code was written against, kept as
> written so that the differences stay legible rather than being edited away.
> **Spec:** [`v0.5.4.md`](v0.5.4.md) — a template becomes a row you can name, version, scope and
> attach
> **Builds on:** v0.5.0 (the asset control, and the definition/configuration split), v0.5.2 (a
> payload carries its own encoding version), v0.5.3 (failing closed on an unrecognised id)

## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | **Three levels**: `templates` (lineage) / `template_versions` (one immutable answer) / the Todo's attachment | §Templates names exactly two — lineage and version — and v0.5.0's "configuration" was the version with no identity. The attachment is the third because a Todo names *which* it uses, which is a fact about the Todo and not about the template |
| 2 | A version's buttons are **an encoded payload on the version row**, not a child table | A version is immutable, and one immutable thing is one row. Three existing payloads already do this (`sources.assetControls`, `dissolved_task_state.records`, `review_events.response`), and a child table would make immutability a convention to be maintained instead of a shape |
| 3 | `templates` holds **id and name only**, and the name is not part of identity | §Identity: "IDs must not be derived from… mutable template name", and §Templates: "A display name can change without changing identity" |
| 4 | A **button id is unique across the whole app**, minted rather than typed | The record is a set of ids (`AssetDecisions.customActions`, `ListEntities.kt:434`) and `controlForTask` dedups by id (`Settings.kt:236-251`) — safe today only because both kinds name the same two literals. Under user-created templates, an id colliding across two templates would make one template's marks unreadable by the other's row. Scoping the record by `templateId/buttonId` instead would rewrite the format of every stored mark and every payload for a case the editor can simply prevent |
| 5 | `★` becomes the button with the **fixed id `favorite`** | It is already the wire name (`ItemAction.Favourite.WireName`, `ListEntities.kt:738`), so no payload changes spelling and no migrated mark is orphaned |
| 6 | The record becomes **one selection set** — `task_asset_state.selections`, carried to `list_items` and `file_review_state` by decision 15 — and `isFavorite` / `customActions` are backfilled, then dead | Decision 5 is cosmetic unless storage agrees. One set is also *smaller* than the two columns it replaces. `task_state.isFavorite`/`customActions` are already dead by [v0.5.1](v0.5.1.md) and are left alone, not resurrected |
| 7 | Scope is a **list of `type:argument` rules**, read as a **conjunction**; only `kind` ships; **an unknown rule type matches nothing**, and so does an **empty scope** | The user's four future rules are one shape, so the encoding is a list and a later rule costs no migration. Conjunction is what makes a list worth having — several rules narrow — and it is the reading that fails closed, where the other reading of the same encoding writes just as easily and would let a rule nobody could evaluate *widen* the template. The same argument covers an empty scope, which is the quietest authoring mistake there is: a template saved before its scope was filled in. A `kind` rule half understood is the one case that narrows instead, because set membership read partially is a smaller set |
| 8 | `sources.assetControls` **keeps its name and changes its payload** to a list of refs. `""` still means *nothing was ever chosen* | The name is still the honest one, and the column's documented meaning (`Settings.kt:519-521`) is load-bearing for `task_imports` too. Renaming a column is a table rebuild for a word |
| 9 | **No match means no control**, and `controlFor` may return nothing | The user asked for it in as many words. The fallback (`Settings.kt:216-222`) exists to answer a question nobody asked when there was only one template; with a choice, falling back would attach a template the user did not pick |
| 10 | The **built-in is seeded as a row** at migration, keeping `builtin.media.asset-control` and its `custom1`/`custom2` buttons | It has to exist as a row to be listed, attached and edited. Keeping the id means a `sources` row written before this release still resolves to the template it was always going to get — the same argument the registry makes for its fixed strings (`Templates.kt:166-167`) |
| 11 | A Todo's configuration **byte-identical to the built-in's buttons attaches the built-in**; anything else mints its own template | Keeps the common upgrade silent and mints only where something would otherwise be lost. "Identical" is the encoded form, so it is decidable without a guess |
| 12 | **Settings → Asset controls is replaced** by **Settings → Templates** | It was the same editor over the same idea in a second place (`SettingsScreen.kt:302-311` vs `MainActivity.kt:1570-1584`). Two places to edit one thing is the defect; the section and its rows become the built-in template's page |
| 13 | The import dialog **stops editing tags** and gains an attach step | Same reason. The dialog's copy of the editor (`AssetControlTagEditor`) is removed; the dialog links to the template's page instead |
| 14 | **Every database has the built-in, whichever way it was created** — the migration seeds an upgraded one and a callback seeds a new one, and the callback repairs an empty table | Added during step 5, because the invariant was found broken on a real device: `user_version 24`, both tables present, no rows, created by a build that predated the callback. A migration runs once and never again, so that database could never be repaired by anything that already existed. Decision 10 says the built-in *is* a row; this says nothing is trusted to have written it |
| 15 | **`selections` goes on three tables, not one** — `task_asset_state`, `list_items`, `file_review_state` — and the last two are read-only projections | Added during step 3, for the reason [v0.2.0](v0.2.0-reviewed.md) gave for the `list_items` decision columns it froze: a List row and a folder-browser row each have to report the marks their Task carries, and filling the field from SQL is one query where joining the pair table is one per row. Written by nothing after the migration, and the two columns they replace are kept, because dropping one needs SQLite 3.35 and minSdk is 24 — so the pair is also the copy a wrong merge can be checked against |
| 16 | **One version per lineage.** The attach step offers **one row per lineage**, and choosing it *moves* that lineage to the current version rather than adding a second reference; `decodeTemplateAttachments` **collapses** a column that names one lineage twice, keeping the highest version and the lineage's first position | Added after the acceptance walk, on a defect the user found by importing: a Todo holding `T@1` **and** `T@2`, drawn as three chips by `controlFor` (first match, the older one) and as four by `controlForTask` (which unions), with the fourth button unreachable. A version is *how the template stood when a run happened*, not a choice being held, and there is no state in which holding two means anything — so the two shapes are the same mistake said once and said twice, and the reader repairs the second without a migration |

## 1. Schema — 23 → 24

Two new tables and three columns, and the three are **one column in three places** — see
§Three projection slots below. `MIGRATION_23_24` in `data/ListeaDatabase.kt` (`:1106`), after
`MIGRATION_22_23`, added to `addMigrations` (`:1810`), and `version = 24`.

```sql
CREATE TABLE IF NOT EXISTS `templates` (
  `id` TEXT NOT NULL, `name` TEXT NOT NULL, `createdAt` INTEGER NOT NULL,
  PRIMARY KEY(`id`)
);

CREATE TABLE IF NOT EXISTS `template_versions` (
  `templateId` TEXT NOT NULL, `version` INTEGER NOT NULL,
  `scope` TEXT NOT NULL, `buttons` TEXT NOT NULL, `buttonsVersion` INTEGER NOT NULL,
  `createdAt` INTEGER NOT NULL,
  PRIMARY KEY(`templateId`, `version`),
  FOREIGN KEY(`templateId`) REFERENCES `templates`(`id`) ON DELETE CASCADE
);

ALTER TABLE `task_asset_state`   ADD COLUMN `selections` TEXT NOT NULL DEFAULT '';
ALTER TABLE `list_items`         ADD COLUMN `selections` TEXT NOT NULL DEFAULT '';
ALTER TABLE `file_review_state`  ADD COLUMN `selections` TEXT NOT NULL DEFAULT '';
```

### Three projection slots, not one

The plan's original shape was one column, on `task_asset_state`. Step 3 added two more, and they are
the same column for the same reason — so they are described together here rather than turning up one
at a time in a later diff.

`list_items` and `file_review_state` join `task_asset_state` in carrying a `selections`, and the
justification is v0.2.0's own `list_items.isCompleted`: **an entity field a DAO query fills rather
than the app writing it is a projection slot, and a dead one is still cheaper than a rebuild.**
`list_items.selections` is filled by `COALESCE(GROUP_CONCAT(tas.selections), '')` over the Task's
pair records and decoded as a union (`decodeActionIds`), so a List row reports what its Task's marks
are without the reader joining the pair table per row; `file_review_state.selections` follows the
folder browser's same walk. Neither is written by any code path after this step. The two columns
they fold are kept rather than dropped — dropping one needs SQLite 3.35 and minSdk is 24 — and that
turns out to be the useful half of the trade: the pair is a second copy of every mark, so a merge
that is ever found wrong can be redone from the rows it came from.

**The three move together in one migration and not three.** A version of this release with one
`selections` and later two would be two schema steps for one decision, and the second would have to
backfill what the first already had.

No index on `template_versions`: the only read is *all versions of one template*, which the primary
key already orders, and the list screen reads `templates`.

**Encodings.** `buttons` carries its encoding version in the column beside it, exactly as
`dissolved_task_state.records` carries `recordVersion` (`ImportEntities.kt:283`) — a payload is never
read without knowing what wrote it, and this one will gain a field the first time a button type holds
a value rather than a presence. `scope` carries none, and that is not an oversight: a rule type this
build cannot evaluate is *defined* behaviour (decision 7 — it matches nothing), so the payload
already has a forward-compatible reading and a version column would be a second mechanism doing the
first one's job.

```text
buttons        one line per button, order significant
               id \t name \t type \t recordValue
               custom1	C1	tag	cust1
               favorite	★	boolean	favorite

scope          one line per rule
               kind:image,video
```

`sanitizeActionText` (`Settings.kt:493`) is reused unchanged for a typed name or record value, so a
name still cannot contain `\t`, `\n`, `|` or `:`. That is the existing behaviour and this release
does not widen it; the cost is unchanged and one sanitiser is still better than two.

`ButtonType` is a `String`-keyed enum written to disk, so an unknown type read back is dropped with
its own line rather than the whole payload — the rule every decoder here already follows.

**Where the two rows come from, and why it is two places rather than one.** Decision 14, added during
step 5. `MIGRATION_23_24` seeds a database that was already at 23; `SeedBuiltIn` in
`data/ListeaDatabase.kt` seeds one Room *creates*, which never runs a migration at all, and repairs
one that has the tables and no rows. Both write through one description of the rows —
`builtInAssetControlRows` — so what a device holds does not depend on how it got there. The guard is
*the table is empty* and not *the built-in is missing*: nothing in the app deletes a template, so an
empty table can only mean the built-in was never written, and the day a template can be deleted the
guard is what has to change (`TemplateSeedTest` names that coupling where a reader will find it).

## 2. The record

`AssetDecisions` (`ListEntities.kt:434`) loses `isFavorite` and keeps a single
`selections: Set<String>`. Everything downstream follows:

| Reader | Today | After |
|---|---|---|
| `AssetStateEntity` (`TaskEntities.kt:192`) | `isFavorite` + `customActions` | `selections` |
| `ReviewDecisions` (`ListEntities.kt:413`), `ReviewItem.taskDecisions` (`:665`), `unionOf` (`:460`) | favourite + set | one set |
| `ResolvedAssetControl.actions` (`Settings.kt:386`) | `★` first, then tags | the template's buttons in order |
| `ItemAction` (`ListEntities.kt:720`) | `Favourite` object + `Custom(id)` | one `Button(id)` |
| `dissolved_task_state.records` | `DISSOLVED_RECORDS_VERSION = 1` | **version 2**, and v1 stays readable |
| `task_asset_state` decode | two fields | `encodeActionIds` (`ListEntities.kt:475`) |

`ResolvedAssetControl.FavouriteOnly` (`Settings.kt:415`) is removed with the fallback it served.

**Why the id set needs no version beside it, while the dissolved payload does.** The dissolved
payload is a *snapshot of a whole Task* and will grow fields; the selection set is a set, and a
button type that carries a value rather than a presence will need a column of its own rather than a
richer form of this one. Choosing a payload format here would be inventing the shape of a field
nobody has asked for yet.

## 3. The migration

The part that decides whether anyone loses a mark. `MIGRATION_23_24` does four things, in order.

1. **Seed the built-in.** One `templates` row (`builtin.media.asset-control`, "Media Asset Control")
   and one `template_versions` row at version 1, scope `kind:image,video`, buttons `★` + `custom1` +
   `custom2` — that is `DefaultCustomActions` (`Settings.kt:328`) with the favourite in front, which
   is exactly what a fresh install draws today.
2. **Backfill the record.** `selections` from `isFavorite` and `customActions`, merged through the
   shipping `encodeActionIds` rather than concatenated in SQL, so the stored form is canonical by
   construction and cannot drift from what the app writes next. `favorite` sorts among the ids like
   any other — it is not special-cased here, which is the point of decision 5.
3. **Mint a template per distinct configuration.** For each `sources` row with a non-empty
   `assetControls` (`ImportEntities.kt:143`) and each `task_imports` row likewise (`:210`): decode,
   group the kinds by their encoded tag list, and for each group that is *not* the built-in's attach
   the built-in; for each group that *is* different, mint one template scoped to those kinds, named
   after the Todo it came from, with `★` plus its tags as buttons. A Todo whose two kinds differ
   therefore produces two templates — acceptance #7, and the shape change [v0.5.4](v0.5.4.md)
   §The scope describes.
4. **Rewrite the columns** to the new payload: one line per attach, `templateId \t version`. Both
   `sources` and `task_imports`, so a Task imported before the upgrade still reports what it was
   judged with.

**What the migration cannot see, and the honest cost.** The app-wide default tags live in DataStore
(`Settings.kt:867-868`), not in the database, so a migration cannot read them. A Todo that never
chose (`assetControls = ''`) resolves to the **seeded built-in**, not to whatever the user had set
as the app-wide default. The per-Todo configurations — which are what actually governs a Task — are
preserved exactly. A user who had customised only the app-wide default and never touched a Todo will
find the built-in carrying the shipped `C1`/`C2` instead of their names. That is a real, small loss,
stated here rather than discovered; the alternative is a startup step that reads DataStore and mints
a version, which is machinery for a case that may not exist. The legacy keys are left in DataStore
untouched, so nothing is destroyed and a later release can still read them.

- **`TemplateListScreen`** — a new file, `ListeaNestedScaffold(title = "Templates", backLabel =

- **`TemplateDetailScreen`** — name, scope, and the buttons, each edited by the existing

**Settings → Asset controls is deleted**, per decision 12. `AssetControlSection` (`:955-971`) and

### What the screens built, and the three places they differ

**All six steps are done.** The screens went in on top of a store that already worked, exactly as the
order asks, and the suite is green at **728 tests across 80 classes**.

- **Settings → Asset controls went out with step 4, as this plan said it must.** It could not leave
  earlier: until the resolver read stored templates it was the only place a tag could be edited and
  the only thing a new Todo recorded with, so deleting it first would have taken a working surface
  away and left a stored row nothing read. `AssetControlSection` and `AssetControlTagEditor` are gone
  from `SettingsScreen.kt`, and so is the third paragraph of the Templates card — the one sentence on
  that page describing where the release had got to rather than what the app does. What stands there
  now is the final copy: *a template is also what a new Todo starts with, so there is one place to
  edit a button rather than two.*
- **There is still no create path, so the list has no *new template* button.** The plan's own
  list-screen description has none, and a lineage is minted by whatever has something to name — the
  upgrade, and the import dialog's *New template* when it lands. That is why **step 6's *New template*
  button explains itself rather than being silently inert** — see §5. `TemplateStore` therefore has
  one method, `update`, and `TemplateWriteDao.insertTemplate` still has no caller. (`insertMintedTemplate`
  in `ListeaDatabase.kt:1348` is a different thing: a migration-local raw-SQL writer for the rows the
  upgrade mints, which no DAO is involved in.) Authoring from a blank page is a real thing to want
  and is not this release's; a button here would be a screen with nothing behind it.
- **`SettingsTextField` gained `commitAsYouType`.** The template page's buttons cannot use the
  webhook dialog's commit-on-blur, because Update does not move focus on touch: a name typed and then
  followed by a tap on Update is a name that would never have been committed. The template's own
  name field is a plain `OutlinedTextField` over a draft instead, for the same reason.

Two smaller things the screens needed and which are worth knowing about: `HelperText` and
`SettingsTextField` became `internal` rather than file-private, and `assetKindPlural` was split into
a public `assetKindChipLabel` with the plural derived from it, so the chip on the template page and
the sentence under it cannot come to disagree.

### What step 6 built, and the one rule it adds

`ImportConfirmDialog`'s per-kind tag editor is an **attach step** now
(`ImportTemplateAttach`, `MainActivity.kt:1604`), and the run's plumbing is unchanged — the dialog
still hands `ImportOptions` a value that goes to `sources.assetControls` and is stamped onto every
`task_imports` row; only what the value *is* has changed, from a tag blob per kind to a list of
`templateId \t version` refs.

- **The step is drawn whatever the folder holds.** The editors it replaced were drawn only for kinds
  the folder actually had, because a tag edited for a kind that is not there would be a question
  about nothing. That rule belonged to a per-kind control, not to this one — a template governs a
  *set* of kinds, so whether the folder's material is admitted is the resolver's answer to give and
  not this dialog's to pre-empt. A folder of PDFs is offered the templates and the user decides.
- **Two templates whose scopes overlap cannot both be chosen.** The second is drawn **disabled with
  the reason** (*Governs the same files as one already attached*) rather than hidden, which is the
  rule this plan set out: the dialog never offers an overlap, so the resolver never has to answer
  which of two wins. Disabled rather than absent, because a template that vanishes from a list is a
  template the user thinks was deleted.
- **A run with nothing attached is refused**, and this is the dialog's one gate: **Create** is
  disabled until something is ticked. A Todo with no template is a Todo whose every file draws an
  empty chip row and whose Tasks can carry no mark at all, and that is a thing a user would find out
  after importing a folder rather than before.
- **`New template` does nothing yet, and says so.** Tapped, it prints *Starting a new template from
  here is not in this release. Templates are made and edited under Settings → Templates.* — because a
  button that sits inert reads as broken and teaches nothing, while one that explains itself teaches
  where the thing actually is. This is the spec's out-of-scope entry made visible rather than silent.

## 5. Import

`ImportConfirmDialog` (`MainActivity.kt:1445-1627`) changes in one place: the per-kind tag editor at
`:1570-1584` becomes an **attach step**.

- **Add a template** — a multi-select over the stored templates, using the `FilterGroup` chip
  pattern (`FileArrangeUi.kt:235-267`) or the `ImportHistoryChoice` radio list (`MainActivity.kt:1750`)
  where radio is the better fit. Multi-select, because the user asked for several.
- **New template** — a button whose action is **not built** (out of scope in the spec), placed beside
  the step so the shape of the choice is visible from the start. It does not sit inert: tapping it
  says where a template is made today and that this is not the release that adds a second place.
  As built, that differs from this plan in one word — the plan said *does nothing*, and a control
  that answers nothing is one the user cannot tell from a control that failed.
- The dialog **does not offer two templates whose scopes overlap**, which is how the deferred
  conflict question is kept out of the resolver for now.
- **One row per lineage, and ticking one moves it.** Added with decision 16, after the walk. The plan
  above said *a multi-select over the stored templates*, and the store's list is **one entry per
  lineage at its current version** — which is right for the list and was wrong for the matching: a
  Todo recorded on an older version matched no row, so it could not be seen or unticked, and ticking
  the current version's row appended a second reference instead of replacing the first. The rows and
  the match now agree on the unit — the lineage — and a row whose lineage is held at an older version
  is drawn ticked with *Held at version N. This run will attach version M.* The clash rule reads its
  input off the same ticked rows, so it fires on the stale case it was written for.
- **The new-Todo seed resolves the store, not the registry.** The seed was
  `Templates.AssetControlSeed.ref`, which is the constant `@1`; it is now the built-in's current
  version read out of `TemplateResolver.attachable`. A registry constant is frozen by design — it is
  what the migration seeds — and a *seed for a new Todo* is a different question that was answered
  with the wrong one.

`ImportOptions.assetControls: Map<AssetKind, AssetControlConfig>` (`Importer.kt:51-69`) becomes the
attached refs. The run writes them to `sources` and stamps `task_imports` as it does today
(`ListsViewModel.kt:1665-1693`), so nothing about the run's *plumbing* changes — only what the value
is.

`AppSettings.controlFor` (`Settings.kt:216`) is replaced by a lookup over the stored templates:
the first attached template whose scope matches the file, resolved to its buttons; nothing when none
matches. `controlForTask` (`:236`) becomes the same over a Task's assets, still `★`-first within a
template and still stable in order, because it decides a webhook array's order.

## 7. What is not touched

- **`lists.taskReviewTemplateId` / `review_events.templateId`.** The Task Review template, a
  different kind, still code-defined at `builtin.media.rapid-review@1`. Review history keeps pointing
  at the version it was made under, which §Templates requires.
- **`TemplateKind` and the `Templates` registry's other two members.** `MediaViewer` and
  `MediaRapidReview` stay exactly as they are; `MediaAssetControl` becomes a *seed* — the value
  `MIGRATION_23_24` writes into the new tables — and its `contentHash` test stays green, because the
  definition is not edited.
- **`task_state.isFavorite` / `customActions`.** Dead since v0.5.1 and still dead. Not dropped: that
  needs SQLite 3.35 and minSdk is 24.
- **The webhook wire format.** Values are resolved at delivery time from a template's buttons, as
  they are resolved today from a configuration's tags, so a renamed button changes future payloads
  and no stored row.
- **`docs/development.md`.** Left as it is, as asked in the previous release.

## 8. Order of work

1. The domain types and their encodings, with their tests, before anything reads them.
2. The schema, the DAO and the migration — with `AppSettings` still resolving the old way, so the
   suite stays green across the step.
3. The record change, in one commit with every reader it moves. Nothing in between.
4. `AppSettings` resolving from stored templates, including the empty answer.
5. The template list and detail screens, on top of a store that already works.
6. The import dialog's attach step, last, because it is the only surface that needs every piece.
7. The full suite, then the device: an upgrade over the existing fixture, and a Todo whose only
   template is scoped to images to show the videos with no chips at all.

**Where execution stands: all six are done.** Everything is in the working tree, the suite is green
at **728 tests across 80 classes**, and every step that touches a database or a screen has been

**One production bug was found by the suite while doing step 3, and it is the kind that has no
symptom on the day it ships.** `MIGRATION_21_22` interpolated `DISSOLVED_RECORDS_VERSION` into the
row it writes. Step 3 raised that constant from 1 to 2, so an already-shipped migration silently
changed what it claimed it had written — for databases yet to be upgraded, and not for any database
already at 22. A migration is frozen at what it wrote the day it shipped; a constant is not. The
literal is now written out and the reasoning is at `ListeaDatabase.kt:1000`. The same reading was
applied to `insertMintedTemplate`'s `buttonsVersion`, and deliberately *not* to
`builtInAssetControlRows`, which the creation callback shares and which therefore has to mean *the
version this build writes* rather than a frozen moment.

**Two things about the sequencing that turned out to matter.** Nothing in the release was ever
landed in a state where a format changed without its reader — the record, its readers and the
migration went in together, which is why the suite is green at every point rather than only at the
end. And the upgrade can mint **two templates with the same name**: a Todo whose image and video
configurations differed produces one template per kind, each named after the Todo it came from. That
is acceptance #7 working as specified and it is worth knowing before it is reported as a duplicate —
the name is not identity (decision 3), so two lineages may share one.

**And a defect the device found that the suite could not, which is the same lesson as the bug above
read from the other end.** The duplicate-attachment defect (decision 16) was three correct-looking
pieces of code — a list that offers one row per *version*, a match that compares whole *references*,
and a seed that reads a *constant* — and none of them is wrong on its own, which is why 728 green
tests said nothing. It was found by the user importing a folder and reading the screen. What the
device pass afterwards established is narrower and worth stating plainly: the **reader** repairs the
bad column without a migration, and the **recovery** path carries the judgments across by path
without carrying the attachment with them, so a Todo rebuilt over a dissolved one is attached by the
run's own choice. Both are recorded in
[v0.5.4](v0.5.4.md#acceptance-as-run--the-duplicate-that-was-one-attachment-said-twice), with the
suite at **731 tests across 80 classes** and the three new cases in `TemplateAttachmentTest` — which
is where they belong, since the untested composable is where the bug lived.
