# Listea v0.5.2 — A dissolved history remembers each file

> **Status:** Iteration, planned. **Not implemented.**
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.5.1 (the record belongs to the Task–Asset pair)
> **Supersedes:** nothing. It repairs what v0.5.1 left behind, and the repair shape is decided in
> [v0.5.1-plan.md](v0.5.1-plan.md) §9.

## The change in one paragraph

v0.5.1 moved the record down to the **Task–Asset pair** and left dissolution writing to the columns
it had retired. So a Todo dissolved after the upgrade snapshots a value frozen at the moment of the
migration, and a recovery writes its answer into a column **no surface reads**: the tags and the `★`
a user asked to keep do not come back, while the picker reports them carried. v0.5.2 makes the
history **carry the pair records themselves** — one encoded payload per dissolved Task, holding each
file's path and that file's own record — and restores them file by file.

## Why

### The defect, in the words of the person who found it

> 用户删除了、解体了一个已经部分 review 过的 todo，并选择了 keep records when delete。这时候，如果
> 用户想从 upstream re-import 并加载历史，那只能恢复是否 check 了的状态，而没有 asset 的状态。

That is the shape of it, and the cause is the one they named: *快照表只记录了 task 层的信息*. The
snapshot was written when a Task's marks were a Task's, so it copied one row per Task — and when
v0.5.1 moved the marks to the pair, nothing moved the snapshot with them.

Two things are wrong with the result, and the second is worse than the first:

- **A dissolution records the wrong thing.** `snapshotDissolvedState` reads
  `task_state.isFavorite` / `customActions`, which v0.5.1 retired. Every mark made since the upgrade
  is missing from the snapshot, and what is there is the value the migration left behind rather
  than the value at the moment of dissolution.
- **A recovery restores nothing visible.** `writeRecoveredState` puts the answer back with
  `UPDATE task_state SET isFavorite = …, customActions = …`. Completion is unaffected — it stayed on
  `task_state` and is still the live column, which is why this read as a *lossy* recover rather than
  a broken one.

### Why the history has to be per file, and not a fold

The cheap repair is to fold the Task's pairs into the single row the snapshot already has, and apply
that fold to every file on the way back. It restores the marks, and it is wrong: recovering a
three-photograph Task would stamp every photograph with the union of what any of them had. **That is
v0.5.1's own bug, arriving through the recovery door.** A history has to be able to say *which file*.

### Why a payload, and not a column per field

The three shapes were put to the user in [v0.5.1-plan.md](v0.5.1-plan.md) §9 and this one was
chosen: keep one row per Task and store the pair records as an **encoded payload**, rather than as
more columns. The reason is the defect's own lesson — a snapshot that mirrors the record's *shape* is
a second model of the record, and has to be migrated every time the record gains a field. That cost
came due once already. A payload pays it never again, and it is what this codebase already does:
`review_events` and `webhook_history` both snapshot a payload beside the columns that identify it.

Two reservations were raised with the decision, and both stand as recorded there: a payload needs a
reader of its own, which is answered by storing the encoding's **version beside the payload** the way
`review_events` stores `templateId` and `templateVersion`; and a payload is read whole, so a question
like *which of my histories marked this file* cannot be answered from one column — accepted
knowingly, because nothing asks it and the payload is per-Task and small.

## The rule

- **The history is per Task; the records in it are per file.** One `dissolved_task_state` row per
  dissolved Task, holding one record for each Asset that Task had.
- **Completion stays the Task's.** It is written to and read from `task_state`, before and after, and
  this release does not move it.
- **A file is named by its path.** Not by its Asset id: ids are minted per import
  (`UUID.randomUUID()`) and a recovery happens after the old Assets are gone, so the path — which is
  what the import matches on to keep an Asset's identity across a re-run — is the only thing the two
  sides can agree on.
- **The payload carries the version of its own encoding.** A reader either knows the shape or says
  so; it never guesses at a payload a later version wrote.
- **A file the new import did not produce recovers nothing**, which is the existing rule, now applied
  per file rather than per Task.
- **A history written before this release recovers completion and no marks.** Its marks were
  Task-level and there is no honest per-file answer to give them. Doing otherwise would spread them.

## What a user sees

Nothing new to learn, and the thing they expected restored:

1. Dissolve a partly-reviewed Todo with *keep records*, then re-import the same folder and choose the
   history. **Every file comes back with its own tag and its own `★`** — the tags that were on the
   second photograph are on the second photograph.
2. A file that is new to the folder, or that the history does not name, comes back unmarked.
3. The picker is unchanged. It still counts Tasks, and it still reads a history without consuming it.
4. A history made before this release restores each Task's checked state and nothing else.

## Acceptance

On a device, against a Todo with at least one Task holding **more than one file** — the shape the
whole rule is about, and the one no single-file fixture can show.

1. Mark two files of one Task differently (a tag on one, a different tag and a `★` on the other).
2. Dissolve the Todo, keeping records.
3. Re-import the same folder and load the history.
4. Each file carries its own marks, and neither carries the other's.
5. The Tasks' checked state comes back.
6. Dissolve a Todo **without** keeping records; nothing is offered back at that folder.

## Out of scope

- **Pruning and retention.** The history is kept until the user dissolves something else; nothing
  purges it. A retention policy is a real question and not this release's.
- **Reading a history as a listing.** What a history carried is legible only by restoring it. A
  surface that shows it before the restore is a product decision nobody has asked for.
- **The other two bands, typed fields, and the rest** — [v0.5.0](v0.5.0.md)'s deferrals, unchanged.
