# Listea v0.7.1 — Implementation plan: an add-on that follows the Task

> **Status:** **Agreed (2026-10-21); implementation in progress on `feature/add-ons`.** The model,
> the encoding, schema 29 and export v4 are settled below. No schema has changed yet and nothing is
> tagged or published.
> **Spec:** [`v0.7.1.md`](v0.7.1.md) — what the round is for. This document is how it is built.
> **Builds on:** v0.7.0 (schema 28, export v3, the authored-reference rule for marks, the static
> frame) and v0.5.4 (a template is a lineage with immutable versions)
> **Branch:** `feature/add-ons`
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)

## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | The entity is an **add-on**: `AddOn*` in code, `addons` / `addon_versions` in storage, `addOn` on the wire, *add-on* in prose | A template governs files by kind; an add-on asks about the Task. Sharing a word would make every sentence about scope and buttons ambiguous |
| 2 | An add-on is **neither an Asset nor a row in `templates`** | `assets` means files a Task presents (paging, missing detection, marks, `assets[]`); a special Asset would spread exceptions through all of them. A `templates` row would need a nullable scope, nullable buttons and nullable questions, and every reader would have to decide which half is real |
| 3 | **One add-on per Todo**, stamped per Task in `task_imports.addOn`; `sources.addOn` holds the Todo's current choice | The user's rule: the questionnaire follows the Todo and therefore the Task. A mixed List needs per-Task answers. One reference per row means the picker is a choice, with no scope or first-match rule |
| 4 | The page is a **Task page after the last Asset**, counted in the navigator | It is the only position that matches *the Task's whole review* without inventing start/end attributes the user deferred. Paging already knows where the last Asset is |
| 5 | The questionnaire is **optional**, has **no required flag**, and the completion checkbox stays a direct path | The user's explicit scope for v0.7.1. Nothing in the completion or export path may make an answer a precondition |
| 6 | **Three question types**: `rating` (1–5), `yes-no`, `text`; user-defined prompts; question ids opaque | The user's three types. The scenario's classification is a Yes / No question; a category type is not added |
| 7 | Questions are encoded **one per line** (`id \t type \t prompt`) with `questionsVersion = 1`; an unknown version, unknown type, duplicate id or blank prompt makes the **whole version unreadable** | Rendering part of a questionnaire would silently drop a question and orphan its answer. This matches the button decoder's fail-closed rule |
| 8 | Answers live in **`task_review_answers`**, keyed `(taskId, questionId)`, cascading from `tasks`, carrying `kind` and the **authored add-on id + version** | A row per fact, not a blob: one answer per question, partial edits, hidden answers explained later. The authored reference is what makes an old answer readable after the add-on moves, the same rule marks follow |
| 9 | **Hidden, not deleted.** Visible while the Task is still attached to the **same add-on lineage** and its version still offers the same question id **and type**; otherwise omitted from the page and the payload, listed by Info | Removing a question must not destroy what somebody said; restoring it must bring the answer back. The lineage check stops a different questionnaire reusing an answer whose question id happens to match. This is the mark-visibility rule applied at Task level |
| 10 | Answers are written **as they are given**; the write path re-validates against the attached version; re-tapping clears; blank text clears | No Save button is the rest of the app's behaviour. Re-validation is the second gate for a stale surface. Clearing is how an optional answer is taken back |
| 11 | The edit model is the template's: **lineage + immutable versions**, rename in place, no delete; creating seeds one Rating question | The user asked for add-ons to sit under the same Settings section; the storage and editing rules that make templates trustworthy apply unchanged. A seed keeps a new add-on attachable |
| 12 | Export adds a **Task-level `addOn` object after `assets`**; **body version 4 only when at least one answer is present**; answers in question order; typed values | A sibling keeps `assets[]` meaning files. Version 4 is a superset of 3 and 2, so rounds without add-on answers stay byte-identical to v0.7.0, and `templates[]` stays file templates only |
| 13 | Refresh **adopts the offered add-on version** like a template and shows its own notice; unticking removes the reference | One run re-stamps Tasks, so an untouched tick would otherwise pin the old version forever. The notice must say what happens to existing answers: hidden, not lost |
| 14 | Settings stays **one list** under **Templates & Add-ons**; a new add-on is created from the same screen; its editor is a separate page | The user asked for the temporary merge. One list answers *what can I attach*; separate pages keep scope and questions from sharing a form |
| 15 | No add-on on a manual item; no read-only-viewer page; no answer history; no delete | Scope boundaries. Manual items have no import and therefore no attachment. `updatedAt` is the only trace of a re-answer |

## 1. The model in one picture

```text
Todo (sources)
  assetControls: "templateId\tversion" …        <- what its files offer
  addOn:         "addOnId\tversion" | ""        <- the questionnaire for its Tasks

Task (tasks)
  ├─ Task–Asset pairs (task_asset_state, task_asset_marks)
  │    per file: selections, PDF passages          <- what the template recorded
  └─ Add-on answers (task_review_answers)
       per question: typed value                   <- what the reviewer said about the Task

task_imports
  assetControls: stamped at import                 <- what this Task is judged with
  addOn:         stamped at import                 <- the questionnaire this Task shows
```

Three layers, three vocabularies. The export mirrors them: `templates[]` and each Asset's
`actions`/`marks` are the pair layer; `addOn` is the Task layer.

## 2. Boundaries and the new files

### Domain and storage

- `domain/AddOns.kt` — `AddOnId`, `AddOnVersionRef`, `AddOnQuestionType`, `AddOnQuestion`,
  `StoredAddOnVersion`, `AddOnAnswerValue`, `AddOnAnswer`, `encodeAddOnQuestions`,
  `decodeAddOnQuestions`, `encodeAddOnAnswer`, `parseAddOnAnswer`, `visibleAnswers`,
  `hiddenAnswers`.
- `data/AddOnEntities.kt` — `AddOnEntity`, `AddOnVersionEntity`, `AddOnDao` (reads),
  `AddOnWriteDao` (two inserts and a rename; no update of a version, no delete).
- `data/TaskReviewAnswerEntity.kt` — the Room row and its `toAddOnAnswer` / `toEntity`.
- `data/AddOnStore.kt` — `create(name)`, `update(addOnId, name, questions)`, snapshot.
- `AddOnResolver.kt` — attachment encode/decode, `withAddOn`, `upgradeAddOn`,
  `refreshAddOnNotice`, and the resolver (`attachable`, `versionOf`, `questionsFor`).

### Surfaces

- `SettingsScreen.kt` — route `addons`/`addon/<id>`, the renamed index row, the detail branch.
- `TemplateListScreen.kt` — one list of both kinds; the new-kind chooser.
- `AddOnDetailScreen.kt` (new) — name and questions editor.
- `MainActivity.kt` — the **Add an add-on** section and its picker.
- `ReviewScreen.kt` + `AddOnPage.kt` (new) — the extra page, the navigator, the Info section.
- `ListsViewModel.kt` — store flows, create/update, attachment in `applyImport`, answer writes and
  observation, payload assembly.
- `Exporters.kt`, `Webhook.kt` — the `addOn` view and version 4.

### Untouched on purpose

`TemplateResolver` and its encoding learn nothing about add-ons. `task_asset_marks` and
`AssetMark` are not reused. `ExportAssetView` gains no field. The answer table is not attached to
`assets`.

## 3. Implementation phases

Each phase ends with its tests green before the next begins. Commits are layered: docs, then the
body, then the tests that pin it.

### Phase 1 — Vocabulary, encoding and schema 29

Files: `domain/AddOns.kt`, `data/AddOnEntities.kt`, `data/TaskReviewAnswerEntity.kt`,
`data/ListeaDatabase.kt`, `data/ImportEntities.kt`, `data/PayloadRows.kt`, `data/ListsDao.kt`,
`app/schemas/com.example.listea.data.ListeaDatabase/29.json`, tests.

1. **Domain vocabulary.**
   - `@JvmInline value class AddOnId(val value: String)`.
   - `data class AddOnVersionRef(val addOnId: AddOnId, val version: Int)`.
   - `enum class AddOnQuestionType(val key: String) { RATING("rating"), YES_NO("yes-no"),
     TEXT("text") }`, with `fromKey` returning null for an unknown key.
   - `data class AddOnQuestion(val id: String, val type: AddOnQuestionType, val prompt: String)`.
   - `data class StoredAddOnVersion(val ref: AddOnVersionRef, val name: String,
     val questions: List<AddOnQuestion>)`.
   - `sealed interface AddOnAnswerValue { data class Rating(val score: Int); data class YesNo(val
     yes: Boolean); data class Text(val text: String) }`.
   - `data class AddOnAnswer(val questionId: String, val type: AddOnQuestionType,
     val value: AddOnAnswerValue, val authoredAddOnId: AddOnId, val authoredAddOnVersion: Int,
     val createdAt: Long, val updatedAt: Long)`.
2. **Encoding.** `ADD_ON_QUESTIONS_VERSION = 1` and `SUPPORTED_ADD_ON_QUESTION_VERSIONS = 1..1`.
   `encodeAddOnQuestions(questions)` writes `id \t type \t prompt`, prompts already sanitised.
   `decodeAddOnQuestions(text, version)` returns null for an unsupported version, a line with fewer
   than three fields, an unknown type, an empty id or prompt, or a duplicate id. An empty payload is
   `null` as well: a version with no questions is not a questionnaire. Values:
   `encodeAddOnAnswer` writes `1..5` / `yes|no` / the trimmed text; `parseAddOnAnswer(type, raw)`
   returns null on a range violation or an empty text.
3. **Entities and migration.**
   - `AddOnEntity(id, name, createdAt)`.
   - `AddOnVersionEntity(addOnId, version, questions, questionsVersion, createdAt)`,
     primary key `(addOnId, version)`, FK to `addons` `CASCADE`.
   - `TaskReviewAnswerEntity(taskId, questionId, kind, value, authoredAddOnId,
     authoredAddOnVersion, createdAt, updatedAt)`, primary key `(taskId, questionId)`, FK to
     `tasks` `CASCADE`.
   - `MIGRATION_28_29` creates the three tables, adds `sources.addOn` and
     `task_imports.addOn` as `TEXT NOT NULL DEFAULT ''`, and logs `28 -> 29`. Register it and raise
     `version = 29`.
   - `SourceEntity.addOn`, `TaskImportEntity.addOn` default `""`.
   - DAOs: read flows for lineages and versions; `insertAddOn`, `insertVersion`, `renameAddOn`; answer
     reads/writes on `ListsDao` (`observeAnswersForTask`, `answer`, `insertAnswer`,
     `deleteAnswer`, `getPayloadAnswers`).
4. **Rows that carry the reference.**
   - `PayloadTaskRow.addOn: String?`; `getPayloadTasks` selects `ti.addOn`.
   - `ReviewItem.addOn: String = ""`; every queue query that selects `ti.assetControls` also selects
     `ti.addOn`, and `toReviewItem` passes it.
   - `toReviewItem` signatures gain `addOn: String = ""` so folder-resolved rows default to no page.
5. **Migration tests.** Extend `MigrationFixtures` with the three tables and two columns, add
   `subtractV29Additions()`, raise `CURRENT` to 29 in every chain, register `MIGRATION_28_29` in all
   of them. New `MigrationV28ToV29Test`: tables and columns exist; existing rows read `""`; a Task
   delete cascades its answers; an add-on delete cascades its versions; no existing Task gains a
   page.
6. **Domain tests.** `AddOnQuestionsTest` (round-trip all three types; unknown version/type,
   duplicate id, blank prompt, short line → null; values validated); `AddOnAnswerTest`
   (encode/parse; rating 0/6/text-too-long rejected; yes/no only); `AddOnAttachmentTest`
   (single reference round-trips; empty; malformed; duplicate lineage keeps the highest version;
   two lineages keep the first well-formed one).

### Phase 2 — Store, resolver and attachment rules

Files: `data/AddOnStore.kt`, `AddOnResolver.kt`, `ListsViewModel.kt`, tests.

1. `AddOnDao.observeAddOns()`, `observeVersions()`, `addOnsOnce()`, `versionsOnce()`, `addOn(id)`,
   `versionsOf(id)`; mirror `TemplateDao`'s read-only shape.
2. `AddOnWriteDao` has `@Insert(ABORT)` for lineage and version and `renameAddOn`, nothing else.
3. `AddOnStore` mirrors `TemplateStore`:
   - `create(name)`: sanitise the name, refuse blank; mint a UUID; insert the lineage and version 1
     with one seeded `RATING` question whose prompt is *Overall rating*; one transaction; return the
     id or null.
   - `update(addOnId, name, questions)`: sanitise the name and prompts; refuse no questions, a blank
     prompt, a duplicate id or an unreadable latest version; rename when the name moved; append
     `n + 1` when the encoded questions differ; write nothing when neither moved.
   - `snapshot()` for the import dialog.
4. `AddOnResolver`:
   - `of(addOns, versions)` builds `StoredAddOnVersion`s, skipping a lineage with no row and every
     version whose questions do not decode. `attachable` is the highest readable version per
     lineage, sorted by name then id.
   - `versionOf(ref)`, `questionsFor(encoded)` (decode the single reference, then `stored`).
   - Attachment helpers: `encodeAddOnAttachment(ref?)` writes one line or `""`;
     `decodeAddOnAttachment(text)` reads the first well-formed line, collapsing a repeated lineage
     to its highest version; `withAddOn(held, choice, on)` returns the one reference or none;
     `upgradeAddOn(held, offered)` moves to the offered version of the same lineage and never adds
     or removes one; `refreshAddOnNotice(held, offered)` names the add-on and the answer rule when
     a version moves.
5. `ListsViewModel`: `addOns` / `addOnVersions` flows, `addOnResolver` (`WhileSubscribed`, like
   `templateResolver`), `createAddOn(name)`, `updateAddOn(...)`, `snapshotAddOns()`.
6. Tests: `AddOnStoreTest` (seed, rename-only, append, unchanged no-op, refusals, version payload
   immutable), `AddOnResolverTest` (attachable highest readable, unreadable skipped, attachment
   decode/with/upgrade/notice), `AddOnVisibilityTest` (same id + type visible; removed, type-changed,
   unreadable or no attachment hidden; visible order is question order; hidden keeps its value).

### Phase 3 — Settings: Templates & Add-ons and the editor

Files: `SettingsScreen.kt`, `TemplateListScreen.kt`, `AddOnDetailScreen.kt` (new), tests.

1. `SettingsRoute.AddOns` (value `addons`) and `SettingsRoute.addOn(id)` (`addon/<id>`); parse it
   beside `templateId`. The index row's title becomes **Templates & Add-ons**, its state
   *N templates · M add-ons*, and it opens `AddOns`.
2. `TemplateListScreen` observes both kinds, lists them by name, and labels an add-on
   *Add-on · N questions*. The header counts both. **New** opens a small chooser — *Template* /
   *Add-on* — then the name prompt; the two create paths call `createTemplate` or `createAddOn`.
   The empty state keeps its explanation and offers both.
3. `AddOnDetailScreen`: a draft of the name and the question list, like `TemplateDetailScreen`.
   - Name field; questions, each with a prompt field, a type chip row (Rating / Yes / No / Text) and
     a remove action; three **Add question** buttons, one per type, append a row with a blank prompt.
   - **Update** is enabled only when the name is non-blank, there is at least one question, and no
     prompt is blank; a blank row is named in the page's error line. **Cancel** discards.
   - A trailing *Version N* label shows the current version; Update appends and the label moves.
   - No scope, no delete, no reorder.
4. `SettingsScreen` branches on `openAddOnId`: `AddOnDetailScreen(addOnId, onBack = -> addons)`.
5. Tests: `AddOnDraftTest` (pure validation: blank name/prompt, no questions, unchanged draft,
   type change is a change, remove-all refused); instrumentation
   `AddOnSettingsTest` (create, edit, rename, version increment, attachable row appears).

### Phase 4 — Attachment: import options, dialog, refresh, stamping

Files: `Importer.kt`, `ListsViewModel.kt`, `MainActivity.kt`, `data/ListsDao.kt`,
`data/ImportEntities.kt`, `data/ListEntities.kt`, tests.

1. `ImportOptions.addOn: AddOnVersionRef? = null` and `upgradeAddOn: Boolean = false`, with KDocs
   mirroring `templates` / `upgradeTemplates`. Create/Refresh seed both; a sync passes the row's
   value and does not upgrade.
2. `ImportFolderRequest.Confirm.addOns: List<StoredAddOnVersion> = emptyList()`, filled at the same
   two construction points as `templates`.
3. `applyImport`:
   - `val addOn = if (options.upgradeAddOn) upgradeAddOn(options.addOn, snapshotAddOns()) else
     options.addOn`, then `val addOnRef = encodeAddOnAttachment(addOn)`.
   - Validate that a non-null ref resolves to a readable version before writing; an unreadable ref is
     refused with *Nothing was changed* (a Create cannot name an add-on this build cannot read; a
     Refresh's upgrade keeps the held ref if the offered list lacks it).
   - Pass `addOnRef` to `registerSource`, `runImport` and `configureSource`.
   - `registerSource` / `configureSource` gain `addOn: String = ""`; `runImport` gains
     `addOn: String = ""` and stamps every Task's `task_imports.addOn`.
4. `MainActivity` dialog: a new `ImportSection` **Add an add-on** after Review, with summary *None*
   or the name. Contents mirror `ImportTemplateAttach`:
   - *Add an add-on* heading and a **New add-on** link that says where to create one (the dialog's
     choices were read when the folder was, so the page must be reopened).
   - One row per add-on: a radio (single choice), the name, *N questions*, and the held version line
     when the Task is on an older one. Choosing a selected row again clears it to *None*.
   - A line saying what the page is: *One page after the last file, never required.*
   - The refresh notice from `refreshAddOnNotice`, drawn in this section and above Confirm.
   - The draft is a `AddOnVersionRef?` in the dialog state; it is not part of `Confirm`'s gate.
5. `ListsDao.toReviewItem` and all queue queries carry `addOn`; folder-resolved rows default to
   empty. A Task's `ReviewItem.addOn` is the raw stamped string.
6. Tests: `ImportAddOnTest` (create writes both columns; refresh upgrades an untouched held
   reference; unticking clears both; a sync preserves; unreadable refused before any write; at most
   one row in the draft); `ReviewItemAddOnTest` (mixed list yields some items with and some
   without); `AddOnRefreshNoticeTest` (null when nothing moves, names the add-on when it does,
   withdrawn when unticked).

### Phase 5 — The review page and the answers

Files: `ReviewScreen.kt`, `AddOnPage.kt` (new), `ListsViewModel.kt`, `data/ListsDao.kt`, tests.

1. **Page model.** In `ReviewScreen.kt`, replace the Asset-only step with a page step:
   ```kotlin
   internal fun pageStep(pageCount: Int, index: Int, forward: Boolean): Int?
   internal fun taskPageCount(assetCount: Int, hasAddOn: Boolean): Int
   ```
   `assetStep` stays for the folder browser paths that still page Assets alone; the review surface
   uses `pageStep`. `AssetRun` gains `addOnPage: (@Composable () -> Unit)? = null`, derives
   `pageCount = assets.size + if (addOnPage != null) 1 else 0`, and renders the add-on content when
   `selectedIndex == assets.size`. A null Asset branch still handles a manual item with no add-on.
2. **Session.** `ReviewSession`:
   - Resolve `storedAddOn = addOnResolver.versionOf(ref)` from `item.addOn`; `hasAddOnPage =
     storedAddOn != null && storedAddOn.questions.isNotEmpty()`.
   - `pageCount = taskPageCount(assets.size, hasAddOnPage)`; clamp `pageIndex` to it.
   - `page = assets.getOrNull(pageIndex)`; every file-specific value (kind, control, decisions,
     PDF tools/marks, file band) is computed only when `page != null`.
   - On the add-on page, the middle band is a `MediaInfoBar(contentDescription = "Add-on info")`
     opening the Task Info sheet.
   - Navigator: `hasPageLevel = pageCount > 1`; counter
     `${index+1}(${pageIndex+1}/$pageCount)/${items.size}`; the file slot reads the file name on an
     Asset page and **Add-on** on the add-on page.
   - Navigation arrows and swipes use `pageStep`. Forward off the add-on page is
     `dispatch(TaskAction.CompleteTask)`, unchanged; back returns to the last Asset.
   - `canLeaveForward = item.reviewBlocked == null` is unchanged on every page.
3. **Answers, live.** `ListsViewModel.observeTaskAnswers(taskId): Flow<List<AddOnAnswer>>`;
   `setAddOnAnswer(taskId, question, value)` and `clearAddOnAnswer(taskId, questionId)`.
   The write path reads `task_imports.addOn`, decodes the version, finds the question by id, checks
   the type and value, and writes with the authored id/version. It refuses a question the current
   version no longer offers, a type mismatch and an invalid value. Text is trimmed; blank text
   deletes. `ListsDao` performs an insert-or-replace preserving `createdAt`.
4. **`AddOnPage`.** A scrollable column:
   - Header: the add-on's name, *Answers are kept as you go · nothing here is required*.
   - One block per question in version order:
     - Rating: prompt, five 1–5 buttons; the selected one highlighted; tapping it clears.
     - Yes / No: prompt, two buttons; tapping the selected one clears.
     - Text: prompt, an `OutlinedTextField` with the stored answer as its initial draft; commit on
       Done or focus loss, and on leaving the page; blank clears.
   - A question with no answer shows no selection, which is the ordinary state.
   - The page's own state is keyed by `(taskId, question.id)`; paging away and back re-reads from
     the flow.
5. **Info.** `ReviewItemInfoSheet` gains `addOnInfo: AddOnInfo?` (name, version, visible answers,
   hidden answers). It is drawn on every page of a Task with an add-on, after the Task/file facts.
   Hidden rows say *no longer asked* and show the stored value and, when the authored version is
   readable, the prompt it was given. On the add-on page the sheet is opened with no `asset`, so
   file save/share offers are absent.
6. **Tests.**
   - Pure `ReviewPageTest`: page count with/without an add-on and with zero Assets; pageStep
     forward/back/edges; a blocked Task's forward stays inert at the add-on page.
   - Robolectric `AddOnAnswerDaoTest`: one row per question; re-answer preserves `createdAt` and
     moves `updatedAt`; clear; task delete cascades.
   - Instrumentation `AddOnReviewTest`: a Task with two Assets and an add-on reads `(1/3)`, `(2/3)`,
     `(3/3)`; left off file 2 shows the questionnaire; answering all three types writes rows;
     re-tapping clears; left again completes; right returns; Info shows the answers; a Task without
     an add-on has no extra page.

### Phase 6 — Export v4

Files: `Exporters.kt`, `Webhook.kt`, `ListsViewModel.kt`, `data/PayloadRows.kt`,
`data/ListsDao.kt`, tests.

1. `ExportAddOnView(id, name, version, answers: List<ExportAnswerView>)` and
   `ExportAnswerView(questionId, type, prompt, value: AddOnAnswerValue)`.
   `ExportTaskView.addOn: ExportAddOnView? = null`.
2. `PayloadAnswerRow` and `getPayloadAnswers(taskIds)`; `PayloadFacts` gains `addOnResolver` and
   `answersByTask`.
3. `exportTaskViews(..., addOnResolver: AddOnResolver = AddOnResolver.Empty,
   answersByTask: Map<String, List<PayloadAnswerRow>> = emptyMap())`:
   - For each Task, read `task.addOn`, resolve the stored version; if unreadable, `addOn = null`.
   - `visibleAnswers(stored, answers)` in question order; if empty, `addOn = null`.
   - Populate `id`, `name`, `version` from the attached version; `prompt`/`type` from the current
     question; `value` typed.
4. `Webhook.buildWebhookPayload`:
   - `carriesAddOn = tasks.any { it.addOn != null }`; version =
     `4 when carriesAddOn`, else `3 when carriesMarks`, else `2`. Add
     `EXPORT_VERSION_ADD_ON = 4`.
   - `taskJson` appends `"addOn"` **after** `"assets"`, only when non-null. `addOnJson` key order:
     `id`, `name`, `version`, `answers`; answer key order: `questionId`, `type`, `prompt`, `value`.
   - Rating → `Int`, Yes/No → `Boolean`, Text → `String`; a value that fails to parse omits the
     answer rather than guessing.
5. `ListsViewModel.payloadFacts` reads the add-on tables and answers in the same transaction-ish
   snapshot as templates, and passes them in. A round with no answers pays one query that returns
   nothing.
6. Tests:
   - `ExportAddOnTest`: shape and key order; typed values; question order;
     hidden/removed/type-changed answers omitted; no answers → no key; unreadable add-on → no key;
     v2 body unchanged without add-ons; v3 unchanged with marks only; v4 with both.
   - `WebhookBodyTest` extensions pin the key order and version rule.
   - `ExportAddOnPipelineTest` (Robolectric): a Task's stamped ref and rows become the view; a later
     add-on version hides a removed question.

|---|---|
| Add-on is Task-level, not an Asset | Schema (`task_review_answers` FK to `tasks`); no `assets` change; `ExportAssetView` unchanged |
| One per Todo, per-Task stamp | `ImportAddOnTest`; mixed-List queue test |
| Page after the last Asset | `ReviewPageTest`, `AddOnReviewTest`, device walk |
| Three types, optional, no Save | `AddOnAnswerDaoTest`, `AddOnReviewTest` |
| Hidden, not deleted | `AddOnVisibilityTest`, Info check, refresh walk |
| Editor and versions | `AddOnStoreTest`, `AddOnSettingsTest` |
| Export sibling and v4 | `ExportAddOnTest`, `WebhookBodyTest`, body inspection |
| Existing payloads unchanged | v2/v3 byte-shape tests |
| Existing data migrates inert | `MigrationV28ToV29Test`, device logcat |

## 6. Out of scope, restated

Position attributes, required answers, more than one add-on, List-level add-ons, category types,
question reordering and branching, answer history, deletion of lineages, the read-only viewer page,
manual items, and any change to delivery. These are recorded in the spec's
[Not in this round](v0.7.1.md#not-in-this-round) with the reasons; a later round changes that list
rather than quietly broadening this one.
