# Listea v0.8.1 — Implementation plan: a Task Review template the Task owns

> **Status:** **Implemented on `main`, unreleased (2026-10-24).** Schema 30 and 31, the stored Task
> Reviews, viewer events, and the caught-event table are committed; no tag or release. The model,
> the storage, the encoding, schema 30 (plus schema 31, §3c, added the same day) and the acceptance
> fixture are settled below. The child table is part of this version's acceptance.
> **Spec:** [`v0.8.md`](v0.8.md) — the framework arc. This is the first sub-version, reordered
> ahead of the Package work so that Headless stops being a special case before anything has to
> choose one.
> **Builds on:** v0.7.1 (schema 29, export v4, Add-ons) and v0.5.4 (a template is a lineage with
> immutable versions)
> **Branch:** `main`
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)

## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | Task Review moves onto the **stored, versioned** path: `template_versions` gains `kind`, `definition`, `definitionVersion` | An Asset Control is a lineage with versions; a Task Review has the same lifecycle. Two storage paths is what made Headless special, and the only way to stop it being special is to stop it being stored differently |
| 2 | The stored payload is a **separate type**, `TaskReviewDefinition`; the code-defined `TemplateDefinition.TaskReview` is not changed | The code-defined definitions carry pinned content hashes. The stored payload is what a run enforces, and it says only what this build enforces — no decorative fields |
| 3 | The **Todo owns** the Task Review (`sources.taskReview`), stamped per Task (`task_imports.taskReview`) | The user's rule: the List organizes and sorts; it does not say how a Task is judged. A Task is the thing reviewed, so the review definition follows it |
| 4 | The List's `taskReviewTemplateId`/`Version` become a **legacy fallback** and are no longer written | Existing rows must keep meaning something: an old List ref resolves when a Task carries no stamp. Keeping the columns (rather than dropping them) is also the additive-migration rule |
| 5 | Resolution is **per item**: Task stamp → List legacy ref → `builtin.media.rapid-review@1` | One session can walk Tasks from several Todos, each judged by its own stamp. The fallback is what keeps a pre-v0.8.1 List reviewing exactly as it did |
| 6 | `commitOn` is **explicit**: `CommitPolicy.Explicit(controlId)`, naming either a template `ACTION` button or the built-in `complete` control | The submit control belongs to the template, not the viewer. This is the compatibility test the user asked for: Headless and a custom Submit go through one path |
| 7 | A template that does not name `complete` **draws no completion checkbox**; its own ACTION button is the commit | Otherwise the viewer would still own a submit control the template never declared. The checkbox is simply the built-in control named `complete` |
| 8 | `ButtonType.ACTION` is added at `buttonsVersion = 3`; an ACTION button records no value | A Submit is a control, not a tag. It belongs to the template's button list so the template owns it, and version 3 keeps 1–2 decoding unchanged |
| 9 | Viewer events are typed and **fail closed**: `ViewerEventType.IMAGE_POINT`; a response containing an event type or version the build cannot read decodes as unreadable, not as a partial list | Dropping one event from a committed response would silently change what somebody recorded. Same rule as the button and add-on decoders |
| 10 | `ReviewResponse.PrimaryReview(completed, events)` is a second encoding under a new envelope (`primary=2`); legacy `completed=…;selections=…` is unchanged and still parsed | Old events must stay readable byte-for-byte. One response type with a version beats two types with a discriminator nobody can see |
| 11 | A template-version change does **not reinterpret an answered Task** | The event row already records the authored template id and version, and the response records its own encoding version. A Task refreshed onto a newer template keeps old events as history; only a new commit uses the new definition |
| 12 | Sampling is a **viewer gesture** reported as a normalized point; the app samples the colour | The viewer says *where*, the engine says *what*. The geometry is a pure function, JVM-testable without Compose or Android |
| 13 | A long press in the letterbox, or on a page that is not an image, produces **no point** | A colour read outside the picture is a colour of the background, not of the content. The band says so rather than recording it |
| 14 | Sampling decodes a **bounded bitmap** and averages a 5×5 neighbourhood to an uppercase `#RRGGBB` | Large photos must not OOM the review. A small average is stable for synthetic blocks and honest for real photographs. EXIF orientation is applied on API 28+ (`ImageDecoder`); the pre-28 fallback is documented as unrotated |
| 15 | The pending sample is **session state**, and Submit with none is refused in the UI **and** at the write boundary | A template that accepts events cannot commit an empty event list. The write boundary is the guarantee; the disabled/explained control is the courtesy |
| 16 | Two Task Review lineages are **seeded on upgrade and fresh install**: `builtin.media.rapid-review` (the old behaviour, stored) and `builtin.image.sample-review` (the fixture) | The fallback chain resolves to a stored row, so there is one lookup path. Headless is a definition now, not a code path |
| 17 | Settings shows a Task Review **read-only** in v0.8.1; only its name may be renamed, and no version is appended by the editor | The round's subject is storage and submission, not a review-template editor. Rendering a scope/button editor for a payload it cannot edit would be a lie |
| 18 | Migration 29→30 is **additive only**; the List columns stay; no response is rewritten | State, marks, add-on answers, events, Lists and export history survive unchanged. A backfill of `sources.taskReview` would invent history the Todo never had |

## 1. The model in one picture

```text
Todo (sources)
  assetControls: "templateId\tversion" …        <- what its files offer        (unchanged)
  taskReview:    "templateId\tversion" | ""     <- which review judges its Tasks (new)

Task (task_imports)
  assetControls, addOn                          <- stamped at import            (unchanged)
  taskReview:    "templateId\tversion" | ""     <- stamped at import            (new)

A review session, per item
  item.taskReview  ──> stored Task Review version ──> TaskReviewDefinition
        │                                                  viewer, accepts,
        │                                                  commit, completes, advance
        ├─ no stamp ──> the List's legacy columns ──> the same lookup
        └─ still none ──> builtin.media.rapid-review@1
  pages: Assets through the media viewer, then the optional Add-on page  (unchanged)
  long press on an image ──> ImagePoint(x, y, #RRGGBB, path)  (pending, visible)
  Submit (a template ACTION button) ──> PrimaryReview(completed, [event])

review_events
  templateId, templateVersion, response "primary=2 …"   <- the authored reference and the encoding
```

The export path is untouched in this round: `templates[]` still lists file templates, `addOn` is
still the Task-level object, and v2/v3/v4 bodies are byte-identical. A v5 mapping waits for the
structured page.

### Surfaces

## 3. Implementation phases

Each phase ends with its tests green before the next begins. Commits are layered: docs, then the
body, then the tests that pin it.

### Phase 1 — Vocabulary, encoding, and the stored definition

Files: `domain/ViewerEvents.kt`, `domain/ReviewResponse.kt`, `domain/TemplateButtons.kt`,
`domain/TaskAction.kt`, tests.

1. **Events.**
   - `enum class ViewerEventType(val key: String) { IMAGE_POINT("image.point") }` with
     `fromKey` returning null for anything else.
   - `sealed interface ViewerEvent { val type: ViewerEventType; data class ImagePoint(val x:
     Double, val y: Double, val color: String, val assetPath: String) : ViewerEvent }`.
     `x`/`y` are normalized 0..1 in the image's own coordinates; `color` is `#RRGGBB`; `assetPath`
     is the Asset's path within the Task, `""` when the viewer cannot name one.
2. **Commit policy.** `sealed interface CommitPolicy { data class Explicit(val controlId: String)
     : CommitPolicy }`. The id is either a button id of the template's own list or
     `TASK_REVIEW_COMPLETE_CONTROL = "complete"`, the built-in checkbox.
3. **Definition.**
   ```kotlin
   data class TaskReviewDefinition(
       val viewer: TemplateVersionRef,
       val accepts: Set<ViewerEventType>,
       val commit: CommitPolicy,
       val completesTask: Boolean,
       val advanceAfterCommit: Boolean
   )
   ```
   Encoded one fact per line, order fixed:
   ```
   v=1
   viewer=builtin.media.viewer@1
   accepts=image.point
   commit=explicit:submit
   completes=true
   advance=true
   ```
   `decodeTaskReviewDefinition(text, version)` returns null for an unknown version, a malformed
   `id@version`, an unknown accept key, a `commit` mode other than `explicit`, a blank control id,
   a missing required line, or a non-boolean flag. An empty `accepts=` line is legal and means
   "this review catches no viewer events".
4. **Response.** `PrimaryReview(completed: Boolean, events: List<ViewerEvent>)`:
   ```
   primary=2
   completed=false
   event=image.point\t0.4213\t0.6107\t#C0392B\tphoto.png
   ```
   Points are formatted with four fixed decimals (`Locale.ROOT`); parses outside 0..1, an
   unknown event type, a malformed colour or a `primary=` version other than 2 make the whole
   response unreadable (`parse` returns null). `PrimaryReview.completesTask` is its `completed`
   flag. `ReviewResponse.parse` dispatches on the first line: `primary=…` → primary; otherwise
   the legacy `completed=…;selections=…` grammar. The existing `MediaReview` encoding is not
   changed.
5. **Buttons.** `ButtonType.ACTION("action")`; `TEMPLATE_BUTTONS_ACTION_VERSION = 3`;
   `SUPPORTED_TEMPLATE_BUTTON_VERSIONS = 1..3`; `buttonsVersionFor` returns 3 when any ACTION is
   present. An ACTION line still has four columns (`id \t name \t action \t ""`); decoding under a
   version below 3 drops it, exactly as COMMENT is dropped under 1.
6. **Actions.** `TaskAction.fromKey` returns null for unknown keys. No stored definition carries
   actions this round; the decoder exists so the vocabulary is complete when a viewer starts
   declaring navigation.

### Phase 2 — Stored Task Reviews and schema 30

Files: `domain/Templates.kt`, `data/TemplateEntities.kt`, `data/TemplateStore.kt`,
`data/TemplateResolver.kt`, `data/ListeaDatabase.kt`, `app/schemas/…/30.json`, migration tests.

1. **`StoredTemplateVersion`** gains `kind: TemplateKind = TemplateKind.ASSET_CONTROL` and
   `taskReview: TaskReviewDefinition? = null`, after `name`, with `scope`/`buttons` defaulted so
   every existing call site still compiles. A task-review version has an empty scope and only
   ACTION buttons.
2. **Seeds.**
   - `MediaRapidReviewStored` — ref `builtin.media.rapid-review@1`, name *Rapid review*,
     `viewer = MediaViewer`, `accepts = emptySet()`, `commit = Explicit("complete")`,
     `completes = true`, `advance = true`, no buttons.
   - `ImageSampleReview` — ref `builtin.image.sample-review@1`, name *Sample a point*,
     `viewer = MediaViewer`, `accepts = {IMAGE_POINT}`, `commit = Explicit("submit")`,
     `completes = true`, `advance = true`, buttons `[TemplateButton("submit", "Submit",
     ButtonType.ACTION, "")]`.
   - `Templates.StoredTaskReviews` lists both; `Templates.all` and every code-defined hash stay
     as they are.
3. **Entities.** `TemplateVersionEntity` gains `kind TEXT NOT NULL DEFAULT 'asset-control'`,
   `definition TEXT NOT NULL DEFAULT ''`, `definitionVersion INTEGER NOT NULL DEFAULT 0`.
   Reads decode `definition` when `kind = 'task-review'`; an unreadable definition yields no
   stored review (the fallback chain continues) rather than an exception.
4. **Store.** `create(name)` writes `kind = 'asset-control'` and empty definition explicitly.
   `update` reads the row's kind: for a Task Review it renames only and appends no version; scope
   and buttons are never written over a payload kind.
5. **Resolver.** `TemplateResolver` splits `attachable` (asset controls) from
   `attachableReviews` (readable Task Reviews, highest version per lineage, sorted by name then
   id), and exposes `reviewFor(templateId, version)` and `reviewForEach(encoded)`.
   `Empty` has an empty `attachableReviews`.
6. **Migration.** `MIGRATION_29_30` adds the three `template_versions` columns and the two
   `sources`/`task_imports` columns, all with SQL defaults; it inserts the two built-in Task
   Review lineages at version 1 with `INSERT OR IGNORE` using the same constants as the fresh
   installer. `version = 30`; export schema 30. Update `MigrationFixtures`,
   `MigrationV28ToV29Test` (CURRENT = 30), `MigrationChainTest`, `MigrationSmokeTest`, and
   `TemplateSeedTest` (three lineages, five versions; exactly two are Task Reviews).

### Phase 3 — Ownership: the Todo stamps, the Task carries

Files: `data/ImportEntities.kt`, `data/ListEntities.kt`, `data/ListsDao.kt`, `Importer.kt`,
`ListsViewModel.kt`, `MainActivity.kt`.

1. **Columns.** `SourceEntity.taskReview: String = ""`; `TaskImportEntity.taskReview: String =
   ""`. Both SQL defaults `''`.
2. **Write paths.** `registerSource`, `configureSource`, `setSourceConfig`, `runImport`,
   `touchTaskImport`, `resolveNewTask` and `TaskImportEntity(...)` carry a `taskReview` string
   beside `assetControls`; `CatalogRow`/`TaskAssetControls` gain the field.
3. **Import options.** `ImportOptions.taskReview: TemplateVersionRef? = null` (null = the
   built-in rapid review) and `upgradeTaskReview: Boolean = false`.
4. **`applyImport`.** Resolve the reference: a refresh adopts the offered version when
   `upgradeTaskReview` is set (the same rule as templates); a Create submits what the dialog
   chose; a sync re-stamps what the Todo holds. Encode once and pass the same string to the
   Todo's row, the run and the write-back. A chosen reference this build cannot read refuses a
   Create before anything is written; a refresh may carry an unreadable held one forward.
5. **Dialog.** The Review section gains a **Task review** radio list below the asset templates,
   drawn from `request.taskReviews`, seeded with the Todo's held choice or the built-in. It is
   one choice, not a set. `importRunIdentity` includes the seeded reference and the upgrade
   flag; `Confirm` passes the choice. No List writes.
6. **Resolution for review.** `ListsViewModel` exposes the stored review versions alongside the
   resolver. The detail state and `ReviewItem` carry `taskReview`; `ReviewSession` resolves a
   per-item `TaskReviewTerms(definition, ref)` through the chain of decision 5. The List's legacy
   columns are read where they stand and never written.

### Phase 4 — The viewer event, the commit, and the response

Files: `SwipeCard.kt`, `MediaZoom.kt`, `MediaSampling.kt`, `ReviewScreen.kt`, `MediaUi.kt`,
`ListsDao.kt`, `ListsViewModel.kt`, tests.

1. **Geometry.** `MediaZoomState.imagePointAt(px, py): ImagePoint?` inverts the fitted rect and
   the graphics transform: `screen = center + (content − center)·scale + translation`, with the
   letterbox rect computed from `contentAspect` and the private viewport. A point outside the
   fitted content returns null.
2. **Gesture.** `SwipeCard` gains `onLongPress: ((MediaZoomState, Offset) -> Unit)?`, installed in
   the existing `detectTapGestures` through `rememberUpdatedState` so the detector is not
   re-keyed. A drag or pinch still cancels it; the device walk confirms the arbitration.
3. **Sampling.** `MediaSampling.sampleColor(uri, point): String?` decodes a bitmap bounded to a
   long edge of 1024 px (`ImageDecoder` with a target sample size on API 28+; `BitmapFactory` with
   `inSampleSize` below), averages a 5×5 window (minimum 1 px radius) around the point, and
   returns uppercase `#RRGGBB`. It runs off the main thread; a decode failure returns null and the
   band says the colour could not be read.
4. **Band.** On an image page whose resolved definition accepts `IMAGE_POINT`:
   - long press → sample → a pending line showing the swatch, `(x, y)` to two decimals and the
     hex value; a second long press replaces it;
   - the template's ACTION buttons are drawn beside the asset chips; pressing `Submit` calls the
     same `dispatch`-style commit path with `PrimaryReview(completed, listOf(event))`;
   - with no pending sample the Submit control is disabled and the line says *Long-press the
     image to sample a point*;
   - after commit, the recorded result (latest readable `PrimaryReview` for the Task) is shown in
     the same line as *Recorded*.
   The pending sample is held encoded in `rememberSaveable`, keyed by session, Task and page, so a
   rotation keeps an uncommitted point and advancing clears it.
5. **Commit control.** The completion checkbox is drawn only when the resolved definition's
   `commit` names `complete`. A template naming another control draws that control and no
   checkbox. `completesTask` decides the state write; `advanceAfterCommit` decides whether the
   queue moves on, exactly as the checkbox did.
6. **Write boundary.** `ListsDao.submitReview` still owns the atomic state+event write. The
   ViewModel refuses to build a `PrimaryReview` with zero events when the definition accepts
   events; `submitReview` keeps its presentability guard. A committed primary event records the
   authored template ref and version in the existing columns and the encoding version in the
   response text — no new event column this round.
7. **Recorded display.** A List-scoped query reads the latest event per Task; responses are parsed
   with `ReviewResponse.parse`. An unreadable response is displayed as recorded-but-unreadable
   rather than hidden; a legacy `MediaReview` still displays as before.

### Phase 5 — Settings, the fixture, and the walk

1. **Settings.** `TemplateListScreen` names a Task Review by what it accepts (*Review · image
   point*), not by a file scope. `TemplateDetailScreen` shows the viewer, accepted events, commit
   control, completion and advance flags read-only; the editor and Update are not offered for a
   Task Review.
2. **Fixture bytes.** A generated PNG (1100×700) of labelled colour blocks with a known palette,
   plus a short `docs/` note naming each block's `#RRGGBB`. It is generated by a checked-in script
   or a one-off command recorded in the note; the bytes are committed so the walk does not depend
   on a local tool. **Built as:** `docs/assets/fixtures/sample-point.png`, generated by
   `docs/assets/fixtures/generate_sample_point.py`, with the palette table in
   `docs/assets/fixtures/README.md`.
3. **Device walk.** Push the fixture to `/sdcard/Pictures/ListeaSample/`, import it as a
   file-per-Task Todo with the *Sample a point* review and the default asset control, long-press a
   block, confirm the swatch matches the block's named colour, Submit, check the Task advances and
   the band reads *Recorded*, reopen the List and confirm it still reads, then re-import (refresh)
   and confirm older events survive the version/stamp. Also walk a plain media List to confirm the
   checkbox path is unchanged.

## 3a. Deviations recorded during implementation

Things built differently from the text above, and why. The model, the storage, the encodings and
the policies are as planned; these are interface and naming choices made while writing the code.

| # | Planned | Built | Why |
|---|---|---|---|
| D1 | `reviewFor(templateId, version)`, `reviewForEach(encoded)` | `reviewForRef(TemplateVersionRef)` and `reviewFor(encoded)`; `attachableReviews` for the picker | Every caller holds one of two things: a ref (the per-item terms, a resolver lookup) or the stored stamp form `templateId\tversion`. A pair-taking function would have made each caller re-encode a ref to call it, and the attachment parser already exists for imports. |
| D2 | A stored definition is the only lookup | `reviewForRef` also falls back to the in-code `Templates.StoredTaskReviews` when the seed row is absent | The seed runs in the database callback, which an in-memory test database may never see. A write path that depended on that timing would refuse a judgment the build can read; user reviews still get no fallback and still fail closed. |
| D3 | `sampleColor(uri, point)` | `sampleImageColor(context, uri, point)` | Reading a `content://` image needs the resolver, and the sampler is called from a composable that has the context. The signature is the honest one for the boundary. |
| D4 | Test named `TemplateResolverTest` | `TemplateResolverReviewTest` | `TemplateResolverTest` already exists and covers the asset-control half; adding a second suite under the same name is not possible. |
| D5 | Test named `TemplateButtonsTest` | cases added to the existing `TemplateButtonTest` | Same reason, and the ACTION vocabulary is the same encoding contract that suite pins. |
| D6 | Sampling unit-tested | No `MediaSampling` unit test | Decoding is platform-bound (ContentResolver, BitmapFactory/ImageDecoder) and Robolectric does not stand in for real image decoding usefully. The pure geometry (`imagePointAt`) is covered by `ImagePointTest`; the colour read is covered by the device walk against the fixture's named palette. |
| D7 | Settings subtitle *Review · image point* | Implemented as planned; an empty `accepts` line reads *Review · file decisions*, an unreadable definition *Task review · unreadable* | The Headless review is a review too, and naming its empty set as "nothing" would read as a broken template. |

  exactly Blue's palette value in `docs/assets/fixtures/README.md`. Submit completed the Task and
  the round (*Quick Review complete · 1 / 1 processed*).
- Reopening the review from the List showed `Recorded: (0.38, 0.25) · #1E88E5` and a disabled
  Submit. The band lives on the review surface; the List's Task preview is the plain viewer, so
  "reopen the List and confirm it still reads" means reopening the review from it.
- `review_events` gained one row: `primary=2\ncompleted=true\nevent=image.point 0.3796 0.2489
  #1E88E5 …` under `builtin.image.sample-review@1`. The 32 earlier rows were untouched.
- Refresh Import (*Keep it*, 1 Task and 1 Asset updated) left the stamp, the completion and all 33

- A plain media List still opens the built-in completion checkbox, draws no Submit, and on leaving

- Settings names the seeds *Review · image.point* and *Review · file decisions*, each *Version 1*.

**One defect found by the walk, and fixed.** The queue built from catalog rows dropped the Task's

`reviewItemFor` record the finding.

The full unit suite passed on the same tree; `assembleDebug` and the existing APK were installed
with `adb install -r` (never `connectedDebugAndroidTest`). Nothing was committed, pushed, tagged
or published.

**Follow-up the same day: the forward swipe was offered before its event.** A one-Asset Task whose
template accepts events still offered the leave gesture with nothing reported. The card animated
off-screen first and the dispatch then refused the leave, so the picture's slot stayed empty — a
black surface. The leave gate now also closes when the template accepts events and no event is

and leaves. Pinned by `ReviewPageTest`; verified on the device both ways.

## 3c. The per-event child table (same day)

**Asked after the walk: an event caught by a template should be stored where an event belongs.**
Tags live in `task_asset_state.selections`, PDF annotations in `task_asset_marks`, add-on answers in
`task_review_answers`; an event existed only inside `review_events.response` text. The response is
still the permanent, canonical record — it is what a later build reads to know what somebody
committed — but a text line is not a place a reader can ask *what did the latest submission catch*.

**Decision: keep the response canonical, add a child table derived from it.**

- `review_event_answers`, primary key `(reviewEventId, ordinal)`, FK to `review_events(id)` with
  `ON DELETE CASCADE`. An event is ordered within its submission, and the same point may be
  reported twice; the ordinal is that order. Re-submitting appends a new parent and a new set of
  rows; nothing in the table is updated in place.
- `type` and `value` are exactly the response line's two halves. `ViewerEvent.encodeValue()` and
  `parseEventValue()` are shared by both writers, so the canonical response and the queryable row
  cannot spell the same event two ways.
- `assetId` is nullable and **deliberately has no FK to `assets`**: it is provenance, and deleting a
  file must not erase the history of what was reported about it. The same direction
  `task_asset_marks` and `task_review_answers` take.
- The write happens in `submitReview`'s existing transaction, so a submission is either wholly on
  record (response and rows) or not at all. The Asset is resolved by the event's source URI against
  the Task's own Assets; a URI no Asset still carries leaves `assetId` null rather than dropping
  the event.

**Irrevocability is policy, not schema.** A like/dislike may be revisitable while a flashcard
answer often is not; that belongs to the template's commit policy (`advanceAfterCommit`, the commit
control) and to a future current-state row for revisable answers. This table is history, and history
is append-only for both.

**The Info sheet's Recorded section** reads the child table (`observeLatestEventAnswers`) and lists
the latest submission's events beside Actions and Marks: a summary (*1 event* / *None*), then
`Image point · (0.13, 0.69) · #8E24AA` and the file's name when the Task has several. It is shown
only for a template whose definition accepts events, so a legacy media Task's sheet is unchanged.

**Migration 30 → 31** creates the table and index and backfills every readable primary response
through the app's own `ReviewResponse.parse` — never a migration-only parser. An unreadable
envelope or a legacy media response writes no rows; the response itself is never rewritten.
