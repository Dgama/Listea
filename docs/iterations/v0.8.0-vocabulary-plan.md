## 1. The goal in one sentence

**A vocabulary Task imported from a `.listea` Package is the same kind of Task as a dating Prompt
Task: same identity, same page model, same Task Review template, same submission boundary, same
add-on, same swipe rules and same v5 export. The only differences are a declared Viewer capability
and the renderer that draws the word card and plays its pronunciation Resource.**

The round is judged globally, not by a vocabulary screen existing. It succeeds if:

- no core path (`PackageProtocol`, `ReviewPages`, `ListsDao`, `Exporters`, `ListsViewModel`
  submission) learns the word "vocabulary";
- the three Task surfaces stop hard-coding `parseProfilePrompt` and a profile card, and share one
  content-page dispatch, so a third kind would be one capability row, one parser and one renderer
  arm;
- adding the vocabulary Viewer requires **no database migration** and no change to the page model,
  templates, add-ons or export grammar.

## 3. The architectural rule: a Viewer is a capability and a renderer, not a Task kind

v0.8.2 built exactly one structured Viewer and hard-coded it in three places:

- `ReviewScreen`, `ListItemViewerScreen` and `CatalogTaskPreviewScreen` each call
  `parseProfilePrompt(payload)` and draw `ProfilePromptPage`;
- `ListsViewModel.submissionAccepted` calls `parseProfilePrompt` to check that the chosen option is
  declared by the body.

Those are seams, not architecture. This round moves them:

1. **`PromptContent`** — a tiny domain interface: `stem` and ordered `options`. `ProfilePrompt`
   implements it; `VocabularyPrompt` joins it.
2. **`ViewerCapability.parse`** — each capability owns its body parser, so the compatibility table
   remains the one place that answers "can this build read kind/schema?". `Viewers.all` gains
   `builtin.viewer.vocabulary@1`.
3. **`PromptContentPage`** — one composable that dispatches a parsed content to its renderer
   (`profile` → the existing card, `vocabulary` → the new card) and resolves its Resources. All
   three Task surfaces call it; none parses a body or names a viewer.
4. **Submission** — the option-membership check asks the resolved capability for its parsed
   content instead of asking the profile parser.

The page model, the navigator, the template resolution, the add-on, the queue guide and the export
are untouched. A vocabulary Task is a Task whose `task_payloads.kind` happens to be `vocabulary`.

## 4. The `vocabulary`/1 Prompt

`kind = "vocabulary"`, `schema = 1`, `response = "choice.single"`, Viewer id
`builtin.viewer.vocabulary@1`, intent `choice.select`.

```json
{
  "stem": "Choose the meaning of this word.",
  "word": "serendipity",
  "phonetic": "/ˌserənˈdɪpɪti/",
  "definition": "the occurrence of events by chance in a happy way",
  "example": "a fortunate stroke of serendipity",
  "audio": "serendipity-audio",
  "answer": "a",
  "options": [
    { "id": "a", "label": "a happy accident" },
    { "id": "b", "label": "a long journey" },
    { "id": "c", "label": "a formal apology" }
  ]
}
```

Rules:

- `stem`, `word` and `options` are required. The protocol already owns `stem` and `options`; the
  Viewer adds `word`.
- `phonetic`, `definition`, `example` are optional display strings, bounded like profile fields.
- `audio` is an optional **Resource key**. The Resource is declared once at Package level with
  `kind: "audio"` and a `member` such as `media/serendipity.mp3`, and used by the Prompt. It is not
  an Asset, not a page, and not part of the page count.
- `answer` is an optional option id. When present it must name one of `options`; it drives the
  read-only reveal ("Meaning: …") and, after an answer is on record, the correct/incorrect line.
  It is content, not a judgment: the event still records the option the person chose.
- **Order is the contract.** The parser preserves the array order and nothing in the importer,
  database or renderer sorts or shuffles it. The acceptance test uses an order that is not
  alphabetical.
- Unknown fields are refused, as `profile`/1 already refuses them. A body this Viewer cannot read
  is a Prompt this build cannot show, never a guessed card.

### What the card shows

- the stem as instruction, the word as the largest text, phonetic beneath it;
- a play/pause control for the pronunciation Resource (disabled with a one-line reason when the
  Resource is missing);
- the options as full-width rows, in declared order, using the same inverted-selection convention
  as the profile pills;
- in a read-only surface, or once an answer is on record: the definition, the example, and the
  correct answer when the body declares one.

## 5. Changes by layer

### Domain — `app/src/main/java/com/example/listea/domain/`

- **`VocabularyPrompt.kt` (new)** — `VocabularyPrompt : PromptContent` and
  `parseVocabularyPrompt(payload, response = SINGLE)`. Strict, bounded, order-preserving.
- **`PromptContent.kt` (new)** — the `PromptContent` interface, `decodePrompt(kind, schema,
  payload)` (the one call a surface uses to go from a stored envelope to drawable content), and the
  shared option-array parser both bodies use.
- **`ProfilePrompt.kt`** — `ProfilePrompt : PromptContent`; `ViewerCapability` gains
  `parse: (String) -> PromptContent?`; `Viewers.Profile` names `::parseProfilePrompt`;
  `Viewers.Vocabulary` is added.
- No change to `PackageProtocol`'s grammar. Its `supportsKind` goes through `Viewers`, so the new
  capability makes vocabulary Prompts importable as available automatically.

### Submission — `ListsViewModel`

- `submissionAccepted` resolves the capability and calls `capability.parse(payload)`; the chosen
  option must be declared by the parsed content. All other checks (revision, required Resources,
  template intent, commit policy, non-revisability) are unchanged and remain viewer-agnostic.
- A test imports a vocabulary Prompt and proves an accepted choice, a stale label refusal and a
  missing required audio refusal.

### UI — one dispatch, three call sites

- **`PromptContentPage.kt` (new)** — `PromptContentPage(content, resources, selectedOptionId,
  interactive, notice, player, onSelect, modifier)`. It resolves the profile photo / vocabulary
  audio from `TaskResourceView` and delegates to `ProfilePromptPage` or `VocabularyPromptPage`.
- **`VocabularyPromptPage`** — the card and audio control described above. The audio control uses
  the screen's existing `ExoPlayer` (Review already owns one; both read-only surfaces own one), so
  no new player lifecycle is introduced. It stops and clears the pronunciation item when the
  content page leaves composition, so it cannot play over a video page.
- **`ReviewScreen`**, **`ListItemViewerScreen`**, **`CatalogTaskPreviewScreen`** — replace their
  local `prompt`/`photo` derivation and `ProfilePromptPage` call with `decodePrompt` and
  `PromptContentPage`. `contentNotice` keeps its meaning, with "this build cannot read" now covering
  any parsed-content failure.

### Audio

- The pronunciation is a Resource, so it inherits the existing import, missing-state and
  requiredness behaviour. The card does not read files itself; it plays
  `TaskResourceView.uri` through the screen's player.
- Missing **required** audio is already caught by `taskResources.firstOrNull { required && missing }`
  in `contentNotice` and by the write boundary; missing **optional** audio only disables the button.

## 6. What deliberately does not change

- **Schema.** 32 stays; no migration. A new kind is a capability row and a renderer, not a schema
  event.
- **Templates.** `builtin.structured.single-choice@1` is the headless template for both
  `profile`/1 and `vocabulary`/1: it accepts `choice.select`, commits immediately, is revisable and
  advances. Revisability is a template property; a Todo that wants a final recall answer can choose
  a non-revisable template later without touching the Viewer.
- **Page model.** One Content page, then Assets, then the Add-on. Vocabulary adds no page type and
  no Asset.
- **Add-ons, export v5, webhooks, the queue, the guide, the Info sheet.** A choice is a choice;
  v5 already carries content identity plus the chosen id and label.

## 9. The optional challenge (acceptance 7)

**What is already true.** One Task can hold Assets of several kinds (PDF, PNG, MP4) plus one
Content page. The mixed-media Task in acceptance 6 exercises that unchanged.

**What is missing.** A Task with four *prompt* questions — PDF, vocabulary, dating, image — is four
Prompts under one Task. The protocol's unit is one Prompt per Task, and v1's answer path records one
primary response per commit; v5's `result` carries one choice. Recording four independent answers
would need a part-identified event, a multi-commit template and export v6. That is a framework
round, not a viewer; this round will not fake it with a single choice labelled "done".

**Taken up in v0.8.4 (delivered as `0.8.4-preview`).** That framework round is designed as **TaskParts** and the
taker's **Composition**: one Task may hold several Prompts, each with its own response, events and
page; export v6 carries the per-part results and an explicit partial-completion shape. The
`workbook`/1 stretch below is superseded as the vehicle for four *recorded judgments* — a workbook
drawn as one Prompt still records one set-level choice, while v0.8.4 records each part. See
[v0.8.4](v0.8.4.md); nothing in this round's build changes.

**Stretch, only after 1–6 pass on device:** a `workbook`/1 Viewer, still one Prompt and one choice,
whose body names ordered `parts` — a child `vocabulary`/1 or `profile`/1 body, and Asset members for
the PDF and image. The Content page draws the parts in one scroll (child Prompts read-only), the
Asset pages keep their normal viewers, and the Task's single choice is the set-level judgment. It
proves Viewer composition and keeps the add-on, swipe and export contracts. The plan and its
limitation (one recorded answer, not four) will be written into the docs before any code. If the
core walk is not green, the stretch is not started.

## 10. Risks

- **Audio lifetime.** The pronunciation uses the screen's player; leaving the page must stop and
  clear it, or a word can play over a video or after the queue advances. The disposal is explicit
  and device-checked.
- **Duplicate parsing.** The three surfaces currently duplicate the profile derivation; the shared
  dispatch is the fix, and the build should be left with one call site for `decodePrompt` per
  surface and none outside it.
- **Paywall of the fixed order.** A later "shuffle" feature must be a Viewer/schema option, never a
  default; this round adds no shuffle and a test pins the order.
- **Required audio vs optional audio.** The same declaration may be required for one Prompt and
  optional for another (protocol rule); the card reads requiredness per Task use, never per file.

## 12. Out of scope

- Option randomization or a scheduler; both are product features above the Viewer.
- Reveal grading beyond the read-only correct/incorrect line; no new event, response contract or
  export version.
- A vocabulary-specific template; reuse `builtin.structured.single-choice@1`.
- Multiple Prompts under one Task as a recorded, multi-answer judgment (the challenge's full form;
  see §9). It is designed in v0.8.4 as TaskParts and is not part of this round.

1. **Import and option order.** `vocabulary/` imported four Tasks. The cards showed the declared,
   non-alphabetical orders unchanged — serendipity `c, b, a`; ubiquitous `b, a, c`; ephemeral
   `a, c, b`; meticulous `c, a, b` — and no option was shuffled or sorted.
2. **Pronunciation.** Listen played the 0.8 s mp3 through the screen's ExoPlayer with no error; the

3. **One Package, two Viewers.** `mixed/` imported as two Tasks under one Package Todo; one drew the
   dating card, one the vocabulary card, in the same frame and through the same single-choice
   template. Both committed.
4. **Global swipe rules.** Verified surface by surface:
   - Quick Review: the judging Content page refused forward and back swipes; an option tap
     committed, landed on the add-on page, and the forward swipe from there advanced or finished.
     With no add-on, the commit advanced straight to the next Task.
   - List Review: the same refusal both ways; the commit landed on `5(2/2)/5`, and the forward swipe
     finished the round.
   - Plain Task browsing (Todo preview): options draw read-only, the Content page swipes forward to
     the add-on page, then crosses to the next Task; back crosses to the previous Task.
   - List item browsing: read-only, no judging control, and swipes cross items. This was the
     surface that looked like a swipe-gate breach during the walk; it is the documented read-only

5. **Add-on.** A vocabulary commit landed on the add-on page (`1(2/2)/4`), answers persisted, and
   the forward swipe completed the Task.
6. **Mixed List.** A five-Task List (media-mix, single-pdf, mixed dating+vocabulary, dating,

instead of judging leaves the forward swipe inert, and on the last Task there is no queue arrow to

## 14. Follow-up fixes after the walk — 2026-10-26

Reading the accepted build turned up five things. None is vocabulary-specific; each is fixed at the
shared level, and none changes the schema, the protocol or export v5.

> **Naming note (added 2026-10-27).** The counts below are the file counts the accepted build
> displayed, and they stay as the record of that walk. v0.8.4 names the decision unit **TaskPart**
> rather than Asset: the same vocabulary Task is **1 TaskPart + 1 Add-on** and still **0 Assets**.
> See [v0.8.4](v0.8.4.md) and [The two vocabularies](../vocabulary.md). No build behaviour changed.

- **A Todo's card counts the add-on it carries.** A Task with a readable questionnaire now reads
  `0 Assets, 1 add-on` on a vocabulary Prompt, and `6 Assets, 1 add-on` on a folder Task; a Task
  without one keeps its Asset count alone. The count comes from the same
  `AddOnResolver.readableVersion` the review surfaces use, so a version this build cannot read is
  not counted. Device: the `test` Todo's `ListeaAcceptance_folder` card read `6 Assets, 1 add-on`,
  and the vocabulary Tasks read `0 Assets, 1 add-on`.
- **A PDF Task offers its passage tools.** The mixed-list PDF never showed C1/C2. There were two
  causes, neither a viewer bug: the import attached only Media Asset Control (the PDF-scoped
  template was not ticked), and the fixture PDFs were Pillow saves — a bitmap inside a PDF, with no
  text to select. The generator now writes a real text layer (Helvetica, WinAnsiEncoding), its
  README says why, the two PDFs were regenerated, and the Tasks were refreshed with **PDF Marks**
  v2 attached. List Review on `single-pdf` then offered `Copy | C1 | C2` on a long-press; C1 tagged
  *PDF* and wrote a `custom1` row to `task_asset_marks` with `authoredTemplateVersion 2`. A PDF
  still draws no chip row by design: its tools live in the selection menu, and the band keeps Info.
- **One glyph means one level, on every surface.** The outer pair is always `<<`/`>>` — the queue,
  Tasks or files — and the inner pair always `‹`/`›` — a page inside the current item. Before this,
  a Task with no page level drew single chevrons for queue moves, so `‹` meant *next Task* in one
  bar and *next file* in another. A bar that read `‹ 2 / 5 ›` now reads `« 2 / 5 »`. Device: List
  Review on `single-pdf` read `« 2 / 5 »`, and the Todo preview of the vocabulary Task `ephemeral`
  read `« ‹ 1(1/2)/4 › »`. This is the rule
  [Review and actions](../review-and-actions.md#the-frame-what-belongs-to-the-item) already
  stated; the bar now follows it.
- **The bar makes room for four arrows.** On the 360dp device, a capped title with four 40dp arrows
  and a two-level position pushed the queue's last arrow off-screen. The tags moved out of the title
  column onto a bar-wide line under the row, and the file's name is no longer drawn below 400dp, so
  the item's name takes the leftover width. On `ListeaAcceptance_folder`'s seven-Asset Quick Review
  all four arrows are reachable. [Review and actions → The frame](../review-and-actions.md#the-frame-what-belongs-to-the-item)
  records the layout and the width floor.
- **The read-only task band is a plain checkbox.** A Task judged by a headless template — a
  vocabulary Prompt, a dating Prompt — used to draw *Checked* / *Not checked* beside the box, while
  an image Task in the same Review drew the same fact as the box alone. `TaskStatusBar` now draws
  only the checkbox: empty is not checked, filled is checked, and the state is still in its content
  description for a screen reader. The cause was recorded rather than just fixed: v0.8.2f §9 added
  the band for headless templates and justified the words locally — "a checkbox nobody can press
  needs its meaning written out" — without comparing it to the textless `TaskCompletionBar` beside
  it, so the same fact acquired two visual languages. The amendment is in
  [v0.8.2f §9](v0.8.2f.md#9-the-second-acceptance-round-provenance-headless-swipes-and-an-info-sheet-that-knows-its-level).

The `.listea` asset semantics these counts expose — a Prompt Task's own file as an Asset, and a
section of a paper as a Task holding several decision units — remain scheduled for
[v0.8.3](v0.8.md#v083--shared-resources-and-the-reveal-card-proof). This round changes display
and fixture behaviour only.

Not run: the 2× font-scale and 320dp checks. `settings put system font_scale 2.0` is refused on
this phone (the shell lacks `WRITE_SETTINGS`), and the walk ran at the device's 360dp width and 1.0
font scale. No crash appeared in the crash buffer across the follow-up walk.
