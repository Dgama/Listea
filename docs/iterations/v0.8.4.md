# Listea v0.8.4 — one Task, several decisions

> **Status:** implemented and device-verified 2026-10-27; delivered as `0.8.4-preview` (versionCode
> 804), unreleased. Schema 33 and export v6 ship in that build. The implementation plan is
> [v0.8.4-plan.md](v0.8.4-plan.md); the gate before code, and its implementation acceptance, are in
> [v0.8.4-design-check.md](v0.8.4-design-check.md#gate-7--implementation-acceptance).
> **Baseline:** [v0.8.3-preview](v0.8.md), schema 32, export v5, `listea.package/1`.
> **Supersedes:** the 2026-10-26 note "Asset semantics for Package Tasks" in
> [v0.8.md](v0.8.md#asset-semantics-for-package-tasks-recorded-2026-10-26-not-implemented). The decision unit
> it called an Asset is a **TaskPart**; the section-to-Task decision belongs to the taker's
> **Composition**, not the setter's expression. The note's intent — a single-question Task counts
> one decision, a section Task counts several — is preserved.

## At a glance

v0.8.4 answers one question:

> **Can one Task hold more than one question?**

Yes. A Task becomes **one undertaking over 1..N TaskParts**, where a **TaskPart** is one **Prompt**
instantiated in that Task. A Task with one part is exactly today's Task. The file flow keeps working
unchanged: a photo Task is one TaskPart with no Prompt payload and one Asset; a folder Task is one
TaskPart with several Assets.

The round settles the vocabulary that made this hard to say:

| Word | Before v0.8.4 | In v0.8.4 |
|---|---|---|
| **Prompt** | one question, one Task | the setter's declared decision unit; may contain internal steps; a Task may hold several |
| **TaskPart** | — | **new:** the taker's instance of one Prompt; the decision unit inside a Task |
| **Asset** | presented file/page, but also used for the virtual Task's decision unit | presented file/page **within a TaskPart**; never the decision unit |
| **Section** | a declared grouping that could become a Task | a **declared tag** on Prompts; the taker's **Composition** decides the Task |
| **Package** | sometimes a stored envelope | an **exchange protocol**; not an internal entity |
| **Item** | file/queue/list entry | retired for the decision unit; not used |

The [two-vocabulary page](../vocabulary.md) is the canonical reference; this document is the model
and the decisions.

## Why this round

The vocabulary round (0.8.3-preview) delivered Package Prompts as one Task per Prompt. Testing it
exposed three things:

1. **The catalog showed `0 Assets` for a vocabulary Task.** That is correct as a file count and
   wrong as a decision count. The app had no word for the thing being counted, so the file word was
   borrowed.
2. **A single question and a group of questions could not both be said.** The current importer
   binds one Prompt to one Task. A section of 20 questions becomes 20 Tasks; there is no
   representation of "these 20 are one sitting" that is not also "these 20 are one Prompt."
3. **The setter/taker boundary was being crossed.** The setter's Section was being treated as a
   request to make a Task, and the importer was being asked to infer intent from the manifest. The
   setter declares content; the taker composes the sitting. v0.8.4 puts that boundary back.

The user also asked the naming question directly: *item*, *asset* and *section* had become tangled,
and the project should align with the "doing questions" scenario. The answer is the two-vocabulary
split: separate the setter's words from the taker's words, then state the equalities.

## Decisions

These are the normative decisions of the round. Each is marked **[settled]** (decided, and shipped
in `0.8.4-preview`), or **[open]** (deliberately deferred).

### D1. Task = 1..N TaskParts [settled]

A Task is one undertaking over **one or more** TaskParts. It remains the durable object for:

- identity (the opaque Task id),
- List membership,
- Task completion,
- the Add-on,
- the export envelope,
- history and revision policy.

A Task with one part behaves exactly as today. A Task with zero parts is not a reviewable Task and
must not be minted by any importer. The importer diagnoses "no parts" rather than creating an empty
Task.

### D2. TaskPart is the decision unit [settled]

A **TaskPart** is one Prompt instantiated in one Task. It owns:

- its current response(s),
- its part-level events,
- its completion contribution (required/optional),
- its availability,
- its pages: an optional Content page (the Prompt payload) and 0..N Asset pages.

A TaskPart may be **degenerate**: no Prompt payload, a freeform response, and one or more Assets.
That is the file and folder Task. The degenerate part is not a fake Prompt; it is the honest shape
of "the decision is about this file/folder, and there is no setter question."

A TaskPart is **not** an Asset. A folder Task has one TaskPart and three Assets: one decision,
three pieces of material. A vocabulary Task has one TaskPart and zero Assets: one decision, no file
page, the pronunciation audio is a Resource.

### D3. Prompt remains the setter's decision unit [settled]

A Prompt is the setter's smallest **declared** decision unit. It:

- has a response contract (`choice.single`, `choice.multiple`, `freeform`, and, since
  `0.8.4-preview`, `structured`),
- may present `files`,
- may use `resources`,
- may declare internal **steps/fields/conditions** in its body.

A Prompt is content. It is never stored as a Task and never becomes a Task by itself. The same
Prompt taken on by two Todos is two TaskParts with independent state and history.

A Prompt may contain several internal questions. A conditional chain — "Did you eat? → What did you
eat? → Where?" — is **one Prompt** when it is one logical judgment. The branch is inside the
TaskPart. "One decision unit = one answer" is too narrow; a decision may produce several answers
along one branch.

### D4. Asset and Resource keep their file meanings [settled]

- **Asset**: a file **presented as a page** within a TaskPart. It is material, not the judgment
  target.
- **Resource**: a file a TaskPart **depends on** but does not present as a page.

Both keep their current identity, pairing, attachment and history rules. The role belongs to the
use: the same bytes can be an Asset in one TaskPart and a Resource in another. Neither is the
decision unit; the TaskPart is.

### D5. Section is a tag; Composition is the taker's rule [settled]

- **Section** is a **declared tag** on Prompts, with an entry in the Package's `sections` registry
  for its title and order. It is an attribute of a Prompt, not a parent and not a Task constructor.
- **Composition** is the **taker's rule** for which Prompts become TaskParts of one Task, and in
  what order. It is recorded as the import's `compositionKey`.
- A **body group/step** is inside one Prompt. It is not a Section and not a Composition.
- The Section is the **collection** of Prompts that carry its tag. v0.8.4 adds **no separate
  Collection entity**: a filter or saved selection is a future `custom:<key>` composition or a UI
  concern, not Section semantics. The registry's `order` is a display hint; it never orders a
  Task's parts — the Composition does.

This splits the three things the word "Section" was carrying:

| Concern | Owner | Representation |
|---|---|---|
| Which questions belong together as a declared grouping | setter | `section` tag + `sections` registry |
| Which questions the taker does in one sitting | taker | Composition (`compositionKey`) |
| How a single questionnaire is laid out internally | setter's Prompt body | body steps/fields |

The protocol does **not** declare Task boundaries. The app's Composition does. The setter may say
"these belong to drill-1"; the taker decides whether drill-1 is one Task or nineteen.

Two alternatives were considered and rejected in the naming round. A separate **Collection** entity
would duplicate Composition and add a second grouping key with no new behaviour. Treating a Section
as an **ordered structure** would let the setter order a Task's parts, which is the boundary this
round is putting back on the taker's side. The tag plus Composition split is the smaller model and
keeps the setter's declaration free of taker intent.

### D6. Part-level state, Task-level completion [settled]

- Primary events carry `partKey`: a commit answers a specific TaskPart.
- A TaskPart has a current response (part state) and a history (events).
- Task completion remains a Task-level current state. It is **aggregated** from the parts according
  to the Template's completion policy, or set by the user's explicit completion control.
- The Add-on remains a Task-level questionnaire after all parts. It is not a part.

The full state machine is [below](#state-machine).

### D7. Package is an exchange protocol; ImportPlan unifies the importers [settled]

Both importers produce the same normalized **ImportPlan**:

```text
ImportPlan
└── PlannedTask × N
    ├── compositionKey
    ├── title
    └── PlannedPart × 1..N
        ├── partKey
        ├── origin: package | file | folder | legacy | synthesized
        ├── prompt payload (0..1)
        ├── assets (0..N)
        ├── resources (0..N)
        └── required
```

- The **file importer** synthesizes a **degenerate TaskPart**. It does not fake a Package or a
  Prompt.
- The **Package importer** reads declared Prompts as TaskParts according to the Composition. It does
  not fake a file layout.
- The Package remains an exchange envelope. There is no internal Package entity; provenance is
  carried by `origin`, `promptKey` and `compositionKey` on the parts and the import's
  composition record.
- The local importer's existing identity/reconciliation rules (path-based) do not change; the
  ImportPlan is a common **output shape**, not a forced identity scheme.

### D8. Protocol v2 [settled]

`listea.package/2` ships in `0.8.4-preview`. The direction:

- `prompts[].files` replaces `prompts[].assets` (the internal term remains Asset).
- `prompts[].section` is an optional tag; the top-level `sections[]` registry holds
  `sectionKey`, `title` and order.
- `response: "structured"` is a new contract; the Prompt body declares the field set; the Viewer
  for the kind/schema interprets it.
- Conditions live **inside the Prompt body only**. There are no manifest-level conditions and no
  cross-Prompt conditions in v0.8.4.
- The protocol still does not declare Tasks or compositions. `sections` is a declaration, not a
  Task.
- The v0.8.4 reader accepts v1 and v2. A v1 Package imports as one-Prompt compositions
  (`prompt:<promptKey>`); v1 `assets` map to Assets. A v2 Package uses the new grammar.
- Unknown fields are rejected, as in v1. The full grammar and limits are in
  [the protocol page's v2 section](../package-protocol.md#v2-implemented-for-v084) and freeze in the
  implementation plan.

### D9. Schema 33 and export v6 [settled]

- **Schema 33** adds per-part state: a `task_parts` table, per-part payloads, part state, a
  `partKey` on primary events, field identity on structured answers, and composition provenance.
  The migration is additive and preserves existing Tasks, responses, Assets, Resources and history.
  Existing Tasks gain **one TaskPart** each.
- **Export v6** carries `parts[]` with per-part results and an explicit partial-completion shape. A
  single-part Task with a v5-compatible response may still export the v5 body; a Task with more than
  one part or a structured response requires v6. The round uses v6 if any Task requires it.

The exact DDL and export schema are in [the plan](v0.8.4-plan.md); this document fixes their
semantics.

### D10. Identity and composition provenance [settled]

- The Task's domain id stays **opaque**. No `p:<promptKey>` or `s:<sectionKey>` is ever a Task id,
  export id or wire id.
- `compositionKey` is **import provenance**:
  - `prompt:<promptKey>` — one Prompt per Task (today's shape),
  - `section:<sectionKey>` — all Prompts tagged with that Section in one Task,
  - `custom:<userKey>` — future; representable, not shipped.
- Re-import matches `(todoId, packageKey, compositionKey)`. A composition membership change does not
  auto-change the Task's identity; the existing keep/reset/drop content policy applies.
- Two Todos over the same Package remain independent. The same Prompt in two Tasks is two
  TaskParts.

### D11. Version and scope [settled]

- The round is **v0.8.4**, per the user's decision. It is a **framework** round within 0.8, not the
  v0.9 product layer. The other reviewer's suggestion of 0.9.0 was considered and overridden.
- The design round was **documentation only**. The implementation was cut on 2026-10-27 and follows
  the preview convention: **`0.8.4-preview`** (versionCode 804) until v0.8.4 is closed.
- The v0.8.3 open items are inherited, not silently dropped; see
  [Inherited open items](#inherited-v083-open-items).

### D12. Naming [settled]

- New independent concepts get new words: **TaskPart**, **Composition**, **ImportPlan**.
- Words that still match the file flow keep their meaning: **Task**, **Asset**, **Resource**,
  **Todo**, **Upstream**, **Template**, **Viewer**, **Add-on**.
- Narrowed: **Prompt** (setter's unit, may contain steps), **Section** (tag, not parent).
- Retired for the decision unit: **Item**. Corrected: **Asset** is never the decision unit.
- Not yet aligned and marked open: `files` vs `materials`, custom composition, cross-Prompt
  conditions, per-part revisability, mixed-contract parts, the UI label. The
  [vocabulary page](../vocabulary.md#open--not-yet-aligned) is the list.

## The model

```text
List 1 ─── N ListEntry N ─── 1 Task
                                 │
                                 ├── 1..N TaskPart
                                 │        ├── 0..1 Prompt payload
                                 │        ├── 0..N Asset (presented file/page)
                                 │        ├── 0..N Resource use (dependency)
                                 │        ├── 0..1 current part response
                                 │        └── 0..N primary ReviewEvent (partKey)
                                 │
                                 ├── 0..1 current TaskState (completion)
                                 ├── 0..N Task-level ReviewEvent (legacy / complete / add-on)
                                 └── 0..N add-on answer (0..1 current)
```

Set against the exchange format:

```text
Package                          Taker
├── prompts[]  ── Prompt ──────► TaskPart (instantiated)
│   ├── files[] ─────────────────► Asset pages
│   ├── resources[] ─────────────► Resource uses
│   ├── section tag ──┐
│   └── response ─────┼──────────► response contract
├── sections[] ───────┘
└── (no Task)         Composition ──► Task boundaries
```

The arrows are translations, not ownership. The setter owns the left column; the taker owns the
right; the Composition is the taker's rule, not a setter declaration.

## TaskPart

### Identity

- `partKey` is stable **within one Task**. It is not a domain id and is not globally unique.
- Package part: `partKey = promptKey` (the Prompt's key within the Package). The pair
  `(taskId, partKey)` is unique.
- Local/degenerate part: the local importer emits exactly one, with `partKey = local:0`. The local
  importer's Task identity remains path-based. A Task migrated from schema 32 with no Package
  Prompt gets `legacy:<taskId>`, so its part key records that it predates compositions; a migrated
  Package part keeps its `promptKey`.
- If the same Prompt appears twice in one composition (a declaration error), the composition is
  rejected; a Task cannot have two parts with the same `partKey`. A legitimate repeated question
  must be two Prompts with different keys.
- The part's `position` is the composition order, not `partKey`. Reordering changes position, not
  identity.

### Requiredness

- `required` is a **Composition property**, default `true`. The same Prompt can be required in one
  Task and optional in another.
- The setter's Prompt does not declare Task requiredness. It declares the response contract; the
  taker decides whether this sitting requires it.
- An optional part still has a page and can be answered; it does not block completion.
- A composition may have zero required parts only when its Template's completion policy is
  `explicitOnly` or `anyPart`; this is validated at import and covered by the design-check.

### Degenerate parts

A degenerate part is a legitimate TaskPart with:

- no Prompt payload,
- a freeform response,
- 0..N Assets.

It is used by:

- **file-as-Task**: one degenerate part, one Asset, the decision is about the file;
- **folder-as-Task**: one degenerate part, N Assets, the decision is about the folder;
- **notes-only** (future): one degenerate part with no Assets but an explicit freeform content
  page — only if the Template supplies a page. Without a payload or an Asset, a part has no page and
  is not reviewable; the importer must diagnose it.

The part's origin distinguishes it: `file`, `folder`, `legacy`, or `synthesized`. The importer never
fakes a Prompt to make the part fit the Package shape.

### Availability

| Availability | Meaning | Blocks completion if required? |
|---|---|---|
| `present` | In the composition and renderable. | Yes, while pending. |
| `unavailable` | In the composition but not renderable: unknown Viewer, missing required Resource, malformed payload, unsupported contract. | Yes, if required. The user sees the diagnostic; the Task cannot complete through the template. |
| `detached` | Removed from the composition by a re-import; the row and its history remain. | No. It is not part of the current Task. |

A detached part is **not deleted**. Its history remains; it is excluded from completion and from
the default export. The export plan may expose it under a provenance field so nothing is silently
lost. An unavailable part is still part of the Task; the user or the producer must resolve it.

## Composition

### Keys

| Key | Meaning | Member set | Shipped |
|---|---|---|---|
| `prompt:<promptKey>` | One Prompt per Task | one | yes (today's shape) |
| `section:<sectionKey>` | All Prompts tagged with the Section | the registry's members, in manifest order | v0.8.4 |
| `custom:<userKey>` | A stored member list | arbitrary | not in v0.8.4; representable |

The key is a string in import provenance. It is not a domain id. Two Todos importing the same
Package with the same composition get two independent Tasks with the same `compositionKey`; the
uniqueness is per `(todoId, packageKey, compositionKey)`.

### Selection and order

- The Composition selects Prompts from the Package's declared set. It cannot invent a Prompt.
- Order follows the manifest's `prompts[]` order by default. A Section composition uses the
  manifest order of its members. A custom composition may later carry its own order.
- A Section with zero Prompts is a declaration with no members; the composition is invalid and
  diagnosed. A Section tag naming an unknown registry entry is a manifest error.
- A Prompt with no Section can still be selected by `prompt:<key>`; it is not required to belong to
  a Section.

### What the Composition is not

- It is not a setter declaration. The manifest does not contain a `composition` field.
- It is not a Task id. It does not enter the export as an id.
- It is not a Section. A Section tag may be the selector, but the Composition is the taker's rule.
- It is not a per-Task override of the Package's content. It selects and orders; it does not rewrite
  a Prompt.

## State machine

### Part states

| State | Meaning | Entered by | Leaves by |
|---|---|---|---|
| `pending` | Presentable, no accepted response. | Import, reset, detached part reattached. | A valid commit → `answered`. |
| `answered` | At least one accepted response; the current result is the latest accepted event. | A valid commit. | A reset → `pending`; a revisable commit keeps `answered` and appends; a detach → `detached`. |
| `unavailable` | In the composition, not renderable. | Import/runtime availability. | The cause is fixed and the part is re-evaluated. |
| `detached` | Removed from the composition; history retained. | Re-import membership change. | Reattachment by a later import (a new current part? see below). |

`answered` is not a per-response state; a revised part is still `answered` with a later current
response. `revisable` is a Template policy, not a state.

A detached part that is reattached by a later re-import is a **new current part** if its content
changed; the old row remains detached in history. If the content is byte-identical and the
composition returns to the same membership, the importer may reattach the existing row; the
reconciliation policy decides. The default is conservative: reattach the existing row only when the
fingerprint matches; otherwise a new part is minted and the old row stays detached.

### Commit

A part commit is a `ReviewSubmission` scoped to `(taskId, partKey)`. It is valid only when:

- the part is `present` and in the current composition;
- the payload revision matches the part's current revision, or the re-import policy has already
  reconciled it;
- required Resources are available;
- the Template accepts the intents and the response contract accepts the value;
- the Template's commit policy allows the commit (e.g., a non-revisable part that is already
  answered refuses a second commit).

A valid commit is **atomic**:

1. append a primary `ReviewEvent` with `taskId`, `partKey`, template version, Viewer capability,
   response encoding and timestamp;
2. update the part's current response (projection);
3. recompute the Task's automatic completion, or leave an explicit completion untouched;
4. advance the page per `advanceAfterCommit` **after** the write succeeds.

A failed validation writes nothing and does not advance. A non-revisable answered part is read-only;
the Template may present the current response but not a new commit.

### Revisability

- Revisability is a **Template-level** policy applied to each part in v0.8.4. Per-part policies are
  open.
- A revisable part appends a new event; history keeps both; the current response is the latest.
- A non-revisable part refuses a second commit; the current response remains.
- A revised part does not uncomplete a Task by itself. Completion is a Task state, not a pure
  function of the latest answers.

### Completion

Task completion remains `task_state.isCompleted` with a **provenance**:

| Provenance | Set by | Recomputed on part change? |
|---|---|---|
| `automatic` | The Template's completion policy, after a part commit/reset. | Yes. |
| `explicit` | The user's completion control (`complete` / `uncomplete`). | No; the user owns it. |

The Template's completion policy is one of:

| Policy | Meaning | Default |
|---|---|---|
| `allRequiredParts` | Complete when every required part is `answered` and no required part is `unavailable`. | Multi-part default. |
| `anyPart` | Complete when at least one required part is `answered`. | Available for "pick any" sittings. |
| `explicitOnly` | Never auto-complete; the user's control is the only path. | Available when the setter/taker wants a checklist. |
| `singlePart` | Preserve the current single-part behavior: the template's primary commit completes the Task as it does today. | Single-part default. |

Single-part templates that today record Task-level state (a media rating, a mark, a completion) may
continue to do so. The `singlePart` policy preserves that behavior; the part-level response is
populated by templates that commit per part. The migration does not force a media template to write
a part event, and an empty part response with a complete Task is valid under `singlePart`.

Rules:

- An `unavailable` required part blocks automatic completion; an optional one does not.
- A `detached` part does not block.
- The explicit completion control is always available unless the Template hides it. Completing with
  pending required parts is allowed by the user's explicit decision; the UI should show the pending
  count and ask for confirmation. This preserves the architecture's direct path while making the
  cost visible.
- Un-completing is an explicit state edit; it does not delete responses.
- The Add-on remains optional and Task-level. It does not affect `isCompleted` under the current
  contract. The Add-on page is still offered after the last part.

### Navigation and the Add-on

The page list for a Task with parts:

```text
for each present part in composition order:
    Content(partKey)       if the part has a payload
    Asset(partKey, asset)  for each Asset, in attachment order
AddOn                      if present
```

- The inner navigator walks **pages**, as today. The part is a grouping and state unit, not a third
  arrow level.
- A part commit with `advanceAfterCommit` moves to the next part's first page. After the last part
  it moves to the Add-on if present, otherwise to the next Task if the Task completes and the queue
  advances, otherwise it stays. The commit does not walk the committed part's remaining Asset
  pages; the inner arrows do. For a single-part Task this is exactly today's arrival rule (a
  content commit lands on the Add-on), so the media regression holds.
- The Add-on is not a part and has no `partKey`. It remains Task-level.
- The queue guide may label part boundaries (e.g., "Question 2 of 5") inside the second level, but
  the fixed arrow count does not change.
- A single-part Task with one Asset produces exactly today's page list: no Content page (no
  payload), one Asset page, optional Add-on. The media regression is a hard invariant.

### Counts

Three counts are distinct and must never be substituted for one another:

| Count | Counts | Vocabulary Task | Photo Task | Folder of 3 |
|---|---|---|---|---|
| Parts / questions | TaskParts | 1 | 1 | 1 |
| Assets / files | presented files | 0 | 1 | 3 |
| Pages | navigable pages | 1 Content | 1 Asset | 3 Assets |

The catalog should show the parts count as the decision count and the Assets count as the file
count. "1 Part + 1 Add-on" is the correct phrasing where the v0.8.3 note said "1 Asset + 1 add-on";
"0 Assets" is correct as a file count and should be explained by the part count, not replaced by
it.

## Import and reconciliation

### ImportPlan

Both importers produce the same shape (see [D7](#d7-package-is-an-exchange-protocol-importplan-unifies-the-importers-settled)).
The shape is the **output** of the import; it does not force the local importer's identity scheme to
become Package identity. The plan defines the exact types.

### Provenance

Each TaskPart records:

- `origin` (`package`, `file`, `folder`, `legacy`, `synthesized`),
- `promptKey` (Package parts only),
- `compositionKey` (the Task's import provenance),
- the payload revision (Package parts only).

These are provenance, not identity. They may be exported for traceability; they are not used as
domain ids.

### Re-import: the policy

The existing keep/reset/drop policy applies to the **part set** as a content change. The Task's id
does not change just because the membership changed.

| Change | Task id | Existing parts | New parts | Completion |
|---|---|---|---|---|
| Same composition, same members, same content | kept | kept | — | unchanged |
| Same composition, new Prompt | kept | kept, availability refreshed | added, `pending` | recomputed if automatic |
| Same composition, Prompt removed | kept | the removed part becomes `detached`; history kept | — | recomputed; detached does not block |
| Same composition, Prompt key renamed | kept | old part `detached`; history kept | new part `pending` | recomputed |
| Same composition, reordered | kept | kept; `position` changes | — | unchanged |
| Section tag membership changed | kept | added/detached as above | — | recomputed |
| `compositionKey` changed (e.g. `prompt:a` → `section:s`) | **new Task**; the old Task is not merged | — | — | new Task |
| Payload revision changed, policy `keep` | kept | kept; response kept | — | unchanged |
| Payload revision changed, policy `reset` | kept | current response cleared for changed parts; history kept | — | recomputed if automatic; explicit completion untouched |
| Policy `drop` | single-part: start over, same id (existing exception); multi-part: delete the Task and mint a new one | reset/replaced by policy | — | reset |

Rules:

- **Absence is not deletion.** A removed Prompt detaches its part; it does not erase the response or
  the event history.
- **A composition change is not an identity change.** The Task id survives membership changes; the
  provenance changes, and the policy decides the content.
- **A compositionKey change is a different composition.** The old Task is not silently merged into
  the new one. The Todo's scope/retirement policy decides whether the old Task remains visible.
- **Two Todos are independent.** The same Package, same composition, two Todos: two Tasks, two
  TaskParts per Prompt, independent state and history.
- **`drop` is destructive by definition.** It is recorded and never silent. The single-part
  "start over" exception is preserved for compatibility.

### Local and Package, side by side

| Surface | Composition | Parts | Payload | Assets | Identity/reconciliation |
|---|---|---|---|---|---|
| File as Task | local (path) | 1 degenerate | none | 1 | existing path-based |
| Folder as Task | local (path) | 1 degenerate | none | N | existing path-based |
| Package, one Prompt | `prompt:<key>` | 1 | yes | 0..N | `(todoId, packageKey, compositionKey)` |
| Package, Section | `section:<key>` | N | yes per part | 0..N per part | same |
| Legacy Task (pre-33) | legacy | 1 | moved from `task_payloads` | existing | migrated, ids kept |

The local importer does not create a Package row or a Prompt body; the Package importer does not
create a file layout. Both meet at the TaskPart.

## Protocol v2 direction

The full draft lives in [package-protocol.md](../package-protocol.md#v2-implemented-for-v084). The
design-level points:

- `protocol: "listea.package/2"`.
- `prompts[].files` replaces `assets`; the internal Asset term remains.
- `prompts[].section` is an optional tag; `sections[]` is the registry of `sectionKey`, `title`,
  order.
- `response: "structured"` is a new contract. The body declares the field set; the Viewer for the
  kind/schema interprets it. The protocol validates the envelope, not the fields.
- Conditions are inside the Prompt body. No manifest-level `when`; no cross-Prompt conditions. A
  later Prompt depending on an earlier answer is out of the v0.8.4 Core; the producer may emit a
  follow-up Task.
- The manifest has no `composition`/`tasks` field. The app's Composition decides Task boundaries.
- v1 and v2 are both readable. v1 imports as `prompt:<key>` compositions; v2 uses the new grammar.
- Unknown fields reject, as in v1. The new fields are strict; a v1 reader must not accept v2
  silently.

The exact grammar, limits and diagnostics freeze in the implementation plan before code.

## Schema 33 direction

The exact DDL is in [the plan](v0.8.4-plan.md). The semantic requirements:

1. Every Task has at least one TaskPart.
2. A TaskPart has a `partKey` unique within the Task, a `position`, an `origin`, an optional
   part-keyed payload, and `required`.
3. A TaskPart has a current response (part state) separate from its event history.
4. Primary `ReviewEvent`s carry a `partKey`; Task-level events (complete/uncomplete, Add-on) may
   keep a null `partKey` with an explicit kind. Legacy events are not reinterpreted.
5. Structured answers are **projected with a field identity** (a field key), not only an option
   key; the projection is part of the structured commit and the export reads it. Existing
   viewer-event rows are **not reinterpreted**: they keep their ordinal option rows and gain no
   invented field key. A structured answer is therefore readable by the new projection without
   rewriting old history.
6. Composition provenance is stored for Package Tasks; `(todoId, packageKey, compositionKey)` is
   the reconciliation key. The Task id remains the primary key of the Task.
7. The migration is additive: existing Tasks, payloads, Assets, Resources, responses and history
   survive; every existing Task gains one part. The migration is tested on a schema-32 fixture.
8. No table rebuild is done for terminology alone. A table rebuild is allowed only where the
   primary key change is unavoidable (e.g., per-part payload) and is covered by the migration test.

## Export v6 direction

The exact schema is in [the plan](v0.8.4-plan.md). The semantic requirements:

- A single Task body carries `parts[]` in composition order.
- Each part carries `partKey`, `promptKey` (provenance, optional), `kind`, `schema`, `revision`,
  `required`, its Assets (or Asset links), and `result` (the current response or null).
- `result: null` (pending) is distinct from an answered empty response. The export must not
  collapse them.
- The Task carries `completed` and its provenance is not exported as a state edit; the export
  reports the current state.
- The Add-on remains Task-level and optional; its existing body is preserved.
- Detached parts are excluded by default; if the plan exposes them, they are under a clear
  provenance field with `present: false`. No silent loss.
- A single-part Task with a v5-compatible response may still produce the v5 body; a Task with more
  than one part or a structured response produces v6. The round's document version is v6 if any
  Task requires it.
- The v5 reader remains; existing export history is not rewritten.
- The mapping is pure: it reads a snapshot and writes JSON; it does not touch the database.

## What does not change

- Source retirement, Source entities and the existing identity rules.
- The Add-on: one per Todo, Task-level, optional, after the parts, not part of `isCompleted`.
- Media and PDF viewing, attachment rotation, pair state, marks, and the page arrow semantics:
  `<< >>` Task-level, `<>` Asset-level.
- Resume, Quick Review/List Review queues, List membership, templates and Viewer contracts, except
  where the part grouping adds a page/part label.
- The file/folder import UX and its path-based identity.
- The Package checkpoint/resource import state; it remains import state, not a domain Package.
- The export history: old documents remain readable.
- The one-Prompt-per-Task shape: it remains a valid composition, not the only one.

## Inherited v0.8.3 open items

The 0.8.3 status block still lists three open items. v0.8.4 must close or explicitly defer each:

| Item | v0.8.4 position |
|---|---|
| Payload revision policy | **Closed in the multi-part context** by D6/D9 and the per-part revision policy: a revision change is a content change; keep/reset/drop applies per part; history is preserved. The exact UI copy is in the plan. |
| Independent-Todo proof | **Kept open until the implementation test.** The plan adds a test with two Todos over one Package (one single-part composition, one multi-part) proving independent Tasks, states and histories. The design does not claim it is proven until that test runs. |
| Protocol/capability freeze | **Deferred to acceptance.** v0.8.4 freezes `listea.package/2` and the TaskPart capability set when the implementation is accepted; v1 remains the compatibility contract. This docs round does not freeze code. |

## Out of scope

- Cross-Prompt conditions (a later Prompt depending on an earlier answer). The Core's boundary is
  intra-Prompt only; a producer may emit a follow-up Task.
- Custom composition UI and storage (representable as `custom:<key>`, not shipped).
- Per-part revisability policies.
- Mixed-contract parts in one Task (composite Templates).
- Multiple Add-ons per Todo.
- A `.listea` archive format.
- Webhook/n8n grading implementation.
- Any Kotlin, schema, protocol, export or version change. This round is documentation only.

## Amendments in v0.8.5

Two decisions in this round were deliberately narrower than the model proved to need. v0.8.5
widens them; the original text above is kept as the record of what v0.8.4 shipped.

1. **An explicit completion can be reopened.** v0.8.4's rule — a later part answer never clears an
   explicit sign-off — still holds for ordinary recomputation. It does not hold when a **required**
   conditional part moves `inactive → active`: the sign-off described a smaller Task than the one
   now on screen, so the Task reopens and `task_state.completionSource` becomes `reopened`. No
   `review_events` row is written; that table remains append-only submissions.
2. **Conditions are no longer only intra-Prompt.** The `form` body's field-level `when` is
   unchanged, but v0.8.5's protocol v3 adds a manifest-level `when` on a Prompt, resolved between
   the parts of one Task. The v0.8.4 closure is unchanged: nothing conditions across a Task
   boundary, and one Task per question cannot resolve a cross-Prompt condition.

See [v0.8.5](v0.8.5.md), decisions D3, D4 and D8.
