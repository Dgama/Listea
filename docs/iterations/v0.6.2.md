# Listea v0.6.2 — The model comes off the screens

> **Status:** **Implemented (2026-10-20).** The walk's findings were agreed, the plan was written
> and the round is built: schema 27, per-Todo addresses, grouped History, the index-shaped Settings
> and the flow fixes below. Entries 3, 4 and 7 are the explicitly deferred presentation items. The
> implementation record — including the four decisions that narrowed or changed the text below —
> follows the status block.
> **Audience:** Coding agent and maintainers
> **Depends on:** v0.6.0 — the export contract and the two-id schema are settled and must not move
> during this round
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)

## Implementation record

What was built, and where the build deliberately departs from the discovery text.

- **Schema 27.** `sources` gains `webhookUrl` / `webhookFromDefault`, `webhook_history` gains
  `webhookUrl` / `roundId`, and `lists.webhookUrl` is cleared and read again as the List override.
- **A one-time bootstrap, not a migration snapshot.** The default and the old gate live in
  DataStore, which Room's migration cannot read. `MIGRATION_26_27` adds the columns, clears the
  List URLs and leaves a marker in `schema_backfills`; the first delivery, address edit or Test
  consumes it and copies the default in one transaction. Fresh installs never see the marker.
- **Upgrade with the old gate OFF leaves addresses empty.** The discovery text said the snapshot
  would fill every Todo. Copying the default anyway would make an install that had deliberately
  switched delivery off begin posting the moment the gate was removed, so a gate-off upgrade
  writes empty addresses and each round records *no address set* until the user edits the Todo.
  This is the one deliberate narrowing of the snapshot decision.
- **New Lists default `exportOnCompletion = false`.** Both creation paths (Create List and a
  folder-backed List) now start off. The old seed read `defaultWebhookEnabled`, which no longer
  exists as a gate and is not a statement about a List; no List starts posting because it was
  created after the upgrade. The user turns it on per List.
- **Test writes exactly one history row**, as a round of one with a fresh round id — the same shape
  a real single-export round has, so History does not special-case it.
- **The default address is a preference, not a gate.** `defaultWebhookEnabled` now only preselects
  *Use default* in configuration. Delivery is authorised by the Todo's method; a List's own switch
  still decides whether completing it starts a round.
- **Groups sharing an address merge.** A round splits by resolved address and a `By(webhook)`
  round whose Todos share one address is one POST, not one per Todo. *Inherit* still groups per
  Todo.
- **Deferred, as agreed:** `?` / `i` explanations (3), template preview/detail (4) and Todo card
  density (7). The new sections and rows leave room for all three.

## Before the UI work

### A Todo must own its webhook address

This comes from entry 8 below. The walk found that the dialog offers *Webhook* as an export method
without ever asking where it should post, and the audit found the model behind that: **there is no
address anywhere but Settings, read at send time.**

What the app does today, measured:

- Every webhook the app sends — a List round, a folder round, a resend, the Test button — posts to
  `settings.defaultWebhookUrl` **as it stands at that moment**. No Todo or List holds an address;
  `lists.webhookUrl` is a legacy column nothing reads.
- A history record keeps the body, the outcome and the mechanism, but **not the address**. A resend
  posts the stored body to the default as it stands now, so changing the default silently
  redirects every old record.
- One switch, `defaultWebhookEnabled`, is at once the app's only global stop for POSTs (a group
  with Webhook blocked by it is recorded as *not attempted*) and the value a new List is seeded
  with for export-on-completion. It is not a statement about addresses at all.

The decisions taken from the walk:

1. **A Todo owns its webhook address, as a value taken when it is configured.** *Use default* copies
   the default's value at that moment; a later edit in Settings reaches no existing Todo. Adopting
   the new default is a deliberate edit on that Todo. The Todo shows the address it holds — for a
   *use default* Todo, the default as it was when it took it.
2. **A Todo's address governs everything its own Tasks send:** its own export groups, the folder
   Quick Review rounds its Tasks take part in, and the webhook exports of Lists holding its Tasks.
   A List neither reads the Settings default nor the default switch: with no List address of its
   own, a round resolves each group by the Todo its Tasks came from — the export method first, and
   now the address with it. Tasks with no owning Todo fall back to the default address.
3. **A List may carry an address of its own, and only a non-empty one changes the rule above.**
   A List URL is a deliberate, List-specific override for that List's webhook groups; empty means
   *follow the Todos*. This is the one case where the List is not reading a setting — it is holding
   an answer the user typed for it.
4. **`defaultWebhookEnabled` stops being a gate, and no separate master switch replaces it.**
   Delivery is authorised by each Todo's export method, and Quick Review keeps its own switch. The
   Settings value means only the configuration preference in point 5. Because a List no longer
   reads either the default URL or this switch, the old "List blocked by the global setting"
   problem disappears rather than being rehoused.
5. **Settings' *Default enabled* changes meaning.** It says whether *use default* is preselected
   when configuring, not whether webhooks may be attempted. Off puts the cursor in the custom
   address field when Webhook is chosen. If no default URL exists and *use default* is chosen,
   Create Tasks refuses at Create with an error; if one exists, choosing it shows that URL.
6. **Choosing Webhook in Create Tasks opens the address configuration** — *use default* or a custom
   URL — instead of only describing when the trigger fires.
7. **A resend may use a different address, for that resend only.** The history record keeps the
   address the attempt used, and the resend is offered with that address prefilled and editable —
   precisely so a round that failed because its Todo pointed at a bad URL can be salvaged without
   editing the Todo first. The edit is temporary: it does not write back to the Todo, the List or
   the record. Rows written before this change carry no address; their resend is prefilled with the
   current default and says the original was never recorded.

Non-UI work this requires, to be settled before the screens are touched:

- **Schema 26 → 27.** `sources` gains the address and whether it came from the default;
  `webhook_history` gains the address attempted. **As implemented**, a one-time bootstrap (kept in
  `schema_backfills` because DataStore is not readable from a Room migration) snapshots the current
  default onto every existing Todo, marked *from default*, **only when the old gate was on**. With
  the gate off, every address stays empty: an install that had deliberately switched delivery off
  must not start posting when the gate is removed. Edge: if the default is empty at upgrade, those
  Todos hold no address until edited — today they would also fail, so nothing that worked stops
  working.
- **The List's own address reuses `lists.webhookUrl`, which already exists**, and the migration
  **clears its legacy values**: the column has been ignored since v0.5.6 and may hold stale copies
  of an old default. Resurrecting one would redirect posts nobody asked to redirect. Empty is the
  correct starting state for every existing List.
- **Delivery resolves an address per group, not once per round.** `ExportSource` / `PlannedExport`
  carry the address; `deliverPayload` uses it per group. With an empty List URL, groups resolve by
  Todo address and are split where addresses differ (the plan must decide whether groups sharing
  an address merge into one POST); with a List URL set, that address is used for the List's webhook
  groups. Folder rounds already group by Todo and take each Todo's address.
- **History and resend**: store the attempted address; a resend takes an optional temporary
  address (point 7); a pre-27 row falls back to the current default.
- **List creation stops reading webhook settings.** It no longer seeds export-on-completion from
  `defaultWebhookEnabled`. **As implemented**, both creation paths start it **off**: no List begins
  posting because it was created after the upgrade, and the user turns it on per List.
- **Docs to amend with the implementation:** `settings.md` and `webhooks.md` ("Default URL is the
  only URL there is"), and the helper text on the Webhook settings page.

### Export history is grouped by the round that produced it

This comes from entry 9 below.

What the app does today, measured:

- **Storage is already one row per actual export attempt**, which is the shape the user wants: a
  round that splits into three exports writes three rows, each with its own body, method and
  outcome. Rows are never merged.
- **Nothing links the rows of one round.** `webhook_history` has no round id, so two records from
  the same round are indistinguishable from two unrelated rounds; the screen shows one flat list,
  ordered by time.
- History is reachable from three places: the Exports landing page, the Webhook method page, and a
  note on the Txt method page. All three open the same screen, and all three sit inside
  configuration pages where history has nothing to do.

Decisions:

1. **One History entry, at the bottom of Settings' main screen.** The History cards are removed
   from the Exports landing page, the Webhook page and the Txt page. The Exports card stops
   reporting history counts and describes methods only.
2. **Storage stays per actual export.** A new round id is written on every row of one delivery
   round, so the screen can say which records belong together. A resend updates its record and
   keeps the round id; the Test button's one record is a round of its own. Rows written before
   this change have no id and are each treated as a round of one.
3. **Display: a round summary that expands into its exports** (recommended), or a flat list whose
   rows say *1 / 2 of export …*. The summary carries time, list, event, number of exports and an
   aggregate outcome, and contains no payload; each child is one actual export with its method,
   address, item count, outcome, body and Resend/Delete. The flat form is the fallback if the plan
   finds the hierarchy too heavy, but the summary matches this release's primary/detail rule and
   keeps a three-export round to one row.

Non-UI work:

- **Same schema change as the entry above (26 → 27):** `webhook_history` gains the round id
  alongside the attempted address.
- **Delivery**: one id generated per `deliverPayload` round and passed to every `keepRound` of that
  round.
- **Reads**: the history query and the pending/record counts must decide their unit — exports or
  rounds. `pendingWebhookCount` is currently per attempt; the Settings summaries need to say
  which number they mean.
- **UI after that**: consolidate the entry points, group the screen by round, and change the
  history screen's back label from *Exports* to *Settings*.

## The change in one paragraph

The model is right and the output is now a contract, but the screens still carry the model: they
explain what an Upstream, a Todo, a Task or an export method is, instead of leading with the work.
This round is the *无痛* half of the parity goal — the core flows must be walkable without leaning on
the explanatory paragraphs, with a primary line, a secondary line and detail on demand. No
capability is removed; explanation may be hidden, never a control.

## How this document is kept

Each report from the walk is one entry, in the order the user met it, and says:

- **Where** — the screen and the moment in the workflow.
- **What got in the way** — in the user's terms, not the code's.
- **What is expected** — the outcome the user wants, as a behaviour rather than a layout.
- **Status** — *confirmed*, *open*, or *deferred*.

A decision that overturns something already written in `docs/` amends that document too, rather
than being recorded only here.

## Observations from the walk

### 1. The Create Tasks dialog shows every decision at once — *implemented*

- **Where:** Upstream → inside a folder → **Create Tasks** → the configuration dialog.
- **What got in the way:** name, grouping, keep-the-folder-tree, what happens when a Task's
  content changes, where a round exports, the attached templates and the optional history all sit
  in one long form, each row carrying a permanent explanatory sentence. The user has to read the
  whole page to find the one thing they came to change, and every future choice lengthens it.
- **What is expected:** content grading. The grouping choice — *import method* in the user's words —
  collapses to one row that states the current answer ("One Task per file"), and expands on tap to
  show *One Task per file* / *One Task per folder* and their explanations. The same pattern applies
  to the other sections, so the dialog opens as a short list of decisions with their answers, each
  one tap from its options. A choice added later joins its section instead of adding another
  always-visible block.

### 2. "Keep the folder tree" reads as global or as belonging to the wrong method — *implemented*

- **Where:** the same dialog, grouping section.
- **What got in the way:** the checkbox is drawn below **both** grouping rows, so it appears under
  *One Task per folder* — the last row — and reads either as a setting for the whole dialog or as
  one belonging to folder-as-Task. It is in fact only meaningful for *One Task per file*, and is
  only drawn when that is selected.
- **What is expected:** a method's extra options are nested directly under that method, visible
  only while it is the selected one — *Keep the folder tree* indented under *One Task per file*. If
  another method later gains an option of its own, it appears under that method in the same way,
  never as a shared block below the list.

### 3. Permanent explanatory text should live behind a `?` / `i` — *deferred*

- **Where:** the option rows in this dialog, and the same pattern wherever settings explain
  themselves.
- **Note:** almost every option carries a sentence of explanation that is read once and then sits in
  the way. The user wants these collected behind a `?` or `i` affordance later. **Not this
  round** — recorded so the hierarchy work leaves room for it rather than baking the sentences into
  the new layout.

### 4. The template picker does not say enough for the user to judge a template — *deferred*

- **Where:** the same dialog, the **Add a template** area.
- **What got in the way:** each row shows the template's name, the scope it applies to (which file
  kinds it governs) and how many buttons it carries. That is enough to tell two templates apart but
  not to judge whether one *fits* the round: the button count says nothing about what the buttons
  are, and the name is only as informative as the person who chose it. The user has to remember or
  leave the dialog to check.
- **What is expected:** later, take one of two routes — show more of the template itself, such as
  the actual buttons it would put on a file, or offer a jump/preview that opens the template's real
  effect before attaching it. **Not this round** — recorded so the 0.6.2 layout leaves the row
  somewhere a preview can grow.

### 5. An Upstream cannot be removed once it has been added — *implemented*

- **Where:** the **Upstreams** tab's main list; the same folders are also listed under
  Settings → Upstreams.
- **What got in the way:** there is no way to remove a folder registration. A folder added by
  mistake, or one that is no longer used, stays on both lists for good. Revoking its grant in
  Android's own settings only makes it *unavailable*; the row remains.
- **What is expected:** a delete action on the Upstream itself. Deleting removes the registration
  only — not the folder's files, its Todos, its Tasks or its Lists. A confirmation names what stays
  behind before anything is removed. This follows the existing rule that an Upstream is a *place*
  and a Todo is a *decision taken about part of one*: removing the place does not remove the
  decisions.
- **Safety assessment (before implementation):** no serious consequence found.
  - Nothing outside the `upstreams` table is keyed on an Upstream's id. Todos, Lists, Tasks and
    Assets are located by the SAF grant plus a path (`rootUri` + `relativePath`), so removing the
    row cannot orphan them.
  - A folder that is gone or unreadable is already handled at every level: an Upstream card whose
    grant is lost says so and stays; the browser reports the Upstream's folder unreachable; Create
    Tasks and Refresh Import refuse with "Could not read this folder. Nothing was changed."; a
    List page shows "Source unavailable" and a re-sync refuses without writing; Quick Review says
    the folder could not be read; a file that will not load draws a placeholder rather than
    crashing. Nothing is deleted by any of these paths.
  - An unused `deleteUpstream(id)` query already exists, so the change is a screen path plus a
    confirmation — no schema change.
  - Two points to settle when planning. **(a)** Deleting a registration must not release the SAF
    grant: another Todo or List under the same grant may still need it. At most, release it only
    when nothing else uses that root, and only with its own warning. **(b)** Settings' checked-file
    tools choose their roots from the Upstream list, so removing the last Upstream under a grant
    also removes that root from those tools even though its files and Todos remain.
  - One pre-existing gap, not caused by the delete: when the *whole* folder disappears, scans bail
    out instead of reporting every file missing, so stored `sourceMissing` flags stay as they were.
    The "unavailable" states above are what tell the user, and nothing is deleted or corrupted.

### 6. The two Todo policies are missing from Create Tasks — *implemented*

- **Where:** the Todo card's overflow menu (⋮) holds **Follow the upstream** and **Keep decisions
  when deleted**; neither appears in the Create Tasks dialog that made the Todo.
- **What got in the way:** both are decisions about the Todo, and the moment the Todo is made is
  when the user has the folder and the intent in mind. As it stands the dialog decides the
  grouping, the change policy, the export and the templates, but the other two standing answers
  can only be changed afterwards, from a menu on a card the user has to find first. Follow the
  upstream in particular is currently seeded silently from a Settings default, so a Todo can come
  into existence already syncing itself without that having been said in the dialog.
- **What is expected:** both switches are offered in the Create Tasks dialog. They do not stand as
  two more flat rows: they join the same graded layout as everything else (entry 1), in the large
  configuration section they belong to — the user's examples are **Sync** and **Others** — so the
  dialog stays a short list of sections with their answers, each one tap from its options.
- **Note:** this is not a new capability; both policies already exist and are already writable.
  What changes is where they are offered and how they are grouped.

### 7. The Todo card carries more than a card should — *deferred*

- **Reported together with entry 6; recorded separately because the status differs.**
- **Where:** each Todo card on the Todo tab.
- **What got in the way:** under the name the card prints four standing lines — grouping, folder
  and Task count; last run; the change policy; the attached templates with button counts — before
  the action row. Read once they are useful, but they turn a list of Todos into a form, and every
  future fact adds another line. The action row sits further down than it should.
- **What is expected:** same treatment as entry 3 — later, the standing detail retreats behind a
  `?` / `i` affordance (or an expanding card), leaving the name and the one or two facts a user
  scans for. **Not this round** — recorded so the 0.6.2 card layout leaves room for it.

### 8. Webhook is a method with no address to configure — *implemented*

- **Where:** Create Tasks → *When a round over this Todo finishes* → **Webhook**; afterwards, the
  Todo card's ⋮ menu; Settings → Exports → Webhook.
- **What got in the way:** choosing Webhook creates a Todo that exports to a URL the dialog never
  asked about. The row explains *when* the trigger fires and says nothing about where to post, so
  the Todo is created believing it will export while nothing may be configured. There is no way to
  give one Todo its own address: the only address in the app is the Settings default.
- **The two questions asked of the current build, and its answers:**
  - *A Todo chose "use default"; the default is edited later. Where does its next webhook go?* —
    To the new value. The address is read from Settings at send time.
  - *A round is now a history record and the Todo or List is deleted. Which webhook does Resend
    use?* — Whatever the Settings default is now. The record keeps the body and the outcome but not
    the address, so a changed default silently redirects a replay.
- **What is expected:** the address becomes a fact of the Todo, taken when it is configured:
  *use default* copies the default as it stands then, and later changes in Settings reach no
  existing Todo. The Todo's own settings surface (today the ⋮ menu) shows the address it holds and
  lets it be changed; the change governs later webhook exports from that Todo, Quick Review rounds
  involving its Tasks, and the webhook exports of Lists holding them. A List with no address of its
  own follows its Todos; a non-empty List address is a deliberate override, edited on the List's
  own export configuration. A history record keeps the address it used, and **Resend offers that
  address prefilled and editable** — so an invalid URL can be corrected for that one replay
  without editing the Todo, and the correction is temporary. Settings' *Default enabled* means
  "preselect *use default* when configuring", not
  "attempt webhooks"; with it off the custom URL field is focused. Choosing Webhook opens that
  configuration; *use default* with no default URL refuses at Create.
- **Status:** the full decisions, the schema change and the delivery/history work are recorded at
  the top of this document, because they must land before the UI is rearranged.

### 9. History is scattered across configuration pages and does not show what belongs together — *implemented*

- **Where:** Settings → Exports (History card), Settings → Exports → Webhook (History card), and
  Settings → Exports → Txt (History note). All three lead to one screen.
- **What got in the way:** history is a record of what the app did, not part of configuring how it
  does it. Sitting it inside the Webhook and Txt pages makes two configuration screens double as
  archives, and the same screen is reachable from three doors. On the screen itself, one export
  round can produce several actual exports — different Todos, different methods — but the rows are
  shown as unrelated entries. Nothing says *these three records were one round*.
- **What is expected:** one History entry, at the bottom of Settings' main screen; the History
  cards disappear from the Exports, Webhook and Txt pages. Storage stays one record per actual
  export — never one merged record — but the records of one round are linked, and the screen shows
  that link either as a parent row that expands into the actual exports, or as *1 / 2 of export …*
  on each row. The full decision, the new round id and the display choice are recorded at the top
  of this document.

### 10. Settings mixes an index with a form — *implemented*

- **Where:** the Settings tab's main screen.
- **What got in the way:** the screen is uneven. **Templates** and **Exports** are index rows that
  open a page of their own, but **Upstreams**, **Review**, **Media and review behaviour**, **Todos**
  and **File management** spill their controls directly into the scrolling page — seven switches,
  six on one card, an add-upstream flow and the checked-file cleanup tools, all at the top level.
  The two hierarchies read as the intended shape and the inline cards as the exception, so the
  screen looks like a form with two links in it rather than an index.
- **What is expected:** one shape everywhere. Settings' main screen shows only the outermost
  information — one row per category, with the category's name and a one-line state summary, the
  way Templates and Exports already read. Tapping a category opens a page that holds all of that
  category's settings. No switch, add button or cleanup tool stays on the main screen.
- **Note:** no schema or delivery change. This is navigation and state hoisting: the new pages need
  the same survive-a-tab-switch treatment the existing nested Settings pages already have, and the
  History entry from entry 9 sits at the bottom of this index.

### 11. Refresh Import promises a newer template version and then keeps the old one — *implemented*

- **Where:** the template step of the Refresh Import dialog, reached from a Todo's ⋮ menu.
- **What got in the way:** a Task keeps the template version it was imported under, which is the
  designed snapshot and the reason a review of an older List still shows the old tag names. The
  intended way to carry a Todo forward is Refresh Import, and the dialog says so: the row is ticked
  and reads *"Held at version 1. This run will attach version 2."* But the run only picks up
  version 2 if the row is unticked and ticked again. The draft is seeded from the Todo's stored
  references, the picker replaces a reference only in response to a toggle, and the confirm button
  submits the draft untouched. Confirming therefore re-stamps version 1 onto every Task the run
  touches, and the List review keeps showing the old template — while the dialog said otherwise.
- **Why it matters:** this is the only path by which an existing Todo adopts an edited template, so
  as it stands that path does not work from the UI; the row's promise and its behaviour disagree,
  and the failure is silent and durable because a refresh re-stamps the Tasks it touches.
- **What is expected:** leaving a ticked row alone attaches the version the picker currently
  offers, exactly as the row says — on confirm, each held reference whose lineage is still offered
  and ticked is replaced with that lineage's current version. A lineage the picker no longer offers
  keeps its held reference. The alternative — correcting the copy to say the old version stays — is
  rejected: it would leave no way to adopt a template edit, and `docs/templates.md` already defines
  refresh as re-asking and re-stamping.
- **Note:** no schema change. The fix belongs with the other delivery and flow work of this round,
  but it is a defect today, not a presentation preference.

### 12. A refresh re-labels Tasks that were already reviewed — *decided, keep*

- **Where:** the version question that follows from entry 11.
- **What was asked:** a Todo holds Tasks reviewed under version 1; the template is edited and the
  Todo refreshed; new Tasks are reviewed under version 2. What does the next export say about each
  Task's template?
- **The behaviour, kept deliberately:** a Task carries the template reference stamped by its last
  import or refresh, and a refresh touches every Task still in the folder. After it, **all of that
  Todo's Tasks report version 2 on the next export**, including the ones whose marks were made under
  version 1. The package carries no per-mark version provenance; only a Task the refresh no longer
  touches (its file is gone and the content policy keeps it) still reports version 1.
- **Why keep it:** one run, one control. A refresh is the moment the user says *move this Todo and
  its Tasks forward*; letting one Todo hold two live versions would make Quick Review show one Task
  whose chip row differs from the next and make "which template governs this Todo" unanswerable.
  The export states what governs a Task now, not the history of how it came to be marked.
- **What the UI must say:** a refresh that will move a held version must state, before confirming,
  that Tasks already marked will be read under the new version. If the new version only renames
  buttons, the wire values are unchanged and nothing material moves; if it adds or removes buttons,
  marks on a removed button become invisible and unsent (never rewritten), and a new button starts
  unmarked. This is a copy requirement on the Refresh Import dialog, not a delivery change.
