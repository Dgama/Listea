# Listea v0.5.2 — Implementation plan

> **Status:** Plan, implemented. **The release it describes has shipped.** Where the shipped code
> departs from this document the departure is recorded in place rather than left for a reader to
> find — §0 decision 8 and §4 are the one so far.
> **Audience:** Coding agent and maintainers
> **Specification:** [v0.5.2.md](v0.5.2.md)

## Framing

One defect, one shape of repair, and it is the shape already decided in
[v0.5.1-plan.md](v0.5.1-plan.md) §9: the history carries the pair records as an encoded payload.
This plan is about doing that without adding a second model of the record to maintain — which is
what the defect is made of, and the thing the repair must not repeat.

## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | The history stays **one row per Task** | The alternative — a row per pair — was rejected in §9 for being a second model of the record. The Task is also the right unit for everything else the row carries: the completion, the group path, the Todo it belonged to |
| 2 | The records go in **one encoded payload column**, with the encoding's **version** beside it | §9's chosen shape. The version is `review_events`' move — `templateId` and `templateVersion` stored so a payload is never read without knowing what wrote it |
| 3 | A file is named by its **`relativePath`** | Asset ids are minted per import (`UUID.randomUUID().toString()`) and a recovery runs after the old Assets are gone, so they cannot match. The path is what the import itself matches on to keep an Asset's identity across a re-run, which is the property v0.5.1 already rests on |
| 4 | The retired mark columns **come off** the table in this step | A column nothing reads is exactly what caused this defect. `dissolved_task_state` has no third-party reader, and the rebuild is the honest option; leaving them would be carrying v0.5.1's compromise forward with none of its justification |
| 5 | `isCompleted` **stays** | Completion is the Task's, before and after this release. It is the one thing the old snapshot recorded correctly, and it goes on being recorded the same way |
| 6 | A history written **before** this release gets an **empty payload** | Its marks were Task-level and there is no honest per-file answer. Spreading them across the recovered Task's files would be v0.5.1's bug through the recovery door |
| 7 | An Asset whose `relativePath` is **null** is left out of the payload | It cannot be named, so it cannot be matched on the way back. Unreachable in practice — every import writes a path — but the column is nullable, and a payload that cannot be decoded is worse than one that is short |
| 8 | The recovery's Task-level write **stops touching the two retired columns** | Nothing reads them, and a mark written there is a Task-level answer on a path whose whole point is that the answer belongs to a file. Made while building; see §4 |

## 1. The payload, and its codec

A new file, `data/DissolvedRecords.kt`, holding the format and nothing else. Version `1`.

```
<escaped relativePath> \t <0|1 isFavorite> \t <encodedActionIds>
```

Lines joined by `\n`; `''` means no files. The action ids are `encodeActionIds`' existing encoding,
so a record inside a payload is spelled the same way one is spelled in `task_asset_state`.

**Escaping.** A path is a user's filename and may contain a tab, a newline or a `%`. All three are
escaped (`%25`, `%0A`, `%09`) so the line and field separators stay unambiguous; decoding is a single
left-to-right pass, so `%25` and a literal `%0A` cannot be confused. An unknown `%XX` decodes to
itself rather than throwing, because a payload that fails to decode is a history that cannot be read
at all.

**The version is checked, never assumed.** `decodeDissolvedRecords(encoded, version)` returns `null`
for a version it does not know. The caller then restores completion and no marks, which is the same
answer a pre-release history gets, and is a partial restore rather than a guess.

Both directions are pure functions over strings and belong in a test of their own.

## 2. The schema, and `MIGRATION_21_22`

`DissolvedTaskStateEntity` loses `isFavorite` and `customActions` and gains:

| Column | Holds |
|---|---|
| `recordVersion` | `1`. The version of the encoding in `records` |
| `records` | The payload, `''` for a history with no files |

SQLite before 3.35 has no `ALTER TABLE … DROP COLUMN` and `minSdk = 24` ships 3.9, so this is the
standard rebuild: create `dissolved_task_state_new` with the entity's shape, copy every row with
`''` and `1`, drop the old table, rename, and recreate **both** indices (`sourceId`, and
`(rootUri, sourcePath)`) — Room compares the created schema against `22.json` and an index left
behind is a migration that fails on open rather than on the first query.

The table has no incoming foreign keys and, on the attached device, **no rows at all**, so the copy
is trivial — but it is written and tested as though it were not, because a user's database is.

## 3. The snapshot write path

`snapshotDissolvedState` stops being one `INSERT … SELECT` and becomes read-then-write, which is the
move `recoverStateFrom` already makes in the other direction for the same reason (no `UPDATE … FROM`
before SQLite 3.33).

1. One query: every Task of the Todo, with its `groupPath`, its completion, and one row per Asset —
   `LEFT JOIN assets` and `LEFT JOIN task_asset_state`, so a Task with no Asset still yields a row
   and a Task whose Assets exist without records still yields one per Asset with the defaults.
2. Group by Task, drop the rows with a null path (decision 7), encode each Task's records.
3. `INSERT` one row per Task, with `recordVersion = 1`.

The read happens inside `deleteTodo`'s existing transaction, before anything is removed — the
ordering the current comment already states as the whole of the safety.

## 4. The recovery read path

`recoveryMatches` selects `recordVersion` and `records` in place of the two retired columns. For each
match:

1. Write the completion to `task_state`, exactly as now.
2. Decode. `null` (an unknown version) ends this match here — completion only.
3. For each `(relativePath, decisions)`: find the new Task's Asset at that path and write the record
   through the existing `writeAssetState` funnel. A path the new import did not produce matches no
   Asset and writes nothing, which is the existing per-Task rule now applied per file.

`writeAssetState` is reused rather than a new query added: it is already "the only way a pair is ever
changed", it reads inside the caller's transaction, and it no-ops on an Asset that is not there.

**The write behind step 1 narrowed while it was built, and this is that record.** It used to update
`isCompleted` *and* the two retired columns; it now updates `isCompleted` and `updatedAt` and leaves
those two exactly as `writeTaskState` leaves them. Nothing reads them, so this is not a fix — it is
refusing to leave a Task-level mark behind on a path whose whole point is that a mark belongs to a
file. A recovery that wrote one would be one migration away from marking every file of a Task at
once, which is the defect this release is repairing. The plan said *"exactly as now"*; the honest
reading of that was the completion, and the columns are a departure recorded here rather than
discovered later by whoever finds a stale `★` in a dead column.

## 6. What is not touched

- **The pair record itself** — `task_asset_state`, its encoding, `setAssetAction` and
  `writeAssetState`. This release changes where a *history* keeps them, not what they are.
- **Completion, and where it lives.** `task_state.isCompleted` is read and written exactly as now.
- **The picker.** `dissolvedHistoriesAt` selects no mark columns and is unchanged.
- **`review_events`, `webhook_history`, and the payloads they snapshot.** They are the precedent this
  release follows, not things it changes.
- **Everything from v0.5.1** — the per-pair record, the folds, the surfaces. This is the debt v0.5.1
  recorded against itself and nothing more.

## 7. Order of work

1. The codec and its test, alone, before anything calls it.
2. The entity, the schema step and `22.json`, with `MigrationV21ToV22Test` and the chain green.
3. The snapshot path, with the two read queries it needs.
4. The recovery path.
5. `HistoryRecoveryTest` rewritten onto the pairs, and `HistoryRecordsTest` written for what it can
   no longer see.
6. On a device, against a Todo whose Task holds more than one file — the shape this whole rule is
   about.
