## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | The Select gate becomes a **named predicate on `CatalogView`**, not an inline condition | The condition is the whole of the defect, and an inline one in a composable cannot be asserted — this project has no Compose UI tests. A function in `Catalog.kt` beside `catalogAtScope` can be, and the screen then reads it rather than re-deriving it |
| 2 | Quick Review's gate **does not change** | It is correct, and for a different reason: a round queues the Tasks that lie exactly here and does not descend, so a folders-only root really has nothing for it. The two look alike and are not |
| 3 | `refreshCompletion` is called from the **four** writes that lack it, rather than the flag being derived on read | Every write that can change the answer already calls it; the four are the gap, not the rule. Deriving it on read would put the answer in two places and make the stored column decorative — and the column is what `observeSummaries` groups by in SQL, so it would have to be recomputed per row per emission anyway |
| 4 | `addTasksToList`'s **early return stays** | `additions.isEmpty()` means the membership did not move, so the answer to "are all of them done" cannot have changed. The refresh goes after the insert, where the membership actually moves |
| 5 | An **emptied** List becomes *In progress* | `refreshCompletion` already refuses to call a List with no members complete, and `applyReconcile` / `removeMissingSourceItems` already put Lists in that state. Calling it from a dissolution makes the four writes agree with the four that already do, rather than inventing a rule |
| 6 | A **data-only step, 22 → 23**, repairs the rows that already drifted | The four call sites fix the bug; they do not fix the databases it already corrupted, and the reporter's own List is one of them — `3 / 3` with `completedAt` null, on the device, verified. A migration is where this project does one-time data work and Room requires a version bump for one, but **no table changes shape**: the step costs a version number and nothing structural. Made while building; see §2b |
| 7 | The two confirmed answers are **recorded, not built** | §3 of the spec. Both were asked about and answered *as intended*; the release's job is to write them down where the next reader will find them, and to pin the first with a test |

## 1. The Select gate

`Catalog.kt`, beside `catalogAtScope`:

```kotlin
/**
 * Whether this scope offers a way into picking.
 *
 * A Task at this scope is something to pick, and so is a folder below it — a folder's box takes
 * the whole folder, which is what makes a scope of folders the place a selection is most useful
 * rather than the place it is unavailable. Quick Review's question is narrower for a reason of its
 * own: it queues the Tasks that lie exactly here and does not descend, so a folders-only root
 * really has nothing for it. The two are deliberately not one function.
 */
fun CatalogView.offersSelection(): Boolean = tasks.isNotEmpty() || scopes.isNotEmpty()
```

`CatalogScreen.kt:221` becomes:

```kotlin
if (selecting || view.offersSelection()) {
```

The comment above it keeps its first paragraph — *"Offering a List of nothing is the same mistake
one step further on"* — and loses the second, which reasons only about `tasks`. It is replaced by
the reason the two gates differ, because that is the sentence whose absence caused this.

The `selecting ||` half stays and is load-bearing on its own: descending into an empty folder
mid-selection must not strand the user in a mode with no way out.

## 2. The stale completion flag

Four edits in `data/ListsDao.kt`, each one line, each at the end of the write's transaction:

| Function | Line | Added |
|---|---|---|
| `createListFromTasks` | 544 | `refreshCompletion(listId, now)` before `return listId` |
| `addTasksToList` | 584 | `refreshCompletion(listId, now)` after `insertItems`, beside `clearDissolutionNote` |
| `deleteTodo` | 1801 | for each row of `held`, after `noteDissolution` |
| `dropTask` | 1965 | for each row of `held`, after `noteDissolution` |

The two removal sites already loop over the Lists that lost rows and already write a note to each;
the refresh goes in that loop rather than in a second pass over the same list. `membershipChanged`-style
extraction is not needed — `noteDissolution` and `refreshCompletion` are two sentences to the same
address, and a helper that did both would have to be named for neither.

`refreshCompletion` is `open`, already `@Transaction`-safe inside a caller's transaction, and takes
`(listId, now)`, which both loops already have in hand.

**Ordering is not load-bearing.** It reads `list_items` and `task_state` after the deletes and the
inserts, which is what the four existing call sites do; a note written before or after it changes
nothing, so it goes after, where the loop is already writing.

## 2b. The rows that are already wrong

The four call sites are the fix. They are not the whole of it, because a flag that was written wrong
stays wrong until something writes it again — and the List the defect was reported from is sitting on
a device right now reading `3 / 3` under *In progress*. Nothing in the release above would move it.

So `MIGRATION_22_23` repairs every List in the database, with no DDL: a List with rows and none
unfinished is completed, and one with no rows at all or any unfinished row is un-completed. Those two
statements are `refreshCompletion` written as SQL, because a migration cannot call a DAO, and they
mirror `itemCount` and `unfinishedItemCount`'s join so that a reader can diff them.

**The timestamp for a repaired row is the upgrade.** The moment it really became complete was never
written down, and `completedAt` is not only read for null-ness — `Webhook.kt` sends it. An invented
earlier value would be a worse answer than an honest "as of now"; rows that were already right are
not touched, which is what keeps a real completion time intact.

**The fixture does not hand-write the old schema**, which is the one place this deviates from every
other migration test here. A v22 database and a v23 one are the same database with a different number
in `user_version`, and that identity is this release's premise rather than its conclusion — so the
fixture is built by the app's own Room and then rewound, and `the step changes no table` asserts the
premise rather than assuming it. Copying four hundred lines of DDL to reproduce a schema that is
already correct would be pretending to a difference that does not exist.

## 3. Tests

New:

| File | Covers |
|---|---|
| `data/ListCompletionTest.kt` | The reported defect and its three siblings, through the seam the user's path reaches: **a List built from Tasks that are already done is complete** (the report), a List built from a mix is not, `addTasksToList` that finishes a List completes it, and **a dissolution that takes the last unfinished row completes the List** while one that empties a complete List un-completes it |
| `data/MigrationV22ToV23Test.kt` | The repair, against the five states the four writes could leave: completed, left unfinished, **already complete and keeping its own timestamp**, emptied, and recorded complete while still holding an unfinished Task. Every membership carries `list_items.isCompleted = 0` — the dead column — so a repair written against the wrong one completes nothing and says so |
| `CatalogScopeTest.kt` (extended) | `offersSelection` as a property of a scope: true at a folders-only root, true where both are, true at a leaf holding Tasks, **false for an empty scope and false for a flat Todo with no Tasks** — the two cases where it must not offer a List of nothing |

`TemplateMatchAfterRecoveryTest.kt` was written in the same session and is already green; it is the
test §3 of the spec points at, and this release neither changes it nor depends on it.

## 4. What is not touched

- **`ListDetailScreen`'s checkboxes.** They tick completion, which is a different question from
  selecting to build a List, and it is not this release's.
- **`refreshCompletion`'s own rule.** `itemCount > 0 && unfinished == 0`. The release adds callers.
- **Anything about templates, the payload or `dissolved_task_state`.** v0.5.2 is closed; this is what
  using it turned up. The migration chain gains a step and is otherwise untouched — every fixture
  that enumerates it by hand gains `MIGRATION_22_23`, for the reason recorded in
  [v0.5.2-plan.md](v0.5.2-plan.md) §5: Room opens at the current version whatever a fixture was
  written at, so a chain that stops one step short does not test the old schema, it refuses to open.
- **`docs/development.md`.** Its migration list stops at 18 → 19 and is left as it is.

## 5. Order of work

1. `offersSelection` and its tests, before the screen reads it.
2. The four `refreshCompletion` call sites, with `ListCompletionTest` written against the failure
   first — the reported defect reproduces without a device, so it can be watched going red.
3. The screen's one line.
4. The step and its test, with the four call sites already in — the repair is written against a
   known-good rule rather than ahead of it.
5. The full suite, then the device: the two shapes the release is about are a tree Todo and a List
   built from a recovered Todo, and both are reachable without disturbing the acceptance fixture.
   The migration is checked there too, because it is the half a unit test cannot prove: a real
   database, written by the shipped build, going 22 → 23 with the reporter's own List in it.
