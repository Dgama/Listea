# Listea v0.2.0 — Post-Implementation Architecture Review and Completion Contract

> **Status:** Final implementation contract for the remaining v0.2 architecture-completion work
> **Audience:** Implementation agent and maintainers
> **Supersedes:** the ad-hoc implementation-review findings, where explicitly noted below (see §1.6 and §5.1)
> **Specs it synthesizes:** [`../ARCHITECTURE.md`](../ARCHITECTURE.md), [`v0.2.0.md`](v0.2.0.md), [`v0.2.0-plan.md`](v0.2.0-plan.md)
> **Reviewed against:** working tree at `882ed4b`, full unit suite green (335 tests, 0 failures)

## Framing

**v0.2.0 is an architecture release, not a feature release.** Nothing a person can see is supposed to change. What changes is what the app believes it is doing when they do it.

The audit behind this document found that **persistence and state semantics are largely correct**. The database genuinely separates Task, Asset, ListEntry, TaskState and ReviewEvent; the migration is careful and well tested; every reader of current state resolves it through `task_state`; the webhook wire format is protected by code that is byte-identical to v0.1.

What is still incomplete is one level up. **The production review pipeline is database-shaped, not Task-shaped.** Below the DAO a Task is a first-class thing with its own identity. At the DAO's write boundary and above it, a Task is still addressed, resolved and sometimes *created* by one file's source locator. That is the last surviving piece of the `item == file == review unit` model this release exists to remove.

The release principle stands:

> **Same Listea outside, different Listea inside.**

with one clarification this review makes explicit: **"different inside" must include the production interaction and data flow, not only the Room tables.** A schema that separates Task from Asset, sitting under a write path that addresses Tasks by file path, has moved the ambiguity rather than removed it.

The goal of the remaining work is narrow and testable: make **v0.3 (PDF as a second Asset/viewer type)** and **v0.4 (one Task, many Assets)** *additive* — a new viewer and a longer list — rather than a second domain rewrite of the review pipeline.

## 1. Final reviewed verdict

### 1.1 Genuinely complete

- **Five separate persisted concepts.** `tasks`, `assets`, `task_state`, `review_events` and the rebuilt `list_items` carry five identity spaces. Task and Asset receive independent UUIDs even in the one-Task/one-Asset media case.
- **TaskState as the single source of current truth.** Every query that reports checked/favourite/custom-action state joins `task_state`: `observeSummaries`, `observeItems`, `getItems`, `observeFolderScopes`, `observeFolderScopeItems`, `observeFileStates`, `getFileStates`, `observeFileCompletion`, `unfinishedItemCount`. The legacy decision columns on `list_items` and `file_review_state` are carried across the migration and read by nothing — pinned by three explicit "a stale column is never the answer" tests.
- **ReviewEvent is a submission, not a mutation log.** `insertReviewEvent` has exactly one caller, `ListsDao.submitReview` (`ListsDao.kt:220`). List Detail checkboxes, favourite toggles, custom-action toggles, unchecking, navigation, resync and webhook delivery all write state and no event.
- **Navigation is pure.** `goTo` (`ReviewScreen.kt:516`) sets the current task id and the List's resume cursor, and does nothing else. `finished` is set only inside the completion handler at the last index. Reaching the final Task by navigating does not end the round; the forward control is disabled there.
- **Templates.** `TemplateKind.ASSET_VIEWER` and `TemplateKind.TASK_REVIEW` are distinct; versions are immutable, enforced by a content-hash test that fails the build on an in-place edit; the List persists the exact `(templateId, version)` a submission is recorded under.
- **Manual-item and standalone-List creation removed**, with the legacy set named by `legacy_manual_tasks(taskId)` rather than inferred from `assetCount == 0`.
- **Migration v12 → v13.** Real v12 schema exported before the version bump; Room validates the migrated result against the entities; every legacy row shape covered by a realistic raw fixture; public IDs byte-identical and still attached to the same rows; no fabricated ReviewEvents; older data-transforming migrations covered by v7 and v9 chain fixtures.
- **Webhook compatibility.** `Webhook.kt`, `FileManagement.kt`, `FolderListStatus.kt`, `MainActivity.kt`, `Settings.kt`, `SwipeCard.kt`, `MediaPreview.kt`, `MediaZoom.kt`, `VideoControls.kt` and `FileArrange.kt` are **unchanged from v0.1**. Only the inputs to the payload builder moved. The body is additionally pinned byte-for-byte by `WebhookBodyTest`.

### 1.2 Confirmed correct by targeted verification

Beyond the standing suite, the review ran throwaway probes against the real schema (since deleted; no production code was modified):

- Deleting a List leaves its files' Tasks and their state intact.
- Rebuilding a List over the same folder reuses the same Tasks and Assets — no duplicates, state preserved.
- Two Lists over the same folder share one Task per file.
- Entering Quick Review over a folder heals the registration gap described in §1.4.

### 1.3 Structurally incomplete

| | Finding | Effect |
|---|---|---|
| **W1** | Task-level writes are addressed by `(rootUri, relativePath)` | A Task is identified for judgment by one Asset's location |
| **W2** | `taskForContent` mints a Task+Asset on a *write* path when the locator misses | An unresolvable locator silently creates a second Task instead of failing |
| **W3** | `AssetNavigator` (`ReviewScreen.kt:702`) is a pass-through with no Asset collection and no dispatch point | There is nowhere for a second viewer to be chosen |
| **W4** | `AssetViewer` (`ReviewScreen.kt:740`) and `ItemPreview` (`ReviewScreen.kt:961`) take the Task-shaped `ReviewItem` and dig Asset fields out of it | The viewer boundary is not addressed by an Asset |

W1 and W2 are the same defect seen from two sides, and they sit inside the state-and-history core — the part of v0.2 guarded by the most tests (`ReviewSubmissionTest` 12, `CurrentStateTest` 19, `ListsDaoTest` 16). That is precisely why they must be fixed now rather than in v0.4: deferring them means re-proving 47 tests later, against semantics nobody will have in mind.

### 1.4 Blocker

**F1 — checked-file readers require a `file_review_state` registration row that the review surface no longer writes.**

`getCheckedFilePaths` (`ListsDao.kt:503`) and `observeCheckedFileCount` (`ListsDao.kt:514`) inner-join `file_review_state`. In v0.1 every completion path created that row, because swipe and checkbox both ran through `setFileCompleted` → `writeFileState` → `registerFiles`. v0.2 correctly forked submission off state-writing but left the registration side effect only on the state-writing branch, so `submitReview` never registers.

Reproduced: create a folder List, submit a review on one file. `task_state.isCompleted = 1` and List Detail shows it checked, but `getCheckedFilePaths` returns `[]` and `observeCheckedFileCount` returns `0`.

User-visible consequence: after swiping through a List Review, Settings → File management reports **0 checked files** and "Delete checked files" says nothing is checked. It heals as soon as anything registers those files. Not data-destructive — it under-reports and never over-deletes — but it breaks a documented feature and is a straight regression against v0.1.

The reason 335 tests missed it: every existing checked-file test calls `registerFiles(...)` in its setup.

### 1.5 Accepted debt

Recorded in §6. None of it blocks release, and none of it is made harder by the completion patch.

### 1.6 Corrected interpretation of F2–F5

The first-pass audit classified four items. Re-derived against the concrete v0.3/v0.4/v0.5 roadmap, two of the four classifications change. **This section supersedes the earlier findings.**

- **F2 — "the pure domain data classes are unused."** True, but *not itself the load-bearing problem.* `Task`, `Asset`, `TaskState`, `ListEntry` and `ReviewEvent` in `domain/Domain.kt` have no production references; the working type is still `ReviewItem`. Replacing `ReviewItem` wholesale is presentation-layer churn the compiler would find, and it is **deferrable**. The real content of F2 is **W1/W2 above**: Task-level writes addressed by Asset locator. That is required now. → **N2.**
- **F3 — `TaskAction` dispatch is nominal.** **Optional and opportunistic.** PDF changes the viewer; multi-Asset changes the navigator; neither changes what completing a Task means. The type already exists, so adding dispatch later is additive. Worth landing only because N3/N4 rewrite the same call site. → **A1.**
- **F4 — `AssetNavigator` has no state.** **Half required now.** The *collection* and the *viewer-dispatch boundary* must exist in v0.2, because v0.3 needs somewhere to choose a PDF viewer. A `selectedAssetId` must **not** be invented now: its semantics (reset on Task change? persist in the round snapshot? survive process death?) cannot be designed without a real multi-Asset Task, and guessing them now guarantees rewriting them later. → **N3 + N4.**
- **F5 — `SwipeCard` lives inside `AssetViewer`.** **Incorrectly classified. This is not an architecture violation, and the earlier finding is withdrawn.** `SwipeCard` also owns the zoom state and hands it to its content; hoisting it above the viewer would move zoom ownership *up* into the review surface, which is worse, and would require modifying the leftover-pan arbitration the plan deliberately ring-fenced. The spec's rule — gesture *bindings* belong to the Task Review Template — is about who decides what a swipe **means**, and that is already `ReviewSession`, which supplies `onSwipeForward` / `canSwipeForward` as parameters. The viewer only arbitrates those against its own content gestures, which is its job under [Gestures and semantic actions](../ARCHITECTURE.md#gestures-and-semantic-actions). → **Deferred permanently as written**; see §5.1.

### 1.7 Required before manual release acceptance

**N1, N2, N3, N4**, plus the automated verification in §7. A1/A2/A3 are approved but not independently blocking.

## 2. Final domain-flow requirement

After the completion patch, the production flow must read as follows. Every element below already exists in the schema or the code; nothing here is a new abstraction.

```text
List / Quick Review context
        ↓
     ReviewTask
        │
        ├── TaskId              ← the address for every Task-level write
        ├── TaskState           ← current truth: completed, favourite, custom actions
        ├── ListEntry/context   ← membership, ordering, resume cursor
        └── Assets[]            ← presentation resources, 0..N
               ↓
        AssetNavigator          ← owns the collection; the single viewer-dispatch boundary
               ↓
         selected Asset         ← in v0.2 always the sole Asset; no chrome at 1 / 1
               ↓
          AssetViewer           ← renders exactly one Asset


Task-level write:
    TaskId  →  TaskState / ReviewEvent

Asset-level presentation:
    AssetId / source locator  →  viewer
```

Binding rules the implementation must satisfy:

1. **Task is the judgment unit.** Nothing else is judged.
2. **`TaskId` is the address for Task-level writes** — completion, actions, and review submission.
3. **Asset is a presentation resource.** It owns no judgment, no completion and no navigation.
4. **A source locator `(rootUri, relativePath)` identifies and resolves an *Asset*, never a Task.** It may still *lead to* a Task by resolving the Asset that belongs to one; it may not *be* the Task's address for a state or history write.
5. **ListEntry is membership and review context** — ordering, queue scoping, the resume cursor, and the legacy public item id. It is not Task identity and not Task state.
6. **TaskState is current Task truth**, one row per Task, always present.
7. **ReviewEvent is a submitted Task judgment**, append-only, carrying the exact TemplateVersion in force.
8. **AssetViewer renders one Asset.** It arbitrates content gestures (zoom, pan, scroll, playback, scrub) against the callbacks the review layer hands it.
9. **AssetNavigator owns the Asset collection boundary** and chooses the viewer.
10. **TaskNavigator owns Task navigation** — previous, position, next, back — outside every viewer, entered through explicit controls.

## 3. Required patch before v0.2 manual acceptance

### N1 — Fix the checked-file reader regression

**Status: confirmed blocker.**

`getCheckedFilePaths` (`ListsDao.kt:503`) and `observeCheckedFileCount` (`ListsDao.kt:514`) must derive checked state from `assets` + `task_state` and must **not** require a `file_review_state` registration row.

**Prefer removing the legacy reader dependency over adding another registration side effect to `submitReview`.** Registration is a folder-browse and public-id concern; adding it to the submission path would deepen a dependency this release is supposed to be retiring. Dropping the join is also the smaller change.

Shape (verified against the real schema during review):

```sql
SELECT a.relativePath FROM assets a
JOIN task_state ts ON ts.taskId = a.taskId
WHERE a.rootUri = :rootUri AND ts.isCompleted = 1 AND a.sourceMissing = 0
ORDER BY a.relativePath COLLATE NOCASE ASC
```

The probe confirmed this restores v0.1 behaviour exactly across all four write paths — it returns both the checkbox-checked and the review-submitted file, and still correctly excludes a registered-but-undecided file and a completed-but-missing one.

No public-ID impact: List Review sends `list_items.publicId`; folder review registers on entry, so `legacy_item_ids` is unaffected.

**Required regression tests — neither may call `registerFiles()` in setup:**

1. A folder List created in v13 → submit a review → checked paths and count are correct.
2. A **migrated** `list_items` row that had no historical `file_review_state` row → submit a review → same.

### N2 — Address Task-level writes by `TaskId`

**Status: load-bearing, required in v0.2.**

Introduce `TaskId`-addressed APIs, or equivalents:

```text
setTaskCompleted(taskId, completed, now)
setTaskAction(taskId, action, enabled, now)
submitReview(taskId, response, template, context, now)
```

Route the three ViewModel entry points through them: `setItemCompleted` (`ListsViewModel.kt:772`), `submitItemReview` (`:814`), `setItemAction` (`:832`). `ReviewItem.taskId` is already populated on both entry paths — List Review from `list_items.taskId`, Quick Review from `ensureTasksForFiles` — so this is plumbing an existing field, not deriving a new one.

**Requirements:**

- **Task-level state and history writes must not use `(rootUri, relativePath)` as their identity or address.**
- Replace the file-based list-scope lookup `listsContainingFile(rootUri, relativePath)` (`ListsDao.kt:929`) with a Task-based one, e.g. `listsContainingTask(taskId)`. Verified equivalent during review and index-backed by `index_list_items_taskId`: a file in two Lists returns both; a Task no List covers returns empty; two Lists over one folder share one Task.
- **`DecisionTarget.File` may remain** (`ListEntities.kt:364`) where it is still legitimately needed as a source-locator accessor for the webhook and folder-review compatibility paths — `toPayloadRow` (`ListsViewModel.kt:1289`) and `deliverFolderReview` (`:1240`). It must stop being the identity of Task-level judgment.
- **Explicitly prohibited:** any Task-level state or history write path that mints a new Task because an Asset locator failed to resolve. `taskForContent` (`ListsDao.kt:1299`) creating a Task+Asset is correct on *resolution* paths (folder listing, List creation, reconcile); it must not be reachable from a Task-level write.
- **Make `writeTaskState` (`ListsDao.kt:1253`) update-only.** `taskForContent` already inserts `task_state` at Task creation, so the insert branch is unreachable in normal operation. Making it explicit means a write addressed at a vanished Task is a silent no-op (zero rows updated) rather than a foreign-key violation.
- **Preserve the disappeared-Task behaviour:** no state and no event written, and **no silently created replacement Task**. `ReviewSubmissionTest`'s "a submission about a row that has gone writes no event and no state" must still pass, by the update-only route rather than by the current null-check.

### N3 — Make `AssetNavigator` a real collection boundary

`AssetNavigator` (`ReviewScreen.kt:702`) must receive an actual Asset-shaped collection — `List<ReviewAsset>` or an equivalent production type.

**In v0.2 it may:**

- render only the first/sole Asset;
- render **no** Asset chrome at `1 / 1`, per [§5.6 of the iteration spec](v0.2.0.md) and [Asset Navigator](../ARCHITECTURE.md#asset-navigator);
- render the existing `PreviewPlaceholder` for an empty collection;
- hold **no** `selectedAssetId` state.

**It must:** become the single viewer-dispatch boundary, so that v0.3 adds

```text
media → MediaViewer
pdf   → PdfViewer
```

as one branch, without touching the Task Review surface, the Task Navigator, the write path or the webhook boundary.

### N4 — `AssetViewer` receives an Asset, not a Task surrogate

Introduce the smallest Asset-shaped production value the current UI needs — the proposed `ReviewAsset` — and have `AssetViewer` (`ReviewScreen.kt:740`) and `ItemPreview` (`ReviewScreen.kt:961`) take it. There are only two `ItemPreview` call sites (`ReviewScreen.kt:762`, `ListItemViewerScreen.kt:89`).

Provide one function, `assetsOf(item): List<ReviewAsset>`, returning 0 or 1 today. **`ReviewItem` itself is unchanged.** In v0.4, `assetsOf` becomes a DAO-backed read of `assets WHERE taskId = ?` and everything above it compiles untouched.

`ReviewAsset` must contain **only** what presentation needs — source URI, display name, presence flag, and the cached size/modified metrics the info sheet and arrangement already read. Do not overdesign it.

**Do not add a persisted Asset kind in v0.2 to anticipate PDF.** The repository already has two classifiers — `MediaKind` (extension-based, filtering) and `previewKindOf` (mime-based, rendering) — plus the currently unused `domain.AssetKind`. A fourth mapping with no consumer is speculative. `ReviewAsset` carries `name` and `sourceUri`, which is exactly what both existing classifiers take; the current media classifier remains responsible for image/GIF/video behaviour. This matches the plan's standing decision that a persisted kind arrives when a second viewer actually needs one.

## 4. Opportunistic / cheap adjuncts

Approved if the patch already touches the same code. None is independently release-blocking.

### A1 — `TaskAction` dispatch

If N3/N4 rewrite the `ReviewScreen.kt:545` interaction call site — which they do — route the interaction through the existing `TaskAction` type rather than calling the ViewModel directly from each gesture lambda. Desirable because it removes an abstraction the live workflow currently bypasses, and because doing it later means editing these lines twice.

The invariant remains:

```text
raw input / gesture  →  semantic action  →  Task-level operation
```

### A2 — TaskState existence and count robustness

- Add the invariant test: **every ListEntry resolves to a Task with exactly one TaskState.**
- Make `unfinishedItemCount` (`ListsDao.kt:1386`) robust with `LEFT JOIN … COALESCE(ts.isCompleted, 0) = 0`, so it agrees with `itemCount` (`ListsDao.kt:1368`), which counts `list_items` outright. Today they disagree if a Task ever lacked state — verified to produce a 2-item List that renders one row and marks itself complete on that one row. Unreachable in current code, and largely subsumed by N2's update-only `writeTaskState`; do it only if it is genuinely trivial and consistent with total-count semantics.

### A3 — ReviewEvent response contract

Add a cheap test and KDoc stating that:

- a review submission writes **completion**;
- `favorite` and `customActions` in the response are a **snapshot of the current TaskState**;
- the submission call does **not** independently mutate those fields.

**Do not change behaviour.** Today the ViewModel sources both from `item.decisions`, so event and state agree; the gap is that the DAO's contract permits a caller to produce an event that disagrees. Documenting and testing the contract is the right fix at this size.

## 5. Explicitly deferred work

None of the following is required for v0.2, and each stays additive after N1–N4.

| Deferred | Why it remains additive |
|---|---|
| Wholesale replacement of `ReviewItem` | With N2 done, the residue is presentation-layer churn the compiler finds site by site. No state, history, migration or webhook semantics depend on it. |
| Routing every production type through the pure domain data classes | Same reason. The types exist and compile; adopting them is mechanical and can be done incrementally. |
| Database-backed `ReviewItem.assets` | `assetsOf` (N4) is the seam. Swapping its body for a DAO read changes nothing above it. |
| `selectedAssetId` / multi-Asset selection state | Additive once N3's collection exists, because `AssetNavigator` will already be the only thing holding the list. Its semantics cannot be designed correctly without a real multi-Asset Task — see §9. |
| Persisted `AssetKind` | The architecture already says a persisted kind arrives with the second viewer. Adding it in v0.3 is a column plus a backfill of a value the renderer can already derive. |
| PDF viewer | v0.3. After N3, it is one dispatch branch and one new composable. |
| Full template-driven UI generation | v0.5. Explicitly a non-goal of v0.2, and `TemplateVersion` already carries the action set a later surface would read. |
| Broad ViewModel / repository rewrite | Non-goal of v0.2 and unchanged by this patch. |
| **Hoisting `SwipeCard` above `AssetViewer`** | See §5.1 — this was a misclassification, and the current arrangement is correct. |
| v14 cleanup migration / legacy-column removal | The legacy columns have no live reader. Removing them is a separate, independently testable release. **Do not create v14 in this patch.** |

### 5.1 Correction to the earlier F5 finding

**Viewer-owned gesture arbitration is appropriate.** The earlier finding that `SwipeCard` living inside `AssetViewer` is an architecture violation is **withdrawn**.

The Task Review layer owns **the meaning** of review gestures — `ReviewSession` decides that a forward swipe means `CompleteTask` and a back swipe means `PreviousTask`, and supplies those as callbacks. The Asset Viewer owns **arbitration** of those callbacks against the interactions its content needs: zoom, pan, scroll, playback, scrub. That division is exactly what [Gestures and semantic actions](../ARCHITECTURE.md#gestures-and-semantic-actions) describes.

Hoisting `SwipeCard` would have moved zoom-state ownership up into the review surface — architecturally worse than the thing it was meant to fix — and would have required modifying the leftover-pan arbitration the plan explicitly ring-fenced.

**v0.3 note.** `SwipeCard` bundles zoom-state ownership with horizontal-swipe arbitration. A PDF viewer will need vertical scroll and may need a different zoom model, and **must not be forced to reuse `SwipeCard` wholesale**. It is free to implement its own arbitration against the same review callbacks. The contract a viewer must honour is the callback signature and the meaning behind it, not the mechanism.

## 6. Accepted technical debt and known limitations

Recorded so a later reader does not mistake them for oversights. None is a blocker.

1. **`ReviewItem` remains a mixed presentation/read model.** Its `id` field means `list_items.id` in List Review and `file_review_state.id` in Quick Review. After N2 it is no longer the write address, which is what mattered.
2. **`ListItemEntity` still carries several roles** — Room row, carrier for a projection whose decision fields come from `task_state` rather than from the identically-named physical columns, and webhook payload DTO (`toPayloadRow` constructs one with `taskId = ""`). Guarded by tests today; fragile to future edits.
3. **Legacy persistence columns remain.** `list_items.isCompleted/isFavorite/customActions` and `file_review_state`'s decision columns are frozen migration residue with no live reader. Deliberate, per the plan: they are the only remaining copy if the migration is ever found wrong.
4. **No true multi-Asset selection yet.** By design — see §9.
5. **No Compose UI coverage** unless added during this patch. Navigator hierarchy, absent `1 / 1` chrome, disabled-next and the zero-Asset placeholder are read-verified only.
6. **`IN (:paths)` >999 exposure remains out of scope.** Pre-existing since v0.1; `minSdk` is 24 and SQLite's pre-3.32 limit is 999. v0.2 added two more queries on the same path without changing the threshold.
7. **Task title ownership remains deferred.** Titles stay on `list_items.title` and the folder listing; moving them would touch the webhook `title` field and the reconcile diff for no v0.2 benefit.
8. **Package namespace cleanup remains deferred.** `com.example.listea`. A release blocker eventually, not for this patch. `versionCode`/`versionName` must be set before any build ships.
9. **Known issue — orphaned `review_events` on legacy manual-Task deletion.** `review_events` has no foreign key to `tasks`; the `legacy_manual_tasks` cleanup deletes `tasks` rows, leaving events with a dangling `taskId`. Nothing reads them, so there is no present impact, but "history is never deleted" and "history stays attributable" pull in opposite directions here. **Unresolved and named.** Resolve it in whichever release introduces a review-history reader; do not resolve it in this patch.

## 8. Manual acceptance after architecture completion

Only what cannot be established from code, schema or host-side automation. **M5 must run after N1.**

**Preconditions for all:** debug build on a device or emulator; a real SAF grant containing at least one JPEG, one animated GIF, one MP4, and five or more files.

**M1 — Navigator layout and chrome.** Folder tab → create a List from a folder of ≥5 files → Lists → open → Review. Observe the top bar; tap the media to hide and show chrome.
*Expect:* back arrow, filename, `‹`, `N / M`, `›` on one line without truncation in both orientations; `‹` greyed on the first Task, `›` greyed on the last; **no second counter anywhere**; chrome fades without the media re-decoding or a video restarting.
*Validates:* Task Navigator outside the viewer, no redundant Asset chrome, ends-of-queue disablement. *Severity if it fails:* Medium; High if a control is unreachable.

**M2 — Gesture arbitration on real touch hardware.** In Review: pinch-zoom, pan to each edge and keep panning, scrub a video near the screen edges, then swipe left cleanly on an unzoomed image.
*Expect:* panning a zoomed image never advances the Task; only leftover pan past the edge moves the card; video transport keeps its drags; a clean left swipe still checks and advances.
*Validates:* Task navigation does not steal viewer gestures. *Severity if it fails:* High — it would mean a v0.1 behaviour broke.

**M3 — Image, GIF and video rendering.** Step through the JPEG, animated GIF and MP4 in both the review surface and the browse viewer. Open a legacy manual item if one exists.
*Expect:* GIF animates; video honours the autoplay/mute settings; zoom works; the zero-Asset placeholder appears rather than a crash.
*Validates:* Coil/Media3 behaviour Robolectric cannot exercise; zero-Asset representability. *Severity if it fails:* High.

**M4 — Real installed v12 → v13 upgrade.** *Take a device backup first — there is deliberately no in-app rollback.* Install v0.1, create a folder List, check items, favourite one, set a custom action, let one source go missing, leave a manual item and a standalone List present, send one webhook. Install v0.2 over it.
*Expect:* every List present with the same title and progress; checks/favourites/actions intact; missing source still flagged; manual item still readable, reviewable and deletable; standalone List usable; webhook history unchanged; resume returns to the same item.
*Validates:* the migration against a database Room actually wrote. *Severity if it fails:* Critical — data loss.

**M5 — Real SAF destructive file operations.** *Run after N1.* Check 2–3 files **by swiping through List Review only** — no Quick Review, no List Detail checkbox. Settings → File management.
*Expect:* the count equals the number swiped; "Delete checked files" lists exactly those; after deletion the files are gone, the rows show *source missing*, and decisions survive.
*Validates:* N1 end to end, plus SAF delete permissions no host test can reach. *Severity if it fails:* High.

## 9. v0.2.5 recommendation — multi-Asset media-only stress test

**This is an architecture stress test, not a new product direction.**

Before introducing PDF, validate the Task/Asset architecture using **only the already-supported media viewer**, so that multi-Asset behaviour is exercised without a second renderer's complexity confounding the result. If Task/Asset separation is going to break, it should break against three JPEGs rather than against a PDF renderer.

**Proposed test Task shapes:**

```text
Task A  →  2 images
Task B  →  3 images
Task C  →  5 images
```

**Minimum real multi-Asset behaviour v0.2.5 introduces:**

- one Task owns multiple Assets;
- `AssetNavigator` enumerates them and renders a real selector when there is more than one;
- the selected Asset can change **independently of the current Task**;
- TaskState remains attached to the Task, never to an Asset;
- completing and reviewing the Task remains Task-level regardless of which Asset is on screen;
- Task navigation and Asset navigation are **visibly distinct** on screen;
- switching Assets creates **no ReviewEvent** and alters **no TaskState**;
- webhook and result behaviour remain Task-based;
- **no PDF support.**

**What it validates:**

```text
Task navigation  ⟂  Asset navigation  ⟂  Task judgment
```

These three are independent dimensions. v0.2 can only assert the first and third, because every Task has exactly one Asset and the middle dimension has no degrees of freedom. v0.2.5 gives it degrees of freedom while every other variable stays fixed — which is what makes it a controlled test rather than a feature.

It is also where `selectedAssetId` semantics get designed against a real case: whether selection resets on Task change, whether it belongs in the round snapshot, and whether it survives process death. Answering those with a real multi-Asset Task in front of you is the reason §5 defers them rather than guessing now.
