# Listea v0.5.1 — Implementation plan

> **Status:** Plan, for implementation. **No production code or schema is changed by this document.**
> **Spec:** [`v0.5.1.md`](v0.5.1.md) — the Task–Asset pair, and why the record lives there
> **Builds on:** v0.5.0 (the template; the three bands), v0.4.0 (ownership; a List that spans Todos)
> **Inspected:** `data/TaskEntities.kt`, `data/ListEntities.kt`, `data/ListeaDatabase.kt`,
> `data/ListsDao.kt`, `data/CatalogRow.kt`, `data/ReviewAsset.kt`, `ReviewScreen.kt`, `MediaUi.kt`,
> `ListsViewModel.kt`, `QuickReview.kt`, `Settings.kt`, `Webhook.kt`, `ListDetailScreen.kt`,
> `ReviewArrange.kt` at `59589fb`

## Framing

The specification's claim is that the template's instance is recorded per Task–Asset pair, and that
nothing outside the template moves. Everything here follows from it:

> **The record is the Task's state, filed under one of its Assets. The Task owns it; the Asset keys
> it.**

> **`task_state` keeps completion. `task_asset_state` carries `★` and the tags.**

> **The migration copies, and destroys nothing.**

## 0. Decision log

| # | Decision | Why | Where |
|---|---|---|---|
| 1 | The record is a new table **`task_asset_state`**, not columns on `assets` | `assets` is the import run's (`ListsDao.kt:1552`: "runImport is the sole writer of `tasks`, `task_state` and `assets`"), and an `assets` row describes a *file* — locators, measurements, presence. A judgment in it would make "re-measured" and "changed their mind" the same kind of event, and would give the import run a column it must never write | §2 |
| 2 | Primary key **`assetId`**, with **no `taskId` column** | `AssetEntity.id` (`TaskEntities.kt:102`) is a globally unique UUID and already carries `taskId`, so a second copy is a derivable fact that can drift. Ownership is expressed by the FK chain (`tasks` → `assets` → `task_asset_state`), not by a duplicated column. Scoping by Task is one join on `index_assets_taskId` | §2 |
| 3 | A new value type **`AssetDecisions(isFavorite, customActions)`**, and `ReviewDecisions` is **kept** for rows that report both halves | A *pair* row — a catalog row, a List row, a folder file-state, a shared-file state — legitimately carries completion *and* the marks. The split is between the two **state tables**, not between the two row types | §1 |
| 4 | `ReviewItem.decisions` is **split**: `isCompleted` stays on the item, `AssetDecisions` moves onto `ReviewAsset` | The item is the Task; the asset is the pair. Keeping one `ReviewDecisions` on the item with two empty fields is the shape that would let the bug back in, because a caller could read marks off the Task again | §1, §4 |
| 5 | `ReviewAsset` gains **`assetId`** | A chip tap has to address the pair, and the asset is what is on screen when it is tapped. It carries no id today because nothing wrote through it | §1 |
| 6 | The item's completion readers are **unchanged in behaviour** — they simply read `item.isCompleted` | The ten sites that read `decisions.isCompleted` read nothing else off it, so the split is mechanical for all of them | §4 |
| 7 | The migration **backfills** `task_asset_state` from `task_state`, one row per Asset, and **leaves `task_state.isFavorite` / `customActions` populated and dead** | Acceptance #8 — a Task imported before this release must behave exactly as it did — falls out of the copy. Leaving the old columns is v13's precedent verbatim (`ListsDao.kt:1313-1321`) and destroys nothing, which matters for a manual item whose record has nowhere else to go | §2 |
| 8 | The columns are **not dropped** | `ALTER TABLE … DROP COLUMN` needs SQLite 3.35, i.e. API 31+, and this app ships minSdk 24. Dropping would mean a full table rebuild for no reader's benefit | §2 |
| 9 | Task-level aggregates (catalog card, List row, folder file-state, shared-file states) fold the pairs — **in SQL where the row is a query, in Kotlin where it is assembled by hand** | `customActions` is a set of ids in a comma-joined string (`ListEntities.kt:418`). The catalog already assembles its rows in Kotlin (`ListsDao.kt:2602-2622`), so the fold has a home there; everywhere else the row *is* a Room `@Query`, and a query that re-emits when a pair changes is worth more than a Kotlin fold over a second query. `GROUP_CONCAT` + `decodeActionIds` is a union. **Amended during implementation — see §5** | §5 |
| 10 | The **badge row** keeps its union resolution and changes only its *decisions* source | It is shared with the List's own rows, where no file is on screen at all and the union is load-bearing. In the review surface it now reads the current page's pair | §4 |
| 11 | The **webhook payload and the submission response stay Task-level unions** | The payload is one entry per Task by contract (`Webhook.kt:327`); a Task that presents three files submits one judgment carrying all three records | §6 |
| 12 | `review_events` is **unchanged** — no `assetId`, no per-pair response | An event is a Task-level submission (`ListEntities.kt` `ReviewEventEntity`). Which pair each mark was set on is not reconstructed afterwards; the response pins the ids, which is what it has always guaranteed | §6 |
| 13 | A Task with **no Asset** has no middle band | No pair, nowhere to record. Flagged in the spec under [Out of scope](v0.5.1.md#out-of-scope) | §4 |
| 14 | `★` is per pair, completion is not | `★` is carried by the template definition (`Templates.kt`), completion is the outer band's | §1 |

## 1. The domain shape

Three values change shape and one is added.

```kotlin
/** What the template records about one Asset. The pair's half of a row that reports both. */
data class AssetDecisions(
    val isFavorite: Boolean = false,
    val customActions: Set<String> = emptySet()
)
```

`data/TaskEntities.kt`:

- **`task_asset_state`** — `@PrimaryKey assetId`, `isFavorite: Boolean`, `customActions: String`,
  `updatedAt: Long`; FK to `assets(id)` `onDelete = CASCADE`; an index on `assetId` is the primary
  key already, so no second index.
- `TaskStateEntity.decisions` — **removed**. The remaining reader is `isCompleted` and it reads the
  field. (Keeping a `ReviewDecisions` getter that always answered `false`/`emptySet()` for two of
  three fields is exactly the lie decision 4 exists to prevent.)
- `AssetStateEntity.decisions: AssetDecisions` — the new getter, shaped like the old one.

`data/ReviewAsset.kt`:

- `ReviewAsset` gains `assetId: String` and `decisions: AssetDecisions = AssetDecisions()`.
- `AssetEntity.toReviewAsset(decisions: AssetDecisions = AssetDecisions())` so every existing
  one-argument call keeps compiling and answers "nothing recorded", which is what a caller with no
  state row to hand actually knows.

`data/ListEntities.kt`:

- `ReviewItem.decisions: ReviewDecisions` → `ReviewItem.isCompleted: Boolean`.
- `ReviewDecisions` is untouched and keeps its three fields; it is now built only by pair rows.
- `FileReviewStateEntity.decisions`, `ListItemEntity.decisions` and `SharedFileState` keep their
  shape — they are already pair-shaped — but their queries read the marks off the pair.

`data/CatalogRow.kt`:

- `CatalogProjection` / `CatalogRow` keep `isCompleted`, `isFavorite`, `customActions`; the last two
  become the **task-level union** rather than the task's own row, and are filled in Kotlin (§5).

## 2. The schema, and `MIGRATION_20_21`

`ListeaDatabase.kt`: `version = 21`; `MIGRATION_20_21` added to `addMigrations` beside `MIGRATION_19_20`
(`ListeaDatabase.kt:1209`); `21.json` exported.

```sql
CREATE TABLE IF NOT EXISTS task_asset_state (
    assetId       TEXT NOT NULL PRIMARY KEY,
    isFavorite    INTEGER NOT NULL,
    customActions TEXT NOT NULL,
    updatedAt     INTEGER NOT NULL,
    FOREIGN KEY (assetId) REFERENCES assets (id) ON DELETE CASCADE
);
```

The backfill is one statement, and it is the whole of the behaviour preservation:

```sql
INSERT INTO task_asset_state (assetId, isFavorite, customActions, updatedAt)
SELECT a.id, ts.isFavorite, ts.customActions, ts.updatedAt
FROM assets a
JOIN task_state ts ON ts.taskId = a.taskId;
```

Room's `NOT NULL` columns on an entity without Kotlin defaults need a `defaultValue` in the
`@Entity`/`@ColumnInfo` or the exported schema will disagree with the created table — the same
detail `MIGRATION_18_19` handled for `assetControls` (`ListeaDatabase.kt:850`). The create and the
`21.json` must agree byte for byte, which `MigrationChainTest` asserts.

**What the backfill does to a multi-Asset Task.** `Camera`'s three photographs each get a copy of
the Task's one record, so all three come up ticked where the Task was ticked — the behaviour the
user saw, preserved exactly, so that the change is visible from the first tap afterwards rather
than from the migration. It is not an attempt to guess what the record *would* have been per file;
there was no such fact to recover.

The three insert points that create an Asset also create its state row, in the same transaction:
`reconcileTask` (`ListsDao.kt:2669-2692`) and `resolveNewTask` (`ListsDao.kt:2796-2809`). A
re-import **updates assets in place** — `updateAssetMetrics`, keyed by the existing row's id — so a
pair's record survives a re-run, which is the property the whole design rests on and which
`ImportRunTest` must keep holding.

## 3. The write path

`writeTaskState` (`ListsDao.kt:1444`) keeps its shape and its callers, and stops carrying the two
columns in its `change` function: `setTaskCompleted` and `submitReview` now pass a completion-only
lambdas, and `updateTaskState` writes only `isCompleted` and `updatedAt`.

A sibling is added beside it, obeying the same three rules its doc gives — read inside the caller's
transaction, update-only, null when there was no row:

```kotlin
protected open suspend fun writeAssetState(
    assetId: String,
    now: Long,
    change: (AssetDecisions) -> AssetDecisions
): AssetDecisions?
```

`setTaskAction` (`ListsDao.kt:934`) becomes `setAssetAction(taskId, assetId, action, enabled, now)`:
a write addressed by the pair, which no-ops when the Asset has gone — the same silent no-op a
vanished Task gives, and for the same reason. It keeps `taskId` in its address because the caller
has it and because a write that names only half of the pair cannot be logged or reasoned about.

`ListsViewModel.setItemAction` (`ReviewScreen.kt:658`'s target) takes the page:

```kotlin
fun setItemAction(item: ReviewItem, asset: ReviewAsset, action: ItemAction, enabled: Boolean)
```

and `ReviewScreen` passes `assets.getOrNull(currentAsset)`. A null page is the no-asset case, where
the middle band is not drawn and there is nothing to call.

`submitItemReview` (`ListsViewModel.kt:1272`) keeps reading a pair — but **which pair is a choice**,
and decision 11 makes it the Task's union: it reads the current page's control resolved over the
Task's kinds and the union of the Task's pair records, exactly as the payload does, so the response
snapshot and the payload cannot disagree. Its `ReviewResponse` shape does not change.

## 5. Where a Task-level answer is needed

> **Amended during implementation.** This section as written above said all four sites fold the pairs
> in Kotlin, and that the catalog row's own `isFavorite` / `customActions` become that union. Two
> things came out differently, both for the same reason — the row at three of these four sites *is* a
> Room `@Query`, and a query is the thing that re-emits when a pair changes.
>
> **1. `CatalogRow` no longer carries the marks at all.** The two fields were dropped rather than
> folded. Once each Asset carries its own record, nothing on any screen read a Task-level pair of
> fields off a catalog row, and `CatalogRow.asPreviewItem` was the only thing that ever turned them
> into anything — so a union there would have been a second way to ask a question with one caller.
> Where a Task-level answer is genuinely wanted, it is `unionOf(row.assets.map { it.decisions })`,
> which is one line at the call site rather than a field that has to be kept true.
>
> **2. Three of the four sites fold in SQL, not Kotlin.** `observeItems`, `getItems`,
> `observeFileStates`, `getFileStates` and `getSharedFileStates` all gained
> `LEFT JOIN task_asset_state tas ON tas.assetId = a.id` and read
> `COALESCE(MAX(tas.isFavorite), 0)` / `COALESCE(GROUP_CONCAT(tas.customActions), '')`.
> `GROUP_CONCAT` over a comma-joined set of ids *is* a union, because `decodeActionIds` splits on the
> comma and drops blanks on the way out — which is what makes the fold legible at all. The Kotlin
> fold would have meant a second query plus a `combine`, and the live one is subscribed to by every
> screen that draws a List.
>
> `unionOf` is not dead: it is still what `ReviewItem.taskDecisions` uses, so a surface that has the
> pairs in hand folds them the same way. What changed is where the fold happens — at the leaves, one
> query per row set, rather than once at the top.

Four places speak about a Task with no single file on screen:

| Site | What it folds | Where |
|---|---|---|
| `ListsDao.getCatalogTasks` (`:2780`) | nothing — the row carries `isCompleted`, and every Asset carries its own record. Callers that need a Task-level answer use `unionOf` | Kotlin, at the call site |
| `ListsDao.observeItems` / `ListsDao.getItems` | the row's marks become the union over the Task's pairs, by `MAX` and `GROUP_CONCAT` | SQL |
| `ListsDao.observeFileStates` / `getFileStates` / `getSharedFileStates` | the same fold, grouped by path, over every Task that reaches the file | SQL |

The fold in Kotlin is one function, and it is the same one the payload and the response use:

```kotlin
/** A Task's pair records, together: `★` if any pair carries it, every id any pair holds. */
fun unionOf(decisions: List<AssetDecisions>): AssetDecisions
```

### The live re-read

A round freezes *which* items it walks and must not freeze what has been decided about them
(`ListsDao.kt:2644-2655`). That re-read is the reason a tap shows up in the same frame, and it moves
too:

| Site | Today | After |
|---|---|---|
| `ListsViewModel.kt:881`, `:931` | `dao.observeTaskStates(ids).map { withLiveDecisions(queue, it) }` | `combine(observeTaskStates(ids), observeTaskAssetStates(ids))`, both watched |
| `QuickReview.kt:239` `withLiveDecisions` | copies `states[taskId].decisions` onto the item | copies completion onto the item and each pair's record onto **its** `ReviewAsset`, by `assetId` |
| `ListsViewModel.kt:2381` `deliverFolderReview` | `dao.getTaskStates(taskIds)` | the same plus `dao.getTaskAssetStates(taskIds)`, so the payload is built from current records |

A new query, `observeTaskAssetStates` / `getTaskAssetStates`, scoped by Task through
`JOIN assets a ON a.id = tas.assetId WHERE a.taskId IN (:taskIds)` — decision 2's join, and the
reason no `taskId` column is needed.

Note what this replaces. Today `getFileStates` takes `MAX(ts.customActions)` — the lexicographic
maximum of an encoded id list — which is a *stable pick* rather than a union, and is already lossy
for a file held by several Tasks. The fold is strictly more correct, and it is what makes the
`MAX` in `CatalogRow.taskAssetControls`' doc comment (`CatalogRow.kt:134-139`) the only place a
stable pick is still deliberate.

**One real defect found by these tests, and fixed.** `ListsDao.getItems` — the one-shot twin of
`observeItems`, and the read a webhook payload over a List is built from — was missed when
`observeItems` was rewritten, so it went on reading the retired `ts.isFavorite` / `ts.customActions`.
Every screen was right and the payload would have been wrong: a List row showing `p2, p7` would have
been sent as carrying nothing. `PerAssetRecordTest`'s union test asserts the two readers agree, which
is what caught it; the query now folds the pairs exactly as its live twin does. This is the failure
mode §7 is about, arrived at from the direction the plan did not expect — not a test that had to be
rewritten, but a query that was not.

**A second one, reported by the user against the fixed build, and the same shape.** §5 names *two*
folds — the membership row's, in SQL, and `ReviewItem.taskDecisions`, in Kotlin over the item's
Assets — and both were written. What was missed is that the second is only ever as good as the Assets
it is handed: `ListsViewModel.observeDetail` resolved them through `observeAssetsForList`, the bare
`assets` rows, and **`observeAssetStatesForList` — the query written for this surface — had no call
site in the app at all.** So the List's own screens, detail and review alike, drew every chip
unticked no matter what had been marked in Quick Review, and `submitItemReview` would have recorded
an empty judgment. The SQL answer was correct throughout and simply was not the one on screen, which
is why the DAO-level tests all passed: **they could only ask the question the right way.** The fix is
one more flow in the `combine`; the test that holds it is `ListDetailRecordTest`, written through the
ViewModel because that is the layer the two answers met, and confirmed to fail against the unfixed
code before being kept. §5's row 9 is the note that should have warned of it — "in SQL where the row
is a query, in Kotlin where it is assembled by hand" describes two folds but does not say that the
second needs a query of its own to have been *called*.

## 8. What is not touched

- `AppSettings`, the template definitions, `controlFor` / `controlForTask`, `ResolvedAssetControl`,
  and the whole of v0.5.0's configuration model. The lookup is not what was wrong.
- `sources.assetControls` and `task_imports.assetControls`. Those say what a Task is *judged with*;

- The List, the queue, the navigator, the media transport, the Info sheet's own layout.
- `review_events`, its columns and its encoding.

## 9. Dissolution and recovery: the defect, and the rule for repairing it

Not fixed here — **v0.5.2's first item.** What follows is the defect, then the decision that was
taken about how to repair it, so that v0.5.2 does not have to re-derive either.

The same family as the `getItems` miss above, one layer further out: **dissolution and recovery still
address the retired columns**, so a history records and restores marks through a path nothing reads.

`snapshotDissolvedState` (`ListsDao.kt`) fills `dissolved_task_state` from `COALESCE(ts.isFavorite,
0)` and `COALESCE(ts.customActions, '')`, and `writeRecoveredState` puts a recovery back with `UPDATE
task_state SET isFavorite = …, customActions = …`. Both columns went dead in this release, so the
pair now means:

- **A dissolution records nothing that was marked under v0.5.1.** The snapshot copies the frozen
  pre-migration value — on the attached device, whatever was marked at the moment the migration ran.
- **A recovery restores nothing visible.** The write lands in a column no surface reads, so the tags
  and the `★` a user asked to keep are gone while the picker reports them carried.
- Completion is unaffected. `isCompleted` stayed on `task_state` and is still the live column, which
  is why this did not show up as a broken recover but as a *lossy* one.

**`HistoryRecoveryTest` cannot see any of it**, and that is the part worth recording. Its fixture
writes the judgment with `UPDATE task_state` and its `stateOf` reads it back with `SELECT
ts.isFavorite, ts.customActions` — the same dead columns at both ends. The test named *a recovered
Task takes the judgment that was made about its path* passes while the app shows nothing, which is
exactly the failure mode §7 describes: green because the test and the code agree about a column the
user never sees. The lesson for the next release is that a retired column has to be retired at
*both* ends of every test that touches it, not only where the screens read.

The fix is not a rewrite of those two queries, because the snapshot's shape cannot carry it: one row
per Task keyed by `groupPath` has no way to say *which* file a mark was on, and the Asset rows are
already gone by the time a recovery runs. Making recovery faithful means making the history per-file
— a file column on `dissolved_task_state`, one row per pair, a match on it in `recoveryMatches`, and
a schema step of its own (the device already sits at 21, so this cannot ride in `MIGRATION_20_21`).
Folding the Task's pairs into the single row would be far smaller and would restore the marks, but it
would stamp every file of a recovered folder with the union of what any of them had — the reported
bug, arriving through the recovery door. That is a rule to be made deliberately, not assumed at
commit time, so **v0.5.1 ships with this defect recorded and not fixed**, and the acceptance below
covers the camera and the Todo rather than dissolve → recover.

### The rule, now made — v0.5.2, and it is neither of the two above

Three shapes were put to the user, and the third was chosen. Recorded here because the choice
constrains what v0.5.2 may do, and because the reasoning is what a later reader will be missing.

| | Shape | Why or why not |
|---|---|---|
| **A** | Give `dissolved_task_state` a file column, one row per pair | Correct, and rejected: the snapshot stays **a second model of the record**, so it has to be migrated every time a record gains a field. This defect is that cost coming due — it would come due again |
| **B** | Do not snapshot at all: keep the dissolved Tasks as tombstones and prune later | The industry default for *user-facing undo* (a recycle bin, `deleted_at`), and it removes the whole class — one source of truth, recovery is un-marking rather than copying. Rejected on its **semantic** cost, not on storage: the dissolved Tasks stay alive, so `runImport` must reconcile against them instead of minting fresh ones, and the template conflict below becomes a standing property of a live row rather than a moment in a restore |
| **C** | **Keep one row per Task, and store the pair records as an encoded payload** — path → that file's record | **Chosen.** It keeps every benefit of A — self-contained history, bounded live tables — while the snapshot stops being a schema, so a field added to a record is carried without touching this table. It is also what `review_events` and `webhook_history` already do here |

**The user's two reservations, and what answers them.** The first is that a payload needs a small
importer of its own to be read back, and that this is a place for a future defect to hide. The answer
is the one the codebase already gives: `review_events` stores `templateId` **and** `templateVersion`
beside its `response` payload, deliberately as two columns rather than one `id@version` token, so a
payload is never read without knowing what wrote it. The dissolution payload gets the same treatment
— a version on the encoding, so a reader either knows the shape or says so, and never guesses. The
second is that a payload is loaded whole, so a question like *which of my histories marked this
particular file* cannot be answered by reading one column. That is the real limitation of C and it is
accepted knowingly: it is a question nobody has asked, the payload is per-Task and small, and the
answer if it is ever asked is a projection **over** the payload rather than a redesign.

The user's own summary, which is the decision: *C 把所有复杂性全封装到 payload 里了。以后等业务稳定，
我们再来考虑哪些要封装，哪些不要。* The tables are still moving; A would add complexity that has to be
maintained through exactly the churn it cannot survive.

One conflict runs through all three and is worth naming, because it is not a reason to prefer any of
them: **a history made under one template may be restored under another.** Dissolve under a control
that declares `p1, p2` and re-import under one that declares `p3, p4`, and the restored record names
tags the new Task's control does not offer. A and C meet it at the moment of restore, where the
surface can simply say the record was made under another template. B meets it as a standing state,
because the Task that holds the record is alive and must answer for which control it is under — which
