## The change in one paragraph

Today, *what to record about a file* is a blob of tags that belongs to one Todo, is edited at the
moment that Todo is imported, and cannot be named, found again or reused. The app-wide default is
the same blob under a different name — **Settings → Asset controls** — so the app has two editors
for one idea and no way to say *this* set of buttons is a thing. v0.5.4 gives it the four things
the user asked for: an **id**, a **name**, a **version**, a **scope** that decides which files it
governs, and the **buttons** it carries. It becomes a row, so Settings can list it, an import can
attach it, and an edit can mint a new version rather than overwrite the old one. `★` becomes a
button like any other — of type `boolean` — because that is what it always was.

## Why

### The chef's notebook has no name

[v0.5.0](v0.5.0.md) told the story of a chef standing in a market, writing down *the price* for the
tomato dish and *how fresh they look* for the pepper dish. The tag row is his notebook, and v0.5.0
was right that it varies with the intention and the file kind both. What it left undone is that the
notebook is **not a thing**. It is a column on a Todo, filled in by a dialog at the moment of
import, and the only way to reuse yesterday's answers today is to remember them and retype them.

Three symptoms, and they are one symptom:

- **The same notebook is configured twice.** Two Todos over the same market with the same intention
  each have their own copy, and nothing connects them.
- **The app-wide default is the same idea wearing a different hat.** **Settings → Asset controls**
  edits a tag set per file kind; the import dialog edits a tag set per file kind; the two use the
  same editor widget (`AssetControlTagEditor`) and neither is the other's parent.
- **A change is not a decision.** Editing tags rewrites what every future Task records, with no
  version to point at and no way to say *I changed my mind on Tuesday*.

### What the architecture already says, and what v0.5.0 left lying

[ARCHITECTURE.md](../ARCHITECTURE.md) §Templates has said from the start:

> A **Template** is a stable, user-recognizable lineage. A **TemplateVersion** is an immutable
> definition used to interpret a particular review or viewer configuration.
>
> Editing a template creates a new version. Completed and historical reviews continue to reference
> the exact version under which they were made. A display name can change without changing identity.

The code has only half of that. `domain/Templates.kt` holds three code-defined versions and a
registry; nothing is stored, nothing is created at runtime, and `TemplateId`'s own comment says so:

> The odd one out among these: not generated, because a Template is defined in code and its id is a
> fixed string… Nothing mints one at runtime; `Templates` is the only place they come from.

v0.5.0 split the word in two — a **definition** (code, hashed, immutable) and a **configuration**
(which tags, which names, which wire values — on the Todo, editable) — and said the split was what
let Settings manage templates "without the architecture bending". It was right, and it named the
seam precisely. What it did not do is give the configuration a lineage. This release does: the
configuration stops being an anonymous blob and becomes a **stored, named, versioned template**,
which is the thing §Templates was describing all along.

The user's rule — *add and remove buttons freely, but nothing is updated until you confirm* — is
§Templates' *editing a template creates a new version*, expressed as a gesture. It is not a
constraint the architecture has to absorb; it is the architecture, arriving as UI.

### What a template is, in the user's words

> id：身份
> 名字：代称，便于管理，展示给用户
> version：因为模板可以调整，version来区别历史与现在
> 使用范围：匹配 asset 的方式…
> 组件：负责描述这个 template 里面有什么。比如说 asset control 下面的 control 条的按钮。
>
> 按钮拥有 id，名称，类型，记录值

The model below is that, spelled out. It is a **subset** of what §Templates permits — a small,
code-shaped vocabulary with a user-editable configuration, no component table of arbitrary widgets,
no drag-and-drop builder, no plugin runtime. §Templates explicitly lists those as separate product
decisions that "template abstraction does not imply"; this release takes none of them.

## The model

### Three levels, not two

v0.5.0 had a definition (code) and a configuration (a Todo's blob). v0.5.4 has three:

| Level | What it is | Where | Mutable |
|---|---|---|---|
| **Template** | The lineage: an opaque id, and the name a person calls it | `templates` | The name only |
| **Template version** | One immutable answer: what it applies to, and what it offers | `template_versions` | No — an edit appends |
| **The Todo's attachment** | Which templates this import uses | `sources.assetControls` | Yes, at each run |

The middle level is the one that was missing, and it is the one §Templates is about. Its immutability
is what makes "confirm to update" mean something: the version a Task was imported under stays
readable forever, and editing the template tomorrow cannot reach back and change what that Task says
it is judged with.

**A version is immutable, and that is enforced by shape rather than promised.** A version is written
once and never updated; an edit inserts version *n+1* beside it. Nothing in the app updates a
`template_versions` row.

### A button

```
Button
├── id            opaque, unique across the whole app, minted not typed
├── name          what the chip says                       ("C1", "★")
├── type          boolean | tag            (option, field, note: later)
└── recordValue   what the payload sends    ("cust1", "favorite")
```

`type` is what a button *records*, and it is the field that makes the next three button kinds
possible without a second mechanism. Two ship:

| Type | What it holds | Stored as |
|---|---|---|
| **`boolean`** | on or off | the button's id being present in the asset's selection set |
| **`tag`** | on or off | *the same* |

They are the same storage because they are the same thing today: a tag is a boolean whose meaning is
decided downstream. The distinction that matters is not on/off, it is **what a future type will
need** — an `option` holds one of several, a `field` or a `note` holds text — and both of those want
a value rather than a presence. That is why the record is a payload with a version on it rather than
another column, exactly as [v0.5.2](v0.5.2.md) decided for the dissolved history and for the same
reason: a record that mirrors its own shape has to be migrated every time it gains a field.

Shipping two types that store identically is deliberate, not a smell. It is what lets `★` be a
button `boolean` while a user-added chip is a button `tag`, and it is the seam the third type grows
from without a schema change.

### `★` is a button now

`ItemAction.Favourite` is a `data object` with no id, and its state is a dedicated boolean column
(`task_asset_state.isFavorite`). v0.5.4 makes it a button with the **fixed id `favorite`** — the wire
name it already sends — so that an asset's record is one set of button ids and nothing else.

This is the user's item 1, and it is the part of the release with the widest blast radius, because
`isFavorite` is read by the chip row, the badge line, the Info sheet, the webhook payload and the
dissolved-history payload. It is worth it: without it, *"a button of type boolean"* describes only
the buttons that happen to already be stored as a set, and `★` remains a special case in the model
that exists to explain it.

The consequence to state plainly: **a template that does not carry `★` produces a row with no
star**, and *no template at all* means no chips — which is what the user asked for:

> 导入过程中，没有匹配上的 asset 不加载 template。比如我只选了现在的图片 template，那视频就没有
> template 和 asset control。

Before this release `AppSettings.controlFor` was never empty: it fell back to the app default for the
kind (`Settings.kt:216-222`). That fallback became wrong the moment a user could choose what to
attach — falling back to *something* attaches a template the user did not pick — so it is gone, and
`controlFor` returns nothing when nothing matches. **No match means no control, and no control means
no chips.**

### The scope

A version carries a **scope**: the rule that decides which files it governs.

```text
kind:image,video
```

One rule per line/field, `type:argument`. Only `kind` ships, because it is the only rule the
product has: the file's kind already decides which row is drawn
([v0.5.0](v0.5.0.md) §The file kind), and it is resolved from the filename rather than by opening
the file. The user's list of future rules — a specific mime, a filename pattern, a size, dimensions —
are all *the same shape*, so the encoding is a list rather than a single value and a later release
adds a rule type without a migration.

**A scope is the conjunction of its rules, and an empty scope admits nothing.** Several rules narrow
— `kind:image` with a filename rule beside it means the images whose names match — which is what
makes a list of rules worth having rather than a second way to write one. An empty scope is the
quietest authoring mistake there is, a template saved before its scope was filled in, and it must not
mean *every file*: a template that says nothing about what it applies to cannot be applied.

**An unknown rule type makes the template match nothing**, and the template's page says so. That is
the failing-closed direction [v0.5.3](v0.5.3.md) §3 established for an unrecognised action id, and
it is the same argument: a rule this build cannot evaluate must not be quietly dropped, because
dropping it *widens* the template's reach, and a template that silently governs files it was never
written for is a row of chips nobody chose.

### What the Todo stores

`sources.assetControls` stops being *the tags, per kind* and becomes **the templates this Todo
applies** — a list of references, each a lineage and the version it was attached at. The column
keeps its name, which is still the honest one; the payload changes, which is what
[v0.5.2](v0.5.2.md) did to `records` and for the same reason.

That version number is load-bearing rather than decorative, and it is the difference between this
release and v0.5.0's configuration: a Todo imported under version 1 keeps saying version 1 after
somebody edits the template to version 2. Editing a template changes what *future* imports get, and
never what an existing Task is judged with.

**Two templates that both match a file is a case this release does not answer**, and the user
deferred it explicitly:

> 现在你也不用管 template 范围冲突，比如 jpg 模板和图片模板有重叠。目前假定没有冲突。

The assumption is written down rather than assumed silently: the import dialog **does not offer two
templates whose scopes overlap** — the second is drawn disabled, with the reason — and the resolver
takes the **first match in the order the Todo attached them**, so that the behaviour is at least
deterministic and statable even when a database arrives with an overlap the dialog would not create.
Which of two overlapping templates *should* win — most specific, most recent, or refused outright —
is a real question and it is not this release's.

## What a user sees

1. **Settings → Templates**, with a row saying how many there are, opening a list. The existing
   **Asset controls** section is **gone**, and the thing it was editing — the built-in template — is
   what its page now opens. There is one editor for a button where there were two.
2. Each row names one template and what it applies to. Tapping it opens the template's own page:
   its name, its scope, and its buttons.
3. Buttons can be added, renamed, re-valued, retyped and removed **on the page, freely**. A bar at
   the bottom says the template has unsaved changes; **Update** writes them as a new version, and
   **Cancel** leaves the old one exactly as it was. Nothing is written until Update.
4. The template's page says which version you are editing, and that updating creates the next one.
5. **At import**, the Create Tasks dialog asks what this Todo records with: **Add a template**
   (pick one or more from the list) or **New template** (a button that says where a template is
   started today, rather than doing nothing at all). The tags are no longer edited in the dialog —
   that is the template's job now, and the dialog links to it. **There is one row per template, not
   per version**: a template is something a Todo has or does not have, so choosing it *moves* it to
   the current version rather than adding a second one, and a Todo sitting on an older version is
   drawn ticked with *Held at version N. This run will attach version M.* Two templates whose scopes
   overlap cannot both be chosen. A run with nothing attached cannot be created.
6. A file that matches no attached template gets **no chips at all** — not an empty row, not a
   default. Videos in a Todo whose only template is scoped to images have no asset control, which
   is the point.

## Acceptance

1. **Settings → Templates** lists the templates, the built-in one among them, and opening it shows
   its name, its scope and its buttons.
2. Rename a button, add one, remove one, then **Update**. The version number goes up, the list shows
   the new name, and the template's *previous* version is still what an earlier Task reports.
3. Cancel an edit and nothing moves — not the name, not the buttons, not the version.
4. Import a folder, attaching only the image-scoped template. Open a Task: the photographs carry its
   chips, the videos carry **none**, and neither carries `★` unless the template says so.
5. Import a folder attaching two templates. Files matching each get their own template's chips.
6. **Upgrade over an existing database.** Every Todo keeps the tags it had, as a template of its
   own, named so it can be told apart; Tasks imported before the upgrade still report the marks they
   were imported with; and a `★` set before the upgrade is still a `★` afterwards.
7. A Todo whose old image and video tag sets **differed** comes out as two templates, each scoped to
   the one kind it was configured for.

## Acceptance, as run — the schema step only

The release is not finished. What this section covers is **step 2 of [the plan](v0.5.4-plan.md)**:
the two tables, the built-in seeded into them, and `task_asset_state.selections` filled from the two
columns beside it. **Nothing reads the new column yet and nothing writes it** — the reader and the
writer move together in a later step, and moving a format's meaning without its reader is the thing
the plan's ordering exists to prevent.

The full suite is green at **706 tests across 78 classes, 0 failures** (678/75 before this step). The
new migration is covered by `data/MigrationV23ToV24Test.kt`, whose fixture is the current schema with
this step's own additions subtracted and which asserts that subtraction rather than trusting it; every
fixture that enumerates the migration chain by hand gained the new step, because Room opens at the
version the app ships whatever version a fixture was written at.

**Walked on the maintainer's phone on 2026-09-18, on a build of this release, over the database the
v0.5.3 run left behind** — 4 Lists, 9 Tasks, 12 Assets, 12 pair records, and a genuinely mixed set of
marks: several `★`, two `custom1`/`custom2` tag sets, and one user-generated button id
(`ac0c7a35e5912`).

The upgrade was watched from **both** sides rather than reconstructed — which is what v0.5.3 could not
do, and what its own record says it could not. The database was pulled before the new build was
installed (`user_version 23`, no `templates` table, no `selections` column) and again afterwards
(`user_version 24`).

- **The built-in arrives, once.** `templates` holds one row, `builtin.media.asset-control` named
  `Media Asset Control`; `template_versions` holds one version of it — scope `kind:image,video`,
  `buttonsVersion 1`, and buttons `favorite ★ boolean favorite`, `custom1 C1 tag cust1`,
  `custom2 C2 tag cust2`. Checked byte for byte against the seed the code declares, `★` (U+2605)
  included.

  `isFavorite` and `customActions` in canonical sorted order — `'ac0c7a35e5912,custom1,favorite'` for

  and no star, `''` for the seven carrying nothing. Zero mismatches, and the two columns it read are
  untouched, so the merge could be checked against its own source rather than against a restatement
  of it. Every other table kept its row count.
- **No crash**, and the app was opened four times across the session with nothing fatal in `logcat`.
  Settings' default tag actions — now derived from the seeded buttons rather than declared beside
  them — still draw as `C1, C2` on both Todos' cards, and Quick Review still draws the chip row.
- **A mark made after the upgrade still works, and does not reach the new column.** Toggling `C1` off
  a Camera pair and back on wrote `customActions` both times, and left `selections` reading
  `'custom1,favorite'` throughout. That is the shape of this step rather than a defect — the column is
  a frozen copy of the upgrade until the writer moves — and the mark was put back as it was found.
  **The writer has since moved**: since step 3 a mark writes `selections` and leaves the two columns
  alone, so the observation above is the shape of that step and no longer of the app.

**Steps 3, 4 and 6 of [the plan](v0.5.4-plan.md)**, which are the last three and the ones that make

The suite is green at **728 tests across 80 classes, 0 failures**. Two things about that number are
worth naming. **`AssetControlTest` is gone** — all twenty of its cases — because Settings → Asset

- **Acceptance item 4, end to end.** A folder of one video and two photographs was imported against

  `isCompleted` written by nothing this release — they are read out of the pair records by the query,
  which is what makes decision 15 worth its two extra columns.

**The one production bug found on the way, and it had no symptom on the day it shipped.** Step 3
raised `DISSOLVED_RECORDS_VERSION` from 1 to 2. `MIGRATION_21_22` interpolated that constant into the
rows it writes, so an already-shipped step silently changed what it claimed to have written — for
every database that had not yet passed through it, and for none that had. `MigrationV21ToV22Test`
caught it as `expected:<[1, 1]> but was:<[2, 2]>`. **A migration is frozen at what it wrote the day
it shipped; a constant is not.** The literal is now written out at `ListeaDatabase.kt:1000` with that
reasoning beside it. The same reading was applied to `insertMintedTemplate`'s `buttonsVersion`, and
deliberately *not* to `builtInAssetControlRows`, which the creation callback shares and which
therefore has to mean *the version this build writes*.

**And the same lesson in the fixtures.** Rewinding a database to v23 for the pass above is
`MigrationFixtures.subtractV24Additions` written out in Python, which is where a second copy of the
rule was needed: **a migration `ALTER`s, a fixture rebuilds.** The three `selections` columns come off
the fixture by rebuilding each table and re-creating its indices, not by `DROP COLUMN` — partly
because Robolectric's SQLite rejects it, but the table rebuild is what the app itself has to do, and
a fixture that subtracted by a route the app cannot take would be a v23 the app never produced. The
shared `ColumnsFromLaterSteps` map names the three so that each migration test's column arithmetic
grows in one place rather than three.

## Acceptance, as run — the duplicate that was one attachment said twice

**A defect in this release's own headline feature, found the way defects are found: by the user
importing something.** Reported 2026-09-18, in one sentence, from the screen: a Todo that said
*keep it with 3 buttons, control with 4 buttons*. Nothing in the suite failed. The section above
ends with a Todo correctly recorded as `<templateId>\t1` and drawing `☆ C1`; what follows is what the
same column looks like when it is not.

**What the phone held.** One Todo — folder `Demo`, file-as-Task, nine Tasks — whose
`sources.assetControls` read:

```text
builtin.media.asset-control	1
builtin.media.asset-control	2
```

and all nine of its `task_imports` rows read the same. One lineage, written twice, at two versions.
The lineage itself stood at v1 (three buttons) and v2 (four, `C4` having been added to it). Quick
Review drew **three** chips — `☆ C1 C2`, with `C4` unreachable — because
[`TemplateResolver.controlFor`](../../app/src/main/java/com/example/listea/TemplateResolver.kt) takes
the first match and `T@1` was first. The Todo's own card, which asks `controlForTask` and therefore
unions every attached version, drew **four**. Two surfaces, two answers, one Todo — and the card was
the one that agreed with the template the user had just edited.

**Why.** Three exits from one fact, and the fact is that **the attach step matched whole
references while offering one row per lineage.** A row is a lineage at its *current* version, so:

1. A Todo recorded on `T@1` appeared **nowhere** in the picker — there was no `T@1` row to draw
   ticked and no way to untick it. Ticking the `T@2` row added a second reference instead of moving
   the first, which is how the column came to hold two.
2. `attachedScopes` was computed by filtering the rows against the attached references. Against a
   stale reference it came out **empty**, so the overlap guard — *Governs the same files as one
   already attached*, the one rule written to make this unreachable — never fired.
3. The seed for a **new** Todo was `Templates.AssetControlSeed.ref`, the registry constant, which is
   `@1` and frozen. So the Todo the user created *in order to pick up the new button* opened on the
   old version.

None of the three is a typo; all three are the same mistake read at three places, which is why it
took a person using the app to find it rather than a test of any one of them.

**The rule this release was missing, now stated and enforced in one place.** *A lineage is a thing a
Todo has or does not have.* The version beside it records how the template stood when a run happened
— it is not a choice being held, and there is no state in which holding two of them means anything.
So:

- [`decodeTemplateAttachments`](../../app/src/main/java/com/example/listea/TemplateResolver.kt)
  **collapses** a column that names one lineage twice, keeping the highest version and the lineage's
  first position. A row that is well-formed is untouched; a row that is not is repaired on the way
  in, **without a migration**, and the next run writes it back in the shape the dialog now produces.
  The mobile app has no way to run a data fix over a database it has not opened yet, and this one
  does not need to.
- `withAttachment` and `heldVersionOf` are new, and they live in `TemplateResolver.kt` rather than in
  the dialog that calls them **precisely because the untested composable is where the bug lived**.
  Turning a template *on* now replaces whatever the Todo held of it, in place, keeping its position
  in the order — because order decides which template governs a file when two admit it, and bringing
  one up to date says nothing about that.
- The picker's rows are one per lineage, and a row for a template the Todo holds on an **older**
  version is drawn **ticked**, with a third line: *Held at version 1. This run will attach version
  2.* The user can now see the stale attachment and can remove it; before, it was invisible and
  permanent.
- The new-Todo seed resolves the built-in's current version **from the store** rather than from the
  registry constant.

**The user's own test, run as asked** — *dissolve the broken Todo, choose keep, see whether the
history loads and four buttons appear.* It is the same Todo the defect was found on, and it is the
one test that exercises the repair on data that already has the wrong shape:

- The Todo was deleted with **Keep the decisions** ticked. Nine `dissolved_task_state` rows were
  written, carrying `favorite` for `Attach/two.mp4`, `custom1` for `Attach/one.jpg`, `custom2` for
  `Camera/IMG20260730120139.jpg` and completion for all three of `Attach/`.
- Create Tasks over the same folder was offered **Decisions left behind → Demo, 9 Tasks judged ·
  deleted 2026-09-18 18:12**, and the run reported **9 Tasks created · 9 Tasks recovered · 9 Assets
  added**.
- The Todo that came out of it holds `builtin.media.asset-control\t2` on `sources` and on **all nine**
  `task_imports` rows — one line, one version, which is what the old Todo should have had.
- Quick Review on `Attach/` draws **`☆ C1 C2 C4`** — four chips, `C4` reachable — with `C1` filled
  on `one.jpg` and `★` filled on `two.mp4`, both matching the records that were kept to the id.

So the answer to the question the defect was found with is that the repair is reachable and the load
path is intact: the column the old build corrupted is read back collapsed, and the recovery that was
already written for a dissolved Todo carries the judgments across **by path** without carrying the
attachment across with them. A recovered Todo is attached by *this* run's choice, not by the dead
Todo's record — which is what makes the last bullet possible at all.

**And the same test again, on the other grouping, run by the user.** The folder-as-Task Todo over
the same folder was dissolved with *Keep the decisions* and re-imported the same way, and it came
out right: the four Tasks' checked state, their assets' marks, and `C4` present. Read off the

Every row matched, by path, to the id — including `Attach/one.jpg`'s empty set, which is a recovery

**Suite: 731 tests across 80 classes, 0 failures** (728/80 before the fix). `TemplateAttachmentTest`
grew from 19 cases to 22: the collapse rule, the replace-in-place rule, and *a Todo on an older
version of a template is attached to it, and the run moves it*. Its existing *the third field is what
tells the two shapes apart* case was **rewritten** rather than left alone — it had used two versions
of one lineage to stand for two attachments, which the collapse rule makes a contradiction rather
than an example, so the fixture now uses two lineages and the collapse rule has its own case. That
is worth naming because it is the shape of the bug: the old fixture **encoded the mistake**.

**And a note on what this cost the release's claims.** §What a user sees item 5 said the dialog
*refuses two whose scopes overlap* — it did, but only when both were offered, which is exactly the
case a stale reference escapes. The rule is now stated where it is actually read: *the picker offers
one row per lineage, and the clash rule reads its input off the ticked rows.* Nothing in §The model
changes; §What the Todo stores said a lineage and the version it was attached at, which is what the
code now enforces rather than merely writes.

## Out of scope

- **Scope conflicts.** Two templates matching one file. Deferred by the user, assumed impossible,
  and named in §The scope rather than left silent.
- **New template at import.** The button exists and **says where a template is made** rather than
  doing nothing — an inert control cannot be told from a broken one. Authoring a template inside the
  import flow is a second editor for one thing, and the template's own page is the first.
- **Authoring a template from a blank page.** The list is a list you read and open, and it has no
  *new template* button — a lineage is minted by whatever has something to name, which as shipped is
  **only the upgrade**. A choice between one and several templates is the shape the release is about;
  inventing an empty one is a different feature. `TemplateWriteDao.insertTemplate` is written and has
  no caller, waiting for the feature that needs it.
- **`option`, `field` and `note` buttons.** The record's payload and the `type` field are shaped for
  them; no type ships but `boolean` and `tag`, because a type invented ahead of a workflow is a
  field that has to be honoured for the rest of time.
- **Scope rules beyond the file kind** — mime, filename pattern, size, dimensions. Same reason, and
  the encoding is already a list so that one costs a rule and not a migration.
- **The other two template kinds.** `TemplateKind` has three members and this release moves only
  `ASSET_CONTROL`. `lists.taskReviewTemplateId` and `review_events.templateId` keep pointing at the
  code-defined `builtin.media.rapid-review@1`, and review history is untouched — which matters,
  because §Templates requires a completed review to keep pointing at the exact version it was made
  under.
- **[v0.5.3](v0.5.3.md)'s open question about action ids.** Templates give buttons an *owner* and a
  page, which is a better place to answer *how does a user say two buttons are the same one* than
  the template editor has today. It is not answered here; it is now a question with somewhere to
  live.
