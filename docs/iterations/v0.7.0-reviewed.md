# Listea v0.7.0 — Review of the PDF viewer and quoted-mark plan

> **Status:** Review feedback (2026-10-21)
> **Reviewed:** [`v0.7.0.md`](v0.7.0.md) and [`v0.7.0-plan.md`](v0.7.0-plan.md)
> **Purpose:** Feedback for the agent that will revise and implement the round. This document does
> not replace the spec or implementation plan and records no product decision by itself.

## Overall assessment

The product direction is strong, but the current plan should not yet be treated as ready for
product implementation.

The spec draws the important boundaries correctly:

- A PDF viewer is a reading surface and records nothing by itself.
- Review tools come from a template rather than being intrinsic viewer behaviour.
- Marks live in Listea and never modify the PDF.
- A template update changes whether a stored mark resolves and is visible; it does not erase the
  mark.
- Image and video behaviour remains a compatibility obligation.

The spike is also valuable evidence. It proves on a real device that the selected dependency can
render the fixtures, expose their text, support a first touch-selection implementation, and coexist
with the existing browsing gestures. It states its limitations honestly instead of presenting
spike code as finished product code.

The remaining problems are primarily in the choice of renderer, the missing PDF domain kind, the
meaning of a PDF tool, the anchor used by a durable mark, and the export contract. These decisions
affect the schema and should be settled before schema 28 is designed.

## 1. Renderer: Nucleus adopted; AndroidX PDF deferred

> **Update (2026-10-21, after measurement).** This section's original recommendation to run an
> AndroidX comparison spike has been executed in the only form that matters: the library was
> measured on the maintainer's device. AndroidX PDF `1.0.0-beta01` requires **API 35, or API 30+
> with SDK extension ≥ 13**, for its selection and text APIs. The API 33 OnePlus reports extension
> level 3, so it falls back to `PdfRendererCompatAdapter`, where `selectPageText`,
> `getPageTextContents` and `searchPageText` throw `UnsupportedOperationException`. Rendering
> works; the round's central capability does not. **v0.7.0 therefore adopts Nucleus PDFium**
> (whose manifest declares `minSdk 24`, unchanged from the app's floor), behind a viewer adapter
> and a renderer-neutral anchor. AndroidX PDF is recorded as a **deferred candidate**, with a
> re-evaluation gate stated below. The original text is kept below the updated recommendation as
> the record of what was proposed; it is not the current decision.

The renderer comparison in the earlier plan was incomplete. It compares Nucleus PDFium
with the platform `PdfRenderer`, whose pixel-only API is indeed insufficient for quoted marks. As
of 2026-08-26, however, AndroidX PDF `1.0.0-beta01` offers a different alternative.

The current AndroidX PDF APIs provide or expose:

- an embeddable Compose `PdfViewer` and a View-based `PdfView`;
- touch text selection, handles, and cross-page selection;
- the current selection and selection-change callbacks;
- a customizable selection context menu, into which Listea can add Comment and Tag;
- persistent highlights supplied by the host application;
- page content and selection-bound APIs;
- progressive rendering and release of off-screen page bitmaps.

Relevant primary sources:

- [AndroidX PDF release notes](https://developer.android.com/jetpack/androidx/releases/pdf)
- [Compose `PdfViewer`](https://developer.android.com/reference/kotlin/androidx/pdf/compose/PdfViewer.composable)
- [`PdfView`](https://developer.android.com/reference/androidx/pdf/view/PdfView)
- [`PdfDocument`](https://developer.android.com/reference/kotlin/androidx/pdf/PdfDocument)

The repository currently has `minSdk = 24`. Nucleus PDFium's manifest declares the same floor, and
the round uses no API-gated call above it. AndroidX PDF's release notes describe low-API work, but
its text capability is gated at runtime, and that gate is what the measurement found.

### Settled recommendation

**v0.7.0 adopts Nucleus PDFium.** The viewer is isolated behind a narrow adapter, and the stored
mark uses a renderer-neutral anchor, so a later swap changes no Room column and no exported field.

**Re-evaluation gate for AndroidX PDF.** It may replace Nucleus only when all of the following
hold:

1. AndroidX PDF is stable at the API Listea uses (no beta/experimental dependency).
2. Its **full text-selection capability covers the device range Listea promises to support at that
   time** — not merely the maintainer's next phone, and not only devices with a new enough SDK
   extension.
3. The viewer adapter and renderer-neutral anchor are in place, so the swap requires no schema
   migration and no wire change.

If (2) cannot hold, the product must **explicitly raise its documented capability/API floor**
rather than ship a feature that silently differs by device. A single new device is not evidence
about the supported range.

Because Nucleus remains the renderer, the round explicitly owns the whole selection interaction:
handles, word snapping, reading order including RTL and columns, overlapping selections,
cancellation, lifecycle and future PDFium index changes. Cross-page selection is deliberately
deferred this round; the versioned anchor leaves room for page ranges later.

The seven questions the original review proposed remain the right questions for any future
re-evaluation (API floor, selected text and bounds, restored highlights and hit-testing, gesture
coexistence, fixtures including RTL and multi-column, size/memory, and error reporting). They are a
checklist for that gate, not a prerequisite for this round.

### Cross-platform boundary

AndroidX PDF is an Android-specific viewer implementation. Choosing it does not make the PDF UI,
gesture handling or selection implementation reusable on iOS, desktop or the web. That is an
acceptable trade-off for this Android application, provided the dependency stops at a narrow
viewer boundary.

The platform-independent part should include:

- the Mark domain model and stable identity;
- template and tool resolution rules;
- the versioned quote-anchor representation;
- orphaning and relocation behaviour;
- storage semantics; and
- the export contract.

The platform adapter should own:

- opening and rendering a PDF;
- converting the viewer's native selection into Listea's quote anchor;
- converting a stored anchor into viewer-native highlight geometry;
- page, zoom, pan and selection gestures; and
- renderer-specific errors and lifecycle cleanup.

Android may implement that boundary with AndroidX PDF; a future iOS implementation could use
PDFKit, and a desktop or web implementation could use another renderer without changing the stored
Mark or wire contract. No Room column, domain type or exported field should contain an AndroidX
`Selection`, `PdfPoint`, `Highlight` or another renderer-owned object. Renderer-native objects must
be translated at the adapter boundary into page numbers, versioned positions, exact text, context
and document revision identity.

## 2. Introduce `AssetKind.PDF` before PDF-scoped templates

The domain currently has only `IMAGE`, `VIDEO` and `OTHER`. A PDF template scoped to `OTHER` would
also admit text files, archives and every other unsupported content kind. Viewer classification by
MIME does not fix template resolution because Asset kind deliberately has to be available without
opening the content provider.

The product work therefore needs an explicit `AssetKind.PDF`, including:

- name-based `assetKindOf` classification;
- `TemplateScope` encoding and decoding;
- scope editing and overlap checks;
- import, catalog and filtering tests;
- viewer-availability tests; and
- compatibility tests showing that old stored scopes still decode unchanged.

MIME may continue to answer whether the bytes can actually be displayed. It should not become a
second, inconsistent source of the Asset kind used by template resolution.

## 3. Extend the existing Asset Control model

The PDF tools do not require a parallel tool list or a new template category. The existing Asset
Control already answers which interactions one compatible Asset offers, and the existing
`ButtonType` design explicitly anticipates future value-bearing fields or notes.

The smallest coherent extension is:

- a stored Asset Control template whose scope admits `PDF`;
- existing `TAG` buttons for configured passage-scoped tags;
- a new `COMMENT` or `NOTE` button type whose result carries free text; and
- a new version of the template-button encoding that can describe value-bearing tools without
  reinterpreting version 1 rows.

This preserves stable global button IDs, immutable template versions, attachment order and the
existing first-attached-match resolver.

### Clarification required: what is a tag's input?

The draft payload shows a tag with an `input` value such as `"funny sentence"`. That is ambiguous.
It may mean either:

1. a tag configured on the template, selected by the reviewer; or
2. arbitrary text typed by the reviewer and called a tag.

The first interpretation matches Listea's existing tag model: the stored mark names a stable
button ID and export resolves its configured record value. The second is effectively another free
text field and has different identity, editing and export semantics.

The recommendation is to keep tags configured by the template and reserve free text for Comment.
The domain should use a neutral result field such as `value`, nullable for a configured tag, rather
than forcing both meanings into a property named `input`.

## 4. Add `marks`; do not change the type of `actions`

The existing export contract defines `assets[].actions` as an ordered array of strings. Changing
its elements into objects would break existing image/video receivers and contradict the round's
compatibility requirement.

Quoted results should be a new Asset-level collection:

```json
{
  "actions": ["favorite", "cust1"],
  "marks": [
    {
      "id": "opaque-mark-id",
      "kind": "comment",
      "toolId": "opaque-tool-id",
      "quote": {
        "page": 0,
        "text": "text from the PDF"
      },
      "value": "I think …"
    },
    {
      "id": "another-mark-id",
      "kind": "tag",
      "toolId": "configured-tag-id",
      "quote": {
        "page": 1,
        "text": "another passage"
      },
      "value": "funny_sentence"
    }
  ]
}
```

The exact fields remain a receiver decision. The important structural decisions are:

- `actions` retains its current type and meaning;
- `marks` is plural and independent, because the same tool may produce several marks;
- a mark has its own stable ID;
- internal anchoring data need not be exposed to the receiver;
- images and videos continue to emit their existing `actions`; and
- a PDF may in the future carry both file-scoped actions and passage-scoped marks without either
  concept being overloaded.

If the receiver explicitly guarantees that unknown fields are accepted, `marks` may be an additive
v2 extension. Without that guarantee, the safer choice is contract v3. A fixed, versioned contract
should not depend on an assumption that the receiver ignores new fields.

## 5. Use a resilient quote anchor

`page index + PDFium character range + text` is adequate for reopening an unchanged document with
the same parser. It is not enough to prevent a durable mark from silently pointing to the wrong
passage after:

- replacement of the file at the same path;
- page insertion or reflow;
- a parser or PDFium upgrade changing character segmentation;
- repeated occurrences of the same quote on one page; or
- a still-valid numeric range now containing different text.

The anchor should be versioned and carry at least:

```text
anchorFormatVersion
documentFingerprint
pageIndex
start/end position or selection boundaries
exactText
prefix
suffix
```

On reopen:

1. If the document revision and text at the stored position match, restore directly.
2. If the position no longer matches, search for a unique `exactText + prefix + suffix` match.
3. If no unique match exists, retain the mark as orphaned and show its stored quotation without a
   page highlight.

The viewer must never silently draw an old mark over different text. A full-file fingerprint may
be cached and computed off the UI thread; whether it is a content hash or another sufficiently
strong revision identity is an implementation decision.

The existing open question about changed or missing files may remain open at the product-policy
level, but the schema must already be capable of detecting and representing a detached anchor.

## 6. Settle the domain and wire contract before schema 28

The current plan lists storage before the template model and export contract, while also observing
that the stored shape must be able to produce the final export. The dependency runs in the opposite
direction.

Before designing the Room table, decide:

- the PDF Asset kind;
- tag versus comment semantics;
- the tool/button representation and encoding version;
- the mark's domain fields and stable ID;
- the anchor and orphaning policy;
- which template reference means "created under" and which currently attached version controls
  visibility; and
- the export contract version and shape.

Only then define schema 28. A likely table is `task_asset_marks`, keyed to the Task–Asset pair and
containing an opaque mark ID, tool ID, authored-under template reference, anchor payload/version,
optional result value and timestamps. Current visibility should be resolved through the Task's
current attachment and current template version, rather than copied into the mark.

The schema and foreign-key policy must preserve the spec's rule that removing a template or tool
hides a mark without deleting it.

## 7. Complete the mark lifecycle and no-template behaviour

The acceptance criteria cover creation and restoration but not correction. At minimum, a reviewer
must be able to delete an accidentally created mark. Editing a comment is preferable; if deferred,
delete-and-recreate must be explicit and usable.

The product design should also specify:

- how overlapping marks are drawn and selected;
- whether comment and tag highlights use different styling;
- how a user reads the comment or tag behind an existing highlight;
- whether a selection may receive several tools in one interaction;
- how selection behaves when a template disappears while the viewer is open; and
- whether ordinary Copy/Select all remains available without a PDF template.

The last point needs wording clarification. "No template offers no tools" should probably mean no
Listea review tools and no stored/rendered/exported marks, while ordinary reading functions such as
copying text may remain viewer behaviour. If even text selection must be disabled, say that
explicitly and test it.

## Recommended implementation order

1. **Domain and contract decision record**
   - Add `AssetKind.PDF` to the design.
   - Decide configured Tag versus free-text Comment semantics.
   - Decide `marks` and export v2/v3.
   - Decide the durable anchor and orphan behaviour.

2. **Renderer decision and adapter** *(resolved: Nucleus adopted, AndroidX deferred)*
   - Record the measurement and the re-evaluation gate from section 1.
   - Establish the viewer adapter boundary and prove that no renderer-owned type enters the domain,
     persistence or export layers.
   - Record the compatibility floor (`minSdk 24`, unchanged), package cost and the deferred
     alternative.

3. **Read-only product viewer**
   - Remove spike labels and logging.
   - Implement large-file policy, lifecycle cleanup and mapped error states.
   - Verify every browsing surface, Share and unchanged-file checks.

4. **Template/tool model**
   - Add PDF scope and the value-bearing comment type.
   - Version the button encoding.
   - Add resolver, edit, scope-overlap and compatibility tests.

5. **Schema 28 and mark repository**
   - Store stable mark identity, tool identity, authored-under version, resilient anchor and value.
   - Implement create, read, delete and, if included, edit atomically.
   - Preserve hidden/unmatched marks.

6. **Review UI and rendering**
   - Gate Comment and Tag by the resolved current template.
   - Restore highlights, display mark details and handle orphaned marks visibly.
   - Verify repeated, overlapping and multi-page marks.

7. **Export**
   - Emit only marks whose tool resolves through the current attached template version.
   - Preserve existing image/video `actions` byte-for-byte at the contract level.
   - Add receiver fixtures and compatibility tests for the selected contract version.

## Acceptance additions recommended

In addition to the existing acceptance list, require:

- a 100 MB-class PDF does not require an unbounded heap copy and does not crash the viewer;
- API 24 remains the supported floor: Nucleus PDFium declares `minSdk 24`, no API-gated call is
  used, and lint/build enforce the floor. No API 24 device is available for the walk; the
  maintainer's current device passes it, and the floor is unchanged unless this round deliberately
  raises it (it does not);
- two-column, table, Chinese and RTL selections produce correct quotations;
- an accidentally created mark can be removed;
- a mark never highlights different text after a document change;
- an unresolvable anchor remains stored and is presented as detached rather than lost;
- removing and restoring a tool or template hides and restores the same mark ID;
- no-template behaviour distinguishes ordinary reading tools from Listea review tools explicitly;
- image/video payload fixtures remain unchanged; and
- dependency notices and release packaging are verified for the renderer actually selected.
- the persisted anchor and exported mark contain no AndroidX- or PDFium-specific object or encoded
  implementation detail.

## Recommended technical direction

**Settled direction for v0.7.0:**

> **Nucleus PDFium viewer behind a renderer adapter + the existing Asset Control template model
> extended with `AssetKind.PDF` and a value-bearing Comment type + a dedicated `task_asset_marks`
> table + a versioned, renderer-neutral text-quote anchor + an Asset-level `marks` export
> collection (contract v3 only when marks are present).**

**AndroidX PDF is recorded as a deferred candidate**, not this round's implementation. The
measurement in section 1 shows it cannot provide selection on the maintainer's API 33 device, and
the re-evaluation gate requires full text capability across the whole supported device range, a
stable release, and the adapter/anchor boundary already in place. If that gate is never met, the
product must state a higher capability floor explicitly rather than vary by device.

The current spike establishes feasibility on the real fixtures and device. What this round adds is
everything the spike deliberately left out: the PDF kind, the template vocabulary, durable marks,
the resilient anchor, the review interaction and the export contract.
