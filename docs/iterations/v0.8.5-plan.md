# v0.8.5 implementation plan

> Status: **delivered 2026-10-29 as `0.8.5-preview` (805), device-accepted; unreleased.** The
> design is [v0.8.5.md](v0.8.5.md); this file is the build order and the decisions that code was
> held to. The results and every deviation are in
> [v0.8.5 → Acceptance record](v0.8.5.md#acceptance-record). Baseline: `main` at `29e4a63`, app
> `0.8.4-preview` (804), schema 33, which passed acceptance and is pushed. Target: app
> `0.8.5-preview` (805), schema 34, protocol `listea.package/3`, export v7.

## How to read this plan

The phases are ordered so that each one can be built and tested without the next. P1 is pure and
fully unit-tested; P2 is additive and migration-tested; P3 and P4 make the data readable before P5
makes it writable; P6 is the surface work; P7 is the wire; P8 is the fixture and the full build.
P9 is the only phase that touches the phone. A phase is done when its own tests pass and the
previously shipped suites still pass.

The design document is authoritative on *what*; this plan is authoritative on *where*, *in what
order*, and *how a deviation is recorded*. Where code overturns a design statement, the design is
amended in the same docs layer, not left to drift.

## Scope

### In scope

- Conditions between TaskParts in one Task: `prompts[].when` in protocol v3, stored on the target
  part, evaluated as applicability at read and write time.
- Per-part judgments: `task_parts.partJudgment`, resolved from the built-in judgment set, with a
  Task-level container that keeps the completion policy.
- A media Prompt (`kind: "media"`, schema 1, `response: "freeform"`) and its part judgment, so a
  conditional PDF/image/video review is a first-class part rather than a masked media Task.
- A mixed Task container, so a Section may present a form gate, a PDF, an image/video, a vocabulary
  card, a dating card and another form in one Task.
- Stale answers, reopening, active-aware completion, and the page list that stays stable while
  conditional pages are masked.
- Export v7, dissolution part-record v2, schema 34, and the acceptance fixture.

### Out of scope

- Conditions across Tasks, across sections, or across Packages. A condition always resolves inside
  one Task; the import makes that explicit rather than guessing.
- A condition source that is optional. Every Package part is required today; the protocol
  diagnoses an optional source rather than allowing a target to wait forever.
- Editing `when` from the app. Packages are authored outside the app; the app reads and stores.
- A general expression language. One condition per part, one source field, `equals` or `in`.
- Reworking asset controls, add-ons, the webhook transport, or the task/queue navigation model.
- v1/v2 Package bodies. They stay byte-compatible and keep their v5/v6 export shapes.

### Amendments this round makes to v0.8.4

Both are recorded in `docs/iterations/v0.8.4.md` in P0:

1. **An explicit completion is no longer absolutely final.** It is still never cleared by an
   automatic recompute, but a required conditional part that moves `inactive → active` reopens the
   Task regardless of who completed it. The sign-off described a smaller Task than the one now on
   screen.
2. **Conditions are no longer only intra-Prompt.** The v0.8.4 `form` keeps its field-level `when`
   inside one body; v0.8.5 adds cross-Prompt `when` between parts of one Task. The v0.8.4
   composition closure still holds: nothing crosses a Task boundary.

### P1 — Contracts and pure planning

New domain types, all pure and testable without Room:

- `domain/PartCondition.kt`
  - `enum class PartApplicability { Pending, Active, Inactive }` with a stable wire key.
  - `enum class PartConditionMatch { Equals, In }`.
  - `data class PartCondition(sourcePartKey, field, match, values)`.
  - `encodePartCondition` / `decodePartCondition`, canonical key order `prompt`, `field`, then
    `equals` or `in`; strict decode; the existing `MAX_CONDITION_VALUES = 50` and key rules.
  - `data class ApplicabilityPart(partKey, position, required, present, availability, condition,
    kind, response)` and
    `fun evaluateApplicability(parts: List<ApplicabilityPart>): Map<String, PartApplicability>`.
    The evaluator is ordered by `position`, reads the source's canonical response through
    `ReviewResponse.parse`, and implements D2 exactly: no condition → active; inactive source →
    inactive; pending source → pending; active unanswered source → pending; answered source without
    the field → inactive; otherwise match the value. A missing source row is inactive.
  - `fun PartCondition.matches(value: String?)`.
- `domain/MediaPrompt.kt`
  - `data class MediaPrompt(override val stem: String) : PromptContent` with empty options.
  - `parseMediaPrompt(payload, response)` accepting only `freeform`, strict `{"stem": …}`, bounded
    by the existing label limit.
- `domain/ProfilePrompt.kt`
  - `ViewerCapability` gains
    `conditionFields: (String) -> Set<String>?` — the Viewer's own answer to *which fields may a
    downstream condition name*, so Core never learns a body's shape.
  - `Profile`/`Vocabulary`: `{ "choice" }`. `Form`: the parsed form's field keys, or null when the
    body is unreadable. `Media`: the empty set.
  - `val Media` capability: ref `builtin.viewer.media@1`, kind `"media"`, schema 1,
    responses `{ FREEFORM }`, intents empty, `parse = parseMediaPrompt`.
  - Add `Media` to `all` and `forPrompt`.
- `domain/Templates.kt`
  - `val MediaPart`: ref `builtin.media.part@1`, name "Media Part", viewer `Viewers.Media.ref`,
    accepts empty, `CommitPolicy.ConfirmControl("done")`, `revisable = true`,
    `completesTask = true`, `advanceAfterCommit = true`, `completion = SinglePart` (ignored when
    inherited by a multi-part Task; honoured only when the Task policy is `singlePart`).
  - `val MixedStructured`: ref `builtin.structured.mixed@1`, name "Mixed Task", viewer
    `builtin.viewer.mixed@1` (a label-only reference, no payload capability), accepts empty,
    `CommitPolicy.ConfirmControl(TASK_REVIEW_COMPLETE_CONTROL)`, `revisable = true`,
    `completesTask = true`, `advanceAfterCommit = true`,
    `completion = AllRequiredParts`.
  - A `Templates.BuiltinJudgments` list containing the picker reviews plus `MediaPart` and
    `MixedStructured`; `reviewForRef` falls back to this list, so an internal judgment resolves
    without a seeded row and never appears in the picker.
  - `TemplateLabels.reviewCatchLine`: `builtin.structured.mixed` → "Headless template · records
    each part's answer"; `builtin.media.part` → "Headless template · records the files".
- `domain/PackageProtocol.kt`
  - `PROTOCOL_V3 = "listea.package/3"`, `PROTOCOL = PROTOCOL_V3`.
  - `PROMPT_FIELDS_V3` = v2 fields + `when`; `isV3`.
  - `PlannedPrompt.condition: PartCondition?`; `PackagePlan.hasConditions`.
  - v3 is the only protocol that accepts `when`, `kind: "media"` and `freeform`. A v2 manifest
    using them gets `when-in-v2`, `media-in-v2`, `response-unsupported` respectively; a v3 manifest
    with a bad condition gets the diagnostics below.
  - A second pass after prompt parsing resolves each `when` against the earlier prompts, through
    the source capability's `conditionFields`. Prompt-level diagnostics; the target becomes
    unavailable with the first code.
  - The fingerprint includes each `when` canonically, so editing a condition changes the content
    identity.

Diagnostics (target unavailable unless the scope is PACKAGE, which rejects the whole manifest):

| Code | When |
|---|---|
| `condition-invalid` | Not an object; unknown keys; both or neither `equals`/`in`; empty or >50 values; bad key. |
| `condition-source-unknown` | `prompt` names no Prompt in the manifest. |
| `condition-source-not-earlier` | Source is at the same or a later index than the target. |
| `condition-source-optional` | Source is not required (unreachable with today's all-required Package parts; kept fail-closed). |
| `condition-field-unknown` | The source Viewer's `conditionFields` does not contain `field`, or the source body is unreadable. |
| `media-in-v2` | A pre-v3 manifest declares kind `media`. |
| `when-in-v2` | A pre-v3 manifest declares `when`. |
| `media-file-missing` | A media Prompt declares no files. |
| `unsupported-viewer` / `response-unsupported` | As today; v3 uses the capability's full response set, not "single or structured". |

`Viewers.forPrompt(kind, schema, response)` is the v3 compatibility question. v1/v2 keep their
existing hard-coded response rule so a previously accepted body stays accepted and a previously
rejected one stays rejected.

### P3 — Protocol v3, import planning and judgment resolution

- `Importer.kt`
  - `PlannedPart.condition: PartCondition? = null`,
    `PlannedPart.judgment: TemplateVersionRef? = null`.
  - `PlannedTask.taskReview: TemplateVersionRef? = null` — a per-Task override of the run's
    chosen review.
- `PackageImport.kt`
  - `plannedPromptPart` carries the prompt's condition.
  - `plannedTasks(plan, composition)`:
    - one Task per Prompt: every part with a condition becomes unavailable with
      `condition-source-outside-task`; the Task still imports and, if the part is required, remains
      blocked and is named in the report.
    - one Task per Section: a condition resolves only when its source is an earlier part **in the
      same Task**; otherwise `condition-source-outside-task`.
    - Untagged Prompts keep one Task each; a condition among them cannot resolve.
  - `mixedTask(parts)`: true when any part has a condition, or the present-part families are not
    one of the v0.8.4-homogeneous shapes. Families:
    - single-choice (`profile`, `vocabulary`) with any part count → homogeneous, no per-part
      judgment, Task-level review unchanged;
    - form → homogeneous only when the Task has exactly one form part;
    - media (`media`, schema 1, freeform) → homogeneous only when exactly one part;
    - no payload (asset-only).
    A Task with several forms, several media parts, or more than one family is mixed.
  - For a mixed Task: `task.taskReview = Templates.MixedStructured.ref`; each part gets:
    form → `StructuredForm.ref`; single-choice → `StructuredSingleChoice.ref`; media or
    asset-only → `MediaPart.ref`. An unmappable part is unavailable `unsupported-judgment`.
  - A homogeneous Task keeps the run's chosen Task Review and writes no part judgments, so its
    v0.8.4 behavior and export shape do not move.
  - `folderOffersSectionComposition` stays; add `folderNeedsSectionComposition` (any v3 condition).
- `ListsDao.applyPackages` / `writePart`
  - `writePart` writes `condition` and `partJudgment`.
  - The Task's stamped review is `task.taskReview ?: taskReview` for every Package Task; a refresh
    that turns a mixed Task homogeneous re-stamps the run's review.
  - Re-import reconciliation rewrites conditions and judgments for present parts, clears a removed
    `when`, and recomputes availability. A removed source produces
    `condition-source-detached` on dependent parts, which block if required.
- `MainActivity` import dialog
  - When a folder's manifests contain a condition, the composition default is **one Task per
    Section** and the radio carries a warning: conditional questions need their earlier answers in
    the same Task. Choosing one Task per question remains possible and the report names each
    conditioned part that imported unavailable.
  - No new dialog step; the existing composition radio is the choice.

### P4 — Read model, pages and counts

- `ListsDao.resolveParts` evaluates applicability once per Task from its rows and their states,
  then builds `ReviewPart`s. No stored applicability column.
- `observeDetail` does the same for the live List-preview flow.
- `reviewPages` is unchanged: it already includes every present part, so conditional pages keep
  their place. Masking is a drawing decision, not a filtering one.
- `ReviewItem.parts` and `CatalogRow.parts` now carry applicability/judgment/stale; `partCount`
  and all question counts stay the size of the present part list, conditional parts included.
- `pendingRequiredParts` becomes the count of parts that are:
  `present && required && applicability == Active && partKey !in answeredParts`.
- `observeAnsweredPartKeys` adds `AND stale = 0`, because a stale answer is not an answer for
  completion. `partsCompletionSatisfied` is rewritten in P5 against the same rule; the two paths
  stay one definition.
- `taskPageState`, `reviewPageEntries`, the inner counter, the queue menu and every catalog/progress
  surface keep counting **pages** and **Tasks**. No surface gains a TaskPart level.
- `reviewPageEntries` gives a masked page a detail suffix ("Not needed" / "Waiting for an earlier
  answer") without changing the label or the count.

### P5 — Commit, completion, stale and reopen

- `data/ListsDao.kt`
  - `submitReview` reads the Task's rows and states before the write, computes applicability, and
    refuses a part write when the named part is not `present`, not available, or not `Active`.
    (The stale re-commit is Active, so it is allowed; the non-revisable check moves to the caller
    and takes `stale` into account.)
  - Write order inside the existing transaction:
    1. read Task state, part rows and states;
    2. validate (content presentable, part named/present/available/active);
    3. `before = evaluateApplicability(...)`;
    4. upsert the part state with `stale = false` (or write nothing for a Task-level submission);
    5. `after = evaluateApplicability(...)` with the new response;
    6. for every answered part whose `after == Inactive` and `before != Inactive`, set
       `stale = 1`; also make an already-inactive answered part stale (idempotent);
    7. `reopened = task.isCompleted && any present required part with before == Inactive &&
       after == Active`;
    8. `satisfied = partsCompletionSatisfied(taskId, taskPolicy)`;
    9. `writeTaskState(..., reopen = reopened)`;
    10. insert the review event only when the state write found a row;
    11. `refreshAffected` exactly as today, so a List moves both ways.
  - `partsCompletionSatisfied` evaluates applicability and counts only active, present, available,
    required parts. Answered means `answeredAt != null || response.isNotEmpty()`, **and
    `!stale`**. `AllRequiredParts` is vacuously true when no required part is active; `AnyPart`
    needs at least one active required answer; `SinglePart`/`ExplicitOnly` stay false.
  - `writeTaskState` gains `reopen: Boolean = false`. When `reopen` and the Task was completed, it
    writes `isCompleted = false` and `completionSource = COMPLETION_REOPENED`, bypassing the
    explicit-preservation rule for this one transition. Otherwise the existing keep-explicit rule
    is untouched. Add `COMPLETION_REOPENED = "reopened"` and update the KDoc on
    `TaskStateEntity.completionSource`.
  - `applyImport`: snapshot applicability before `applyPackages`, evaluate after, mark stale on
    parts that are answered and inactive, and reopen a completed Task when a required part moved
    inactive → active. Then the existing completion recompute runs. A re-import never invents an
    answer and never clears an explicit completion except through that reopen.
- `ListsViewModel.kt`
  - `submitItemReview` gains a separate `taskReview` (the container) while `review` remains the
    page's judgment:
    `submitItemReview(item, terms, review, taskReview = review, events, partKey, fields, ...)`.
    The event records `review.ref`; completion uses `taskReview.taskReview.completion`; the
    `completesTask` flag comes from `review`, and the DAO honours it only under `singlePart`.
  - `submissionAccepted` uses the part's live `ReviewPart`:
    - refuses when `applicability != Active` or `availability != null`;
    - STRUCTURED: requires `review.viewer == capability.ref` and the form fields;
    - FREEFORM (media): requires `review.viewer == capability.ref`, no events, no fields;
    - SINGLE: existing rule;
    - `partIsRevisableOrUnanswered` returns true when the part is stale, so one reconfirmation is
      allowed even under a non-revisable judgment. A fresh commit clears stale.
  - The response built for a media part stays `MediaReview(completed = true, selections = …)`; it
    serialises as answered-empty in export.
- Pure tests: applicability table, completion table, reopen detection, stale transitions, and an
  explicit completion being reopened by a required inactive → active.

### P6 — Media part, mixed container and masking in the UI

- `PromptContentPage.kt`: a `MediaPrompt` branch — a read-only stem card, no options, no swipe
  commit. The part's material is on its Asset pages.
- `ReviewScreen.kt`:
  - Resolve `taskReview` once (Task container). Resolve `pageReview` per current page from the
    part's `partJudgment`, falling back to `taskReview`; an unresolvable judgment produces a page
    notice and a disabled page.
  - `pageDefinition` drives `accepts*`, commit control, immediate-choice behavior and
    `advanceAfterCommit`. `taskDefinition` drives the completion policy and explicit completion.
  - `commitPartKey` is unchanged; `commit(events)` passes `pageReview ?: taskReview` and
    `taskReview`.
  - A masked page (`applicability != Active`) renders an explanation card in place of the viewer
    or file: Content and Asset pages both. The card states pending vs inactive, and an Active but
    stale part says the previous answer is set aside and must be submitted again. File identity,
    page count and navigation stay.
  - Controls are not drawn on a masked page. Swipe on a masked page is a page turn, never a
    commit; forward navigation remains available off the Task's last page.
  - The part's own control (Submit / Done) is drawn on Content, image/video and PDF pages of that
    part. A freeform media part's Done is enabled without a viewer event. The PDF band gains the
    control above its Info entry for exactly this case.
  - The Task completion bar appears for a mixed Task (the container's explicit `complete`), with
    `pendingRequiredParts` active-aware. Homogeneous v0.8.4 Tasks keep the bar they have today; a
    SinglePart Task with a part judgment shows the part's control and no duplicate checkbox.
  - `dispatch(CompleteTask)` on a masked page advances a page instead of committing.
- `ReviewPages.kt`: no count change. The page list is the same for every applicability.
- `TemplateLabels.kt`: the two internal judgments get honest lines if they ever reach a picker;
  they do not enter `attachableReviews`.

### P7 — Export v7 and dissolution

- `Exporters.kt`
  - `ExportPartView` gains `judgment: ExportTemplateView?`, `condition: PartCondition?`,
    `applicability: PartApplicability`, `stale: Boolean`.
  - `exportTaskViews` receives `PayloadPartRow`s with condition/judgment/state, computes
    applicability per Task with the same evaluator, and fills the four fields. A judgment exports
    as `{id, version}` (name may be null); it is an identity, not a copy of the definition.
  - `mapExport` adds `carriesConditional` when any Task has a part with a condition or a judgment,
    and `exportVersion(..., carriesConditional)` returns 7 first. `EXPORT_VERSION_CONDITIONAL = 7`.
    v6 stays for compatible v0.8.4 Tasks; v5 stays for compatible single-part Tasks.
- `Webhook.kt`
  - `partJson` takes the document version. For version ≥ 7, after `required` and before `result`,
    it writes, in this order:
    ```
    judgment:      {"id": "…", "version": N} | null
    when:          {"prompt": "…", "field": "…", "equals": "…"} |
                   {"prompt": "…", "field": "…", "in": ["…"]} | null
    applicability: "active" | "pending" | "inactive"
    stale:         true | false
    result:        null | "" | {"choice": …} | {"fields": …}
    assets:        […]
    ```
  - v6 bodies are byte-identical to today; the key order is pinned by tests. The text export uses
    the same body, as it always has.
  - An inactive answered part keeps its result and carries `stale: true`; an inactive unanswered
    part carries `result: null`. `completed` remains the Task's authoritative state.
- `DissolvedRecords.kt`
  - `DISSOLVED_PARTS_VERSION = 2`. A version-2 line is six tab-separated, escaped fields:
    `partKey`, `required`, `partJudgment`, `condition`, `stale`, `response`. Empty judgment or
    condition means none. The reader accepts version 1 (three fields → none/false) and version 2;
    anything else is unreadable and fail-closed.
  - `DissolvedPartRecord` gains `partJudgment: String? = null`, `condition: String? = null`,
    `stale: Boolean = false`.
  - `snapshotDissolvedState` reads the new columns; `recoverStateFrom` restores the response and
    re-derives applicability from the **new** composition, marking answered inactive parts stale.
    It does not write the old condition or judgment over the new part: the composition is
    authoritative and a recovery must not resurrect a branch its Package no longer declares.
    The stored fields exist so the snapshot is a faithful account, not so recovery can overwrite.

Acceptance walk, in the order that exercises the state machine:

1. Import `conditional-mixed` with the add-on, one Task per Section. The queue holds **one Task**.
   Every browsing surface (Todo preview, List preview, Quick Search/Quick Review, List Review,
   catalog, queue menu) says one Task and the same question/page count.
2. Gate `no`: the PDF, image/video, vocabulary, dating and second form pages are present and
   masked with the "not needed" card; the unconditional receipt and the gate remain answerable.
   The inner counter counts every page; TaskParts never appear as a level.
3. Submit the gate and the receipt; press the mixed Task's complete control. The Task completes,
   the List completes, and the webhook/text export is v7 with `applicability` and null results for
   the inactive parts.
4. Change the gate to `yes`: the Task reopens (checkbox clears, List becomes incomplete), the
   conditional pages become answerable, and no stale answer is counted. In the database,
   `task_state.completionSource = 'reopened'` and no submission event was appended for the reopen.
5. Answer the PDF (Done), the image/video (Done), the vocabulary card, the dating card and the
   second form (Submit). Completion follows the active required parts; the add-on remains last.
6. Change the gate back to `no`: the conditional answers are kept, marked stale, shown as previous
   answers if revisited, and no longer counted; the Task stays complete because the active set is
   satisfied. Export says `stale: true` for those parts.
7. Change the gate to `yes` again and re-submit one conditional part; only that part's stale flag
   clears. A non-revisable judgment still permits this one reconfirmation, and refuses a second
   answer afterwards.
8. Re-import the same Package with one Task per question: conditioned parts import unavailable,
   the report names them, and the dialog warned before the choice. Re-import with one Task per
   Section repairs them.
9. Import a v0.8.4 fixture unchanged: page counts, completion, and v6 export bytes are unchanged.

## Schema 34

```sql
ALTER TABLE task_parts ADD COLUMN condition TEXT;
ALTER TABLE task_parts ADD COLUMN partJudgment TEXT;
ALTER TABLE task_part_state ADD COLUMN stale INTEGER NOT NULL DEFAULT 0;
```

- Additive; no table rebuild; no old row rewritten. `condition` is canonical condition JSON;
  `partJudgment` is the encoded `TemplateVersionRef`; `stale` is `0`/`1`.
- `condition` is read fail-closed: an unreadable value makes the part unavailable, not
  unconditional.
- `partJudgment` is read fail-closed: an unresolvable reference makes the part unavailable
  (`unsupported-judgment`).
- `stale` is never true without an answer; a fresh commit writes it false.
- A schema-33 Task has `condition = NULL` everywhere, so all its parts are active; its page list,
  completion and v6 export are unchanged.

## Protocol v3

Manifest shape (only the new parts shown):

```json
{
  "protocol": "listea.package/3",
  "sections": [{ "key": "session", "title": "Session" }],
  "prompts": [
    {
      "promptKey": "gate",
      "kind": "form",
      "schema": 1,
      "response": "structured",
      "title": "Did you eat?",
      "description": "prompts/gate.json",
      "files": [],
      "section": "session"
    },
    {
      "promptKey": "menu",
      "kind": "media",
      "schema": 1,
      "response": "freeform",
      "title": "The menu",
      "description": "prompts/menu.json",
      "files": [{ "name": "menu.pdf" }],
      "section": "session",
      "when": { "prompt": "gate", "field": "choice", "equals": "yes" }
    }
  ]
}
```

`prompts/menu.json` is `{"stem": "Read the menu, then press Done."}`.

Rules and bounds:

- `when` is one object with exactly `prompt`, `field`, and exactly one of `equals` (a string) or
  `in` (1–50 strings). Both or neither is `condition-invalid`.
- The source Prompt is declared **earlier** in the manifest and is required.
- The source field must be one the source Viewer's `conditionFields` declares: a form field key,
  or `choice` for a single-choice part. Media has no fields and cannot be a source.
- Values are strings within the existing limits. A value that names no option is not a protocol
  error: it simply never matches, so the branch is closed. (The authoring tool can warn; the app
  does not guess.)
- `kind: "media"`, schema 1, needs `response: "freeform"`, at least one file, no options, and a
  stem body. The media Viewer owns the body shape; the protocol owns the envelope.
- v1/v2 readers are unchanged. A v3 manifest is rejected by the v0.8.4 reader as an unknown
  protocol; a v2 manifest using v3 vocabulary gets `when-in-v2` / `media-in-v2`.
- The manifest fingerprint includes `when` canonically, so a condition edit is a content change
  and a re-import notices it.

## Part judgments and the mixed container

Resolution order for one page:

1. The part's `partJudgment` ref, if present. If it cannot be resolved → unavailable
   (`unsupported-judgment`), disabled page, named in the Info sheet.
2. The Task's `task_imports.taskReview`.
3. The built-in rapid review.

The Task-level definition remains the only source of the completion policy and of explicit
completion. A part judgment contributes `viewer`, `accepts`, `commit`, `revisable` and
`advanceAfterCommit`; its `completion` field is ignored, and its `completesTask` is honoured only
under the Task-level `singlePart` policy.

| Part kind | Part judgment |
|---|---|
| `form` / structured | `builtin.structured.form@1` |
| `profile`, `vocabulary` / single | `builtin.structured.single-choice@1` |
| `media` / freeform, asset-only | `builtin.media.part@1` (control `done`) |
| mixed Task | Task-level `builtin.structured.mixed@1` (`allRequiredParts`, control `complete`) |
| homogeneous v0.8.4 Task | no part judgment; the Task-level review is unchanged |

The mixed container is an internal reference: code-only, resolvable by `reviewForRef`, never in
`attachableReviews`. A homogeneous Package Task writes no part judgment and keeps its v0.8.4
Task-level stamp, so its export stays v6.

## Applicability, stale and reopen

`evaluateApplicability` is the one implementation, called by reads, writes, import and export.
The state table and the algorithm are the design's; the write order is the P5 list above.

Two details this plan fixes because code can drift from prose:

- **Stale is set on a transition into `inactive`, and is never cleared by anything except the
  part's own fresh commit.** Reactivation alone does not clear it; a re-import does not clear it;
  a completion recompute does not clear it.
- **Reopen is a `task_state` transition, not an event.** `completionSource = "reopened"` is
  written when a completed Task sees a required part move `inactive → active`. A
  `pending → active` move does not reopen an explicit completion. A shrinking active set never
  reopens. This is what keeps `observeLatestResponse` honest: the newest `review_events` row is
  still a submission.

## Read model, pages and counts

- A Task's page list is `reviewPages(item, hasAddOn)` unchanged: every present part, Content if it
  has a body, then its Assets, then the Add-on. Conditional parts always contribute.
- Masking is in the review surface only. Read-only surfaces draw counts and first files; they do
  not draw masked content because they do not draw question content at all.
- Counts:
  - outer `x(m/n)/y`: Tasks and pages, unchanged;
  - catalog question/part count: present parts, conditional included;
  - queue menu: Tasks, unchanged;
  - completion pending count: active required unanswered (stale counts as unanswered);
  - progress bars: Tasks and pages, unchanged.
- A TaskPart is never a counter level in any surface.

## Commit, completion, reopen

Completion reads active required parts:

| Policy | Rule |
|---|---|
| `singlePart` | The one part's commit completes as before; a part judgment's `completesTask` applies. |
| `allRequiredParts` | Every active required part is answered and not stale; no active required part is unavailable. No active required parts → vacuously satisfied. |
| `anyPart` | At least one active required part is answered and not stale. No active required part → not satisfied. |
| `explicitOnly` | Answering never completes; the completion control is the only path. Reopen still applies. |

Explicit completion with open active required parts remains allowed after the confirmation that
names the count. The count excludes inactive parts and includes stale ones.

## Export v7

Version selection: 7 when any Task has a part with a condition or a part judgment; else 6 when any
Task is multi-part or structured; else the existing v5/v4/v3/v2 rules. v6 and v5 bodies are
byte-identical to today.

Per-part keys in a v7 body, in order:

`partKey`, `promptKey`, `kind`, `schema`, `revision`, `required`, `judgment`, `when`,
`applicability`, `stale`, `result`, `assets`.

`judgment` is `{"id", "version"}` (name optional) or null. `when` mirrors the protocol. The Task
shape stays the v6 `parts[]` shape, so a receiver can read the logic and the answer sheets
together. Both the webhook body and the `.txt` body are the same document.

## Dissolution

- Part-record payload v2 carries condition, judgment and stale beside the answer. v1 stays
  readable; an old record reads as unconditional, inheriting, fresh.
- Recovery restores answers and completion; the **new** composition's conditions and judgments are
  authoritative; applicability is re-derived and stale is recomputed (answered + inactive). The old
  condition is not written over a part that no longer declares one.
- The history picker and counts remain Task-based.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Schema 34 migration loses data | Additive DDL; a schema-33 fixture built by SQL; migration test; pull the device DB before installing |
| Masked pages break page/asset indices | The page list is unchanged; masking is a drawing decision; existing `TaskPageState` tests plus new masked-page tests |
| A stale answer silently counts | One completion definition; `observeAnsweredPartKeys` and `partsCompletionSatisfied` both exclude stale; write tests |
| Reopen loops | Only `inactive → active` on a completed Task reopens; `pending → active` and shrinking do not; explicit tests |
| Latest-response corruption | Reopen writes `task_state`, never `review_events`; test that the newest response is still a submission |
| Protocol v3 accepts what v2 rejected | v3-only vocabulary is gated by protocol; v1/v2 grammar tests unchanged |
| Part judgment cannot resolve | Fail-closed `unsupported-judgment`; internal refs resolve from code, not a seed row; test a deleted/unknown ref |
| Export receivers break | v7 only for conditional/judgment Tasks; v6/v5 byte-compat tests; key order pinned |
| Mixed UI duplicates completion controls | Per-page control vs Task bar split; SinglePart hides the duplicate; mixed Task shows the explicit bar; tests/screenshots |
| Composition split imports a blocked Task | Default Section when conditions exist, a dialog warning, and `condition-source-outside-task` named in the report |
| v0.8.4 regressions | Homogeneous Tasks write no part judgments and keep the v0.8.4 review, pages and v6 export |

## Scope decisions settled at sign-off

1. **Column names** are `condition`, `partJudgment`, `stale` (camelCase, matching Room and the
   existing columns).
2. **Reopen is stored in `task_state.completionSource = "reopened"`**, not in `review_events`.
3. **Internal judgments are code-only** (`MediaPart`, `MixedStructured`); they resolve through
   `reviewForRef` and never appear in the template picker.
4. **Media part control is `done`**; the body is a stem; at least one file; freeform only.
5. **Mixed trigger**: any condition, or a Task that is not one of the homogeneous v0.8.4 shapes
   (any-count single-choice, exactly one form, exactly one media, or asset-only).
6. **Composition**: conditions default to one Task per Section; the dialog warns; one Task per
   question remains possible and names each conditioned part it cannot resolve.
7. **Masked pages still count**; the Add-on is never masked; TaskPart is never a counter level.
8. **The Task completion bar is the explicit control for mixed Tasks**; homogeneous Tasks keep
   their v0.8.4 bar behavior.
9. **Source fields are validated by the Viewer capability**, not by Core parsing a body.
10. **Export v7 adds four per-part keys** in the pinned order and selects the version from the
    presence of a condition or part judgment.
11. **Dissolution v2 records the new part facts but recovery re-derives**; the new composition
    wins.
12. **v0.8.4's explicit completion is amended**: a required inactive → active transition reopens
    it; v0.8.4's intra-Prompt condition boundary is widened to cross-part conditions in one Task.
