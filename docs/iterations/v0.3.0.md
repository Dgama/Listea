# Listea v0.3.0 — Upstreams and Todo

> **Status:** Iteration specification, revised 2026-09-17
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.2.5 (Source registration, importers, the Task catalog)
> **Prepares for:** cloud storage and database Upstreams, and a `jobs` layer between assets and Tasks

## Outcome

v0.3.0 separates **where material comes from** from **what there is to review**, and gives each its
own tab.

```text
Upstreams                    Todo
a folder Listea may read      the Tasks one Create Tasks run produced
  → browse, Create Tasks        → browse, Quick Review, Create List
```

Today both live in the Folder tab: "Import Folder" registers a Source, and Quick Review and Create
List sit next to it on the same action bar. The two jobs are different — one brings material in, the
other decides what to do with it — and merging them is what makes the Folder tab hard to read.

## Revision, 2026-09-17

**The first pass at this iteration moved the labels and left the model alone. That was wrong, and
this document has been rewritten around what replaced it.**

The first version kept one `sources` table and one concept behind both tabs:

| UI | Model | What it is |
|---|---|---|
| **Upstream** | `SourceEntity` | A picked folder that material is imported from |
| **Todo** | the Source's catalog | The Tasks an Upstream produced |

The argument for it was cost — renaming the model would touch every DAO, migration and wire path.
The argument was sound and the conclusion was still wrong, because the two tabs were not two views
of one thing. A folder the user has chosen and a body of work an import has produced are **different
lifetimes with different owners**, and one row cannot be both:

- An Upstream exists before it has ever been imported, and outlives every import run over it.
- One Upstream can carry **several** Todos, over different folders in its tree, or none at all.
- A Todo is not "the folder's contents". It is what one run, over one folder, under one importer,
  produced — and there is no folder-shaped shortcut to saying that.

Keeping one row forced the UI to lie about all three. "Add another Upstream" had to register a
Todo binding, because registering the row *was* registering the Todo. The Upstreams card had to
carry a Task count, which is a fact about an import, on a screen about material. Catalog had to be a
button on it, because the row was also the Todo. And Quick Review had to be offered at the top of a
Todo, where the only rows in front of the user are folders.

What the revision changed, in one place each:

| Change | Why |
|---|---|
| `upstreams` is a table of its own, `sources` is what an import run wrote | Two lifetimes, two records. Room `version = 16` |
| An import is started **inside** an Upstream, on the folder it is to run over | Reading part of an Upstream is ordinary; registering one is not implied by it |
| **Add Upstream** lives in Settings, not on the Upstreams tab | Adding a folder is a decision about what Listea may read. The Upstreams tab lists and opens; it does not add |
| Each Upstream holds **its own** access grant | `FolderStore`'s single root was the reason a second folder cost the first. A device now holds as many grants as it has Upstreams |
| The Upstreams card is the way in and carries no actions | Its folder is the only thing it is about. No count, no Catalog, no Create Tasks button |
| The Todo card is the way in; **Refresh Import** is the only button left | Catalog was a button to the place the card now goes. Quick Review was a round over a scope that may hold only folders. Create List was a List built from Tasks nobody had looked at |
| Quick Review covers the Tasks **directly in one folder**, and is not offered where there are none | The tree is how the user says which part of a Todo they mean. A round that recursed would make the folder they chose meaningless |
| Create List is reached by **Select**, inside a Todo | The Tasks are the only rows that can say which of them was meant |
| The Task preview **steps between Tasks**, as well as within one | A preview is opened from a level and a level is a sequence. Sending the user back to the catalog to move one row down costs a screen and a tap to answer a question an arrow answers directly |

**Source is retired as a name for anything inside the system.** A Source is a file outside the app,
which exists whether or not anyone has chosen it; an Upstream is that file once someone has. Nothing
stored is called a Source. `SourceEntity`, `sourceSummaries` and the `sources` table keep their
names because renaming them is a mechanical change with no behavioural gain, and because `sources`
now means something narrower and true — the import run — rather than standing in for two things.

**Three defects fixed alongside, all found by walking the build.**

- **The Upstream browser had no way out.** `openUpstream` was not part of the shell's "a nested
  surface is up" state, so the bottom bar kept drawing over the browser and switching tabs did not
  clear it. Back at the Upstream's own folder now returns to the Upstreams list, and the shell's
  Back handler is off while the browser is up.
- **The Catalog breadcrumb's `Root` sat out of line.** The row had no `verticalAlignment`, so a
  `TextButton` — which Material gives a 40dp minimum height — was top-aligned against plain `Text`
  siblings and pushed `Root` above the folder names beside it.
- **A Todo whose run started inside a subfolder had no level to review.** `openCatalog` set the
  scope to the empty path — the grant's root — for every Todo, but a run started on `xvideo-jp`
  writes every `groupPath` prefixed with `xvideo-jp`, so the Todo's root is that subfolder and the
  grant's root is a level above it. The catalog still drew every Task, because a flat Todo ignores
  the scope, which is why the defect was invisible there; Quick Review applied `directChildOf` to
  the same wrong scope, found nothing, and reported "Nothing to review here yet" over a folder full
  of reviewable Tasks. The scope origin is now the Source's `relativePath`, and the three consumers
  — the catalog's list, Quick Review's queue, the preview's sequence — read one `catalogLevel` so
  they cannot disagree again. See [`review-and-actions.md`](../review-and-actions.md).

**Why the origin and not a rebase.** The obvious fix was to strip the subfolder prefix from every
`groupPath` so a Todo's Tasks sat at the grant's root, as a Todo made on the whole Upstream has them.
That was rejected: `groupPath` is persisted into `list_items.rootRelativePath` by `listItemForTask`
and documented as "the Task's position in the source tree, as `task_imports.groupPath`". Rebasing
would give the same column two meanings depending on when the row was written. Moving the *reading*
of the scope leaves every stored path alone.

**Not addressed this round: build size.** Raised as a jump from ~25 MB to ~90 MB. Measured, the
APK file is **25.2 MB** and the installed app directory on the attached device is **24.6 MB** — the
download has not grown. What is large is what is *inside* it: 75 MB uncompressed, 73.9 MB of that
DEX, with 21,320 Compose icon classes compiled in against the 38 the app names.
`material-icons-extended` is the cause and R8 is off in both build types. It is a
build-configuration problem with no design content, it is deferred rather than fixed, and the
measurements and the three ways out are in
[Development](../development.md#build-size-and-where-it-comes-from).

## Vocabulary

**Task is the unit.** Everything else in this app is either material or an organisation of Tasks.

| Word | What it is |
|---|---|
| **Source** | A file **outside** the system. Not a stored concept, not a row, not a screen |
| **Upstream** | A folder Listea has been given. Material, not work: it holds no Tasks and owns no review context |
| **Todo** | What one **Create Tasks** run produced: the Tasks, and the provenance saying which folder and which importer made them |
| **Task** | One unit of work. The atom: selection, review and state are all at this level |
| **Asset** | One file inside a Task |
| **List** | A persistent organisation of Tasks, currently built by selecting them inside one Todo |

`todo` and `list` are **two ways of organising the same Tasks** — one produced by an import, one
chosen by hand — and neither is a kind of Task.

**A note on the names that were not chosen.** `job` is the better word for what this app calls a
`Task` — the chain should read file → asset → job → task, and today's `Task` is really a job (a unit
of work) while a task is a unit of intent inside it. That rename is not in this release. It touches
every entity, table, DAO and doc in the project, and doing it in the middle of a UI restructure
would make both changes unreviewable.

## The rename, and what it is allowed to touch

Three **persisted** identifiers contain "folder". None may be renamed — renaming any of them
silently discards user data on upgrade:

| Persisted name | Where | Cost of renaming |
|---|---|---|
| `"listea_folder"` | `FolderStore.kt` — SharedPreferences file | The saved root grant; every user re-picks their folder |
| `"folder_quick_review_enabled"` | `Settings.kt` — DataStore key | The Quick Review toggle reverts to its default |
| `"folder_file_arrangements"` | `Settings.kt` — DataStore key | Every per-folder sort and filter |

Also persisted, but semantically about *grouping* rather than about the tab, so they stay on their
own merits: `ImporterKind` key `"folder-as-task"` and `ReviewContextKind.FOLDER` → `"folder"`.

`FolderStore` itself is deleted in this iteration — the multi-grant change replaces it with the
grant set the platform already keeps (`contentResolver.persistedUriPermissions`), and the
`"listea_folder"` key goes with it. An install upgrading to v0.3.0 does not lose its folder: the
grant it was holding is a persisted URI permission like any other, and the migration turns the
Source rows into Upstreams.

**User-visible copy naming the tab** is hardcoded Kotlin, not `strings.xml` — the resource file
holds only `app_name`, so there is no localized copy to miss and a grep is exhaustive.

`TopLevelDestination` is stored by `rememberSaveable`, which serialises an enum by constant name.
Renaming a constant therefore throws on process-death restore from a bundle written by the previous
build. The affected state is transient, but the enum gets an explicit name-based saver rather than
relying on the default.

## 1. An Upstream is a folder Listea has been given

**A folder picked in Settings becomes an Upstream.** This is the load-bearing change, and it is
smaller than it looks: a `sources` row already recorded a picked folder — `rootUri` is the SAF grant
it sits under, `relativePath` is the path beneath that grant, and `''` already means the grant root
itself. What changes is that the row no longer *also* means "a body of imported work".

**Adding is a Settings action.** The Upstreams tab lists Upstreams and opens them; it offers no
picker. Two places to add a folder would be two places for the wording of the confirmation, the
failure and the name to drift apart, and adding a folder is a decision about what Listea may read
rather than about any folder in front of the user.

**Several Upstreams, each with its own grant.** `FolderStore`'s single `rootUri` is gone. An Upstream
is available when the platform holds a persisted read permission for a URI that covers its
`rootUri`; that is a set, and a device holds as many as it has Upstreams. `heldRootUris(context)`
reads it. This costs nothing at rest — the platform was already storing one persisted permission per
picked folder — and it removes the rule that adding a folder costs you the last one.

**The legacy single-root concept survives only where it is data.** Lists built by v0.2.x scanning
carry `sourceRootUri`; those columns are untouched, those Lists keep working, and nothing added now
is bound to them. Settings no longer has a root row, a change dialog or a replacement warning,
because there is no longer a root to change.

## 2. Upstreams

The tab lists one card per Upstream. **The card is the way in and carries nothing else.**

| Card area | Shows |
|---|---|
| Title | The Upstream's `displayName` |
| Detail | Its `relativePath` when it is not the grant root |
| Actions | None. Tapping the card opens the folder |

Opening an Upstream shows the browsed folder: the breadcrumb, the folder cards, the file rows, sort
and filter, and the file viewer. **Create Tasks** is the one action on it, on a folder's own row and
on the Upstream's card.

**A Task count and a Catalog button were both on the first version of this card and both are gone.**
A count is a fact about an import, and this screen is about material that may never have been
imported. Catalog was a button to the Todo, and the Todo now has a card of its own on its own tab.

**No Quick Review and no Create List here, and none in the browser.** They decide what material
*means*, and that decision belongs to the Tasks a Todo holds. A browser action bar that no longer
offers them is the visible point of the split.

### The upstream browser

**Back walks up the tree, and at the top leaves the Upstream.** The browser is a nested surface of
the Upstreams tab, so Back has somewhere to go at every depth: the stack pops while it holds more
than one entry, and at the Upstream's own folder it returns to the Upstreams list. The browser is
part of the shell's nested state (`openUpstream` is one of the things that suppress the chrome), so
the bottom bar and the tab title do not draw over it and switching tabs leaves it.

**Two path vocabularies meet here, and only the stack speaks the Upstream's.** The browsing stack is
based at the Upstream's own folder, so `relativePathOf(stack)` answers relative to that, while every
*stored* path — a Source's `relativePath`, a List's scope, a per-folder arrangement key — is
relative to the grant. `here` is where the two are joined. Keeping stored paths grant-relative is
what leaves existing arrangements and ownership keys untouched by a restructure that moved only
where browsing begins.

Three action-bar entries remain: **Refresh**, **Open List** (when a List owns the folder) and
**Create Tasks**. Open List stays because it is a way back to a List this folder is already part of,
not a way to make anything.

**`quickReviewEnabled` still gates this screen, and only its display.** The setting used to decide
whether Quick Review was *offered* here; it now decides whether the browser draws what is already
decided — the ticks, and the "checked" entries in the sort and filter dialogs. Turning it off is
still presentation only, and it still governs the round itself inside a Todo.

### Create Tasks

The old "Import Folder" action, renamed, with a richer dialog. Renaming follows the vocabulary
rule: the folder is the Upstream's, and what the action *produces* is a Todo of Tasks.

The dialog collects three things and then runs the import:

| Field | Notes |
|---|---|
| **Importer** | `file-as-task` / `folder-as-task`, as today |
| **Name** | Free text, defaulting to the folder's own name. Becomes the Todo's `displayName` |
| **Keep folder tree** | Whether the imported Tasks keep their folder structure |

**The run happens on the folder the user was in.** Started from a folder's row it imports that
folder; started from the Upstream's card it imports the whole Upstream. This is what keeps the
Upstreams pool clean: registering a folder binds nothing, so importing part of one creates a Todo
over part of it and leaves the rest alone — **provided that part is disjoint from every Todo already
made.** A folder nested inside an existing Todo is refused; see
[Out of scope](#5-out-of-scope) for why that is a policy question rather than a defect.

> **Superseded in v0.4.0.** The disjointness requirement and the refusal that enforced it are gone.
> A file is no longer owned by one Task, so a folder may be imported any number of times, nested or
> not, and each run makes its own Tasks. The paragraph above records what v0.3.0 shipped; see
> [v0.4.0](v0.4.0.md) for the decision and the reasoning.

**The default name is a provider read, not the path.** `sourceNameFor` names a folder after the last
segment of its root-relative path, and a picked folder's path is empty — the grant root *is* the
folder — so every Upstream added by picking would have been called "Picked folder". The dialog and
the card therefore ask the provider, through `FolderSource.folderName`, and fall back to
`sourceNameFor` only when it will not say.

**Where the answers go, and why it still has to be said.** Registering an Upstream writes the
`upstreams` row and nothing else; a **run** is what writes the `sources` row, which is the Todo. Two
records, two moments — and a second run over the *same* folder finds the row already there and is a
re-run of that Todo, not a second one. `ListsDao.registerSource` reuses such a row untouched, which
is its documented reuse path and what every caller that only wants the row already there depends on;
the dialog's answers are therefore recorded in a second write, `configureSource`, again *after* the
import has been written, so that "nothing was changed" stays true of a run that failed. Without it
the dialog would ask three questions and act on none of them.

**Keep folder tree is meaningful only for `file-as-task`, and the conflict is resolved silently.**
`folder-as-task` groups one Task per immediate child folder and nests the rest as Assets, so its
Tasks are flat by construction and the option has nothing to act on. When `folder-as-task` is
selected the control is **hidden, not disabled, and stored as `false`** — a greyed-out control
invites the user to wonder what they are missing, and there is nothing to miss.

**What keep folder tree does, exactly.** It is a **presentation** rule, not an import rule:

- **On** — Todo shows the tree. Folders are browsable, exactly as `catalogAtScope` descends today.
- **Off** — Todo shows one flat list of every Task in it, with no folder rows at all.

It is not a change to `groupPath`, and nothing in the import is reshaped. `groupPath` is the
containment key `catalogAtScope` and the quick-review scope rules are built on; rewriting it to
flatten a view would break containment for every Task in the Upstream, and would make the same
import produce different provenance depending on a display setting.

## 3. Schema

`version = 16`, with two hand-written migrations in `ListeaDatabase.kt` following the existing
style.

**`MIGRATION_15_16` splits the two concepts.**

```sql
CREATE TABLE IF NOT EXISTS upstreams (
  id TEXT NOT NULL, rootUri TEXT NOT NULL, relativePath TEXT NOT NULL,
  displayName TEXT NOT NULL, addedAt INTEGER NOT NULL, PRIMARY KEY(id)
);
CREATE UNIQUE INDEX IF NOT EXISTS index_upstreams_rootUri_relativePath
  ON upstreams (rootUri, relativePath);
INSERT OR IGNORE INTO upstreams (id, rootUri, relativePath, displayName, addedAt)
  SELECT id, rootUri, relativePath, displayName, createdAt FROM sources;
DELETE FROM sources
  WHERE lastImportAt IS NULL AND id NOT IN (SELECT sourceId FROM task_imports);
```

Every Source becomes an Upstream — the folder was picked either way, and `createdAt` becomes
`addedAt` because it means the same thing. A Source is **kept in `sources`** only if it can be a
Todo: it has a `lastImportAt`, meaning a run wrote it, or a `task_imports` row still names it,
meaning deleting it would break that row's foreign key. Everything else was never anything but a
folder, and leaving it would put a row on the Todo tab with no Tasks behind it and no run to
refresh.

**`MIGRATION_14_15` — `keepTree`.** `SourceEntity` gains `val keepTree: Boolean = true`, added as
`ALTER TABLE sources ADD COLUMN keepTree INTEGER NOT NULL DEFAULT 1`. The default **preserves
today's behaviour**, because `catalogAtScope` already draws the tree.

The column is on `SourceEntity` rather than a preference or a third importer, for the reason the
existing layout implies: a Source is where configuration about an import lives, and the next
importer option needs somewhere to go that is read at refresh time and not at display time.

**What `sources` means now.** One row per **import run that produced a Todo**. `SourceEntity` keeps
its name — see [Revision](#revision-2026-09-17) — but the table is narrower than it was: it is the
Todo table, and the Upstreams tab does not read it.

## 4. Todo

The tab lists one card per Todo.

| Card area | Shows |
|---|---|
| Title | The Todo's `displayName` — the name the Create Tasks dialog was given, not the folder's |
| Detail | Importer, whether it keeps folders, the folder it came from, Task count |
| Status | What the last run did, or "never run" |
| Actions | **Refresh Import**. The card itself opens the Todo |

**Catalog is gone and the card replaces it.** It was a button to the place the row itself now goes:
a screen that shows a body of work, with a button to that body of work, is the row pretending to be
the screen behind it.

**Quick Review and Create List are gone from this level.** A round over a Todo's top level would be
a round over a set of folders, and a selection made from a card cannot say which Tasks were meant.
Both live one level in, where the Tasks are.

### Opening a Todo

What opening a Todo shows is decided by how it was imported, and is the same tree the Upstreams
browser shows:

| Import | `keepTree` | Opening the Todo |
|---|---|---|
| `file-as-task` | on | Browsable folder tree of Tasks |
| `file-as-task` | off | One flat list of Tasks, no folder rows |
| `folder-as-task` | (forced off) | One flat list of Tasks |

This is `CatalogScreen` with one added axis. It already draws scopes and Tasks through
`catalogAtScope`; the flat case passes the whole row set and draws no `Scopes` section, while the
tree case is what it does today.

The breadcrumb walks back up the tree and, at the Todo's own top level, Back returns to the Todo
tab. "The Todo's own top level" is the Source's `relativePath` and not the empty path: for a Todo
made on the whole Upstream those coincide, and for one made inside `xvideo-jp` they do not. It is
the floor for Back, the name the title falls back to, and the point the breadcrumb's `Root` returns
to. Its `Root` entry is a `TextButton` beside plain `Text` siblings, so the row aligns its children
to the centre — without that, the button's 40dp touch target top-aligns against the labels and
`Root` reads as floated above the path it belongs to.

### The Task preview

Tapping a Task opens it to be looked at, and nothing on that screen decides anything: no checkbox,
no action chips, and no Save or Share. It is the same gallery the List's item viewer is, with the
same two levels of steps, and drawn the same way on purpose — neither is a place where a decision
gets made, so neither grows a control that suggests otherwise.

| Step | Moves between |
|---|---|
| `‹` / `›` | The Tasks of the level the preview was opened from, in catalog order |
| The file steps inside the navigator | The Task's own Assets, when it holds more than one |

Swiping off either end of a Task's Assets moves to the next Task rather than stopping, so the swipe
and the arrows are one behaviour. At the ends of the *level* it stops, because there is no next Task
to reach and nothing to complete.

The screen is handed the whole level rather than the one row that was tapped, read from the catalog
rather than captured at the tap. Two things follow: a refresh that re-imports the material changes
the sequence the arrows walk, and a Task that the refresh takes away closes the screen instead of
leaving the user looking at something that is no longer in the catalog.

**Steps between Tasks were absent in the first pass, and this reverses that.** The argument then was
that the catalog the user is already standing in is a better way to choose the next thing to look at
than a sideways step buried inside a file. What it missed is that the catalog is *behind* the
preview, so moving one row down costs a screen and a tap. What was right in it is kept: a Task is
reached this way only if it was already in the level, so the sequence can never lead anywhere the
user could not have tapped, and nothing about the destination changes because of how it was reached.

### Quick Review

**A round covers the Tasks directly in the folder the user is standing in.** Not the ones nested
below it.

```
Todo
├── 2026-07-11/          ← Quick Review here covers precisely these two Tasks
│   ├── a.jpg  (Task)
│   └── b.jpg  (Task)
└── 2026-07-12/          ← and here covers these
    └── c.jpg  (Task)
```

`catalogAtScope` already computes exactly this: `view.tasks` is `directChildOf(row.groupPath,
scope)`, the same narrowing browsing does, so browsing a folder and quick-reviewing it queue the
same Tasks. The round is `folderReviewQueue(rootUri, scope, files = emptyList(), rows, states =
emptyList())` — the branch that already exists for a scope with no listing, already ordered by
`catalogOrder`. Nothing new is computed; the caller stops passing a listing, and now stops widening
the scope too.

**The action is hidden where there are no Tasks**, which includes the top level of a tree-shaped
Todo. Folders are not reviewable; a round over them would either do nothing or silently reach past
them, and both are worse than not offering it. A flat Todo has one scope and it holds every Task, so
Quick Review is offered there — correctly, since there is no subfolder it could be confused with.

The consequences of dropping the listing are worth stating plainly, because they are the visible
difference from a browsed folder's round:

- An item's `sourceUri` is null, so the round resolves each file through the Task's Assets rather
  than through the browsed folder's `DocumentFile`.
- `publicId` arrives empty, because no `FileReviewStateEntity` was registered for it. It is
  **not** therefore absent from the wire: `deliverFolderReview` mints a stable id through
  `legacy_task_ids` on the first delivery, which is the same path a multi-Asset Task takes and the
  reason a Task no List ever touched cannot silently drop out of a payload
  (`ListsViewModel.kt`, `WebhookCompatTest`). So a Todo round posts `quickreview.completed` through
  the default webhook exactly as a folder round did.
- Filtering and sorting by the *folder's* arrangement does not apply, since there is no folder.
  Tasks come back in `catalogOrder`.

### Create List

Reached from inside a Todo by tapping **Select**. The selection rules are unchanged: folders are
selection units, the checkbox only ticks, and the row still opens the folder.

A folder's checkbox takes the whole folder — the Tasks directly in it and everything under it.
Ticking one at the top of a tree and then clearing a Task inside leaves the folder ticked and that
one Task out; tick it again and it comes back, and clearing the folder and ticking it again starts
from scratch rather than re-applying the Task that was taken back. A Task ticked by hand stays
ticked whether or not a folder is ticked over it.

**Selecting is the only way to make a List**, and it is inside a Todo because Tasks are the only
rows that can say which Tasks were meant.

## 5. Out of scope

- **Deleting an Upstream.** Deferred by request — this iteration adds Upstreams and does not remove
  them. The recommendation on record is deregistration: drop the `upstreams` row and keep the
  `sources` rows, the Tasks, the Assets and `task_state`, which frees the `(rootUri, relativePath)`
  registration for a re-import under a different importer without destroying decisions.
  `ListsDao.deleteUpstream` and the `ListsDao.upstreamsUnder` query it would need — documented as
  being "for the removal check" — both exist and neither has a caller.
- **A folder nested inside an already-imported folder.** Found on device during the review of this
  iteration, not predicted by it. With a Todo over `Demo`, **Create Tasks** on `Demo / Camera`
  refuses: *"This folder is already inside the Source 'Demo'. Refresh that Source instead. Nothing
  was changed."* `ListsDao.registerSourceInternal` admits a second registration only when the two
  root-relative paths are disjoint — `scopesOverlap` is
  `isAncestorOrSame(a, b) || isAncestorOrSame(b, a)`, and it exists to mirror the unique index
  `index_assets_rootUri_relativePath ON assets (rootUri, relativePath)`. One file is an Asset of one
  Task, so a Todo over `Demo` already owns every file beneath it. Two *sibling* subfolders of one
  Upstream can each carry their own Todo; nothing may contain or be contained by a Todo already
  made. **The refusal is correct and the wording around it was not** — §2 and
  [getting started](../getting-started.md#create-tasks-from-an-upstream) read as though any
  subfolder could be imported, and they and acceptance criterion 5 are corrected above. **What is
  deliberately not taken is the policy.** Letting a file belong to two Todos is a decision about what
  re-import means: whether the two share `task_state` and so move together, which Todo's name a
  webhook payload carries, and what **Refresh Import** on one does to the other. Answering it in an
  iteration whose subject was the upstream/todo split would be inventing an answer to a question
  nobody asked.
  **v0.4.0 answered it**, and answered it the way this note anticipated rather than by accident:
  the two Todos do *not* share `task_state`, because a file reached through two Todos is two Tasks.
  The other three questions — whose name a payload carries, what Refresh Import does — are
  properties of one Todo and did not need a shared answer after all. See
  [v0.4.0 step 1](v0.4.0.md).
- **Build size.** 75 MB of APK contents, 73.9 MB of it DEX and 21,320 Compose icon classes inside
  that, caused by `material-icons-extended` and by R8 being off in both build types. A
  build-configuration change with no design content; deliberately not taken in the same iteration as
  a model split. See [Development](../development.md#build-size-and-where-it-comes-from).
- **Multiple Upstream kinds.** A cloud storage or database Upstream is what this iteration is
  arranging room for; none is built here.
- **Lists spanning Todos.** A List is built from one Todo's Tasks. The model does not prevent more,
  and the vocabulary already anticipates it, but no screen offers it.
- **The `jobs` rename.** See the vocabulary note above.
- **Per-importer option plumbing.** `keepTree` is stored and honoured, but there is still no
  general options object. It goes on `SourceEntity` as a column, which is the same thing a general
  options bag would do for one field.
- **The folder-List gate, left standing without a caller.** `ListsViewModel.requestListForFolder`,
  `FolderListGate` and the `FolderListRequest` dialogs are unreachable: Create List is a Todo action
  over catalog Tasks (§4), so nothing starts a List from a browsed folder. They are kept for now
  rather than deleted, with `FolderListGateTest`, `ConsentGateViewModelTest` and the DAO-level
  `ConsentTest` behind them, because they are the tested statement of the overlap rules and of the
  two-consent ordering that v0.2.5's review turned on. Deleting them is a decision about whether any
  List may still be made from a folder; it is not a decision this iteration is taking.
- **Renaming an Upstream or a Todo.** The Todo write exists (`ListsDao.configureSource`, reached
  only from a run today); nothing writes an Upstream's `displayName` after it is added, and no
  screen offers either.

## Acceptance

1. The bottom bar reads Upstreams · Todo · Lists · Settings, and a trip through each tab returns to
   where it was.
2. **Settings** holds **Add Upstream**, and adding one registers a folder without creating anything
   to review. The Upstreams tab offers no picker of its own.
3. **Several Upstreams can be added**, each keeping its own grant: adding a second folder leaves the
   first registered, available and browsable.
4. An Upstream's card opens its folder and carries no actions; **Create Tasks** is offered on a
   folder's row and on the card, and never registers a Todo until it runs.
5. Running Create Tasks on a subfolder produces a Todo over that subfolder, and leaves the rest of
   the Upstream alone — for a subfolder **disjoint from every Todo already made**. A folder nested
   inside one is refused, naming the Todo that owns it; see [Out of scope](#5-out-of-scope).
   *Superseded in v0.4.0: a nested folder is now imported, and the rest of the Upstream is still
   left alone. See [v0.4.0](v0.4.0.md).*
6. An Upstream has no Quick Review and no Create List, and neither does its browser.
7. **Back from the Upstream browser returns to the Upstreams list**, at every depth, and switching
   tabs while it is open leaves it rather than drawing over it.
8. A Todo's card opens the Todo; **Refresh Import** is its only button, and Catalog, Quick Review
   and Create List are not on it.
9. Inside a Todo, **Quick Review** appears where there are Tasks and covers exactly the Tasks at
   that level, not the ones below it. It is absent where the level holds only folders.
10. Inside a Todo, **Select → Create List** builds a List from the Tasks ticked, including folders
    as selection units.
11. A `file-as-task` Todo with keep-tree off opens as a flat list of Tasks with no folder rows; with
    it on, as a tree. A `folder-as-task` Todo opens flat.
12. The Todo breadcrumb reads `Root / …` with `Root` on the same line as the rest of the path.
13. Upgrading an install at v15 keeps every folder it had: each Source becomes an Upstream, every
    Source a run had written stays a Todo, and no List, Task, Asset or decision is touched.
14. The three persisted names above are unchanged, and an existing install keeps its grant, its
    Quick Review setting and its per-folder arrangements across the upgrade.
15. Tapping a Task inside a Todo opens it with **no checkbox, no chips and no Save or Share**, and
    `‹` / `›` step through the Tasks of the level it was opened from, in catalog order. A swipe off
    either end of a Task's Assets moves to the next Task; at the ends of the level it stops.
16. **A Todo made over a subfolder opens at that subfolder.** Its title is the Todo's, its Back
    floor and its breadcrumb `Root` are that folder, and Quick Review there resolves to the Tasks at
    that level. A Todo made over the whole Upstream is unchanged: its root is the empty path, its
    title is the Upstream's name, and it quick-reviews what it always did.
