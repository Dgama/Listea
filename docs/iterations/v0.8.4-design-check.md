## Gate 1 — vocabulary

The vocabulary test is not "did we use nice words"; it is "does every sentence have exactly one
meaning". The canonical reference is [the two vocabularies](../vocabulary.md).

| # | Term | Required usage | Misuse to reject | Status |
|---|---|---|---|---|
| V1 | **Prompt** | The setter's declared decision unit; may contain internal steps/fields/conditions; content, never a Task. | "a Prompt Task" as if a Prompt were a Task; "one Prompt = one Task" as a universal. | expected |
| V2 | **TaskPart** | The taker's instance of one Prompt; the decision unit; may be degenerate; owns response/events/pages. | "Asset" or "Item" for the decision unit. | expected |
| V3 | **Task** | The undertaking over 1..N TaskParts; identity, List membership, completion, Add-on, export. | "Task = one question" as the universal; a Task with zero parts. | expected |
| V4 | **Asset** | A presented file/page within a TaskPart; material, not the judgment target. | "1 Asset + 1 add-on" for a vocabulary Task; "the Asset is the decision". | expected |
| V5 | **Resource** | A dependency; not a page; not an Asset. | "Resource page"; "Resource Asset". | expected |
| V6 | **Section** | A declared tag on Prompts, with a registry entry; not a parent, not a Task constructor. | "a Section Task" as a model claim (only as a composition's name); Section as a third Task level. | expected |
| V7 | **Composition** | The taker's rule for grouping Prompts into a Task; `compositionKey` is provenance. | `p:`/`s:` as a domain Task id or export id. | expected |
| V8 | **Package** | An exchange protocol; not an internal entity. | a stored Package row/lifecycle as the domain model. | expected |
| V9 | **Item** | Retired for the decision unit. | "Item" for the new unit, a file, or a TaskPart. | expected |
| V10 | **Response contract / Response** | The setter's legal-answer declaration vs the taker's recorded answer. | "response" for both halves in the same sentence without qualification. | expected |

**Test:** read the [v0.8.4 design](v0.8.4.md) and [vocabulary](../vocabulary.md) top to bottom and
mark every sentence that uses a term in two senses. The known historical offenders are the
2026-10-26 v0.8 note (corrected there) and the old "one judgment answers one Prompt" sentence
(narrowed to the one-part case).

### Notes on the hard rows

**S2 — a Resource is not a page.** The dating Prompt's image is a Resource. The Viewer may render it
inside the Content page, but the page list has no Resource page. If the Resource is required and
missing, the part is `unavailable`; if required, automatic completion is blocked. The catalog's
Asset count stays 0.

**S3/S4 — the degenerate part and the media regression.** The media Task keeps exactly today's page
list: no Content page when there is no payload; Assets in attachment order; Add-on optional. The
`singlePart` policy preserves the Task-level template behavior, including templates that record a
mark or completion rather than a part event. The part is the grouping; it does not force a new
commit path on media.

**S5 — the part boundary is not a third arrow.** The navigator still walks pages; the part is a
grouping and state unit. The queue guide may label parts, but `<< >>` remain Task-level and `<>`
remain Asset-level. The Add-on is after the last part and is not a part.

**S6 — one decision, several answers.** The structured Prompt produces one part and one structured
response. The branch's internal questions/fields are not parts, Sections or Tasks. A cross-Prompt
branch is not this scenario and is out of scope.

**S7 — a Section is a tag, not a requirement.** The same 19 Prompts can be one Task or 19 Tasks. The
user who wants the pair alone takes `prompt:q19`. The Section registry declares the grouping; the
Composition chooses the sitting.

**S8 — absence is not deletion.** A removed Prompt's part becomes `detached`; its response and
events remain; it is excluded from completion and from the default export. The Task id survives.
The keep/reset/drop policy decides the current responses of changed parts, not the Task's identity.

**S9 — pending is not empty.** A pending part exports `result: null`; an answered empty freeform
exports `result: ""`. The Task exports `completed: false`. The export does not fabricate an answer
to make the shape uniform.

**S13 — the migration is the regression net.** An existing Task has one part after migration; its
payload is reachable; its events keep their history (legacy events have no `partKey` and are not
reinterpreted); its pages are unchanged; its v5 export is unchanged. The migration test runs on a
schema-32 fixture.

## Gate 3 — invariants

These must all hold in the design and, later, in the implementation. A false invariant blocks code.

| # | Invariant | Check | Status |
|---|---|---|---|
| I1 | Every Task has 1..N TaskParts; zero is not a Task. | Import rejects zero-part compositions; migration backfills one part. | expected |
| I2 | Every Prompt selected by a composition has exactly one TaskPart in that Task; no Prompt is silently dropped. | Composition/member validation; no duplicate `partKey`. | expected |
| I3 | Every TaskPart has at least one page: a Content page (payload) or at least one Asset. A part with neither is invalid or unavailable. | Import/page-list validation. | expected |
| I4 | An Asset is a presented file/page within one TaskPart; it is not the decision unit and not shared across Tasks. | Model + export: Assets link to one part. | expected |
| I5 | A Resource is a dependency, not a page; a missing required Resource makes the part unavailable. | Page list excludes Resources; availability blocks completion. | expected |
| I6 | `partKey` is unique within a Task and is not a domain id. | Unique index; no `partKey` used as Task id. | expected |
| I7 | The Task id is opaque; no `p:`/`s:` composition key is a Task/export/wire id. | Export/profile review. | expected |
| I8 | A part has one current response; history is append-only; a non-revisable answered part refuses a second commit. | Commit test. | expected |
| I9 | Task completion is a Task-level state; automatic completion is recomputed from parts; explicit completion is not silently cleared. | State-machine test. | expected |
| I10 | The Add-on is Task-level, optional, after all parts, and not part of `isCompleted`. | Page/commit test. | expected |
| I11 | A media Task's page list is unchanged: no Content page without a payload; Assets in order; Add-on optional. | Media regression fixture. | expected |
| I12 | A single-part Task behaves as today; a v5-compatible single-part body still exports v5. | Compatibility fixture. | expected |
| I13 | A re-import membership change keeps the Task id; a removed part detaches, never deletes; the policy is recorded. | Reconciliation fixture. | expected |
| I14 | Two Todos over one Package are independent; the same Prompt in two Tasks is two TaskParts. | Independent-Todo test. | expected |
| I15 | v1 and v2 are both readable; v2 is strict; the protocol declares no Task and no cross-Prompt condition. | Protocol fixture + grammar review. | expected |
| I16 | The design round changed documentation only; the implementation round that followed was cut only on the user's instruction. | Repository status. | accepted |

### Deviations, and why

| # | Deviation | Reason and record |
|---|---|---|
| V1 | **Built-in Task Reviews are repaired on every open**, not only on create or migration. `SeedBuiltIn.onOpen` now runs `repairMissingTaskReviews` and `repairEarlierNames` after the existing empty-database seed. | The walk found a real database that held the built-ins of an earlier release but not the ones this release added — a state neither `onCreate` nor the release's own migration reaches. `INSERT OR IGNORE` keeps a user's renames, and the name repair only replaces an untouched earlier seed. Documented in `ListeaDatabase.kt` at `SeedBuiltIn`. |
| V2 | **The Section fixture and the Form fixture are separate Packages** (`section-demo`, `form-demo`), not one mixed Package. | A Task's parts are caught in one review, and the built-ins answer one family each: the choice review catches `choice.select`, the Form review records a structured answer and catches no viewer event. **One Task Review cannot govern form and choice parts together today**, and no built-in supports both (open item O4, composite Templates deferred). Splitting the fixtures keeps each scenario honest instead of pretending a mixed Task is reviewable. |
| V3 | **Re-import recomputes automatic completion.** `runImport`/`runImportInternal` take a completion policy and, after reconciling parts, recompute completion for every touched Task with source `automatic`; an explicit sign-off is preserved. | Without it, removing or adding a required Prompt left `isCompleted` claiming a state the current membership no longer supports. This is the part-level application of [Architecture → Package reconciliation](../ARCHITECTURE.md#package-reconciliation-and-checkpoints-v08x) ("completion recomputed if automatic"). |
| V4 | **The import dialog's draft is held with `rememberSaveable(runKey)`**, including the composition word. | Rotation must not discard an answer the user is about to confirm. The composition is stored as its key word, which is both the bundle-safe shape and the exact value the Source records, so the draft and the write stay one expression. |
| V5 | **Acceptance fixtures live in-repo** under `docs/assets/fixtures/section-demo` and `form-demo`, without generators. | They are small, hand-authored v2 Packages: three single-choice Prompts with files and Resources, and one conditional form. The device walk also used temporary revisions of the Section fixture (revision 5 removing, revision 6 adding a required Prompt) to prove W7 and W8; the repository copy stays at its shipped revision 3. |
| V6 | **The Form Task Review's picker line was fixed during the walk.** It first read *records the Task's file decisions*, which is the media review's sentence. | A headless review that catches no viewer event has two honest cases, not one: a media review records file decisions, and a Form review records the form's answer. `reviewCatchLine` now chooses by the viewer, and a JVM test pins all three sentences. |

No deviation contradicts a decision in Gate 6; V1–V4 are implementation consequences, V2 and V5
record the shape the acceptance fixtures actually took, and V6 corrects user-facing copy.
