## Framing

v0.2 made the Task the thing that is judged. **v0.2.5 makes something other than a browse decide what a Task is.**

Today a Task comes into existence three ways — `createFolderList` (`ListsDao.kt:353`), `applyReconcile` (`:590`) and `ensureTasksForFiles` (`:872`) — and all three mint one Task per file, lazily, as a side effect of looking at a folder. That is the last place `file == Task` still lives: not in the schema, which has been clean since v13, but in the fact that *browsing* is what creates the judgment unit. A folder-as-Task importer is impossible while entering `alice/papers/` can mint two rival Tasks for the two PDFs that are already Assets of Task *Alice*.

So the release principle is narrower than "add importers":

> **Only an import run may create a Task. Everything else selects Tasks that already exist.**

Revision 2 adds the second half, which the review made explicit:

> **Being imported is not being reviewable.** A Task may be reviewed only when the whole of it is in the scope, every Asset it needs is resolvable, and every Asset it needs has a viewer in this build.

Everything v0.2.5 ships follows from those two sentences. The catalog exists because you cannot select Tasks you cannot see. Containment exists because a scope that shows half a Task must not offer it. Eligibility exists because a placeholder is proof that the content could *not* be inspected, and a judgment recorded against uninspectable evidence is a judgment about nothing.

This also absorbs [`v0.2.0-reviewed.md` §9](v0.2.0-reviewed.md), which proposed v0.2.5 as a media-only multi-Asset stress test. The folder-as-Task importer produces exactly the Task shapes §9 asked for — 2, 3 and 5 images under one Task — so the stress test is not a separate release, it is acceptance scenario B run with pictures. §9's three open questions about `selectedAssetId` are answered in §9 below, against the real multi-Asset Task it said to wait for.

## 1. Final domain model

```text
Source 1 ─── N Task ─── 1..N Asset          (task_imports carries the edge and its provenance)
   │                       │
   │                       └── sourceUri / rootUri+relativePath / metrics / presence
   │
   └── importerKind, import root, status

legacy_source_tasks ─── Task          (imported by nothing; a closed set that only shrinks)

List 1 ─── N ListEntry N ─── 1 Task ─── 1 TaskState
                                 └────── 0..N ReviewEvent
```

- **Source** — a registered origin. In v0.2.5, a folder: the SAF grant plus a root-relative import path, a display name, an importer kind and version, and the status of the last run. It owns no state and no history.
- **Importer** — a pure grouping rule. Takes a snapshot of the import root, produces planned Tasks with their Assets and a list of notices. It is the only thing allowed to decide Task boundaries.
- **Task / Asset / TaskState / ReviewEvent / ListEntry** — exactly as v0.2 defined them. Nothing in this release changes their meaning, their tables (beyond three additive Asset columns), or who may write them.
- **Catalog** — a read projection over `task_imports` + `assets`. Not an entity, not an owner, no lifecycle. Deleting nothing and owning nothing is the whole point of it being a projection.

**Two sentences a reviewer should be able to check the diff against:**

1. `INSERT INTO tasks` appears in exactly one transaction, and that transaction is an import run.
2. `insertReviewEvent` is unreachable for a Task that is not review-eligible.

## 2. Room schema v14

```sql
sources(
  id TEXT PK,
  rootUri TEXT NOT NULL,                 -- the SAF tree grant, same value assets.rootUri uses
  relativePath TEXT NOT NULL,            -- import root under the grant; '' is the grant root
  displayName TEXT NOT NULL,             -- '' means "derive from the folder label"
  importerKind TEXT NOT NULL,            -- 'file-as-task' | 'folder-as-task'
  importerVersion INTEGER NOT NULL,
  createdAt INTEGER NOT NULL,
  lastImportAt INTEGER,
  lastImportStatus TEXT,                 -- 'complete' | 'partial' | 'failed', null = never run
  UNIQUE(rootUri, relativePath)
)

task_imports(
  taskId TEXT PK REFERENCES tasks(id) ON DELETE CASCADE,
  sourceId TEXT NOT NULL REFERENCES sources(id),   -- NO ACTION: a Source is never deleted in v0.2.5
  groupPath TEXT NOT NULL,     -- root-relative path of what the importer grouped:
                               --   file-as-task   -> the file's own path
                               --   folder-as-task -> the child folder's path
  displayName TEXT NOT NULL,   -- the importer's name for the Task: file name or folder name
  importedAt INTEGER NOT NULL,
  lastSeenAt INTEGER NOT NULL,
  INDEX(sourceId, groupPath)
)

legacy_source_tasks(
  taskId TEXT PK REFERENCES tasks(id) ON DELETE CASCADE
)

legacy_task_ids(
  taskId TEXT PK REFERENCES tasks(id) ON DELETE CASCADE,
  publicId TEXT NOT NULL
)

assets  -- three additive nullable columns, no rebuild:
  sourceUri TEXT, sizeBytes INTEGER, lastModified INTEGER
```

Everything else in v13 is untouched: `tasks`, `task_state`, `review_events`, `list_items`, `lists`, `file_review_state`, `legacy_item_ids`, `legacy_manual_tasks`, `webhook_history`.

### 2.1 Why `assets` gains three columns

A multi-Asset Task has no `list_items` row per Asset, so there is nowhere else for the viewer and the queue to read the three things they need: the document URI to render, and the size and modified time the arrangement filters and sorts on (`FileArrange.kt`). Today those come off `list_items` for a List and off the live folder listing for Quick Review; a catalog scope has neither.

The import run is the moment a scan measured them, which is the same justification `list_items.sourceSizeBytes` already carries. All three are nullable, refreshed by re-import, and never identity.

**Still no persisted `AssetKind`** — v0.2's standing decision holds. The importable-content policy (§4.3) and the viewer-availability rule (§6.4) both classify from the file name at the moment they need it, which is what `MediaKind` already does. A stored kind arrives with the second viewer, in v0.3.

### 2.2 Why provenance is a side table, and carries nothing else

`TaskEntity`'s KDoc states that a Task has no path, no title and no opinion about where it was found, and v0.2 built the read model on it. `groupPath` and `displayName` are exactly those things — so they go on a row *about* the import, not on the Task, in the same style as `legacy_item_ids` and `legacy_manual_tasks`. A Task with its `task_imports` row deleted is still a Task; it is just no longer in any catalog.

It carries **no wire id**. A public id is exporter/legacy transport state, it belongs at the compatibility boundary (§2.4, §10), and nothing in the importer or the catalog may read it.

This also keeps the deferred "who owns a Task's title" question closed: `list_items.title` remains the List-side title, the webhook keeps sending it, and `task_imports.displayName` is only what the importer called the thing it created.

### 2.3 Why adoption is a claim set, not a Source

Every file-backed Task in a v13 database was minted by a browse, not by an import. Modelling that as a Source rooted at `''` would occupy `(rootUri, '')` — the one key a user needs in order to import their whole grant — and `sources` is UNIQUE on it. With no Source deletion and no importer-kind change, that user would have been stuck.

So the legacy set is *named*, not *personified*: `legacy_source_tasks` lists the Tasks that exist because someone once looked at a folder. It has no importer, no root, no status, and can only shrink — when a real import covers one of those files, the Task is adopted into that Source and the claim row goes (§4.4). When the table empties it can be dropped with the whole compatibility case, exactly as `legacy_manual_tasks` is designed to.

A legacy Task is reachable through any List that contains it, exactly as today. It is not in any catalog until it is imported, which is the honest statement: nothing has yet decided that it is imported material.

### 2.4 `legacy_task_ids`

The Task-level counterpart of `legacy_item_ids`, and a compatibility table in the same sense: it exists so that a folder round over a Task with no single Asset and no `list_items` row can still put a stable `id` on the wire.

It is written by the webhook compatibility adapter, lazily, the first time such a Task is reported — never by an import run, never by the catalog. For every single-Asset file-backed Task the adapter keeps resolving `legacy_item_ids` exactly as it does today, so no existing receiver sees a new id.

## 3. Migration v13 → v14

Additive. No table rebuild, no data transformation, nothing dropped.

1. Create `sources`, `task_imports`, `legacy_source_tasks`, `legacy_task_ids`. `ALTER TABLE assets` three times.
2. **Claim.** For every Task that has at least one Asset with a non-null `rootUri`, insert one `legacy_source_tasks` row. No Source is created, and `sources` and `task_imports` are left empty.
3. **Backfill the Asset columns** from any `list_items` row naming the same Task — it already carries `sourceUri`, `sourceSizeBytes` and `sourceModifiedAt` for exactly this file. Tasks that only ever existed through Quick Review keep nulls; the browse path supplies the URI from the listing as it does today, and the first import fills them in.
4. **Nothing else is written.** No `tasks`, no `task_state`, no `review_events`, no `list_items`, no `lists`, no ids of any kind. A Task with no file-backed Asset — a legacy manual item — gets **no** `legacy_source_tasks` row: it has no source material, so nothing could ever import it, and `legacy_manual_tasks` already names it.

**Validation assertions in the migration test** (same idiom as `MigrationV12ToV13Test`):

- every Task with a file-backed Asset has exactly one `legacy_source_tasks` row, and nothing else does;
- `sources`, `task_imports` and `legacy_task_ids` are empty;
- `tasks`, `task_state`, `review_events`, `list_items`, `lists`, `legacy_item_ids` and `legacy_manual_tasks` are row-for-row identical before and after;
- `assets` differs only in the three new columns, and every backfilled value matches the `list_items` row it came from;
- per-List completed/total unchanged.

Room runs it in one transaction. UUIDs are generated in Kotlin with the drain-then-write `backfill()` helper the earlier migrations already use. **Do not touch `MIGRATION_12_13`.**

## 4. The importer layer

### 4.1 Shape, and the scan snapshot

Importers are **pure functions**, in the style this repository already uses for `FolderScan`, `FileArrange` and `folderReviewQueue` — the reason those have hundreds of tests and no Robolectric dependency.

An importer needs to know about a folder that contains no files at all, so the scan must hand it directories as well. `scanFolderFiles` (`FolderScan.kt`) already walks every directory in order to reach the files; it simply does not record them. Extend that walk rather than adding a second one:

```text
scanFolderTree(context, folderUri): FolderSnapshot?      -- blocking, IO, one walk
FolderSnapshot(files: List<ScannedFile>, directories: List<String>)   -- both root-relative

scanFolderFiles(context, folderUri) = scanFolderTree(context, folderUri)?.files
```

`scanFolderFiles` keeps its signature and its two existing callers unchanged. `directories` is every directory under the scanned root, in the same deterministic order, which is what makes "an immediate child folder with no supported files" a fact the importer can see and report instead of a fact it has to guess.

```text
plan(importRoot: String, snapshot: FolderSnapshot): ImportPlan

ImportPlan(
    tasks:   List<PlannedTask>,      // groupPath, displayName, assets (ordered)
    notices: List<ImportNotice>      // skipped unsupported file, empty child folder
)

PlannedTask(groupPath, displayName, assets: List<PlannedAsset>)
PlannedAsset(rootRelativePath, name, uri, sizeBytes, lastModified, sortOrder)
```

No database, no `Context`, no SAF inside `plan`.

### 4.2 file-as-Task

One Task per discovered file; one Asset; `groupPath` = the file's root-relative path; `displayName` = the file name. This is what `createFolderList` does today, expressed as a rule instead of as a side effect. `directories` is unused by this importer.

### 4.3 folder-as-Task, and the content policy

- each **immediate child folder** of the import root becomes one Task, `groupPath` = that child folder's root-relative path, `displayName` = its name;
- every supported descendant file inside it becomes an Asset, ordered by relative path;
- nested folders organise Assets and never create Tasks;
- a child folder with no supported files — including one with no files at all, which `directories` now makes visible — produces **no Task** and one notice;
- supported files sitting directly under the import root become one-Asset Tasks, exactly as file-as-Task would have made them;
- unsupported files are skipped and reported.

**Supported, for this importer, means picture ∪ video ∪ PDF.** Picture and video come from `MediaKind`; PDF is recognised by extension, imported, catalogued and explicitly **not reviewable** until v0.3 (§6.4, §9.3). Everything else — `rubric.txt` in the spec's example — is skipped with a notice.

**Precedence rule, resolving the plan against the spec's "supported files" wording** (amended into `v0.2.5.md` revision 2, so both documents say the same thing):

1. **file-as-Task imports every file the existing scanner admits**, with no content filter. That is v0.1 parity: `createFolderList` has never filtered, and a picture folder holding a stray `.txt` gets an item for it today.
2. **folder-as-Task applies the supported-content policy above**, because it is new and has no behaviour to preserve.
3. **Importing something never implies it can be reviewed.** Rule 1 keeps material visible and selectable; §6.4 decides separately whether a judgment may be recorded against it. The two rules do not contradict each other because they answer different questions.

### 4.4 Ownership: one file, one Task

`assets` is UNIQUE on `(rootUri, relativePath)`. That index *is* the architecture's "initial importers may enforce one Task association per imported Asset", and v0.2.5 leans on it rather than adding a second rule.

An import run resolves every planned Asset locator against `assets` before writing anything:

| the locator is | outcome |
|---|---|
| unknown | new Asset on the planned Task; the Task is created if `(sourceId, groupPath)` is new |
| an Asset of a Task **this Source already owns** | reconciled in place — same Task id, same Asset id |
| an Asset of a **legacy-claimed** Task (`legacy_source_tasks`), and this Source is **file-as-Task**, and the planned Task is that one file | **adopted**: insert `task_imports`, delete the claim row. Identity untouched, state and history untouched. One-way: nothing ever returns a Task to the legacy set |
| an Asset of a **legacy-claimed** Task, and this Source is **folder-as-Task** | **conflict.** Folding an existing Task into a group would merge two Tasks and take a reviewed Task's identity with it |
| an Asset of a Task owned by **another real Source** | **conflict.** Unreachable while §5.6 holds; kept as a defensive branch because the alternative to reporting it is silently splitting one file's judgment |

A conflict is never resolved by minting, moving or deleting. Nothing is written for the affected Task, the rest of the run proceeds, and the report names the file, the owner and the Task in those words. Changing Task boundaries is the case the architecture reserves for an explicit migration policy, and that policy is deferred.

## 5. Import runs and reconciliation

### 5.1 The run, and its coverage

One `@Transaction` in the DAO:

```text
runImport(sourceId, coverage: String, plan, now): ImportResult
```

`coverage` is the root-relative path that was **authoritatively scanned** for this run. It is passed in, never inferred from the plan: an empty scan is precisely the case where the distinction matters, and a plan with no Tasks cannot tell you whether it saw an empty folder or no folder.

Inside, per planned Task: resolve by `(sourceId, groupPath)` in `task_imports`; create `tasks` + `task_state` + `assets` + `task_imports` when absent; otherwise update `lastSeenAt`, add newly discovered Assets, and update metrics and `sourceUri`.

**`sourceMissing = 1` may be set only for Assets whose `relativePath` lies inside `coverage`.** An Asset outside it was not looked at and therefore has nothing new said about it. This is what makes a child-scope refresh safe, and it is the rule a test has to break in order to regress.

**Missing material is flagged, never deleted.** No Task, TaskState or ReviewEvent is removed by an import run, in any circumstance, ever. That is invariant 8 of the architecture and it has no exception in this release.

`task_state` is inserted with the Task and nowhere else, so `writeTaskState`'s update-only contract from v0.2 N2 continues to hold unchanged.

### 5.2 Which runs are allowed to be scoped

| Source kind | full refresh | scoped refresh |
|---|---|---|
| file-as-Task | `coverage` = the Source's import root | allowed: `coverage` = any folder inside it. Used by the Folder-tab shortcut and List re-sync |
| folder-as-Task | `coverage` = the Source's import root | **not allowed** |

A folder-as-Task Task is assembled from a whole subtree, so a half-scanned group is a group whose Asset list is wrong. Refusing scoped refresh for it removes that entire class of bug for the price of one rule.

### 5.3 Identity stability

Re-running the same importer over unchanged material must produce `tasksCreated = 0, assetsCreated = 0` and leave every id untouched. This is the single most important test in the release (§13.1, test 5) and the reason resolution is by locator and `(sourceId, groupPath)` rather than by anything positional.

### 5.4 Reporting, and what is not stored

```text
ImportResult(
    outcome: complete | partial | failed,
    tasksCreated, tasksAdopted, tasksReconciled,
    assetsCreated, assetsUpdated, assetsMarkedMissing,
    conflicts: List<ImportConflict>,
    notices:   List<ImportNotice>
)
```

`sources.lastImportAt` / `lastImportStatus` are the durable summary. The detailed result is returned to the caller and shown on the result screen, then dropped.

**No `import_runs` table.** A run history is a feature nothing in v0.2.5 reads; the architecture asks for provenance sufficient to reconcile, and the Source row plus `task_imports.lastSeenAt` is exactly that. Adding a history table now is the "while we are here" failure mode v0.2 was written to correct.

### 5.5 `complete` versus `partial`

```text
complete  =  no conflicts, and every planned Task for the covered scope was written
partial   =  the transaction committed, but at least one planned Task was not written
failed    =  the folder could not be read, or the transaction did not commit
```

A notice is not a partial: skipping an unsupported file or an empty folder is the importer doing its job, and `rubric.txt` must not stop a candidate import. Only an *omitted Task* does.

A **direct** Import operation commits everything it can and reports `partial` honestly. A **composed** shortcut — Import → Quick Review, or Import → Create List — continues automatically only on `complete`; on `partial` it stops at the report, which offers to open the catalog. Anything the user then selects there is a new, explicit selection, not a continuation. This is the spec's "no List is created from a failed or incomplete import selection", made into control flow.

Review eligibility is deliberately **not** part of this gate; see §8.2 for why a stray unviewable file must not stop Create List, and §7 for the separate check Quick Review makes.

### 5.6 Registering a Source, and why real Sources may not overlap

Registration takes the grant, an import root, a display name and an importer kind. It is rejected when:

- another **real Source's** import root overlaps the requested one under the same grant, by `scopesOverlap` (`FolderScan.kt:28`) — the exact rule folder-backed Lists have used since V3.1 — with the covering Source named in the message; or
- `(rootUri, relativePath)` already exists, which the UNIQUE index also refuses.

Non-overlap is what makes ownership a settled question rather than a race. With it, a Task can change owner exactly once — from the legacy claim set to the one real Source that covers its file — and never back, so catalog membership and Source counts cannot oscillate no matter how often anything is refreshed.

When a covering Source already exists, a Folder-tab action inside it **reuses that Source's catalog scope**. It never registers a second Source, and for file-as-Task it may run a scoped refresh (§5.2) to pick up files added since.

### 5.7 Changing the importer

Changing `importerKind` on a Source that owns any Task is **rejected**, with an explanation naming the two kinds and the Task count. There is no force flag. The user's route is a separate import of a non-overlapping root, and the merge/split migration policy is deferred by the spec.

Bumping `importerVersion` for the same kind is allowed and reconciles normally.

## 6. Catalog, containment and eligibility

### 6.1 Containment

A Task's position in the source tree is one string: `task_imports.groupPath`. Against a scope path `S`, using `isAncestorOrSame` (`FolderScan.kt:21`), which already exists and is already tested:

```text
contained(groupPath, S)  =  isAncestorOrSame(S, groupPath)          -- S contains the whole Task
partial(groupPath, S)    =  isAncestorOrSame(groupPath, S) && groupPath != S
                                                                    -- S is inside the Task
otherwise                =  unrelated
```

That is the entire containment rule. A Task is never partially selectable, and `alice/papers` correctly reports Task *Alice* as partial rather than exposing `sample.pdf` as a reviewable thing.

Two properties to state, because a later importer must uphold them or replace this: it assumes **one grouping root per Task**, and it assumes **every Asset of a Task lies under it**. Both importers in this release satisfy both by construction; an importer that does not — one grouping a CSV row with a file from elsewhere — needs a different projection, not a patched one.

### 6.2 Scope membership for review

A scope's candidate set is the Tasks whose `groupPath` is a **direct child** of the scope path — the parent of `groupPath` equals `S`.

This is a deliberate narrowing of "contained". It preserves v0.1 Quick Review exactly: browsing `2026-07-11` today queues its own files and not `2026-07-11/bilibili/*`, and a recursive rule would silently change that for every existing user. It also gives scenario B what it asks for: at the candidate root the Tasks are `alice` and `bob`; one level down there are none, and `alice` reports as partial.

`contained`, `partial` and `directChildOf` are pure functions next to `isAncestorOrSame`, tested there.

### 6.3 Queries

One catalog query per Source, returning Task rows with their state and their Asset measurements, in the style of `observeFolderScopes`:

```sql
SELECT ti.taskId, ti.groupPath, ti.displayName,
       ts.isCompleted, ts.isFavorite, ts.customActions,
       COUNT(a.id) AS assetCount,
       SUM(a.sourceMissing) AS missingAssets,
       SUM(a.sizeBytes) AS sizeBytes,
       MAX(a.lastModified) AS lastModified
FROM task_imports ti
JOIN task_state ts ON ts.taskId = ti.taskId
LEFT JOIN assets a ON a.taskId = ti.taskId
WHERE ti.sourceId = :sourceId
GROUP BY ti.taskId
```

Asset names for the viewer-availability check come from the same read of `assets` the queue already makes; the catalog row carries a resolved `hasUnviewableAsset` flag so a list screen never re-derives it per row.

Scope filtering is applied in Kotlin with the algebra above, not with `LIKE` in SQL: the predicate is path-segment arithmetic, the existing helper already gets it right (`bilibili2/x` is not under `bilibili`), and a `LIKE 'x/%'` is exactly the bug that helper exists to prevent.

**A multi-Asset Task sorts and filters by the sum of its Assets' sizes and its newest modified time.** `FileArrange`'s unknown rule is unchanged: null stays "no reason to exclude".

### 6.4 Review eligibility

```text
eligible(task, scope) =
        contained(task.groupPath, scope)
    &&  task.assets.all { !it.sourceMissing }
    &&  task.assets.all { assetViewerAvailable(it.name) }
```

`assetViewerAvailable(name)` is **one function**, in the presentation layer next to `MediaKind`, returning true for the picture and video extensions this build renders and false for everything else, PDF included. Eligibility and the catalog badge both call it; nothing else classifies content.

It is filename-based because `MediaPreview.kt` — which classifies mime-first at render time — is one of the files this release must leave byte-identical, and because eligibility has to be answerable for a Task nobody is currently looking at. A provider that disagrees with the extension still lands on the existing `Unsupported` placeholder; that is a display outcome, it changes no stored fact, and it is the same safety net as today.

Three consequences to implement deliberately:

1. **A Task with zero Assets is eligible.** A legacy manual item has no content that could fail to render, and it is reviewable today. Nothing about it changes.
2. **Eligibility is enforced at the write boundary.** `submitReview` writes no state and no event for an ineligible Task and returns no transitions — the same shape as v0.2's "a submission about a Task that has gone". The UI disables the control and says why, so the refusal is never how the user finds out.
3. **Completion by other means is untouched.** A List Detail checkbox, a bulk edit and `setTaskCompleted` are not review submissions and are not gated. An existing List containing an unviewable or missing item keeps its membership, its progress and its history, and can still be completed and delivered exactly as today.

**This is a v0.1 behaviour change and it is intended.** Today a `.txt` or a source-missing item can be swiped in Quick Review or List Review, which records a judgment against a placeholder. After this release it cannot. §14.3 records the cost.

## 7. Quick Review from a scope

`observeFolderReview` (`ListsViewModel.kt:484`) currently registers files, mints Tasks and builds the queue from `file_review_state`. After this release it:

1. resolves the browsed folder — unchanged, still the folder listing, still `registerFiles` for the browse tick, the public ids and file management: registration is a browse concern and stays one;
2. reads the catalog Tasks for that scope;
3. builds the queue from the **eligible** Tasks in the scope (§6.4);
4. creates nothing, imports nothing, and writes nothing about any Task.

**Order is preserved exactly.** The queue is built by walking the browsed listing and mapping each entry to its catalog Task, dropping entries with no Task — structurally what `folderReviewQueue` does today with registrations, so `reviewRound`'s input order, and therefore `arrangeFiles`' output, is unchanged for any folder of files. A folder-as-Task scope has no file listing behind its Tasks, so those are ordered by `groupPath` with the same case-insensitive comparator `scanFolderTree` uses.

`folderReviewQueue` keeps its shape and its purity and takes catalog rows instead of registration rows. `ReviewItem` gains `assets: List<ReviewAsset>`, `rootRelativePath: String?` (the Task's `groupPath`) and `reviewBlocked: ReviewBlock?` (missing content, or no viewer); `assetsOf` (`ReviewScreen.kt:1011`) becomes a read of `item.assets` — the seam v0.2 left for exactly this, swapped as advertised.

What a scope says when it cannot start:

- **nothing imported here** → the import consent dialog (§11.2). No queue, no silent empty round.
- **only partial Tasks** → name the Task and where the whole of it lives, in the spec's words: *This folder contains only part of "Alice." Open the parent scope to review the complete Task.*
- **imported but nothing eligible** → say which condition failed: content missing, or *viewer available in v0.3*.

`deliverFolderReview` (`ListsViewModel.kt:1221`) re-reads decisions by **taskId** rather than by `getFileStates(rootUri, paths)`. That is the same class of defect N1 fixed: a Task without a registration row would otherwise silently drop out of the payload. `toPayloadRow` is otherwise unchanged, and `webhookRelativePath` produces the same wire value it does today for file Tasks (§10).

## 8. Creating Lists

### 8.1 From Tasks

```text
createListFromTasks(title, taskIds, webhookEnabled, webhookUrl, now): Long
```

Inserts the List and one `list_items` row per Task **in the order given**, with `taskId` set, `publicId` minted per entry exactly as today, and the file-shaped columns filled from the Task's Assets:

| column | file-as-Task | folder-as-Task |
|---|---|---|
| `title` | file name | child folder name |
| `sourceUri` | the Asset's URI | null |
| `sourceRelativePath` / `rootRelativePath` | the file's path | the `groupPath` |
| `sourceSizeBytes` / `sourceModifiedAt` | the Asset's metrics | sum / newest |

It resolves no files, scans nothing and calls no importer. Given a Task id it cannot reach, it fails the whole transaction rather than creating a partial List.

### 8.2 `createFolderList` becomes a composition

The Folder tab's Create List keeps its behaviour — overlap detection via `scopesOverlap`, replacement of overlapping Lists, webhook defaults, ordering — but its body becomes: run a file-as-Task import over the folder, then `createListFromTasks` with the resulting Task ids. **For a file-backed Task the resulting `list_items` row must be byte-identical to today's**, which is what keeps `ListsDaoTest`, `WebhookBodyTest`, `WebhookPayloadTest`, `ListArrangeTest` and the legacy-id suite green without edits.

Gating, per §5.5: the composition proceeds only when the import came back `complete`. On `partial` it stops at the report and creates nothing.

**Eligibility does not gate Create List**, and the reason is worth recording rather than rediscovering. A List is membership, not a judgment: v0.1 Lists have always been able to contain a `.txt` or a file whose source went missing, and AR-3 explicitly keeps such a List working, so refusing to create a List over a folder because one stray file has no viewer would break a v0.1 workflow in order to enforce a rule about review submissions. The Task lands in the List, the List Detail row shows it as blocked for review, and the checkbox still works. Quick Review is where eligibility bites, because that *is* a review context.

Import failure and List-creation failure are reported separately, and a failed List creation leaves the imported Tasks in place. That is the spec's independence requirement and it is the whole reason this is a composition rather than a rename.

### 8.3 Re-sync

`previewReconcile` / `applyReconcile` / `refreshSourceMetrics` stay, for folder-backed Lists, with their current UX. `applyReconcile` stops calling `taskForContent` and instead runs a **covered** file-as-Task import — `coverage` = the List's own folder (§5.1, §5.2) — then appends entries by Task id. Everything else about it is untouched: the diff, the missing and restored flags, `refreshCompletion`, and never firing a webhook.

Two cases the current code cannot meet and must report instead of guessing:

- **the List's folder has no covering Source.** Re-sync would have to register one, which is a write, so it asks for the same consent dialog as §11.2 and names the Source it would create. Declining leaves everything exactly as it was.
- **the List's folder is inside a folder-as-Task Source.** Appending a file as its own Task there would contradict that Source's grouping. Re-sync reports it and appends nothing.

**A List created from a Task selection has no folder link and is not offered re-sync.** Reconciliation is an import concern now; the Source refreshes and the List keeps its membership. Saying that plainly is better than pretending a List built from two catalog scopes can be diffed against one folder.

## 9. Multi-Asset presentation

v0.2 built `AssetNavigator` (`ReviewScreen.kt:720`) as a real collection boundary holding no selection state, and deferred three questions until a real multi-Asset Task existed. It exists now, so:

1. **Selection resets to the first Asset on every Task change.** The Task is the judgment unit; carrying "Asset 3" from Alice to Bob is meaningless when their Assets are different things.
2. **Selection is not in the round snapshot.** The snapshot says which Tasks a round walks. Which page of a candidate you were on is view state, not round membership.
3. **Selection is `rememberSaveable` keyed by task id**, so it survives rotation and process death and resets with the Task, which falls out of (1).

Plus, from the spec: switching Assets writes **no** TaskState and appends **no** ReviewEvent; Asset navigation is visibly distinct from Task navigation; completing and reviewing stay Task-level regardless of which Asset is on screen.

### 9.1 Chrome

> **Amended after implementation (2026-09-16, decision log 19 and 20).** The paragraph below is the
> plan's position and only its first half still ships. There is no separate selector and no dot
> row: the page position is the navigator's own `x(m/n)/y`. The rule against *two controls wearing
> one face* still holds and is now satisfied a different way — not by making the two levels look
> unlike each other, but by putting them in one bar as two labelled pairs, the outer moving Tasks
> and the inner moving files, so the difference is which pair you press rather than what a control
> looks like. Read the paragraph as history, not as the rule.

`AssetNavigator` draws a selector only when the Task has more than one Asset — v0.2's `1 / 1` rule is unchanged, and a one-Asset Task must look exactly as it does today. The selector is inside the Asset boundary and must not resemble the Task Navigator's `‹ N / M ›`: same-looking controls meaning different things is the failure this release's whole vocabulary exists to avoid.

**The frame, and what ships instead.** Three bands. The navigator is on top and the completion
checkbox is on the bottom, and **both take real room in the stack and are always present** — they
are the Task's and the queue's, and nothing done to the file takes them away. What the file itself
needs — the tag chips, Info, a video's transport — is drawn *over* the media at its bottom edge and
is the only band a tap hides.

This reverses the "the media fills the screen and the bars are drawn over it" note the media
surface carried in its own header, and it was reversed on evidence: with the chip row composed
inside the media rather than in the frame's own band, the video transport and the chips occupied the
same pixels, the transport was padded by a `chrome.bottom` that nothing had measured, and taps
landed on whichever layer was drawn last. Real room makes the collision impossible rather than
unlikely, which is the only version of this that survives a future change to either band. The
reason that note gave for the overlay rule still holds — a 16:9 photograph in landscape must not be
squeezed into what two fixed bars leave behind — and it is why the two read-only viewers keep the
older behaviour through `framePersists = false`.

The chrome is also themed as one layer. Each band is wrapped in `ListeaMediaChromeTheme`, which is
what forces `LocalContentColor` to white; an unthemed band's `IconButton` and uncoloured `Text`
fall back to black and disappear into the scrim. That is not a style choice — an unthemed bar is a
bug, and it is the bug the four reported defects began with.

### 9.2 Gestures

> **Amended after implementation (2026-09-16, decision log 18).** The paragraph below was the
> plan's position and it is no longer what ships. `SwipeCard` itself is still untouched — zoom
> ownership and forward/back arbitration are as they were — but the *binding* now spends a swipe on
> the pages of a multi-Asset Task before either Task-level action is reached, and the page selector
> moved below the Task navigator's bar. Read the paragraph as history, not as the rule.

Unchanged and untouched. `SwipeCard` keeps zoom ownership and forward/back arbitration ([`v0.2.0-reviewed.md` §5.1](v0.2.0-reviewed.md)); a horizontal swipe still means `CompleteTask` / `PreviousTask`. **Asset switching is an explicit control, not a gesture.** Binding Asset paging to a swipe would collide with the Task Review Template's bindings and re-open a question v0.2 settled.

**What ships instead.** A swipe moves one page and leaves the Task only at a run's two ends:
forward off the last Asset is `CompleteTask`, back off the first is `PreviousTask`. A one-Asset
Task has no interior page, so nothing about it changes and the overwhelming majority of Tasks are
unaffected. The reason the original ruling is no longer the right one is `ARCHITECTURE.md`
[Gestures and semantic actions](../ARCHITECTURE.md#gestures-and-semantic-actions): a template may
bind "either a review action or a navigation action … not which dimension the action belongs to".
The collision §9.2 feared was decided by the reviewer who ran the built-in template against a real
multi-Asset Task and found the two levels indistinguishable on screen, which is the worse of the
two failures. What must still hold is the part §9.2 was protecting: `AssetRun` calls the very same
`TaskAction` path the arrows do, so a swipe and an explicit control cannot drift apart.

> **Further amended after implementation (2026-09-16, decision log 20).** The page marker is *not*
> drawn below the bar. It is the bar's own `x(m/n)/y`, bracketed by an inner arrow pair, and the two
> levels are kept apart by which pair you press rather than by where a marker sits. See §9.1.

### 9.3 Blocked Tasks, and PDFs

A Task that is not review-eligible (§6.4) is **shown, navigable and not submittable**:

- its Assets render as they do today — the existing `PreviewPlaceholder` path for anything without a viewer, with copy naming the reason: *Source missing*, or *PDF — viewer available in v0.3*;
- `canSwipeForward` is false, so the forward swipe is inert, exactly as it already is at the end of a queue;
- the review surface's completion control is disabled and states the reason;
- `PreviousTask` / `NextTask` still work, because navigation has been pure since v0.2 and a blocked Task must not trap the user;
- `submitReview` refuses at the DAO (§6.4), so no path — gesture, control, or future caller — can record a judgment against it.

**No PDF rendering, no PDF viewer, no persisted kind.** v0.2.5 imports PDFs, catalogues them, shows what is there and says when it will be readable. Reviewing them is v0.3's to unlock, and unlocking it is a viewer plus one branch — no change to import, Task, List, Quick Review, TaskState or ReviewEvent semantics, which is exactly the claim §13.1 test 21 is written to prove.

### 9.4 The Info sheet is about the file

Info sits on the file's control row, so everything it says has to be about the file on screen. It
reads the `ReviewAsset` when there is one — its name for the title, its URI for the type, size and
modified time rows, and its URI for Save and Share — and falls back to the item only where there is
no Asset at all, which is the manual item where the item *is* the only thing there is.

The item still supplies what only it knows: whether it is checked, which actions are on it, and
which List it belongs to.

This is a fix, not a refinement. The sheet built its footer from the Task's own `sourceUri`, and a
folder-as-Task Task has several files and no source of its own — so Save and Share, the two things
the sheet exists to offer, were simply absent on exactly the Tasks this release added.

## 10. Compatibility boundaries

**Wire format.** Unchanged for every file-backed Task: same `id`, `title`, `isCompleted`, `relativePath`, `actions`, same `publicId` values from `list_items.publicId` (List rounds) and `legacy_item_ids` (folder rounds). A folder Task is new material with no compatibility obligation; it sends its `displayName` as `title` and its `groupPath`'s parent as `relativePath`, which is what the existing `webhookRelativePath` produces with no special case.

**Wire ids for Tasks with no single Asset.** Resolved by the compatibility adapter, in this order: the `list_items.publicId` of the entry being reported; else `legacy_item_ids` for a single-Asset Task; else `legacy_task_ids`, minting and storing one on first use. The importer, the catalog and every query in §6 are forbidden from reading any of the three.

**File management.** `getCheckedFilePaths` and `observeCheckedFileCount` read `assets` + `task_state` and need no change — a completed folder Task contributes its Assets, which is the truthful answer to "which files did the user check". Pin it with a test.

**Untouched files.** `Webhook.kt`, `FileManagement.kt`, `SwipeCard.kt`, `MediaPreview.kt`, `MediaZoom.kt`, `VideoControls.kt`, `FileArrange.kt` and `Settings.kt` stay byte-identical to v0.1, as they have through v0.2. `FolderScan.kt` is edited once, additively, for the snapshot in §4.1. If the patch needs to edit anything else on this list, that is a signal to re-read this plan rather than to edit it.

## 11. Surfaces

### 11.1 Where things live

The Folder tab stays what it is: a browser over raw material, with its ticks, arrangement, per-folder List ownership and file management intact. It gains **Import Folder**.

A new **Sources** surface lists registered Sources with importer kind, status, Task counts and per-Source actions: Refresh Import, browse catalog, Quick Review, Create List. A Source's catalog view shows its scopes and Tasks, marks partial, blocked and unavailable ones, and is where Task selection for a List happens.

Scope discipline: no other screen changes. This is already the largest UI increment in the release and it is where the estimate will be wrong if it is wrong anywhere.

### 11.2 Import consent

**Nothing is written before the user agrees to an import.** The first Quick Review or Create List on material no Source covers opens a confirmation that names:

- the Source root it proposes to register — the browsed folder, editable to an ancestor;
- the importer — **file-as-Task by default**, for compatibility;
- what will happen: how many files were found, and that Tasks will be created.

No `sources`, `tasks`, `assets` or `task_imports` row exists until it is accepted. Declining leaves the database exactly as it was and returns to the browser.

Once a Source covers the folder, entering Quick Review is immediate again, forever — the confirmation is once per folder, not once per review. A scoped refresh inside a covering Source (§5.2) is a refresh, not a registration, and is offered as an action rather than forced as a gate.

*Importing 128 files…* is **status shown after consent**, never instead of it. The one-motion feel of v0.1 is preserved everywhere except the first entry into un-imported material, which is the boundary this release exists to make visible.

## 14. Risks, limitations and accepted debt

1. **Consent before the first import.** Reviewing un-imported material now costs one dialog, once per folder (§11.2). This is the price of an explicit creation boundary and it is the decision, not an oversight — the shortcut must not be "fixed" later by making the import implicit.
2. **Real Sources may not overlap.** Importing `candidates/` and later `candidates/alice/photos` separately is refused, with the covering Source named. This is what makes ownership unambiguous and non-oscillating in a release that has no Source deletion; revisit it when Source deletion exists.
3. **Eligibility is a v0.1 behaviour change.** A `.txt`, an unknown type, or an item whose source has gone can no longer be *review-submitted*; it can still be checked, counted, listed and delivered. Narrow but real, and pinned by tests 17–20 so a later reader sees it was chosen. The reasoning is AR-3's: a placeholder is evidence the content could not be inspected.
4. **One SAF grant at a time.** `FolderStore` holds a single tree URI and changing it already offers to discard that root's Lists. Sources live under the active grant; a Source under a grant that is no longer held is *unavailable*, not deleted, and must not be swept up by `discardListsForRoot`. Multi-grant support is out of scope.
5. **Two ways to look at the same material** — the raw Folder browser and the Source catalog. Deliberate: the browser is about files (ticks, arrangement, deletion), the catalog is about Tasks. If they drift into looking alike, the vocabulary problem this release exists to fix comes back.
6. **`list_items` stays file-shaped.** A folder Task's entry carries a folder path in columns named `sourceRelativePath`, with `sourceUri = null`. Guarded by tests; worth revisiting when ListEntry is next opened.
7. **No Source deletion, and no import history.** §5.4. A mistaken import is permanent in v0.2.5; the safe version — discard a Source only when none of its Tasks has any state, event or membership — is a separable follow-up, and guessing at it now risks the one operation that could destroy review history.
8. **Legacy Tasks nobody imports stay outside every catalog.** They remain fully usable through their Lists, which is the compatibility obligation; they simply are not claimed by a Source until something imports their folder.
9. **The containment algebra assumes one grouping root per Task.** §6.1. A future importer that violates it needs a new projection, not a patch to this one.
10. **`IN (:paths)` > 999 exposure** is unchanged and still pre-existing. The import path adds locator lookups over potentially large folders — chunk them there rather than inheriting the limit.
11. **Orphaned `review_events` on legacy manual Task deletion** remains open, as recorded in v0.2. The new tables cascade from `tasks` and do not change it.
12. **Namespace and version metadata** — `com.example.listea`, `versionCode 1`, `versionName 0.1.0`. Still out of scope, still a release blocker eventually.

## Handoff to the implementation agent

1. **Only an import run creates a Task.** If a step seems to need a Task created anywhere else, that is the finding — report it, do not mint.
2. **Imported is not reviewable.** Eligibility (§6.4) is enforced at the write boundary, not only in the UI. A disabled button is a courtesy; the DAO's refusal is the guarantee.
3. **Do not redesign the accepted architecture.** `ARCHITECTURE.md` and `v0.2.5.md` revision 2 are in force and no longer contradict each other; this plan implements them. Settled decisions from v0.2 — no persisted Asset kind, no manual Task authoring, no rollback mechanism, viewer-owned gesture arbitration — are not reopened.
4. **Do not expand scope.** §14's limitations are deliberate, and so is the deferred list in `v0.2.5.md`. An abstraction added "while we are here" is the failure mode.
5. **Compatibility is evidence, not intent.** The v0.1-identical files stay identical; the wire stays byte-identical for file-backed Tasks; a `list_items` row for a file Task stays byte-identical. Prove each with a test, not with an argument.
6. **If the repository contradicts this plan, stop and report it** with the failing case — particularly if `groupPath` proves insufficient for a real row shape, if adoption cannot reconcile something a v0.1 database contains, if the non-overlap rule blocks a workflow the spec requires, or if `createFolderList`'s recomposition cannot reproduce a `list_items` row exactly.
7. **Evidence beats compilation.** Per [§10 of the v0.2 spec](v0.2.0.md): passing compilation is not completion, a migration without regression evidence is not completion, and a new abstraction the active workflow bypasses is not completion.
