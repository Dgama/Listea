## Framing

Step 1 settled *who holds what*. Step 2 settles *what happens when a holder gives up*.

The chef's own brief is the spec here, and it has three cases, not one:

| | The story | What step 2 owes it |
|---|---|---|
| **a** | The second market is out of tomatoes — the user deleted a file outside Listea. | The Todo syncing that folder must reconcile. |
| **b** | The chef changes his mind and abandons the first market's intent — the Todo is deleted. | Its Tasks go; **the fact that he already bought eggs does not.** |
| **c** | He changes his mind back, or meant to go again. | A new Todo at that folder can load from what the old one left. |

His words for (b): *"删除后不会改变 checked、tag 状态。类似于一种解散行为"* — a **dissolution**, not a
deletion. That word is the plan's organising idea, and this document uses it throughout.

The two sentences that decide almost everything below:

> **Deleting an intention is abandoning what it meant — so the Tasks go, and the judgments are
> what must survive.**

> **Recovery loads from one history at a time; a recovered Task belongs to the new Todo.**

## What step 1 left behind, and what it costs here

Three facts from the schema, all verified against the current tree, shape the work:

1. **`list_items.taskId → tasks.id` is `NO ACTION`, deliberately** (`data/ListEntities.kt:99-104`).
   A Task any List holds *refuses* to delete until its membership is gone. The comment there says
   the ordering is explicit on purpose, "so getting it wrong fails loudly instead of silently taking
   a Task with it." Step 2 must not defeat that; it must walk through it in the right order.
2. **`task_imports.sourceId → sources.id` is also `NO ACTION`** (`data/ImportEntities.kt:89-113`),
   and its comment already anticipates this release: *"a Source is never deleted in v0.2.5 and the
   row must outlive whatever later release adds deletion."* That later release is this one.
3. **Deleting a `sources` row cascades to nothing.** `sources` has no `foreignKeys` at all
   (`data/ImportEntities.kt:55-70`). Nothing about a dissolution can be left to the schema; it is a
   hand-written transaction or it does not happen.

And one asymmetry that decides the List question: `observeSummaries` (`ListsDao.kt:37-54`)
`LEFT JOIN`s `task_state` and so still **counts** a membership whose Task is gone, while
`observeItems` (`ListsDao.kt:77-101`) `JOIN`s it and so **renders nothing** for the same row. A
List left with a dangling member would read *"3 items, 2 checked"* and draw two rows. Removing the
membership is therefore not a design choice — leaving it is a bug.

## The architecture question, argued

`v0.4.0.md:232-235` flags this itself, and it is right to. `ARCHITECTURE.md` says, in three places:

- `:59` — *"Nothing may infer ownership, scope, or deletion policy from how many Assets a Task has."*
- `:114` — *"Nor may an implementation read anything about a Task's *lifetime* from its Asset count."*
- `:541` — a change *"makes Task lifetime depend on how many Assets a Task has"* **requires explicit
  architecture review.**

and `v0.2.0.md:89` invariant 19 states the same thing as *"No rule may be derived from
`assetCount == 0`."* The chef's original wording for case (a) — *"关闭表示 task 不会删除除非 asset 为
0"* — is that rule, verbatim.

Two further constraints bound what is allowed:

- `:466` — *"Unchanged material should reconcile to the same Task and Asset identities. Missing
  material must not erase review state or history."*
- `:162` — current state *"can move for many reasons that are not somebody rendering a verdict: an
  administrative correction from a list or index screen, a bulk edit, a source file going missing,
  **an import**. Those update TaskState and record nothing."*

`:162` is the licence step 2 runs on: **an import changing `TaskState` is already sanctioned.** What
is not sanctioned is an import changing *identity*.

### The three tiers

So the policy is not one switch but three, named per Todo and stored on the import:

| Tier | Asset set changes | Task identity | `task_state` | ReviewEvents | List memberships |
|---|---|---|---|---|---|
| **`keep`** | nothing else happens; the missing Asset is flagged | survives | survives | survive | survive |
| **`reset`** | the Task presents as un-judged again | **survives** | **cleared** | survive | survive |
| **`drop`** | the Task is deleted and a new one minted | **does not survive** | goes with it | survive, unreachable | membership removed (2a's machinery) |

`keep` is today's behaviour. `reset` reaches the chef's intent — a Task whose content moved should
not keep a stale tick — while touching only current state, which `:162` permits, and disturbing
neither identity nor history. `drop` is the chef's literal wording and is the one that reaches
lifetime.

### What the amendment to `ARCHITECTURE.md` says

`drop` is admitted, not smuggled. The amendment goes beside `:59` and `:114`, and reads:

> An import may carry an explicit per-Todo **content policy** naming what a change to a Task's Asset
> set means. `keep`: the Task and its judgment stand, and missing material is flagged. `reset`: the
> Task's identity stands and its *current state* is cleared — an operation `ReviewEvent and
> ReviewResult` already contemplates for an import. `drop`: the Task's **identity** does not survive
> the change, and a new Task takes its place.
>
> `drop` is the only tier that reaches lifetime, and it is admitted **only** as an explicit,
> user-named, per-import migration policy — which
> [Re-import and reconciliation](../ARCHITECTURE.md#re-import-and-reconciliation) already requires
> for a change of Task boundary — and never as an inference drawn from a Task's structure. No tier reads the *number* of Assets. All three read a *change* in the set of them, and
> a Task left with zero resolvable Assets under `keep` or `reset` is flagged missing and lives.

This is the explicit review `v0.4.0.md:232-235` called for, and the amendment is part of step 2b's
deliverable rather than a footnote to it — the tier does not ship until the doc says what it is.

> **As shipped**, `ARCHITECTURE.md` carries the paragraph above with one clause added, because as
> written it says something the code does not do. `drop` on a Task holding a single Asset *is*
> started over, and that decision reads `assetCount` — so "no tier reads the *number* of Assets" is
> true of choosing a **policy** and false as an absolute. The shipped text says which: the user's
> statement decides *that* something happens, the Task's shape only decides which of two ways of
> honouring it is available, and a policy is never *inferred* from a count.

**Decided, against the original sketch: a Task whose Asset count reaches zero is never deleted.**
The chef's case (a) said *"task 不会删除除非 asset 为 0"*; that clause is dropped. Its Assets are
flagged missing by the existing `setAssetMissing` path and the Task lives, which is what `:59` and
`:114` require and what `v0.2.0.md:89` invariant 19 already forbade. The `drop` tier still deletes
such a Task, but for having *changed*, not for being empty.

The chef's own reason for reversing it is the sharpest argument available and is worth keeping, as
it is the whole of why the rule exists:

> A folder-as-Task Task over a folder that empties, and is then given a file again, must still be
> the same Task. It went 2 → 0 → 1. Deleting at zero does not merely tidy away an empty Task; it
> makes the return impossible, because by the time there is something to return to, the identity
> that held the judgment is gone. **The 0 → 1 step is exactly the case a count-derived rule cannot
> express**, and it is the case this architecture's rule was written for.

So the tiers read a *change to the set*, never its size, and no tier has a zero case.

# Step 2a — Dissolution

Self-contained, and the half with the sharp edges. Ships first; its machinery is reused by 2b's
`drop` tier, which is the ordering reason for the split.

## Schema 17 → 18

Additive only. No table rebuild, no row rewritten:

```sql
ALTER TABLE sources ADD COLUMN keepStateOnDelete INTEGER NOT NULL DEFAULT 0;
ALTER TABLE sources ADD COLUMN contentPolicy     TEXT    NOT NULL DEFAULT 'keep';
ALTER TABLE sources ADD COLUMN followUpstream    INTEGER NOT NULL DEFAULT 0;

ALTER TABLE lists ADD COLUMN lastDissolvedCount INTEGER;
ALTER TABLE lists ADD COLUMN lastDissolvedAt    INTEGER;

CREATE TABLE IF NOT EXISTS dissolved_task_state (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    sourceId      TEXT    NOT NULL,
    sourceName    TEXT    NOT NULL,
    rootUri       TEXT    NOT NULL,
    relativePath  TEXT    NOT NULL,
    importerKind  TEXT    NOT NULL,
    isCompleted   INTEGER NOT NULL,
    isFavorite    INTEGER NOT NULL,
    customActions TEXT    NOT NULL,
    dissolvedAt   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS index_dissolved_task_state_sourceId
    ON dissolved_task_state (sourceId);
CREATE INDEX IF NOT EXISTS index_dissolved_task_state_rootUri_relativePath
    ON dissolved_task_state (rootUri, relativePath);
```

Only `keepStateOnDelete` and the two `lists` columns are 2a's; the other two `sources` columns and
`contentPolicy` belong to 2b and are added in 2b's own migration step (18 → 19) rather than here, so
that 2a can be verified and installed without 2b's semantics existing at all. **The snippet above is
the end state of both steps, not of 2a.**

Three things about `dissolved_task_state` worth stating, because each is a decision:

- **`relativePath` holds a Task's `groupPath`, not a file path.** That is what a later import can
  match a freshly-minted Task against, and it is the only key that survives the delete. It is
  provenance, which `ARCHITECTURE.md:357` allows an Upstream to retain — it is not a domain id, so
  invariant 1 (`:483`) is not in play.
- **`sourceId` is kept although its `sources` row is gone.** It is what groups one history together
  and what a recovery names; there is deliberately no FK, because the thing it points at is exactly
  what the row exists to outlive.
- **`sourceName` and `importerKind` are copied, not joined.** After the delete there is nothing to
  join to, and a picker that could not say *which* history it is offering would be useless.

## The delete transaction

One `@Transaction` in `data/ListsDao.kt`, in this order, and the order is load-bearing:

| # | Step | Why here |
|---|---|---|
| 1 | `taskIdsOf(sourceId)` from `task_imports` | everything else keys off this |
| 2 | `listsHolding(taskIds)` → id, title, count | read **before** anything is removed; feeds the note in step 7 |
| 3 | if `keepStateOnDelete`: `INSERT INTO dissolved_task_state … SELECT …` | must precede step 6, or there is nothing left to snapshot |
| 4 | `DELETE FROM list_items WHERE taskId IN (…)` | `list_items.taskId` is `NO ACTION`; skip it and step 5 fails loudly |
| 5 | `DELETE FROM tasks WHERE id IN (…)` | cascades `assets`, `task_state`, `task_imports`, `legacy_source_tasks`, `legacy_task_ids` |
| 6 | `DELETE FROM sources WHERE id = :sourceId` | `task_imports.sourceId` is `NO ACTION`; safe only after step 5 |
| 7 | `UPDATE lists SET lastDissolvedCount = …, lastDissolvedAt = :now` for each list from step 2 | |

Steps 4 and 5 are separate statements on purpose. `task_imports.taskId → tasks.id` **is** `CASCADE`,
so step 5 would take step 5's own provenance rows with it — which is correct, and is also why the
snapshot has to be written first.

**Steps 4, 5 and 6 are each protected by a foreign key that fails loudly if the order is wrong.**
That is the existing design's own safety net (`ListEntities.kt:99-104`) and the transaction should
lean on it rather than duplicate the check in Kotlin.

## The confirmation

Follow [`../file-management.md`](../file-management.md), which is this project's precedent for a
destructive operation and already sets the voice: *the full listing rather than a count*, and *the
decision is kept and the file is flagged missing* afterwards.

A `DeleteTodoRequest` state machine beside the existing `DeleteCheckedRequest`
(`ListsViewModel.kt:274-277`), rendered by a dialog modelled on `DeleteCheckedFilesDialog` /
`CheckedFileListing` (`SettingsScreen.kt:761-875`). Its `Confirm` step carries:

- the Todo's name and the number of Tasks that will go;
- **every List that will lose memberships, named, with how many each loses** — grouped the way the
  checked-files listing groups by folder;
- a **Keep the decisions** checkbox, preselected from `sources.keepStateOnDelete`, with the
  consequence in words: *"kept here, a later Todo at this folder can load them"* against *"the
  decisions go with the Tasks"*.

The checkbox is the humane place for this decision. The column is the per-import default the chef
asked for, and the dialog is where its consequence is legible, so the choice is made once where it
matters rather than pre-committed weeks earlier.

Entry point: a **Delete Todo** affordance on `TodoCard` (`SourcesScreen.kt:96`), which today offers
only **Refresh Import** (`:139`). It goes behind an overflow on the card, not beside Refresh.

## What a List shows afterwards

Memberships go, and the List says so — the chef's *"留一句说明"* answer, and the same voice as
`file-management.md`'s *"a List whose files you deleted stays complete and says its sources are
missing."*

Mechanism: the two `lists` columns written in step 7 above, phrased in the UI by a pure label
helper. Two nullable columns beside the existing `lastDeliveryAt`/`lastDeliveryStatus`/
`lastDeliveryCode` quartet (`ListEntities.kt:11-59`) is the proven shape in this schema for "what
happened last", and it is deliberately not an audit log — a second dissolution replaces the first
note, which is what "what happened last" means.

Rendered on the List detail screen and in the Lists index, cleared when the List next gains a
membership.

## Recovery: loading from one history

The chef's own guardrail: *"我们应当只允许 load from one history，不允许这个 task 从 history-1，另一个
task 从 history-2 恢复."* One history per import, never a mixture.

Two reads:

- `dissolvedHistoriesAt(rootUri, sourcePath)` — the histories at one folder, newest first, each with
  its `sourceId`, name, importer kind, Task count and date. This is what the picker shows. The
  second parameter is **the folder the intention was made at**, not the grant: a Todo dissolved over
  `Holiday/` is not offered to something being imported at the root of the same Upstream.
- `recoverStateFrom(dissolvedSourceId, newSourceId)` — one `UPDATE` over `task_state`:

```sql
UPDATE task_state
   SET isCompleted   = d.isCompleted,
       isFavorite    = d.isFavorite,
       customActions = d.customActions,
       updatedAt     = :now
 WHERE taskId IN (
     SELECT ti.taskId
       FROM task_imports ti
       JOIN sources s            ON s.id = ti.sourceId
       JOIN dissolved_task_state d
         ON d.rootUri = s.rootUri AND d.relativePath = ti.groupPath
      WHERE ti.sourceId = :newSourceId
        AND d.sourceId  = :dissolvedSourceId
 )
```

**As built, this is a read and then a write, not one `UPDATE … FROM`.** SQLite gained
`UPDATE … FROM` in 3.33 and `minSdk = 24` ships 3.9, so the join is done by `recoveryMatches` and
the writes are addressed by id. The statements above are the shape of the match; the file is the
authority on how it is executed.

Matching is by `(rootUri, groupPath)` and nothing else, which has one consequence worth stating
plainly: **a history whose grouping rule differs from the new Todo's recovers nothing.** Dissolve a
folder-as-Task Todo over `Demo` and re-import the same folder file-as-Task, and the paths will not
line up. That is honest rather than broken — the judgments were about *groups*, and the new Todo
does not have those groups — and the picker says so rather than silently copying nothing, in two
places: **before**, by reporting how many Tasks each history carries, and **after**, by the import
report naming the history it drew from. The second is why `confirmImportFolder` takes the whole
`DissolvedHistory` rather than its id, and why `ImportFolderRequest.Report` carries the name: a
count of zero is a real outcome, and "the history you chose had nothing to say here" is not the same
sentence as "no history was involved".

Placement is in the import flow, not after it: `ImportFolderRequest.Confirm`
(`ListsViewModel.kt:159`) already carries the names of the Todos already at that folder, so the
histories are its natural siblings. The dialog gains a **Recover from…** row when at least one
history exists; choosing one passes it into the run, and the recovery `UPDATE` runs inside the same
transaction as `runImport`, so a failed import recovers nothing.

**A recovery is offered on Create Tasks and never on Refresh Import.** A refresh runs over a Todo
that is still here, and a recovery overwrites a Task's judgment — so loading a history into a live
Todo would take every decision made since and replace it with an older one. Recovery is for a Todo
being born, which is why `requestSourceRefresh` builds its `Confirm` with no histories at all rather
than with a disabled control: the question is not asked because there is no good answer to it.

**Histories are not consumed by a recovery.** A history says *the eggs were bought once*; two later
dishes both knowing that is correct, not reckless — and the alternative needs a delete-a-history
affordance we would then have to design. Growth is bounded by how often a Todo is dissolved, which
is a deliberate act behind a confirmation dialog.

## Consequences worth stating, because they are visible

- **Deleting a Todo un-ticks its files in the Upstream browser.** `observeFileCompletion`
  (`ListsDao.kt:922-933`) reads `COALESCE(MAX(ts.isCompleted), 0)` over *live* Tasks, so a row whose
  only Task is gone reads unchecked. This is consistent with *"deleting an intention is abandoning
  what it meant"* — and it is precisely what the snapshot exists to be able to undo.
  **Where the row exists at all**, which is narrower than it sounds: the read drives from
  `file_review_state` and left-joins outward, so a path nothing has registered has no completion row
  and therefore no tick, whatever its Tasks decided. Registration happens on a folder Quick Review
  (`ListsViewModel.kt:823`), not on browsing and not on importing. Walking 2a on the attached phone
  made this visible — three files whose Task was demonstrably `isCompleted = 1` showed no tick,
  because the install has no `file_review_state` rows at all — and it is deliberate
  (`shownCheckState`, `MainActivity.kt:1060`), not a regression: an empty tick on every file of an
  unregistered folder would claim a review relationship that does not exist.
- **A file keeps its public id across a dissolution.** `legacy_item_ids` is keyed by `assetId` with
  no FK, so its rows dangle — but the `NOT EXISTS` guard in `assignLegacyItemIds`
  (`ListsDao.kt:1417-1432`) joins *live* Assets, and the value it re-mints comes from
  `file_review_state.publicId`, which is keyed by `(rootUri, relativePath)` and is never deleted.
  The file's wire identity survives. **This is load-bearing and needs a test**, because it is a
  property of two mechanisms interacting rather than of either one.
- **`review_events` survives and dangles.** `TaskEntities.kt:182-186` gives it no FK to `tasks`, on
  purpose. History is append-oriented (`ARCHITECTURE.md:160-164`), so this is the design working,
  not a leak — but no surface can reach those rows afterwards, and the plan should not pretend
  otherwise.

# Step 2b — The two per-import policies

Both are properties of the import, both defaulted from Settings, both seeded at Create Tasks time
in the same place `keepTree` is (`Importer.kt:43-62`, `ImportOptions`, `normalizeKeepTree`).

## `contentPolicy`

Applied inside `runImportInternal` (`ListsDao.kt:1748-1828`) at the point where a planned Task
meets an existing one — the `owned[groupPath]` branch that today always calls `reconcileTask`.

The decision itself is **pure and separable**, in the shape `FileArrange.kt` and `QuickReview.kt`
already establish: a function from *(policy, assets added, assets missing, asset count)* to
*KEEP / RESET / DROP*, with no Android and no I/O, so it is JVM-testable and `FolderTypeTest` has a
sibling. The DAO reads it; it does not decide.

> **As shipped.** The tier reaches the run as a **parameter** — `runImport(…, contentPolicy)` —
> rather than being read from the Source row inside `runImportInternal`. This document did not say
> where the value came from, and the first implementation read the row, which is right for the one
> caller that has no dialog ([`syncTodoUpstream`]) and wrong for the one that does. The import
> dialog asks the question and runs on the answer, while the row is only written back afterwards,
> so a refresh under a freshly chosen tier applied the tier the user had just replaced: choose
> *Replace the Task*, press Refresh, and watch a `keep` run report nothing replaced. Null means the
> stored value, which is what keeps that caller reading what the Todo says. Found by the device
> walk for acceptance 16 — no test covered the ViewModel's ordering, and `reset` had no
> folder-as-Task case — and pinned by *"a run applies the policy its caller names, not the one the
> Todo stores"* in `ContentPolicyRunTest`.

- **`KEEP`** — unchanged from today: `reconcileTask` plus `setAssetMissing` for what vanished.
- **`RESET`** — the same, then `task_state` cleared for that Task.
- **`DROP`** — the Task deleted and freshly minted. **Non-single-Asset Tasks only**, per the chef's
  spec. This reuses 2a's membership removal *and* its List note, which is the reason 2a ships first.

  > **Departure, as shipped.** The membership removal is reused unchanged; the note is not. 2a's
  > sentence is *"N items removed when a Todo was deleted"*, and a drop deletes no Todo — it removes
  > a membership because the Task it belonged to was replaced. Reusing the sentence verbatim would
  > make the List report an operation that never happened, so `lists` gained a third column,
  > `lastDissolvedReason`, and the label is written from it: *"…when their content moved"*. It is
  > the one place 2b departs from this document, it is additive to §step 7's schema list rather than
  > a contradiction of it, and it is why `DissolutionReason` exists beside the two counts. See
  > [v0.4.0 → Step 2b](v0.4.0.md#step-2b--the-two-per-import-policies).

`ImportResult` (`data/ImportRun.kt:66-76`) gains `tasksReset` and `tasksDropped` counts beside
`tasksCreated`/`Adopted`/`Reconciled`, so the import report can say what happened rather than
quietly reporting a reconcile. `ImportOutcome` is unchanged.

## Following the upstream

*"当 upstream 有新的，就同步到 todo"* — whether new material flows into a Todo on its own.

The scan already exists and is already read-only: `autoCheckSourceFreshness` (`Settings.kt:69`),
`SourceFreshness`/`ListFreshness` (`ListsViewModel.kt:177-205`), `checkSourceFreshness` (`:1572`),
`previewReconcile`. The policy turns an existing *report* into an existing *write*: enter a Todo
whose `followUpstream` is set, and the freshness scan runs, and when it finds something it goes
through `applyImport` (`:1336-1389`) — the same single writer Create Tasks and Refresh Import
already share, so there is still exactly one run, one transaction, one report.

One thing the plan should not carry over: `requestResync` refuses when more than one Todo covers a
folder (`:1630-1638`). That refusal belongs to the legacy folder-backed-List path and does not
apply here, because a Todo's refresh is scoped to its own `sourceId` and has nothing to guess.

## Settings defaults, and one flagged deviation

Two new Settings entries in the pattern of `askDeleteAfterWebhook` (`Settings.kt:143`, `:493`,
`:318-319`, `:422-423`; ViewModel passthrough beside `setAutoCheckSourceFreshness`
`:1887-1889`; `SwitchRow` in `SettingsScreen.kt`):

| Setting | Recommended default | Behaviour-preserving value |
|---|---|---|
| **Default content policy** | `keep` | `keep` |
| **Follow the upstream** | Off | Off |

**Both defaults are the behaviour-preserving ones, and both are decided.** `docs/settings.md:9-10` is
a documented rule — *"Every switch added after a feature shipped defaults to off, so a fresh install
and an untouched Settings page behave the same as they did before that feature existed."* Before 2b,
a re-import changed no state at all, so `keep` and off are what that rule requires. The migration
backfills `keep` and `0` for the same reason: the four Todos already on the device must not begin
behaving differently because a column appeared.

`reset` is the more interesting value and belongs in the import dialog, offered prominently, where
its consequence is visible — not as an unannounced default.
