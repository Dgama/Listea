# v0.8.4 implementation plan

> **Status:** implemented 2026-10-27; every phase P0–P11 is complete and the device walk is
> recorded in [Gate 7](v0.8.4-design-check.md#gate-7--implementation-acceptance). The build is
> `0.8.4-preview` (804), unreleased. This document scheduled the work the
> [v0.8.4 design](v0.8.4.md) describes.
> **Baseline:** `0.8.3-preview` (803), schema 32, export v5, `listea.package/1`.
> **Delivered:** schema 33, export v6, `listea.package/2` (v1 still readable).
> **Rule:** no hunk surgery on shared files. When the code lands, the commit layers are docs → main
> source → test, and the working tree is left clean.

## How to read this plan

The plan is ordered by dependency, not by screen. Each phase has a **deliverable**, an **exit
criterion**, and the **tests** that prove it. A phase that would ship without its tests is not done.
The phases are sized so that each can be reviewed on its own; the schema phase is the one that must
not be split across a release.

The two largest risks are named up front:

1. **Schema 33 is a key change, not a column addition.** Per-part payloads and per-part Resources
   change primary keys, which SQLite cannot alter. The migration rebuilds those tables; the test
   runs on a real schema-32 fixture before the app is installed over the existing database.
2. **The page/asset index is currently built on "one Content page, then Assets."** A multi-part
   Task has several Content pages. Every `reviewPages` consumer must move from a boolean
   `hasContentPage` to a page-list mapping. This is the highest regression risk in the review
   surface; it gets its own phase and its own tests.

## Scope

### In scope

- Task = 1..N TaskParts; a TaskPart is one Prompt instantiated in a Task.
- Degenerate parts for file/folder Tasks; no fake Prompt.
- Section tag + `sections` registry in protocol v2; taker Composition (`prompt:` / `section:`).
- Per-part response, events, current state, completion contribution.
- A Task-level completion policy on the stored Task Review; the explicit completion control remains.
- Page model with part grouping; no third arrow level.
- Protocol v2 reader with v1 compatibility.
- Schema 33 and the 32→33 migration.
- Export v6 with per-part results and explicit partial completion; v5 retained for compatible
  single-part bodies.
- Import composition choice (one Task per question / one Task per Section) for v2 Packages.
- One structured Viewer (`form`, schema 1) for conditional questionnaires — see the decision below.
- Per-part dissolution/history preservation.
- Catalog and review copy: parts/questions vs Assets/files.

### Out of scope

- Cross-Prompt conditions.
- Custom composition UI/storage (`custom:<key>` is representable only).
- Per-part revisability policies; per-part mixed contracts.
- Multiple Add-ons.
- `.listea` archive.
- Webhook/n8n grading implementation.
- A protocol freeze before acceptance (the freeze happens at the end of this plan).

### Scope decision: the structured Viewer

The framework does not require a new Viewer: multi-part Tasks can be built from `choice.single`
parts. The **conditional questionnaire** scenario (S6) does require a `structured` response and a
Viewer that can draw a body with internal conditions.

**Recommended:** include one minimal `form` Viewer in v0.8.4 (kind `form`, schema 1) with
`choice.single` and `text` fields and a `when` condition; it proves the structured contract and S6.
It is isolated in phase P6 and can be cut without touching P1–P5; if it is cut, S6 and the
`structured` acceptance are deferred, and the round still ships the TaskPart framework with
single-choice parts.

### P1 — Contracts and pure planning

**Deliverable:**

- `domain/` types for a part and a composition:
  ```kotlin
  data class PlannedPart(
      val partKey: String,
      val position: Int,
      val origin: PartOrigin,          // package | file | folder | legacy | synthesized
  ```

- The v2 section registry type.

### P5 — Part commit, state, and completion

**Deliverable:**

- `ReviewSubmission` is scoped to `(taskId, partKey)`; the DAO's commit path is atomic:
  append `review_events` with `partKey`, append the per-event projection (viewer events and/or
  structured fields), update `task_part_state`, recompute or preserve Task completion.
- `task_part_state.response` is the current canonical answer; the event history is append-only.
  A non-revisable answered part refuses a second commit at the write boundary.
- `TaskReviewDefinition` gains `completion: CompletionPolicy`; `TASK_REVIEW_DEFINITION_VERSION`
  becomes 3; v1/v2 definitions read as `SinglePart`:
  ```kotlin
  enum class CompletionPolicy { SinglePart, AllRequiredParts, AnyPart, ExplicitOnly }
  ```
  - Existing stored templates: `SinglePart`.
  - A new built-in `builtin.structured.single-choice@2` (or a multi-part template) uses
    `AllRequiredParts`; the import dialog can attach it.
  - `SinglePart` preserves the current `completesTask` behavior, including media templates that
    record Task-level state and write no part event.
  - `AllRequiredParts`: every required present part `answered`; unavailable required blocks;
    detached does not block.
  - `AnyPart`: at least one required answered.
  - `ExplicitOnly`: only the completion control.
- Completion provenance: `automatic` vs `explicit`; a part commit/reset recomputes automatic
  completion; an explicit completion is not silently cleared by a part change.
- The completion control remains a state edit; completing with pending required parts is allowed
  with a visible pending count and confirmation.
- Commit arrival: `advanceAfterCommit` moves to the **next part's first page**, then the Add-on,
  then the next Task; a failed commit never advances. This preserves the single-part Add-on
  arrival and extends it to parts.

**Exit:** a 3-part Task commits each part, shows the per-part current answer, completes only when
the policy says so; a non-revisable part refuses; a commit with a stale revision writes nothing.

**Tests:** `PartCommitTest`, `PartCompletionPolicyTest`, `PartRevisabilityTest`,
`CommitArrivalPartsTest`, `TemplateDefinitionV3Test`, updated `ReviewSessionTest`,
`TaskWriteTest`, `CurrentStateTest`, `ReviewRoundTest`.

### P6 — Structured Viewer (conditional questionnaire)

**Deliverable (if the scope decision keeps it):**

- A `form` Viewer, kind `form`, schema 1, registered in `Viewers`.
- Body grammar (Viewer-owned):
  ```json
  {
    "title": "…",
    "fields": [
      {"key": "ate", "type": "choice.single", "label": "…", "options": [{"id": "yes", "label": "Yes"}]},
      {"key": "what", "type": "text", "label": "…", "when": {"field": "ate", "equals": "yes"}}
  ```

- Export maps the structured answer to `parts[].result`.

**Exit:** the meal-tree fixture commits one part with the branch's fields; hiding/showing does not
create parts; a changed branch does not leave a hidden field in the response.

**Tests:** `FormViewerTest`, `StructuredResponseTest`, `StructuredExportTest`,

## Schema 33

### New tables

```sql
CREATE TABLE task_parts (
  taskId TEXT NOT NULL,
  partKey TEXT NOT NULL,
  position INTEGER NOT NULL,
  origin TEXT NOT NULL,              -- package | file | folder | legacy | synthesized
  promptKey TEXT,                    -- Package provenance
  required INTEGER NOT NULL DEFAULT 1,
  present INTEGER NOT NULL DEFAULT 1,
  availability TEXT,                 -- null = present; a code = unavailable
  updatedAt INTEGER NOT NULL,
  PRIMARY KEY(taskId, partKey),
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE
);
CREATE INDEX index_task_parts_taskId_position ON task_parts(taskId, position);

CREATE TABLE task_part_payloads (
  taskId TEXT NOT NULL,
  partKey TEXT NOT NULL,
  kind TEXT NOT NULL,
  schemaVersion INTEGER NOT NULL,
  payload TEXT NOT NULL,
  revision INTEGER NOT NULL,
  updatedAt INTEGER NOT NULL,
  PRIMARY KEY(taskId, partKey),
  FOREIGN KEY(taskId, partKey) REFERENCES task_parts(taskId, partKey) ON DELETE CASCADE
);

CREATE TABLE task_part_state (
  taskId TEXT NOT NULL,
  partKey TEXT NOT NULL,
  response TEXT NOT NULL DEFAULT '',
  answeredAt INTEGER,
  revision INTEGER,
  updatedAt INTEGER NOT NULL,
  PRIMARY KEY(taskId, partKey),
  FOREIGN KEY(taskId, partKey) REFERENCES task_parts(taskId, partKey) ON DELETE CASCADE
);

CREATE TABLE task_part_resources (
  taskId TEXT NOT NULL,
  partKey TEXT NOT NULL,
  resourceId TEXT NOT NULL,
  required INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY(taskId, partKey, resourceId),
  FOREIGN KEY(taskId, partKey) REFERENCES task_parts(taskId, partKey) ON DELETE CASCADE,
  FOREIGN KEY(resourceId) REFERENCES package_resources(id) ON DELETE CASCADE
);
CREATE INDEX index_task_part_resources_resourceId ON task_part_resources(resourceId);

CREATE TABLE package_compositions (
  taskId TEXT PRIMARY KEY,
  sourceId TEXT NOT NULL,
  packageKey TEXT NOT NULL,
  compositionKey TEXT NOT NULL,
  present INTEGER NOT NULL DEFAULT 1,
  updatedAt INTEGER NOT NULL,
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE,
  FOREIGN KEY(sourceId) REFERENCES sources(id)
);
CREATE UNIQUE INDEX index_package_compositions_source_package_composition
  ON package_compositions(sourceId, packageKey, compositionKey);

CREATE TABLE package_composition_prompts (
  taskId TEXT NOT NULL,
  sourceId TEXT NOT NULL,
  packageKey TEXT NOT NULL,
  compositionKey TEXT NOT NULL,
  promptKey TEXT NOT NULL,
  present INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY(taskId, promptKey),
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE,
  FOREIGN KEY(sourceId, packageKey, compositionKey)
    REFERENCES package_compositions(sourceId, packageKey, compositionKey) ON DELETE CASCADE
);
CREATE UNIQUE INDEX index_package_composition_prompts_source_composition_prompt
  ON package_composition_prompts(sourceId, packageKey, compositionKey, promptKey);
```

### Changed tables

| Table | Change | Why |
|---|---|---|
| `assets` | `partKey TEXT`; backfill to the Task's part; replace the per-Task unique index with `(taskId, partKey, rootUri, relativePath)` | an Asset belongs to one part |
| `review_events` | `partKey TEXT` (nullable); index `(taskId, partKey, at)` | primary events answer a part; legacy events stay null |
| `review_event_answers` | `fieldKey TEXT` (nullable) *or* a new `review_event_fields` table | structured fields need field identity; viewer events are not reinterpreted |
| `task_payloads` | replaced by `task_part_payloads`; old table dropped after copy | a payload belongs to a part, not a Task |
| `task_resources` | replaced by `task_part_resources`; old table dropped after copy | a Resource use belongs to a part |
| `package_prompt_tasks` | replaced by `package_compositions` + `package_composition_prompts`; old table dropped after copy | a Task may link several Prompts; the composite key includes `compositionKey` so an old Task and a new composition may both hold the same Prompt while the old Task remains |
| `dissolved_task_state` | `partRecords TEXT NOT NULL DEFAULT ''` | preserve per-part answers across dissolution |
| `sources` | `composition TEXT NOT NULL DEFAULT 'prompt'` | the Todo's standing composition rule |

`tasks`, `task_state`, `task_asset_state`, `task_asset_marks`, `package_checkpoints`,
`package_resources`, `task_imports`, `templates`/`template_versions` keep their shape (the template
payload gains the completion policy as a **stored payload version**, not a column).

### Migration 32 → 33

`MIGRATION_32_33` runs in this order, in one transaction:

1. Create `task_parts`; insert one part per Task:
   - `partKey` = the Package Prompt key when `package_prompt_tasks` has one, else `legacy:<taskId>`.
   - `position = 0`, `required = 1`, `present = 1`, `availability = NULL`.
   - `origin` = `package` when linked; else `file`/`folder` when `task_imports` + `sources` say so;
     else `legacy`.
   - `promptKey` = the linked Prompt key, else null.
2. Create `task_part_payloads`; copy every `task_payloads` row using its Task's partKey; drop
   `task_payloads`.
3. Create `task_part_state`; insert one row per part with `response = ''`, `answeredAt = NULL`,
   `revision` from the payload if any, `updatedAt` = now.
4. Create `task_part_resources`; copy every `task_resources` row with its Task's partKey; drop
   `task_resources`.
5. Alter `assets` add `partKey`; backfill from the Task's part; drop the old unique index; create
   the new unique index. (If SQLite cannot drop an index by name on the target versions, recreate
   the table; the migration test decides, and the plan allows a rebuild here because the index
   shape changes.)
6. Alter `review_events` add `partKey` (null); create the index. Legacy rows stay null.
7. Alter `review_event_answers` add `fieldKey` (null); or create `review_event_fields`. No
   backfill: viewer-event rows are not reinterpreted.
8. Create `package_compositions`; one row per distinct old `package_prompt_tasks` Task with
   `compositionKey = "prompt:<promptKey>"`.
9. Create `package_composition_prompts`; copy the old links with each Task's `compositionKey`
   (`prompt:<promptKey>` for migrated one-Prompt Tasks); drop `package_prompt_tasks`.
10. Alter `dissolved_task_state` add `partRecords` (default `''`); old histories read as
    no part records, fail-closed.
11. Alter `sources` add `composition` (default `prompt`); every existing Todo is one question per
    Task, exactly as before.

**Migration invariants** (asserted by the test):

- `COUNT(task_parts) == COUNT(tasks)` after the migration.
- Every `assets.partKey` is non-null and names an existing part of the same Task.
- Every `task_part_payloads` row names an existing part; no payload lost.
- No `review_events.partKey` is invented for legacy rows.
- `task_state.isCompleted` is unchanged; `task_imports` is unchanged.
- The fixture's page list (one Content, Assets, Add-on) is unchanged; the v5 export bytes are
  unchanged.
- The schema JSON 33 equals a fresh install's schema.

## Import composition

### The choice

| Choice | Composition key | Task count | When offered |
|---|---|---|---|
| One Task per question | `prompt:<promptKey>` | one per Prompt | default for every Package, including v1 |
| One Task per Section | `section:<sectionKey>` for tagged Prompts; `prompt:<promptKey>` for untagged | one per Section + one per untagged Prompt | v2 Packages with a `sections` registry; hidden otherwise |

The choice is the **taker's** rule, not a manifest field. The protocol never contains
`composition` or `tasks`.

### The import dialog

- A v2 Package with Sections shows the choice under the Package's summary, with a one-line
  explanation: *one Task per question* or *one Task per section; questions without a section stay
  their own Task*.
- A v1 Package does not show it; its behavior is unchanged.
- A refresh opens on the Source's stored `composition`; changing it is a new run. Tasks of the old
  composition keep their ids and are not merged; the Todo's scope/retirement rules decide their
  visibility.

### Catalog keys

- Prompt composition: `<packageKey>/<promptKey>` (unchanged).
- Section composition: `<packageKey>/~section/<sectionKey>` (the `~` first segment cannot be a
  prompt key, so the two namespaces cannot collide). The catalog shows the Section title as the
  display name.

## Protocol v2

The grammar is drafted in [package-protocol.md](../package-protocol.md#v2-implemented-for-v084). The
implementation plan freezes:

- `protocol: "listea.package/2"`.
- Top fields: `protocol`, `packageKey`, `revision`, `title`, `prompts`, `resources`, `sections`
  (optional).
- `prompts[].files` replaces `assets`; `prompts[].section` is optional; `sections[]` entries are
  `{sectionKey, title, order?}`.
- `response: "structured"` is accepted; the body's fields are Viewer-owned.
- Conditions are inside the Prompt body only; no manifest condition, no cross-Prompt condition.
- v1 and v2 are both accepted. v1 `assets` → Assets; v1 has no Sections; v1 imports with the
  `prompt:` composition. A v2 field in a v1 manifest is an unknown-field rejection; a v1 `assets`
  field in a v2 manifest is an unknown-field rejection.
- Strictness and limits:
  - one Section tag per Prompt;
  - `sections` present if any Prompt has a section; every `section` references a registry entry;
  - duplicate section keys reject;
  - a Section with no tagged Prompts is a declaration; selecting it as a composition is a
    diagnostic, not a Task;
  - limits: `MAX_SECTIONS = 2_000`; the existing Prompt/Resource/Asset limits apply; a structured
    body keeps `MAX_DESCRIPTION_BYTES`.
- The fingerprint includes the canonical `sections` registry, so a title/order change is a content
  change (a policy question: a title-only change should not reset answers; the existing fingerprint
  already treats a manifest title change as content, and the plan keeps the existing policy unless
  the design check says otherwise).
- The v2 reader's diagnostics use the existing scopes and codes; new `section-*` codes are listed
  in the protocol page.

## Review and completion

### Page list

For each present part in composition order:

```text
if payload != null: Content(taskId, partKey)
for each Asset in part.assets (attachment order): Asset(partKey, asset, assetIndex)
if Add-on: AddOn
```

- `assetIndex` is the global index among all Asset pages, so `AssetRun` keeps one list.
- A part with no payload and no Assets is invalid (P3) and never reaches the page list.
- A detached part is not present; an unavailable part is present but the surface shows the
  diagnostic and the completion policy treats it as blocking if required.

### Commit and arrival

- A submission names `(taskId, partKey)`. The write validates the part is present, the payload
  revision, required Resources, the Template contract and revisability.
- Under `SinglePart`: the existing behavior, including a media commit that writes Task-level state.
- Under `AllRequiredParts`/`AnyPart`: the part's current answer updates; Task completion is
  recomputed from parts. A part commit with `advanceAfterCommit` moves to the **next part's first
  page**; after the last part, the Add-on; then the next Task. A failed commit does not move.
- Under `ExplicitOnly`: no automatic completion; the control is the only path.
- The explicit completion control remains; completing with pending required parts shows the count
  and asks for confirmation. Un-completing is an explicit state edit.
- The Add-on is Task-level, optional, after all parts; it does not affect `isCompleted`.

### Template versions

- `TaskReviewDefinition` gains `completion`; definition encoding version 3.
- v1/v2 definitions read as `SinglePart`; existing stored templates do not change behavior.
- New built-in versions (if any) are stored rows, not edits to existing versions; the `Templates`
  content-hash tests stay green.

## Export v6

- Version selection: `6` if any Task has >1 part or a structured result; otherwise the existing v5
  rules.
- v6 Task: `id`, `publicId`, `title`, `completed`, `parts[]`, `addOn`; each part has `partKey`,
  `promptKey?`, `kind?`, `schema?`, `revision?`, `required`, `result` (object/string/null),
  `assets[]`.
- `result: null` vs `result: ""` is preserved; no pending part is exported as answered.
- Detached parts are excluded; the plan may add `detachedParts` under a provenance field only if
  the design check asks for it. The default is exclusion, documented.
- v5 remains for a single-part, non-structured Task; the body is byte-compatible. The v5 reader
  remains; old history is not rewritten.
- The export mapping is pure; the tests pin the body.

## Dissolution

- The snapshot reads `task_parts`/`task_part_state` and writes a versioned `partRecords` payload
  per Task.
- Recovery restores each present part's current response; missing/unknown part records are
  fail-closed (the Task recovers with pending parts rather than a guessed answer).
- A dissolved multi-part Task's `isCompleted` and part answers survive; the history picker's count
  remains Task-based.

## Scope decisions settled at sign-off

These were the open items the design check had to answer before P1. The 2026-10-27 design round
settles them as the plan's defaults. They are implementation-scope choices, not changes to the
TaskPart model; a fixture may still overturn one in P1, and the user may revise any of them before
code starts.

1. **The structured `form` Viewer is in.** It proves the `structured` contract and S6. It stays
   cuttable at P6: if it slips, S6 and the `structured` acceptance are deferred, and multi-part
   single-choice Tasks still ship.
2. **Export v6 Assets are per part.** A Task-level union with part links would duplicate the
   ownership the schema already states; the per-part shape matches the page model.
3. **Per-part dissolution is in.** Otherwise a multi-part Todo with `keepStateOnDelete` would lose
   the answers of its parts.
4. **Completion defaults:** `SinglePart` for existing templates; `AllRequiredParts` for a
   multi-part Section Task. Both are Template-level policies, recorded with the Task's completion
   provenance.
5. **Default composition is one Task per question**, with Section grouping as a toggle in the
   import dialog. This preserves today's shape for a v1 Package and for a v2 Package whose taker
   ignores Sections.
6. **A Section title/order change does not reset state.** The fingerprint separates membership
   from labels: renaming a Section is not a content change to its Prompts.
7. **Catalog copy:** show **questions** when the Task is a question set and **parts** when the Task
   mixes content kinds; always show the file count separately (`3 questions · 2 files`). A media
   Task shows its file count alone.
