# Listea v0.5.0 — The template, and what the middle band is for

> **Status:** Iteration, planned. **Not implemented.**
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.4.0 (Ownership, and a List that spans Todos)
> **Supersedes:** [Roadmap §1](../roadmap.md)'s "including task-specific ones, on top of the
> user-configured set", and the app-wide scope of `AppSettings.customActions`
> **Superseded in part by:** [v0.5.1](v0.5.1.md) — acceptance #5's second sentence. This release
> made the template lookup per file and left the *record* per Task; v0.5.1 moves the record to the
> Task–Asset pair, which is what paging between files of one Task was always meant to show.

## The change in one table

Everything in the Review screen has been type-blind: one set of custom actions is configured in
Settings, and every Asset of every Task is offered all of them. From v0.5.0 an Asset is offered the
tags its **file kind** is configured with, and that configuration is chosen per Todo.

| Was | Is |
|---|---|
| One app-wide set of custom actions | One tag set **per file kind** (image, video) |
| Offered identically on every Asset | Offered according to the kind of the file on screen |
| `AppSettings.customActions` is the whole story | It is the **default a new Todo starts with**; each Todo records what it actually uses |
| Nothing on a Task says what it is judged with | A Task records the asset control its import gave it |

The band that changes is the **middle** one. Nothing about the navigator, the checkbox, or the video
transport changes at all.

## Why

### The three bands

An Asset on the Review screen is surrounded by three bands, and they have different masters:

```text
  ┌─ task & asset navigation + task control ─┐   the name, the position, the checkbox
  │  ┌─ asset control  ← the template ─────┐ │   what to record about this file
  │  │  ┌─ media control ────────────────┐ │ │   play, pause, seek, zoom, page
  │  │  │            the file            │ │ │
  │  │  └────────────────────────────────┘ │ │
  │  └─────────────────────────────────────┘ │
  └──────────────────────────────────────────┘
```

| Band | Holds | Depends on |
|---|---|---|
| **Navigation + task control** | Filename, position (`3(2/3)/7`), the checkbox | The Task's composition, and nothing else. True of any file, of any kind, whatever is being asked of it |
| **Asset control** | The tag row: `★` and the configured tags | **Intention × file kind** — both, and neither alone |
| **Media control** | Transport, zoom, page turning | The file kind, and nothing else. True of any video, whatever it is for |

Only the middle band is a function of two things at once. That is what makes it the band that needs
a template, and it is why "template" in this release means this band and no other. The other two are
templates too, in the sense that they are replaceable sets of behaviour — but the build has exactly
one of each, and fixing them is a deliberate deferral, not an oversight.

### The chef, standing in the market

[v0.4.0](v0.4.0.md) told this story up to the shopping list. The chef knows what he means to cook —
two dishes, so two Todos, one per market — and a List holds the Tasks from both, because a List is an
order over Tasks and he wants one list to shop from.

What v0.4.0 did not have was the chef's own notebook. He is standing in front of the eggs, and the
egg is a single file that one Task covers. What does he write down?

- For the tomato dish, **the price**. That is what that dish turns on.
- For the pepper dish, **how fresh they look**. That is what that dish turns on.

Same market, same eggs, two answers — because the *intention* differs.

And standing in front of the peppers for the tomato dish, he writes down something else again, because
peppers are not eggs: their colour, maybe, or whether they are firm. Same intention, different file,
two answers — because the *thing in front of him* differs.

The tag row is the notebook. It varies with both, so it cannot be configured in one place that knows
only one of them.

### What this overturns

Two things the code currently says, which this release makes false:

1. **Tags are app-wide.** `AppSettings.customActions` (`Settings.kt:42`) is one list, and
   `AppSettings.actions` (`Settings.kt:201-202`) offers it on every Asset regardless of kind. Under
   the new model it is the default a *new* Todo starts with, in the same way `defaultContentPolicy`
   is the default a new Todo's content policy starts with.
2. **Tags come on top of a global set.** [Roadmap §1](../roadmap.md) describes a future template's
   actions as "task-specific ones, on top of the user-configured set". The template does not add to
   the set. It **owns** it.

The second is worth stating plainly because it changes what a template is: not a plugin that
contributes to a shared vocabulary, but the whole of the vocabulary for the files it governs.

## The model

### A template is a definition, and a configuration

The word has meant two things at once in this codebase, and splitting them is what makes a
user-editable tag row compatible with [ARCHITECTURE.md](../ARCHITECTURE.md)'s insistence that a
`TemplateVersion` is immutable and its `contentHash` is asserted by a test.

| | What it is | Where it lives | Editable |
|---|---|---|---|
| **Definition** | What *kind* of control this is, which file kinds it may be used for, and which built-ins it carries (`★`) | Code, versioned, hashed — `Templates.kt` | No |
| **Configuration** | Which tags, with which names and wire values, this Todo wants | The Todo | Yes |

A rendered asset control is the definition's built-ins followed by the configuration's tags. A review
event continues to cite the exact **definition version** it was made under, which is what
`review_events.templateVersion` has always meant; the *configuration* in force is not a property of
the version and is not recorded as one. What was actually applied is already pinned by the response
snapshot, which stores tag **ids** — so a later rename still cannot rewrite history, which is the
property that mattered.

This is the sense in which Settings can offer template management without the architecture bending:
what it edits is the configuration, and configurations were never immutable.

### The built-in definition

One asset control ships, and it is exactly what the app does today:

```text
builtin.media.asset-control @1     "Media Asset Control"
    compatible kinds: image, video
    carries:          ★ Favourite
```

Its `compatibleKinds` is what makes a configuration *valid* — a tag set may be attached to a kind
only if the definition it names accepts that kind. Its `favourite` flag is what makes `★` part of the
template rather than fixed chrome, so a future control may omit it.

What it deliberately does **not** carry yet is typed fields. The chef's notebook in this release holds
labels and nothing else; a purchase count, a price, a freshness rating, a note are all the same
mechanism with a type attached, and they are deferred rather than designed around.

### The file kind

The key is `AssetKind` — `IMAGE`, `VIDEO`, `OTHER` — and it is resolved **from the filename**, through
the same classifier review eligibility already uses.

That is not an implementation shortcut. `assets` has never had a persisted kind column
(`v0.2.5-plan.md` decision 3), and
[`Catalog.assetViewerAvailable`](../../app/src/main/java/com/example/listea/Catalog.kt) is
filename-based for a stated reason: a Task nobody is currently looking at must still be answerable,
and opening every file to find out what it is would make the catalog a scan. The template lookup
inherits that rule, so it costs a string operation and never a content read.

Settings offers the two kinds the built-in control declares — image and video. `OTHER` is not offered
because nothing with kind `OTHER` is reviewable today in any case; a PDF Task is blocked by
`ReviewBlock.NO_VIEWER` before a tag row is ever drawn.

### Where the choice is made, and where it is recorded

Three levels, and each mirrors something the content policy already established:

| Level | Holds | Precedent |
|---|---|---|
| **Settings** | The tag set a *new* Todo starts with, per kind | `defaultContentPolicy` |
| **The Todo** | The answer its import run collected, per kind | `sources.contentPolicy` |
| **The Task** | The resolution its import gave it, per kind | new — this is what makes a Task answerable without a join |

The Task's copy is the one that is new in kind, and it is the reason the chef's notebook works: a
Task must be able to say what it is judged with, at the moment it is being judged, without walking
back to its Todo. An import run stamps it, and a later run re-stamps it — so editing the template in
Settings changes what the *next* run produces and does not silently re-label Tasks already imported.
The Todo card says which control its Tasks are under, in the same places the content policy is
already reported, so the two standing answers are legible together.

The fixture for this release is already on the test device and is worth naming, because it is the
scenario the acceptance test runs. The `Demo` Todo is folder-as-Task, so each of its Tasks is one
folder: `Camera` holds three photographs, `Wechat` one, and `Whatsapp` holds two photographs and a
video — `IMG20260727181605.jpg` (whose file has since been deleted, so its Asset is flagged missing),
`IMG20260905084649.jpg`, and `VID20260905084244.mp4`. One Task, both kinds, three Assets. Paging
through it is the whole test.

## What a user sees

**Settings gains a template manager**, per file kind. Today's Custom action rows are exactly the
control it needs — display name, webhook value, add, remove — drawn once for image and once for
video. A user who configures three tags for image and two for video has done nothing more exotic
than filling in two lists.

**The Create Tasks dialog asks per kind**, next to the three content-policy rows and in the same
shape a Todo's own card reports them back. A folder holding only photographs is asked only about
image; one holding both is asked about both. The dialog pre-fills from Settings, and what it collects
is what the Todo records.

**The Review screen's middle band follows the file on screen.** Paging from a photograph to a video
inside one Task re-draws the tag row: the tags configured for video, and `★` if the video's control
carries it. Paging back restores the photograph's row. On the `Whatsapp` Task above, the row goes
from three tags to two and back.

**The webhook's `actions` array follows the same resolution**, because it is produced by the same
lookup — the tags the Task's control defines, filtered to the ones actually set. A tag id that is no
longer configured in any control the Task is under is still carried in the task's own record and
still not sent, which is the behaviour it has today.

## Acceptance

1. **Settings** shows a template manager with a section per file kind. Editing image's tags does not
   change video's.
2. Configure **three** tags for image and **two** for video.
3. Open the `Demo` Todo, open the `Whatsapp` Task, start a review. The tag row shows **three** tags on
   the first Asset and on the second.
4. Page forward to the third Asset — the `.mp4`. The row shows **two** tags, and `★` is still there.
   Page back; it shows three again.
5. Tick a tag on the video Asset, then page back to a photograph. The video's tag is still set on the
   Task — it appears in the navigator's badge row and in the Info sheet — and it is offered by no chip
   on the photograph, because the photograph's control does not define it.

   > **Superseded by [v0.5.1](v0.5.1.md).** *"Still set on the Task"* was wrong, and this sentence
   > was the model being stated rather than a wiring slip: the record was Task-level, so paging back
   > to a photograph showed the video's tag as the photograph's own. The lookup is per file, as this
   > release says; the **record** is per Task–Asset pair, which is what v0.5.1 changes.
6. **A Todo that was imported before this release behaves exactly as it did.** Its Tasks carry no
   recorded control, the app's per-kind default is the list that used to be app-wide, and every Asset
   of every Task still offers all of it.
7. **A new Todo records what it was imported under.** Change the image tag set in Settings, re-run
   Create Tasks on the same folder, and the new Todo's Tasks offer the new set while the old Todo's
   Tasks still offer the old one.

## Out of scope

Stated so that the shape of what follows is not mistaken for an oversight:

- **Typed fields.** A price, a count, a rating, a note. The mechanism is the same one and the
  definition will carry the field list; nothing in this release builds it.
- **Composing the other two bands.** Media control and the navigator/task control remain the single
  built-in set. They are templates in the same sense and will be split later.
- **Splitting image further.** `jpg` and `png` are one kind for now. The key is `AssetKind`, so
  splitting means a finer enum, not a second mechanism.
- **Making an `OTHER` file reviewable.** A PDF still has no viewer and its Task is still blocked.
- **Templates that are not per-file-kind.** Every template in this release is keyed by kind. A
  template keyed by something else — a Task's source, a field in a sidecar — is not designed for.
