## 1. Final domain model

```text
Template 1 ─── N TemplateVersion
                      │ gives meaning to
                      ▼
List 1 ─── N ListEntry N ─── 1 Task ─── 0..N Asset
                                 ├─── 1 TaskState        (current truth)
                                 └─── 0..N ReviewEvent   (submitted judgments)
```

- **Task** — the unit judged. Opaque UUID. Owns current state and history. Independent of any List. Asset count says nothing about its lifetime.
- **Asset** — content presented through a compatible viewer. Own UUID, distinct from its Task's. Carries the source locator (`rootUri`, `relativePath`) and presence flag. Read-only.
- **ListEntry** — membership of a Task in a List. Keeps the existing `list_items.id` autoincrement; membership is a separate identity space (decision 6).
- **TaskState** — what is true now: `isCompleted`, `isFavorite`, `customActions`. One row per Task, always present.
- **ReviewEvent** — one submitted judgment, with the response snapshot and the exact TemplateVersion that gave it meaning. Append-only.
- **Template / TemplateVersion / TemplateKind** — code-defined; two kinds, Asset Viewer and Task Review.

Source identity `(rootUri, relativePath)` remains the cross-context resolution key, now living on the Asset. It resolves a Task; it is never a Task's identity.

## 2. Room schema (v13)

```sql
tasks(id TEXT PK, createdAt INTEGER NOT NULL)

assets(id TEXT PK,
       taskId TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
       sortOrder INTEGER NOT NULL,
       rootUri TEXT, relativePath TEXT,
       sourceMissing INTEGER NOT NULL DEFAULT 0,
       UNIQUE(rootUri, relativePath), INDEX(taskId))

task_state(taskId TEXT PK REFERENCES tasks(id) ON DELETE CASCADE,
           isCompleted INTEGER NOT NULL DEFAULT 0,
           isFavorite  INTEGER NOT NULL DEFAULT 0,
           customActions TEXT NOT NULL DEFAULT '',
           updatedAt INTEGER NOT NULL)

review_events(id TEXT PK,
              taskId TEXT NOT NULL,
              at INTEGER NOT NULL,
              kind TEXT NOT NULL,                    -- 'submitted' in v0.2
              templateId TEXT NOT NULL,
              templateVersion INTEGER NOT NULL,
              response TEXT NOT NULL,                -- canonical snapshot, not a wire body
              contextKind TEXT, contextRef TEXT,     -- 'list'/'folder' provenance
              INDEX(taskId, at))

legacy_item_ids(assetId TEXT PK, publicId TEXT NOT NULL)      -- compat boundary
legacy_manual_tasks(taskId TEXT PK)                            -- closed legacy set

list_items  -- rebuilt: gains taskId TEXT NOT NULL REFERENCES tasks(id)
lists       -- gains taskReviewTemplateId TEXT NOT NULL DEFAULT 'builtin.media.rapid-review'
            --       taskReviewTemplateVersion INTEGER NOT NULL DEFAULT 1
```

Notes on shape:

- A Task with zero Assets is simply a Task with zero Assets. No `kind`, no lifecycle enum, no scope field (decision 4).
- The UNIQUE moves to `assets`, preserving today's dedupe guarantee exactly.
- `task_state` always exists, so `observeItems` loses its `CASE`/`COALESCE` projection entirely: `list_items JOIN tasks JOIN task_state`. Strictly less divergence-prone than today.
- `legacy_item_ids` and `legacy_manual_tasks` are side tables at the compatibility boundary, so no webhook or legacy-workflow semantics enter Task, Asset or Template.
- `review_events.kind` is retained with a single value. The architecture leaves room for non-submission entries later; a TEXT column now is cheaper than a migration then. `response` is a canonical internal snapshot and explicitly **not** modeled on the webhook body.

### 2.1 `taskId` nullability (decision 9) — resolved

Rev 1 proposed `ALTER TABLE list_items ADD COLUMN taskId TEXT` plus a backfill. **That is not viable**, and the reason is exactly the mismatch you flagged:

- SQLite cannot add a `NOT NULL` column without a default, and has never been able to alter a column to `NOT NULL` afterwards. `minSdk` is 24, so nothing newer can be assumed.
- A nullable SQLite column against a Room entity declaring `val taskId: String` fails Room's open-time schema validation on the `notNull` flag — and would fail `runMigrationsAndValidate` the moment schema export is switched on.
- `NOT NULL DEFAULT ''` would make the empty string a sentinel meaning "broken row", which is worse than null.

**Chosen: rebuild `list_items` inside the migration**, the same table-copy pattern `MIGRATION_10_11` and `MIGRATION_11_12` already use in this codebase. Verified as safe: `list_items.listId → lists.id` is the **only** foreign key in the entire schema, and nothing references `list_items`, so the drop-and-rename has no dependents. `MIGRATION_11_12` already rebuilds this exact table and already carries `id` across explicitly, so autoincrement row ids — and therefore resume and webhook queue scoping — survive untouched.

The result is one consistent answer at all three levels: SQLite says `taskId TEXT NOT NULL REFERENCES tasks(id)`, the Room entity says `val taskId: String`, and the domain may assume a ListEntry always resolves to a Task. The rebuild recreates the `lists` foreign key and both existing indices (`listId`, `rootRelativePath`) verbatim.

The new FK uses default `NO ACTION`; deletion ordering is handled explicitly in the DAO (§4).

## 3. Migration v12 → v13

1. Create the new tables. Add the two `lists` template columns.
2. For every `file_review_state` row: generate Task and Asset UUIDs; insert `tasks`, `assets(rootUri, relativePath, sourceMissing, sortOrder = 0)`, `task_state(isCompleted, isFavorite, customActions, updatedAt)`, `legacy_item_ids(assetId, publicId)`.
3. Resolve a `taskId` for every `list_items` row:
   - source-backed (`rootRelativePath NOT NULL`, owning list has `sourceRootUri`) → look up the Asset by `(rootUri, relativePath)`. **If absent** — which happens legitimately, since `file_review_state` rows are created lazily — create Task + Asset + `task_state` with all decisions false, which is exactly what today's `COALESCE(..., 0)` projects. No `legacy_item_ids` row; one is still assigned lazily at first registration, preserving current behavior.
   - manual (`rootRelativePath IS NULL`) → one Task per row, so identical titles stay distinct; zero Assets; `task_state` from the row's own three columns; record the Task in `legacy_manual_tasks`.
   - defensive: a row carrying `rootRelativePath` whose list has no `sourceRootUri` is treated as manual rather than dropped.
4. Rebuild `list_items` with `taskId TEXT NOT NULL`, copying every column including `id`, `publicId`, `sortOrder`, `createdAt`, `sourceMissing` and the cached metrics, and recreating the FK and both indices.
5. **No ReviewEvents are written.** No fake review count, no migration marker that could be counted as a submission.
6. `lists`, `webhook_history`, `reviewCurrentItemId` and both `publicId` columns: untouched.
7. The now-unused `list_items.isCompleted / isFavorite / customActions` are carried across the rebuild with their values intact, and stop being read. They are dropped in a later release once no reader is provable. (`MIGRATION_7_8` cleared its equivalents; I still recommend against that here, because those values are the only remaining copy if the migration is later found wrong.)

UUIDs are generated in Kotlin, reusing the drain-then-write `backfill()` helper from `MIGRATION_9_10`. Room runs the whole migration in one transaction.

**No application-level rollback mechanism** (decision 7). A plain file copy ignores WAL and sidecar state and would be a false promise. Confidence comes from tests against realistic fixtures, plus a maintainer device backup taken before exercising the release migration.

**Validation, as assertions in the migration test:** every `list_items.taskId` resolves; every Task has exactly one `task_state`; `COUNT(assets) = COUNT(DISTINCT rootUri || relativePath)`; per-list completed/total identical before and after; `review_events` empty; every pre-migration `publicId` present, byte-identical, and still attached to the same row or registration; `legacy_manual_tasks` contains exactly the pre-migration manual rows.

## 4. Legacy manual-item compatibility (decision 5)

**Product change:** the "New item" field and its write path are removed from List Detail (`dao.addItem`, `ListsViewModel.addItem`), and standalone "New list" creation is removed with it (see below).

**Existing manual items are preserved**, reviewable and editable exactly as today, until their List's own lifecycle removes them. The read/write paths they still need — `setManualItemCompleted`, `setManualItemAction`, `removeItem` — stay.

**Mechanism: `legacy_manual_tasks(taskId TEXT PK)`.** A one-column side table naming the closed set of Tasks that were manual items at migration time. Chosen because it is the smallest thing that satisfies the constraint:

- it **names** the legacy rows rather than inferring them, so nothing is derived from `assetCount == 0` (decision 4, invariant 19);
- it is closed at migration and can only shrink, since no new manual items can be created. When it empties, the table can be dropped and the compatibility case disappears with it;
- it introduces no lifecycle vocabulary, no enum, no scope column, and nothing future-facing for a vocabulary or questionnaire Task to accidentally inherit.

Cleanup is explicit and lives in the DAO, not in a SQL cascade, because the Task is not a child of the entry: `deleteList` and `removeItem` collect the affected Tasks that appear in `legacy_manual_tasks`, delete the entry (or let the `lists` cascade run), then delete those Tasks, all inside one `@Transaction`. Source-backed Tasks are never touched by this path, and `removeMissingSourceItems` cannot reach it — it is already guarded by `sourceRelativePath IS NOT NULL`.

**Standalone List creation is removed with it (decided).** The "New list" button on the Lists screen calls `createList(title)`, which creates a List with **no folder link**. Manual entry was the only way such a List could ever gain an item, and `refreshCompletion` requires `itemCount > 0`, so keeping it would ship a control that can only produce permanently empty, never-completable Lists. It goes in the same change: remove the "New list" affordance, `ListsViewModel.createList`, and the now-unreachable insert behind it.

Folder-backed List creation is **unchanged**. It runs through `requestListForFolder` → `commitPendingFolderList` → `dao.createFolderList` from the Folder tab, a completely separate path that never touched `createList`. Renaming and deleting Lists are unaffected.

Existing standalone Lists — created before v0.2, with or without items — are **not** migrated away, deleted, or converted. They keep their entries, decisions, progress, webhook configuration and review behavior. Only the ability to create new ones is removed.

This is a **product-boundary cleanup, not an architectural rule that Lists must be folder-backed.** A List is an ordered review context over Tasks; where those Tasks came from is the creation boundary's business. Future Importer / Task Creator flows may well introduce new ways to create Lists from prepared Tasks, and nothing in this change should be read as foreclosing that. Recorded in `ARCHITECTURE.md` so a later reader does not infer the stronger rule from the absence of the control.

**Docs debt, deliberately deferred to implementation step 8.** `docs/core-concepts.md` (two passages) and `docs/review-and-actions.md` describe manual items and standalone Lists as current capabilities. They are accurate for shipped v0.1 and stay untouched until the code actually changes — revising them now would leave the product documentation describing an app that does not exist yet.

## 5. TaskState vs ReviewEvent (decision 8) — rewritten

**TaskState** is what is currently true about a Task: `isCompleted`, `isFavorite`, `customActions`, and whatever current-state properties come later.

**ReviewEvent** is a *review submission*: a person was presented with the Task through a Task Review interaction and committed a response. It is not a change log for TaskState.

The implementation makes this an explicit fork, not a side effect:

```text
TaskStateWriter.setCompleted(...)        -> TaskState only        (List Detail, bulk, admin edits)
ReviewSubmission.submit(task, response)  -> TaskState + ReviewEvent, one transaction
```

`ReviewSubmission` is reachable only from a Task Review surface. No caller inherits event-writing by calling "set completed".

| Interaction | TaskState | ReviewEvent |
|---|---|---|
| Swipe-left completion on the review surface | `isCompleted = true` | **yes** — submission |
| Completion via the review surface's own control | `isCompleted = true` | **yes** — submission |
| List Detail checkbox (check or uncheck) | updated | **no** |
| Unchecking from anywhere, including the review surface | `isCompleted = false` | **no** |
| Favourite toggle | `isFavorite` | **no** — travels in the next submission's snapshot |
| Custom-action toggle | `customActions` | **no** — same |
| `NextTask` / `PreviousTask` | untouched | **no** |
| Opening, closing, revisiting a Task | untouched | **no** |
| Resync, source missing/restored, file deletion | `sourceMissing` (Asset) | **no** |
| Webhook delivery or resend | untouched | **no** |
| Migration backfill | seeded | **no** |

A submission's `response` captures the state as committed — for the rapid-media template, `{ completed: true, favorite: <bool>, customActions: [...] }` — under the exact TemplateVersion in force. `review_count` is `COUNT(review_events)` for the Task; it is never derived from `isCompleted` transitions. Re-review appends another event; unchecking never deletes one.

Unchecking deliberately writes no event: retracting a state is not committing a judgment, and the v0.2 rapid-media template has no "retract" response to record. If a future template needs one, it adds a response type rather than reinterpreting existing history.

State write and event append share one Room `@Transaction`, so they cannot visibly diverge. The existing completion-transition and webhook path is unchanged and is shared by both entry points, so a List still completes and still fires exactly as it does today whichever way the checkbox was reached.

## 6. Template model, and the navigator hierarchy

### Templates

Code-defined registry, two explicit kinds:

- `TemplateKind.ASSET_VIEWER` — `builtin.media.viewer` v1. Compatible with image / GIF / video Assets; owns zoom, pan, playback, scrub.
- `TemplateKind.TASK_REVIEW` — `builtin.media.rapid-review` v1. Owns the semantic review actions, the completion rule, the gesture bindings, and the composition of the selected Asset's viewer.

Version references are persisted on `review_events` and on `lists`. Immutability is enforced by a unit test asserting a stable content hash per `(id, version)`, so editing a definition in place fails the build and forces a version bump. No editor, no component table, no schema language, no marketplace.

Asset kind is still **not** persisted. `MediaPreview` decides image / GIF / video from name and mime at render; freezing a guess at migration time would let a stored label disagree with the renderer. A persisted kind arrives when a second viewer actually needs one.

### Hierarchy

```text
TaskNavigator                      explicit prev / position / next / back
└── TaskReviewSurface
    ├── AssetNavigator             real boundary; renders nothing at 1 / 1
    │   └── AssetViewer            SwipeCard + MediaPreview; owns zoom/pan/playback
    └── TaskReviewControls         complete, favourite, custom actions, info
```

- The AssetNavigator exists in the composition and state model for every Task shape, and draws a selector only when the Task has more than one Asset (decision 2). A zero-Asset Task renders through the existing `PreviewPlaceholder` — no fake Asset, no crash.
- The existing top bar becomes the TaskNavigator's presentation. It already carries back, title and `N / M`; it gains explicit previous/next controls. The filename stops being the navigator's conceptual owner.
- Session identity moves from `Long` to task id: `currentItemId: Long?` → `currentTaskId: String?`, and the round snapshot `LongArray` → `Array<String>` in `rememberSaveable`. Both are ephemeral UI state.
- `lists.reviewCurrentItemId` and `onReviewExited(listId, queueIds: List<Long>)` keep using ListEntry row ids (decision 6). Resume and webhook queue scoping are membership concerns.

## 7. `PreviousTask` / `NextTask` / `CompleteTask` (decision 3)

```text
NextTask / PreviousTask   ->  change current Task.  Nothing else.
CompleteTask              ->  submit review + persist completed state  ->  then advance
```

`NextTask` and `PreviousTask` do not mutate TaskState, do not complete a Task, do not append a ReviewEvent, do not trigger List completion, and do not trigger a delivery. Inspecting Task A, moving to Task B and leaving A unchecked is a valid outcome, and is already consistent with Listea's existing checked/unchecked semantics.

Reaching the final Task by navigating does **not** finish the round or complete the List — the forward control is disabled there. The completion screen stays reachable exactly as it is today: by completing the final Task. This preserves current behavior precisely, because today the only forward motion *is* completion.

One clarification worth recording: navigation **does** still update the List's resume cursor (`lists.reviewCurrentItemId`). That is session/review-context state, which the architecture explicitly places on the List side, not TaskState — so it is not a violation of "navigation mutates nothing". Navigation will not touch anything owned by the Task.

Gesture bindings belong to the **Task Review Template**. The rapid-media template binds swipe-left to `CompleteTask` and swipe-right to `PreviousTask`; those bindings are the template's, and they do not make swiping the way Listea navigates Tasks. Generic Task navigation's entry point is always an explicit control. Viewer gestures — zoom, pan, playback, scrub — stay with the viewer, the leftover-pan arbitration in `SwipeCard` is not modified, and a future PDF viewer remains free to claim scroll and selection. `SwipeCard` already has the right shape for this: it explicitly knows nothing about what forward and back mean.

Swipe and the equivalent explicit control resolve to the same semantic action and therefore the same submission path, including the legacy completion and webhook checks.

## 8. Webhook compatibility boundary

Unchanged on the wire. A `LegacyPayloadAdapter` translates the new read model into the `ListEntity` / `ListItemEntity` shapes `buildWebhookPayload` already consumes — formalizing what `deliverFolderReview`'s throwaway `ListEntity(id = 0)` rows already do informally.

`item.id` resolves to `list_items.publicId` for List review, or `legacy_item_ids.publicId` for folder review; where a folder-review Asset has no legacy id yet, one is assigned at registration exactly as `registerFiles` does today. The four event names, payload field names, inclusion/filter rules, ordering, null behaviour, confirmation, history, resend, failure handling and the post-success deletion offer all stay as found. No Exporter abstraction. No webhook field enters Task, Asset, TaskState, ReviewEvent or Template.

## 10. Remaining risks and objections

**New, found while revising — needs your decision.** "New list" becomes a dead-end control once manual entry is removed. See §4; I recommend removing it, but it is a product call and I have not assumed one.

**New — enabling schema export may surface latent problems.** Room schemas have never been exported here, which means Room's schema validation has *never actually checked* the SQL written by migrations 7→8, 10→11 and 11→12. Those hand-written `CREATE TABLE` statements declare defaults (`DEFAULT 0`, `DEFAULT ''`) that the entities do not declare via `@ColumnInfo(defaultValue = ...)`. Step 0 is the first time a machine compares them. If the generated `12.json` disagrees with what those migrations actually produce on a device, `runMigrationsAndValidate` will fail — and that failure would be a **pre-existing** defect surfaced, not one introduced by v0.2. Budget for it; it is better found now than after v13 ships on top of it.

**Carried forward from rev 1:**

- *Migration test breadth.* Schemas 1–11 cannot be recovered without building eleven historical commits. Covered by raw-SQL fixtures for the data-transforming steps, per decision 1 and the revised spec.
- *Pre-existing `IN (:paths)` exposure.* `observeFileStates`, `getFileStates`, `setFilesMissing` and `setListRowsMissing` bind one parameter per path; SQLite's pre-3.32 limit is 999 and `minSdk` is 24, so a folder of more than ~999 files can already fail on older devices. This work touches every one of those queries, so chunking them while we are there is cheap — but it is a pre-existing bug, not a v0.2 regression, and I will not expand scope further into it.
- *Task title ownership deferred.* Titles stay on `list_items.title` and the folder listing; the read model exposes `Task.title` resolved from the entry or listing. Moving them would touch the webhook `title` field and the reconcile diff for no v0.2 benefit. Declared as a known limitation.
- *`ListsViewModel` is 1737 lines with no repository layer.* Only the two seams in §6 and §5 are added. Everything else stays put, per the non-goal against a broad rewrite.
- *Housekeeping.* The architecture link in `v0.2.0.md` is fixed. `versionName` is still `0.1.0` / `versionCode 1`. The namespace is still `com.example.listea` — out of scope here, a release blocker eventually.

**No objections to the decisions themselves.** Decision 8 in particular corrects a real defect in rev 1: deriving events from state mutation would have recorded a List Detail tidy-up as a human review, and would not have survived contact with a candidate or vocabulary template.
