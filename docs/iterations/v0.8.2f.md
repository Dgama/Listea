# Listea v0.8.2f — The acceptance fixes: card edits, one template list, a Package that says what it is, and a Task that looks the same everywhere

> **Status:** **Implemented; device-verified 2026-10-25; carried in `0.8.3-preview` (2026-10-27);
> unreleased.** This is a fix round on v0.8.2, not a new feature round: schema 32, the
> `listea.package/1` protocol and export v5 are unchanged. It was built as `0.8.2f` with v0.8.2's
> `versionCode` (802), so it installs over the accepted build; its fixes now ship inside the
> `0.8.3-preview` build (versionCode 803) together with the vocabulary round, while the round's
> own name and record stay as written here. No tag or release is published.
> **Audience:** User and coding agent
> **Depends on:** v0.8.2 — Package protocol, Prompt payloads, schema 32, export v5
> **Spec:** [`v0.8.2-plan.md`](v0.8.2-plan.md) — the round these fixes amend; its §16 records the
> deviations this round adds.
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md) — *Framework evolution — v0.8.x*
> **Branch:** `main`. **No release tag.**

## Why this round

The v0.8.2 device walk accepted the Package protocol and found six things that were wrong at the
edge rather than in the model. Four of them are one theme: a Todo's identity and its stationery had
become frozen at import, and the app insisted on a template where it had no business insisting.
The other two are a gesture that stuck and a Package whose members were still visible as loose
files.

Verifying those fixes turned up a seventh, and a worse one: in v0.8.2 a Task with an add-on could
be judged without its questionnaire ever being shown. It is fixed in the same round and described
in §7. Device-checking that fix turned up an eighth: the read-only previews still counted a Task
without its add-on, so the same Task had one shape in Review and another everywhere else. §8 makes
the page model one thing for every surface.

| # | What the walk found | What this round does |
|---|---|---|
| 1 | A Todo's display name could not be changed after import | **Rename…** on the Todo card, beside the existing card actions |
| 2 | An add-on could only be chosen at Create Tasks / Refresh Import | **Add-on…** on the Todo card, and the same attach-or-clear choice |
| 3 | Left-swiping continuously through a seven-Task preview sometimes stuck | The page detectors stop capturing stale navigation state |
| 4 | `.listea`, `media` and `prompts` are exposed as ordinary folders; file templates do not apply to a Package | Package runs no longer attach file templates, and formats are matched where they apply. A zip-like `dating.listea` remains future work |
| 5 | With one-task-per-file, a dating folder could not be imported without a headless template, and the headless template could not be unticked | One Templates list: file templates multi-select, headless templates single-select, **every row cancellable, none required** |
| 6 | Exports and webhook bodies carried `Media Asset Control` for dating Tasks | Prompt Tasks send no templates and no file actions, and the Todo card says why |
| 7 | A Task with an add-on could be judged in Quick Review without its questionnaire ever opening | An accepted judgment lands on the add-on page; the forward move after it advances the queue |
| 8 | The Todo preview and List item viewer counted a Task without its add-on, so its structure differed from Review | Every Task surface derives its pages from the same `taskPageState`; the add-on is a read-only page there |

## 1. A Todo can be renamed

The Todo card's overflow menu now opens with **Rename…**. The dialog edits the Todo's display name
only: the folder it was imported from is not renamed, and neither is anything on disk. A blank name
is refused by the Save button and ignored by the write path, so a slip cannot leave a Todo nameless.

The name is what the Sources screen and the Todo's own page show. What it does not change is the
name a Task was **imported under** — that stays on the Task, because it is provenance rather than a
label.

## 2. A Todo's add-on can be changed from its card

The same menu carries **Add-on · …**, reading *none* or the attached questionnaire's name. The
dialog is the one Create Tasks draws: *None* plus every add-on this build can read.

Changing an add-on **re-stamps the Todo and every Task it holds in one transaction**. A Task and its
Todo cannot come to disagree about which questionnaire follows them, which is why the Source's own
add-on can be read directly from the card without the drift the older `assetControls` record
suffers. Answers that a new version no longer asks are **kept but hidden**, exactly as a refresh
keeps them: changing the questionnaire is not a reason to erase what was already answered.

## 3. The swipe no longer sticks

A continuous left swipe through a Task's files, across Task boundaries, could stop moving. The
cause was not the gesture threshold: the pointer detector had captured the navigation callbacks and
the *can I advance* flags from the composition that installed it. After the first Task boundary the
captured copy said *no further Task*, so later swipes were read against state that no longer
matched the screen. Swipes that happened to land while a recomposition re-keyed the detector worked;
the ones between recompositions did not, which is why it looked intermittent.

Both page detectors — the one under the viewer and the one under a reviewing Task — now read the
current callbacks and flags through `rememberUpdatedState` and install the detector once. The
threshold is a pure function, `swipeTurn`, and its five cases are pinned by
`ContentPageSwipeTest`, including the seven-Task walk the acceptance used.

**Two page-index defects found while fixing it.** On a Prompt Task the content card is page 0 and
its first file is page 1; Review was passing the raw page as an Asset index, so the first file
opened one Asset late. The List item viewer and the Todo preview now also return to the Prompt's
content page when you swipe right off its first file, instead of offering no way back. Both are
expressed once, as `assetIndexOf` / `pageOfAsset`, and pinned by `ReviewPagesTest`. §8 later folded
the count and index arithmetic around them into `taskPageState`, so no surface computes either.

## 4. A Package's file templates, and what "matching by format" means

The user's model: from any folder level, Create Tasks follows the chosen importer, and under the
file importer it matches each file by **format**. Under Package Prompts, the Prompts are the
material and their files are Resources; a file template is a pen for a file that is itself the
thing being judged.

**A Package run no longer attaches file templates.** The dialog hides the file-template rows for
Package Prompts, and the write path stores an empty attachment rather than whatever the dialog
happened to hold. The headless list is the whole choice. This removes the stray `Media Asset
Control` that legacy Package Todos recorded, at the source: a new Package Todo cannot acquire it.

**Under one-task-per-file, a file no viewer can open is skipped.** The importer used to admit every
file and leave unviewable ones as Tasks nothing could judge. Since this round it admits pictures,
videos and PDFs — the formats a Viewer in this build can render — and reports the rest as
**skipped**, with a count shown after the run. A `.listea` Package imported by the file importer
therefore yields Tasks for `media/*.png` and skips `manifest.json` and the Prompt bodies, which is
what the user asked for: only reviewable Tasks are created.

> **This overturns a documented behaviour.** Before v0.8.2f, an unmatched file became a Task with
> no chip row. That Task was imported but refused a judgment (§6.4), so it was a Task nobody could
> ever review. The rule now lives in the planner rather than in the refusal: what cannot be
> reviewed is not made. The refusal itself is unchanged for databases written by earlier builds.

### The consequence for Tasks imported by an earlier build

A refresh of an older Todo whose Task holds a file the new planner skips sees that file **absent
from the plan** and reports it as missing once. Under **Keep it** the Task is flagged and left
alone; under **Start it over** its decisions are cleared; under **Replace the Task** it is deleted
and not replaced, because the run has no material for it. Nothing rewrites these Tasks at upgrade:
the consequence appears only on the next run over that folder, which is the run that has a policy
to apply. This is recorded in
[What a changed Task means](../core-concepts.md#what-a-changed-task-means).

**The zip-like envelope is not implemented.** The direction is a Package that travels as one
`dating.listea` file rather than a directory with `.listea/`, `prompts/` and `media/` visibly beside
it. That changes how a Package is selected and opened, so it belongs to a protocol round, not to a
fix round; the current discovery rule — a directory containing `.listea/manifest.json` — is
unchanged. Recorded in
[Package protocol → Relationship to the current app](../package-protocol.md#relationship-to-the-current-app).

## 5. One Templates list, and nothing in it is required

The dialog used to draw file templates and a separate **Task review** radio group, and the Create
button refused a run with nothing attached. Both made a choice that is about *later* into a gate on
*this* run: a Todo whose Tasks record their own page decisions is a legitimate Todo, and so is a
Package Todo whose Prompt Viewer is the questionnaire.

**Templates are one list now.** File templates are multi-select under **Templates**; headless
templates are single-select under the same heading, with a subheading rather than a second section.
Any selected row can be unticked, including the headless one, and unticking the selected headless
row is how *no pen* is said. With none selected, a Task records its files' own decisions — the
built-in file-decisions review, written the way a null attachment has always been written.

**The old gate is gone.** **Create** is enabled by the address field alone (a webhook needs an
address); the template step no longer disables it. The default headless choice still follows the
importer — single choice for Package Prompts, file decisions otherwise — but it is a default, not a
requirement, and a deliberate clear is not re-seeded.

The `Media Asset Control` confusion from the walk had the same root: a headless template is
stationery at the same level as the file template, not a Task-level appendix. The Package warning
survives as advice, not a block: a Package whose Prompts are answered in a Viewer and whose chosen
pen catches nothing will not record the answer, and the dialog says so.

## 6. Exports and webhooks say what a Prompt Task actually is

**A Task with a structured Prompt sends `templates: []` and no file actions**, even when its stored
attachment still names `Media Asset Control`. The suppression is at the one assembly point both
renderers walk, so Webhook and Txt agree. A Prompt is answered in a Viewer; sending a file
template's identity told a receiver its Prompt was marked up and offered actions its files never
took.

**History is not rewritten.** A record already sent replays its own bytes, so an old dating export
still shows what it sent at the time — that is the meaning of stored history. What changes is
everything from this build forward, and the Todo card: a Package Todo reads *Templates: not used by
Package Prompts* rather than naming a file template it never used.

`ExportTaskAssemblyTest` pins the Prompt suppression, including the legacy stale attachment; the
existing v2–v5 goldens are unchanged, because a media Task's body is byte for byte what it was.

## 7. A judgment lands on the add-on page

**What the walk found.** A Todo with an add-on, reviewed inside Quick Review, never opened its
questionnaire. Tapping the Prompt's Like or Dislike moved straight to the next Task, and
`task_review_answers` stayed empty: the Todo could be reviewed end to end and the questionnaire it
was stamped with was never shown once.

**The cause is in the page order, not in loading.** v0.8.2 gave the questionnaire a real page —
`ReviewPage.AddOn`, last after Content and Assets — and every surface that *navigates* honours it.
What it did not change is what a committing answer does. A template that declares
`advanceAfterCommit` called the queue move directly, which was correct while the add-on was not a
page: the judgment ended the Task. Once the add-on became a page, that same move skipped it. The
questionnaire was loaded, drawn, and counted in the counter (`1(1/2)/6` on the device); nothing
ever landed on it.

**The fix.** An accepted commit now asks where it should go, through `commitArrival`:

- the template does not advance → stay on the page, as before;
- the Task has no add-on page → next Task, as before;
- the Task has an add-on page and the reviewer is not on it → **land on the add-on page**, whichever
  page the judgment was made from (a Prompt's Like/Dislike, a sampled point's Submit, the last file
  of a media Task);
- the reviewer is already on the add-on page → next Task.

A commit made after the reviewer has been sent to the add-on page is not repeated: forward from
there is a queue move, so the page cannot stick for a template that would refuse a second event.
That is what makes the documented contract hold again — *the add-on is the Task's last page, and
swiping left off it completes the Task*. A template that keeps the reviewer on its own page still
does: the questionnaire stays reachable with the inner arrow.

**Recorded as.** The rule is stated where the add-on contract is stated, in
[Templates → Add-ons](../templates.md#add-ons) and
[Getting started → Reviewing](../getting-started.md#reviewing). `ReviewPagesTest` pins the four
branches of `commitArrival`.

## 8. One Task, one shape, wherever it is browsed

**What the walk found.** The same Task read `1(1/2)/7` in Review, but `1 / 1` in the Todo preview
and `1(1/2)/7` in the List item viewer with no add-on page that could be reached at all. In the Todo
preview the counter excluded the questionnaire outright; in the List viewer it counted only the
Prompt and the files. Neither surface had a loading failure — both had already been handed the
stamp, and the Todo preview dropped it on the way in — they simply modelled a Task as *Content plus
Assets* and stopped.

**The model is now shared.** `taskPageState(item, addOn, requestedPage)` builds the same
`reviewPages` list Review walks and answers the count, the current page, the Asset index and whether
there is an add-on page. Review, Quick Review, the Todo preview and the List item viewer all read
it; no surface computes a count and an Asset offset of its own again. The add-on is resolved by
`AddOnResolver.readableVersion`, the same fail-closed reading Review uses. A version this build
cannot read, or a questionnaire with no questions, draws no page anywhere.

**Read-only means read-only.** The previews draw `AddOnAnswersPage`: every question the attached
version still asks, with the recorded answer or *Not answered*, and no chip, field or callback.
Those surfaces have never had a control that changes state, and a questionnaire you could answer
from a gallery would be one. The answers arrive on the same flow Review reads, so a change made in a
review appears in a preview that is open; nothing in the preview can write back.

**The swipe contract, stated once.** A Task's pages are a sequence, and its surfaces walk it the same
way:

- **inside a Task**, a horizontal swipe turns to the next or previous page — from the Prompt to the
  first file, between files, and from the last file onto the add-on;
- **at the first page**, a backward swipe crosses to the previous Task in the level; **at the last
  page**, a forward swipe crosses to the next Task. A Task is never trapped, and its pages are never
  skipped;
- **Review's Like/Dislike Prompt page does not swipe.** There the tap is the judgment; a swipe that
  could skip the question would be a way to pass a Task unknowingly. The page is reached by tapping
  its position, and the add-on by the inner arrow or the queue menu;
- **a single file opened from a folder is not a Task** and keeps the flat, file-to-file pager it has
  always had. There is no Task structure to show because the thing being previewed is not one.

**A guide row was wrong, too.** Review's queue entries were built without the Content page, so a
Prompt Task's guide named its files one page to the left of the position beside them. The entry now
passes `content`, the same as the List viewer already did.

**Recorded as.** The viewing-surface contract is in
[Review and actions → The viewing surfaces](../review-and-actions.md#the-viewing-surfaces),
the add-on page's read-only form in [Templates → Add-ons](../templates.md#add-ons), and the page
model in [Architecture](../ARCHITECTURE.md). `ReviewPagesTest` pins `taskPageState`'s counts,
indices, clamping and the question-less attachment.

## 9. The second acceptance round: provenance, headless swipes, and an Info sheet that knows its level

**What the walk found.** On `ListeaAccept-new-mix`, several Tasks carried `dating-demo/bob` under
their names, and `dating-demo` exists nowhere the user can see. A dating Prompt — *A mystery
Prompt* — could not be swiped left or right in Review, and neither could a dating Task's add-on
page. At `6(1/2)/7`, tapping a picture's Info opened the Task's add-on answers. And the dating
Prompt's page had no task-level checked state and no asset-level control band at all, so the
headless template had drifted out of the frame every other template uses.

**Where `dating-demo` came from.** A Package Task is addressed internally by a synthetic catalog
key, `<packageKey>/<promptKey>` — here `dating-demo/bob`. The importer stored that key in the same
columns a file Task uses for its path, and every surface that showed provenance showed the key. The
real directory is `dating`; the Package's manifest calls itself *Dating demo*, which is the name the
Catalog already showed. One rule, `taskProvenance`, now decides the line under a Task everywhere: a
Package Task shows its manifest title and never the key (and nothing when the title would just
repeat the Task's name); a file Task shows its path. List rows, queue entries, both previews and the
Info sheet read the rule, so they cannot disagree. `package_checkpoints.title` is joined through
`TaskAssetControls` to supply the title. `TaskProvenanceTest` pins the rule, including the
blank-title and equal-title cases.

**A page with no judgment now moves.** Review's Content page had no gesture host, because an
interactive Like/Dislike card deliberately refuses the swipe — its option tap is the answer. But a
Prompt that cannot be judged has no answer to take: the body is unreadable, the build cannot read
it, a required file is missing, the Task is blocked, or no Task Review in force catches a choice.
Those pages now sit in `ContentPageSwipe` exactly as the previews do: a horizontal swipe turns the
page and crosses Tasks at the edges, and a tap shows and hides the file band. The add-on page's
forward edge follows the same fact: when the Task cannot be judged, leaving the add-on is a queue
move rather than a second commit. A judgeable Prompt page still refuses the swipe.
`ContentPageSwipe` gained an optional tap detector built on `awaitFirstDown(requireUnconsumed =
true)`, so a clickable option pill consumes its own press and a Like stays a Like; the same tap now
reveals and hides the band on the previews' Content pages, which a scrolling card had previously
swallowed.

**Info is a page's, not a Task's.** `ReviewItemInfoSheet` takes a `ReviewInfoLevel` — Content,
Asset or AddOn — and builds a disjoint inventory for each. A Content sheet lists Package (or Path),
List, Status and recorded events. An Asset sheet lists those plus Actions, Source, PDF marks,
recorded events and media facts — and no add-on rows. An AddOn sheet lists only the questionnaire,
its version, its answer count and its answers. Save and Share appear only on an Asset sheet, because
only an asset is a file. The add-on is a bounded Task-level property: it resembles an asset in
interaction, but the sheet no longer treats it as one.

**Every template has a task band.** The bottom of the frame now always states the Task. When the
review commits from the completion checkbox it is that control. When a template names its own
control — the dating Prompt's Like/Dislike — the template's control stays in the dismissible asset
band and the bottom band draws `TaskStatusBar`: the same checkbox, read-only. A tap no longer takes
that state away, which is what the headless Prompt page was missing. The List item viewer now draws
the same read-only band and moved its Info into the dismissible band; the Todo preview deliberately
keeps neither, as before. This is alignment rather than a dating-specific patch: headless templates
change rendering and where a judgment is taken from, not the Task / Asset / add-on hierarchy.

> **Amended 2026-10-27: the state's words were removed.** `TaskStatusBar` first drew *Checked* /
> *Not checked* beside the checkbox, reasoning that a checkbox nobody could press needed its meaning
> written out. The acceptance walk found the result: in the same Review a vocabulary Task showed
> words where a picture Task showed only the box, for the same Task-level fact. The reason was
> local to the new control — it compared the read-only checkbox with the interactive one, not with
> the textless `TaskCompletionBar` already beside it — so the fix had introduced a second visual
> language rather than inheriting the first. The band is now the bare checkbox everywhere: empty is
> not checked, filled is checked. The state remains in the checkbox's content description for a
> screen reader. No behaviour changed; only the label was removed.
