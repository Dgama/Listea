# Listea v0.2.5 — Post-Implementation Review and Acceptance Verdict

> **Status:** Acceptance review of the implemented release. Not accepted as it stands; see §2.
> **Audience:** Implementation agent and maintainers
> **Specs it is judged against:** [`v0.2.5-plan.md`](v0.2.5-plan.md) (revision 2), [`v0.2.5.md`](v0.2.5.md) (revision 2), [`../ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Builds on:** [`v0.2.0-reviewed.md`](v0.2.0-reviewed.md)
> **Reviewed against:** working tree at `f65e4d8` (clean), commits `d5e562c … f65e4d8`
> **Independently verified:** `./gradlew testDebugUnitTest --rerun-tasks` → **385 tests, 0 failures, 0 errors** (re-run for this review, not taken from the implementer's claim)

## Framing

The release principle was two sentences:

> **Only an import run may create a Task. Everything else selects Tasks that already exist.**
> **Being imported is not being reviewable.**

**Both sentences are true of this code.** That is the substantive result, and it is not a small one: the last place `file == Task` lived — lazy minting on a browse — is gone, `INSERT INTO tasks` has exactly one call site inside `runImportInternal`, and `submitReview` refuses at the DAO for a Task whose content cannot be presented. The domain core the plan asked for exists, is coherent, and is tested.

What did **not** land is the half of the release that lets a person reach it. The folder-as-Task importer — the reason v0.2.5 exists as a release rather than as a refactor, because it is what produces the multi-Asset Tasks [`v0.2.0-reviewed.md` §9](v0.2.0-reviewed.md) asked to stress — has no production caller. Neither does the catalog, the Task selection, or `createListFromTasks`. The plan's own handoff rule 7 is the right reading of this: *a new abstraction the active workflow bypasses is not completion.*

And one defect was introduced along the way that is worse than an omission: **the first Create List over any folder now deletes the Lists it overlaps without asking.**

So the verdict is: **the engine is built and correct; the release is not shippable.**

## 1. Reviewed verdict

### 1.1 Genuinely complete

- **Schema v14 and `MIGRATION_13_14`.** Four new tables plus three additive nullable `assets` columns, no rebuild, no transformation, nothing dropped. `MIGRATION_12_13` is untouched — the only deletions in `ListeaDatabase.kt` are the version bump and the entity/migration list additions. The claim set is inserted exactly as §3 specifies, `sources` / `task_imports` / `legacy_task_ids` are left empty, and the Asset backfill reads the `list_items` row for the same Task. Eight fixture tests in `MigrationV13ToV14Test`, plus the chain and smoke tests extended to end at v14 — which is one of the two edits §13.2 permitted.
- **`scanFolderTree` / `FolderSnapshot`.** `FolderScan.kt` is edited once, additively, exactly as §10 allows: the walk records the directories it was already visiting, and `scanFolderFiles` is expressed on top of it so the two cannot diverge. AR-8 is closed — an empty child folder is now a fact the importer can see rather than one it has to guess.
- **The pure importer layer.** `Importer.kt` has no `Context`, no SAF and no database. Both rules are there, and the §4.3 precedence is implemented as written: `planFileAsTask` admits every scanned file with no content filter (v0.1 parity), `planFolderAsTask` applies picture ∪ video ∪ PDF and reports the rest as notices.
- **Source registration and the non-overlap rule.** `registerSourceInternal` reuses an existing `(rootUri, relativePath)`, rejects an overlapping real Source by the same `scopesOverlap` helper folder-backed Lists have used since V3.1, and names the covering Source in the answer. `findCoveringSource` returns the single covering Source non-overlap guarantees.
- **`runImport` and its coverage boundary.** `coverage` is a parameter, never inferred; `sourceMissing` is set only for Assets under it; **nothing is ever deleted by a run**; a scoped refresh is refused outright for a folder-as-Task Source; adoption is one-way and deletes the claim row; a conflict is reported and the rest of the run proceeds. Identity stability (§5.3, the plan's "single most important test") is pinned.
- **Catalog projection, containment algebra, eligibility.** The SQL is the §6.3 query; scope filtering is Kotlin path arithmetic over `isAncestorOrSame`, not `LIKE`; `assetViewerAvailable` is the one classifier and `Catalog.kt` is the one place it lives. The §6.4 consequences are all implemented deliberately, including "a Task with zero Assets is eligible" — which falls out of an empty `all {}` rather than being special-cased.
- **The write-boundary refusal.** `submitReview` returns `emptyList()` before touching state or history when `contentPresentable` is false. `setTaskCompleted` is not gated, so a List Detail checkbox still works — which is what keeps an upgraded v0.1 List containing a `.txt` fully usable.
- **`createListFromTasks` and the `createFolderList` recomposition.** `createFolderList` is now register-or-reuse → import → select → create, gated on `complete`, and the resulting `list_items` row is pinned byte-identical to the v13 one by an explicit test. `ListsDaoTest`, `WebhookBodyTest`, `WebhookPayloadTest`, `ListArrangeTest` and the legacy-id suite stayed green without expectation edits.
- **Multi-Asset presentation.** `AssetNavigator` owns the selection; it is `rememberSaveable` keyed by `item.taskId`, so it resets on Task change and survives process death, and it is not in the round snapshot — §9's three deferred questions answered as the plan said. The selector is a dot row, deliberately not a `‹ N / M ›`, and is drawn only above one Asset. Asset switching writes nothing.

> **Superseded after review (2026-09-16, plan decisions 19–21).** The ruling on *what the selection
> is* stands unchanged — reset per Task, saved, outside the round snapshot, writes nothing — and it
> is the same rule the selection follows today. What changed is who draws it and where: the dot row
> is gone, the page position is the navigator bar's own `x(m/n)/y` between an inner pair of arrows,
> and the navigator and completion bar now take real layout space rather than floating over the
> media. See §9.1 and §9.4 of the plan.
- **Lazy minting removed.** `ensureTasksForFiles` and `taskForContent` are gone from the DAO; `insertTask(TaskEntity(` appears exactly once. `LegacyItemIdTest` and `ListsDaoTest` were re-pointed at a **test-only** `taskIdOf` fixture that runs a real import — the honest way to keep those tests exercising production semantics rather than a surviving back door.
- **Compatibility.** `Webhook.kt`, `FileManagement.kt`, `SwipeCard.kt`, `MediaPreview.kt`, `MediaZoom.kt`, `VideoControls.kt`, `FileArrange.kt`, `Settings.kt` and `FolderListStatus.kt` are **still byte-identical to `v0.1.0`** — verified per file with `git diff v0.1.0 HEAD`. `deliverFolderReview` re-reads by `taskId`; `legacyTaskId` mints lazily at the adapter only.

### 1.2 Confirmed by independent verification

- Full suite re-run from clean (`--rerun-tasks`, 31/31 tasks executed): **385 tests, 0 failures, 0 errors**, up from the 342 baseline.
- **`ReviewSubmissionTest` (13) and both webhook suites are untouched by the diff.** The plan predicted that no existing submission test would need its expectation changed; that prediction held, and it is the strongest single piece of evidence that §6.4 was derived from the repository rather than imposed on it.
- Every one of the thirty §13.1 tests has an identifiable counterpart in the new suites — `ImportPlanTest` 4, `ImportRunTest` 11, `CatalogTest` 6, `EligibilityTest` 5, `CreateListFromTasksTest` 4, `WebhookCompatTest` 3, `ConsentTest` 1, `ImportInvariantTest` 1, plus two new `QuickReviewQueueTest` cases. One of them does not test what it is named for — see **V6**.

### 1.3 Defects

| | Finding | Severity |
|---|---|---|
| **V1** | Create List over an un-imported folder **deletes overlapping Lists without the replace confirmation** | **Blocker — data loss** |
| **V2** | List re-sync registers a Source with no consent dialog | High |
| **V3** | A partial composed import rolls the whole run back instead of committing and reporting | Medium |
| **V4** | `assignLegacyItemIds` is not chunked on the import path | Medium |
| **V5** | Containment is not enforced at the write boundary | Low |
| **V6** | `ConsentTest` does not exercise the consent gate | Medium |
| **V7** | The Quick Review consent has a read-after-write race | Medium |

**V1 — the blocker.** `ListsViewModel.requestListForFolder` (`ListsViewModel.kt:895`–`920`) builds `pendingFolderList` with `replacedIds = conflicts.map { it.id }`, then — **before** the `conflicts.isEmpty()` branch — returns early with `FolderListRequest.ImportConsent` whenever no Source covers the folder. `confirmImportForFolder()` calls `commitPendingFolderList()` directly, which passes those `replacedIds` to `createFolderList`, whose first line is `replacedListIds.forEach { deleteList(it) }`. The `Confirm` dialog that has named the Lists about to be replaced since V3.1 is **skipped entirely**, and the `ImportConsent` dialog's copy says nothing about replacement.

Reachability is what makes this a blocker: on any upgraded database `sources` is empty, so **the first Create List after installing v0.2.5 takes this path** — and an upgraded database is precisely the one that already has folder-backed Lists to overlap. At `c7fa1fe` this could not happen: `if (conflicts.isEmpty()) commit else Confirm` had no third branch. It destroys List membership, webhook configuration and delivery history, and it is silent. Tasks, TaskState and ReviewEvents survive, which is the only reason this is a blocker rather than a catastrophe.

**V2.** §8.3 is explicit: *"the List's folder has no covering Source. Re-sync would have to register one, which is a write, so it asks for the same consent dialog as §11.2."* `applyReconcile` (`ListsDao.kt:704`) calls `registerOrReuseSource` unconditionally inside its own transaction. There is no consent path on re-sync at all. The folder-as-Task half of §8.3 *is* implemented — it throws, naming the reason — but throwing from inside the transaction surfaces as a generic failure rather than as the report §8.3 asked for.

**V3.** §5.5 and §8.2 say a composed shortcut on `partial` *"stops at the report, which offers to open the catalog"*, and §8.2 says *"a failed List creation leaves the imported Tasks in place."* `createFolderList` instead throws on a non-`complete` outcome, and because it is one `@Transaction`, the Source registration and every imported Task roll back with it. The user sees `"Could not create the list. Nothing was changed."` — accurate, but there is no report, no catalog to open, and nothing was imported. A safer failure than the plan's, but not the plan's, and it removes the recovery route the plan designed.

**V4.** §14.10 was specific: *"The import path adds locator lookups over potentially large folders — chunk them there rather than inheriting the limit."* `runImportInternal` calls `assignLegacyItemIds(source.rootUri, plannedPaths.toList())` with every planned path in one `IN (:relativePaths)`. `minSdk = 24`, so on API 24–29 the bind-variable limit is 999: importing a folder of more than ~999 files throws inside the run, and for `createFolderList` takes the List with it. No chunking exists anywhere in the module.

**V5.** Decision 8 and §6.4 define eligibility as *contained + resolvable + viewable* and say it is *"enforced at the write boundary, not only in the UI."* `submitReview` enforces only the second and third. The implementation's own KDoc argues the containment half belongs upstream, and that argument is reasonable — `submitReview` genuinely has no scope to test against — but decision 8 as written is not met, and no test asserts it either way.

**V6.** `ConsentTest` (one test) asserts that `findCoveringSource` and `getCatalogTasks` write nothing, and that the tables are empty. That is a tautology about two read queries. §13.1 test 22 is about **Quick Review and Create List** on un-imported material — which lives in `ListsViewModel`, is untested, and is where **V1** shipped in the same commit that added this test.

**V7.** `QuickReviewScreen` calls `viewModel.importFolderForReview(...)` — which returns immediately, the work running on `viewModelScope` — and then increments `importVersion` synchronously in the same click handler. `remember(target, importVersion)` rebuilds the cold flow at once, and `observeFolderReview` reaches `findCoveringSource` after only a folder listing, while the import is still doing a full recursive SAF tree walk. The likely observed behaviour is the consent screen re-appearing after the user presses Import. Harmless to data — a second press hits `Overlaps → covering` and reconciles — but it is among the first things a device test would hit, and no device test has been run.

### 1.4 Plan scope not implemented

| | Missing | Consequence |
|---|---|---|
| **U1** | **No production path to a folder-as-Task Source.** `ImporterKind.FOLDER_AS_TASK` is constructed nowhere outside `Importer.kt` and one guard in `runImportInternal` | `planFolderAsTask` is unreachable from the app |
| **U2** | **No catalog surface and no Task selection.** `createListFromTasks` has **zero** production callers; `getCatalogTasks` has one, the Quick Review queue | §8.1 ships as dead code |
| **U3** | **No Import Folder action; the Sources screen has no actions and no Task counts.** §11.1 asked for Refresh Import, browse catalog, Quick Review and Create List per Source | The Sources tab is a read-only list of two strings per row |
| **U4** | **Quick Review cannot reach a folder-as-Task scope even if one existed.** `observeFolderReview` (`ListsViewModel.kt:533`–`536`) emits `FolderReview.Ready(emptyList())` and returns as soon as the browsed folder has no *direct files*, before it consults the catalog | `folderReviewQueue`'s groupPath-ordered branch — the entire no-listing case — is dead in production |
| **U5** | **§7's scope messages are absent.** "only partial Tasks" and "imported but nothing eligible" both resolve to a silent empty round rather than to the copy the plan wrote | A user whose Task is partial is told nothing |

Commit `6f4c27b` states U3 openly — *"Deliberately not done: the Import Folder button … per-Source task counts and the catalog drill-down are a later surface detail"* — which is the right way to report a shortfall. But **U1 and U4 together mean acceptance scenario B cannot be run at all**, and scenario B is the 2/3/5-image multi-Asset stress test that [`v0.2.0-reviewed.md` §9](v0.2.0-reviewed.md) defined this entire release around. The multi-Asset presentation praised in §1.1 is therefore correct-looking code that has never rendered a second Asset outside a unit test.

### 1.5 Examined and not a finding

- **`MainActivity.kt` is no longer byte-identical to `v0.1.0`** (+32 lines: the `Sources` route and the `ImportConsent` dialog). It was on v0.2.0's identical list but is **not** on §10's, which drops it deliberately. Permitted.
- **`QuickReviewQueueTest` was rewritten** (16 → 17 tests). §13.2 allowed only two kinds of edit and this is a third — but §7 mandates that `folderReviewQueue` take catalog rows instead of registration rows, so its test could not survive unchanged. Order preservation is re-pinned by a dedicated test and no assertion was weakened.
- **`ImportInvariantTest` asserts on source text with a regex.** Ordinarily a smell; here it is the honest instrument, because "a mint nothing calls is still a mint" is not a runtime property. Its own KDoc says as much.
- **`ImportOutcome.FAILED` is returned when a scoped refresh is refused** for a folder-as-Task Source, though §5.5 defines `failed` as "could not be read, or did not commit". The comment names the stretch; nothing was written, so the value is truthful about the outcome if not about the cause.

### 1.6 Where the plan was ambiguous, and how the implementation resolved it

**§9.3 says a blocked Task is "shown, navigable and not submittable"; §13.1 test 16 says Quick Review "excludes ineligible Tasks".** These cannot both hold for one surface. The implementation resolves it by surface, and resolves it correctly: **Quick Review excludes** — a scope is a fresh selection, and there is no reason to queue something that cannot be judged — while **List Review shows and blocks**, because an existing List's membership is a v0.1 promise AR-3 explicitly preserves. `ReviewBlock` is carried on `ReviewItem` for the second case and filtered out in `folderReviewQueue` for the first. This reading should be written into the spec rather than left to be rediscovered.

Two smaller copy deviations in the same area: `ReviewBlock.NO_VIEWER` reads *"No viewer in this build"* rather than §9.3's *"PDF — viewer available in v0.3"*, and the Asset selector's dots are 10 dp — below the 48 dp minimum touch target. Both are cosmetic; both are the kind of thing §13.3 exists to catch.

## 2. Required before acceptance

### N1 — Restore the replace confirmation (blocker)

`requestListForFolder` must not skip the `Confirm` step. Either chain the two dialogs — consent, then replace, then commit — or fold the replaced-List names into the `ImportConsent` copy so a single confirmation names **both** writes. A List must never be deleted by a dialog that did not name it.

*Regression test, in the ViewModel and not the DAO:* an un-imported folder that overlaps an existing List must not delete that List until a confirmation naming it has been accepted, and declining must leave `lists` and `list_items` unchanged.

### N2 — Give `ConsentTest` the behaviour it is named for

Test 22 must drive `requestListForFolder` and `observeFolderReview`, assert that `sources`, `tasks`, `assets`, `task_imports` and `lists` are untouched before acceptance, and assert that declining changes nothing. Written that way it would have caught **V1**.

### N3 — Make the folder-as-Task importer reachable, or say plainly that it is deferred

Two honest options, and they are not equivalent:

1. **Ship it.** Add the Import Folder action with an importer choice, and lift the `files.isEmpty()` short-circuit in `observeFolderReview` above the catalog read (**U4**) so a folder of folders resolves its Tasks. Then run scenario B.
2. **Defer it.** State in the release notes that v0.2.5 ships the file-as-Task path only, that folder-as-Task is implemented and tested but not exposed, and that the multi-Asset stress test moves to v0.3.

What is not acceptable is the current state, in which the release claims a capability whose only evidence is a unit test.

### N4 — Re-sync consent (**V2**) and chunked `assignLegacyItemIds` (**V4**)

Both are small, and both are things the plan asked for in writing.

### N5 — Fix the consent race (**V7**)

`importFolderForReview` should signal completion — return a result, or expose a flow the screen collects — rather than having the screen guess by incrementing a counter.

### N6 — Run §13.3

**None of it has been run.** Commit `f65e4d8` says so plainly, which is to its credit. Scenarios A–E, **M4** (a real installed v12 → v14 upgrade, device backup first — there is still no in-app rollback) and **M5** (real SAF deletion of checked files) remain outstanding, and M4 is the only evidence that will ever exist for the migration against a database Room actually wrote.

---

## 3. Deferred, and correctly so

§14's twelve limitations are all still true and all still deliberate: no Source deletion, no import history, one SAF grant, `list_items` staying file-shaped, one grouping root per Task, the orphaned-`review_events` case, and the `com.example.listea` / `versionName 0.1.0` metadata. None of them is made harder by N1–N6.

The v0.1 behaviour change in §14.3 — a `.txt` or a source-missing item can no longer be *review-submitted* — is implemented as designed and pinned by `EligibilityTest`. It is the intended cost of AR-3 and must not be "fixed" later by loosening the DAO.

## Handoff

1. **N1 first, and alone.** It is a data-loss regression on a path every upgrading user takes at their first Create List. Do not bundle it with surface work.
2. **Do not reopen the domain model.** §§2–10 of the plan are implemented and correct. Everything in §1.3 is either a defect against that model or a surface that was never built — none of it is a reason to redesign.
3. **`ConsentTest` and the ViewModel are the gap the suite has.** 385 green tests did not catch V1, V2 or V7, because all three live above the DAO and nothing above the DAO is tested. That is the shape of the next test debt, not an argument for more DAO tests.
4. **Evidence beats compilation, and a unit test is not a device.** Per [§10 of the v0.2 spec](v0.2.0.md) and the plan's own handoff rule 7: a new abstraction the active workflow bypasses is not completion. `createListFromTasks`, `planFolderAsTask` and the Asset selector are all currently in that category.
