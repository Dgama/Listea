> tree, unit-tested and walked on the maintainer's device across four passes — over the user's own

> re-walked green ([Acceptance, as run](#acceptance-as-run)).
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md) — §Exporter / Action, which this release
> is the first to make true; §Templates and §Identity for the attachment rule it follows, and
> §List and ListEntry for the homogeneity sentence it does not touch
> **Depends on:** v0.5.4 (a template is a row, and an attachment is a *reference* to one — the

> cannot read)
> **Supersedes:** the sentence in [`docs/webhooks.md`](../webhooks.md) that treats the webhook as
> *the* way decisions leave the app. It is one of the ways, and after this release it is named as
> one — the page is now the *webhook kind's* page under a new [Exports](../exports.md) parent.

## The change in one paragraph

Sending the decisions somewhere is one act, and today the app spells the *mechanism* of that act
into four tables, two screens and a settings page: `lists.webhookUrl`, `lists.webhookEnabled`,
`lists.lastDelivery*`, `webhook_history`, five DataStore keys, a Settings section, a card on every
List, and a notice after every round. That was right while there was nothing else it could be. It is
not: the same decisions are equally well a text file, a CSV row, a folder of stubs, or a Task
recreated from itself. v0.5.6 stops treating the mechanism as the model. An **export** is the act,
an **export kind** is how it happens, and what a Todo and a List each name is **one kind** — never a
set. `webhook` becomes the first kind, `txt` the second, and the seam between *what left* and *how it
left* becomes a thing with a name for the first time.

## Why

### 今天名字错位的地方

The word "webhook" appears in surfaces that are not about HTTP at all:

- `lists.webhookEnabled` is the flag behind the switch a user reads as *"send when this list is
  completed"* — a question about *when*, answered by a name about *how*.
- `webhookCompletedItemsOnly` is a filter on **what goes into the payload**, applied before anything
  is sent anywhere (`Webhook.kt:267-268`). It has nothing to do with HTTP.
- `webhook_history` stores the exact bytes that left and the verdict that came back. Under a second
  kind it is a record of *exports*, one of which happened to be a POST.

### 两个已经存在的后果，一个已经犯过

**A List's URL is a copy, not a reference.** `lists.webhookUrl` is seeded once from
`defaultWebhookUrl` at creation (`ListsViewModel.kt:1987-1988`, `:2047-2048`) and never reads
Settings again. Changing the default URL afterwards reaches **no existing List**. This is exactly
the defect v0.5.4 removed from `assetControls` — a stored copy of an answer that lives elsewhere,
free to disagree with it — and it is still here, one column over.

**一个 List 可以装来自多个 Todo 的 Task，而每个 Todo 的配置都不同。** Nothing in today's model can
express that. The user's own words:

> todo创建（import的时候）和list里的export方式都是单选。都是和todo或者list绑定的属性。
> 我说的同时要写是考虑到list跨todo，不同todo有不同配置。

### 抽象要回答的四个问题

1. **选什么** — the kind.
2. **谁有权选** — a Todo has one; a List has one; the List's wins.
3. **一份 payload 什么时候变成多份** — when a List is in play and has not chosen, a round's items
   are split by the Todo each came from.
4. **结果记在哪** — one record per attempt, whichever kind made it.

## The model

### `ExportKind` — 一个闭集，一个 key

```kotlin
enum class ExportKind(val key: String) {
    WEBHOOK("webhook"),
    TXT("txt");
}
```

Closed, and deliberately: a kind is **code** — a renderer plus a destination, and neither is data.
The list of kinds is the list of exporters this build ships, so it cannot be a table, and a stored
key this build does not recognise decodes to *export nothing* rather than to a guess. That is
[v0.5.3](v0.5.3.md)'s failing-closed rule one level up: a rule this build cannot evaluate must not
be quietly dropped, because dropping it widens what the app does on the user's behalf.

### 单选，两侧都是

A Todo names **one** kind. A List names **one** choice. There is no set anywhere in the model. The
plural case the user described is not a collection on one row — it is a **sum over the Todos a round
touched**, and it is computed at delivery time rather than stored. That distinction is the whole
reason the release is small: nothing has to be kept in sync, because nothing is held.

```kotlin
/** What a Todo or a List does about exporting. One value, never a set. */
sealed interface ExportChoice {
    /** Exports nothing. The default for a new Todo, and the answer for a key this build cannot read. */
    data object Nothing : ExportChoice

    /** Follows the source Todos. **Lists only** — a Todo has nothing to inherit from. */
    data object Inherit : ExportChoice

    data class By(val kind: ExportKind) : ExportChoice
}
```

Encoded as the literal key (`none`, `inherit`, `webhook`, `txt`) rather than as an empty string, so
that *absent*, *inherit* and *nothing* are three different words and no reader has to know which
column it is looking at to tell them apart. `decodeExportChoice` is tolerant in the established way:
an unrecognised key is `Nothing`, and `inherit` **on a Todo** is also `Nothing`, because a Todo has
nothing above it to follow.

### 解析顺序 —— 一步，在触发点上

```
触发（Quick Review 结束 / 离开 review / List 完成 / 一轮结束）
  → 取这一轮的 items，先应用"只导出已勾选"
  → List 在场，且 lists.exportKind 不是 inherit？
        是 → 一份 payload，用 List 的 choice
        否 → 按每个 item 的来源 Todo 分组
             → 每组一份 payload，用该 Todo 的 kind
             → 该 Todo 是 Nothing 的组，不导出
  → 每组交给它那个 kind 的 exporter
  → 每次尝试记一条记录
```

**`list.exportKind` 为空意味着继承，不是"不导出"** — 用户的原话：

> 没有，则统计此次payload涉及的task的来源 → 按照来源todo整理成多份payload → 按照todo各自配置的payload输出

So a List that has not chosen **is not a List that exports nothing**; it is a List whose exports are
decided one group at a time. That is the release's headline behaviour, and it is why the List's
dropdown has four entries rather than three: *Same as the Todos* (the default), *Export nothing*,
*Webhook*, *Txt*. A List has a state a Todo does not — the state of having said nothing — and the
control has to be able to say it.

### 一份 payload 是按来源 Todo 切开的

A group is `task_imports.sourceId` — the Todo a Task came from — which is a column that already
exists and is already joined for every other purpose. Items that share a Todo share a payload;
items whose Tasks came from different Todos do not, because they are exported by different
mechanisms and a receiver of one has no business seeing the other's items.

**每一项的 payload 形状不变。** Same `event`, same `list`, same `items` — a subset. A receiver
cannot tell that a round was split, and does not need to: what it receives is "these items, under
this event", which is what it always received.

### 没有来源 Todo 的 item

> **Corrected 2026-09-18, after the third device pass.** The paragraph below used to describe this
> case as *the folder case* — "a file browsed under no Todo at all" and `deliverFolderReview` passing
> a default-webhook flag. That was wrong on both counts, and the release shipped a defect that the
> wording had already excused: a folder round passes `ExportChoice.Inherit`, exactly as an
> inheriting List does, so **a file's Todo decides for it like any other item**, and only an item that
> genuinely has no `task_imports` row reaches the fallback below. `useDefaultWebhook` no longer exists
> as a parameter at all. The full finding, its mechanism and the fix are in
> [Acceptance, as run](#acceptance-as-run) — the folder round was in fact routing **every** item to
> the webhook.

A manual item, or a file browsed under no Todo at all. That case exports through the **Settings
default**: an unowned group exports by `webhook`, gated by the webhook's own *Default enabled*. It is
a hard-coded answer, kept because this release is about naming the mechanism and not about inventing
a policy for the items that have no owner. A default **kind** in Settings is the obvious next step
and is deliberately not taken — see §Out of scope.

### txt

> **Amended 2026-09-18, after the device pass: the folder is `Download/Listea/txt/`, not
> `DCIM/Listea/txt/`.** The paragraph below states the original decision and is kept as written,
> but the device refuses to write a text file anywhere under `DCIM/` — `MediaStore.Files` accepts a
> non-media row under `Download/` and `Documents/` and nothing else, at any API level, whatever
> permission the app holds. The user chose `Download/` when the failure was put to them. The full
> finding is in [Acceptance, as run](#acceptance-as-run); `MediaSave.kt` carries the reasoning.

**位置。** 用户的定夺：*txt保存位置暂时定在现在图片save to listea下新建一个txt文件夹* — so
`DCIM/Listea/txt/`, under the album `MediaSave.kt:56` already writes to. One directory below the
photographs, one name that means *this is not media*.

**一轮一个文件，不是一个累积日志。** `<yyyyMMdd-HHmmss>-<event>-<source>.txt`, with `-2`, `-3`
appended on a collision. A payload is a snapshot of one round; a file that keeps growing cannot be
attributed to a round afterwards, and *"which round wrote this line"* is the first question anyone
would ask of it. Unlike the media save, which reports `AlreadySaved` and stops
(`MediaSave.kt:181`, `:252`), an export **must land**: failing because a name was taken one second
earlier would be a silent loss of exactly the thing the user asked to be written out.

**内容** — the same facts as the JSON body, rendered as text, with the version line the codebase
already uses for payloads (`DISSOLVED_RECORDS_VERSION`, `TEMPLATE_BUTTONS_VERSION`):

```text
listea-export	1
event	quickreview.completed
list	Demo
source	Demo
at	1789726376530
items	3
item	3f2a…	one.jpg	1	Attach	custom1,favorite
item	9c11…	three.jpg	1	Attach	custom2
item	04b8…	two.mp4	0	Attach	
```

Field per item, in the order the JSON body uses: the public id, the title, `1`/`0` for completion,
the folder the item sits in (empty for a manual item, exactly as the JSON body's `relativePath` is
null), and the action wire values comma-joined. Fields are tab-separated and escaped with the
`%`-encoding `DissolvedRecords.kt:106-115` already uses for a user's filename — a path may hold a
tab or a newline, and a renderer that lets one break the line separator produces a file that reads
as two records.

### 结果记录 —— 两种都记

`webhook_history` gains `kind`, and its Kotlin names generalise (`WebhookRecordEntity` →
`ExportRecordEntity`, `webhookHistory` → `exportHistory`). **The table keeps its name**, for the
reason v0.5.4's decision 8 gave about a different column: renaming a table is a rebuild for a word,
and the word is in the migration's history either way.

Why generalise at all, when the user scoped this release to abstracting the webhook and adding txt:
**a txt export that leaves no trace is unfalsifiable.** The user cannot tell whether the file was
written, and the *Last export* line they asked for on the List card would have nothing to say
precisely when the effective kind is txt. One row per attempt, carrying its kind, is what makes
*"did this round export"* answerable for both.

This is also where the record's home moves: the history row that sits inside Settings → Webhook
today moves up to **Settings → Exports**, because it is no longer one kind's log. See §Settings.

### 三个开关，是 export 的而不是 webhook 的

`quickReviewWebhookEnabled`, `webhookOnReviewExit` and `webhookCompletedItemsOnly` say *when a round
exports* and *what goes into it* — neither is a statement about HTTP. They move to
Settings → Exports and their user-visible wording follows the rename the user asked for on the List
card (*send* → *export*).

**Their DataStore keys do not move.** `quick_review_webhook_enabled` and the two beside it are
frozen literals in the same sense a migration is: renaming one silently resets it for every install
that has it. The Kotlin field names change; the strings on disk do not. See
[the plan](v0.5.6-plan.md) §0 decision 9.

## What a user sees

1. **Settings → Exports**, a new section beside Templates, with an **Open** button that leads to a
   **full screen** listing the kinds: **Webhook**, then **Txt**. Reached as a screen rather than a
   dialog for the reason the user gave: a dialog whose own contents include another dialog is the
   shape this avoids.
2. **Settings → Exports → Webhook** is a full page holding where the webhook sends and nothing about
   when or what: **Default enabled**, **Default URL**, a **Send a test payload** button, and a way
   into **Export history**. The three export-wide switches are not here — they moved one level up,
   to Exports, because none of them is a statement about HTTP.
3. **Settings → Exports → Txt** is a page holding what there is to configure, which in this release
   is nothing: it states where it writes (`Download/Listea/txt/` — `DCIM/Listea/txt/` before the
   device pass; see the amendment above) and what is in the file, and it is
   deliberately not editable. No name template, no format, no on/off — a second kind with a settings
   page of its own would have been a second thing to get wrong rather than a smaller first one.
4. **Settings → Exports** also carries the three switches and **Export history**, because both are
   about exports rather than about one kind.
5. **The List card is split in two.** *Progress* keeps the bar, the count and the **Review** button.
   A new card below it, **Export**, holds a dropdown — *Same as the Todos* / *Export nothing* /
   *Webhook* / *Txt* — the switch **Export when this list is completed**, and the line **Last
   export: …**. The **POST URL** field and the **Test webhook** button are gone from the List
   entirely.
6. **At import**, the Create Tasks dialog gains a choice: **How should this Todo export its
   decisions?** — *Don't export* / *Webhook* / *Txt*. It is drawn for both Create and Refresh, like
   the content policy beside it, and a Refresh opens on the Todo's stored answer.
7. **Every webhook uses one URL** — Settings → Exports → Webhook → Default URL. The per-List URL is
   gone, which is the fix for the copy-versus-reference problem rather than a side effect of it.

1. **Settings → Exports → Webhook** shows the default enabled switch, the default URL, and the
   history; **Txt** shows where it writes. Neither is a dialog.
2. Import a folder choosing **Txt**. Run a Quick Review round to the end. A file appears under

5. Set the List's dropdown to **Txt** and the same round produces **one** file holding every item,

6. **Export nothing** on the List keeps the round silent while its Todos still hold their kinds.
7. **Last export** reports the mechanism that actually ran, for either kind.
8. **Upgrade over an existing database.** A Todo that webhooked before the upgrade still webhooks;

9. A List's POST URL is gone and nothing reads one; changing the Default URL reaches **every** List.
10. **A List that completes while another List's review is open exports nothing and says nothing.**
    No dialog appears over the review, the completing List reads *Last export: Not sent*, and its
    payload is in the history under its own name, with *Resend* on the row.

### Acceptance, as run

**Run on 2026-09-18 on the attached OnePlus PLR110 (API 36), over the user's own database and
against the user's own n8n webhook. Three defects were found that the suite had passed over — two of
them release blockers, in that they left a whole mechanism dead (txt could not be written at all; the
webhook's automatic path died on the main thread) and one that broke the release's headline rule in
the one mode with no stored rows to fall back on (a folder round never found its Todo). All three are
fixed, and each was re-walked green on the device. This section is the record of what the phone said,
not of what the suite said.**

A green suite passed over all three. That is the point of this section existing at all.

#### Blocker 1 — the txt export could not be written

Choosing *Txt* for a List and completing it produced, verbatim:

```
Failed · Primary directory DCIM not allowed for
content://media/external_primary/file; allowed directories are [Download, Documents]
```

`MediaStore.Files` accepts a non-media insert only under `Download/` and `Documents/`, at any API
level this app can run at, whatever permission it holds. The destination was chosen because a
gallery builds albums out of `DCIM` — which is exactly the property that makes `DCIM` available to
`MediaStore.Images` and not to `MediaStore.Files`. A `text/plain` row has no media collection to go
through, so `DCIM/Listea/txt/` was not reachable from this app at all.

**Why the suite could not see it.** Robolectric's `MediaStore` shadow does not enforce the
primary-directory rule, so the suite delivered a text file quite happily at `sdk = [34]` while the
phone refused every one. The comment in `MediaSave.kt` claiming this exact path had been *"verified …
on an API 36 device before this was written"* was false when it was written, and it is the claim
that let the release get this far. It is corrected with the fix.

**Fix, and the user's decision.** The user chose `Download/Listea/txt/` when the failure was put to
them: `Download` is what *output an app produced for you* already means, and `Documents` is where a
user's own files live. `MediaSave.kt` now has a second primary-directory constant — the album's and
the export's answer to different rules, and folding them into one is what produced the bug — and
`MediaSaveTest` carries the tripwire the release shipped without: a plain JVM test asserting the
export path's first segment is one the platform allows. It cannot prove the write will be accepted;
it can refuse to let the path drift back to one that provably will not.

#### Blocker 2 — the webhook's whole automatic path died on the main thread

With a real HTTPS URL finally available, a List completing produced:

```
Failed · NetworkOnMainThreadException
```

`postWebhook` is a blocking HTTP call. Before this release the one place that reached it wrapped it
in `withContext(ioDispatcher)` at the call site; moving the call behind the `Exporter` interface
moved it out of that wrapper, and every round triggered by a checkbox or a swipe — which run on the
main thread — threw instead of delivering. The text kind never showed it, because `TxtExporter`
does its own `withContext`. The two halves of one release were differently safe, and only the
device could tell.

**Fix.** `WebhookExporter.deliver` now runs the POST on an injected dispatcher, and the guarantee is
stated on `Exporter.deliver` rather than left to be rediscovered. `ExporterDeliveryTest` pins the one
mechanical fact that decides it — the work is handed to a dispatcher — which is the part of
`NetworkOnMainThreadException` a plain JVM can assert.

#### Fixed alongside, all found on the device

1. **A failed txt export was reported in webhook's words.** The notice read *Webhook not sent* and
   carried a webhook host, for a round that was never going to open a socket. `WebhookNotice` now
   carries the round's `kind`, so the headline and the host name the mechanism that actually ran; a
   txt notice has no host at all, because a URL sitting in Settings for *other* rounds is not this
   round's destination.
2. **The confirmation promised a webhook a List no longer has.** *"This would post to this list's
   webhook"* — over a round bound for the **default** URL, naming a control the release had just
   deleted. There is one webhook now, so there is one answer.
3. ***1 items*.** The dialog built its own plural instead of calling `countOfItems`, which already
   singularised and already had a test. The helper was covered; the call site was not.
4. **A txt record offered *Resend*** — which would have pushed a tab-separated report at whatever
   URL happened to be in Settings. *Resend* means *post this again*, so it is offered only for a row
   whose kind is a webhook.
5. **A round that exported nothing stayed silent.** See *Decision 1* below.
6. **Three instructions still sent the user to a screen by its old name.** Found on the second pass,
   while reading the screens this walk had to pass through: the Settings card that offers to delete
   checked files said the round "stays in **Webhook history** above" (`SettingsScreen`), the
   post-deletion dialog said the same thing as a path, "Settings › **Webhook history**"
   (`MainActivity`), and the pre-send confirmation said a declined round "is kept in the **webhook
   history**" (`MainActivity`). The screen those three name is **Exports › Every export**, titled
   *Export history*, and it holds both kinds — so a user told to look in "webhook history" is told to
   look somewhere that no longer exists, for a release whose whole subject is the word *webhook* being
   used where it is not about HTTP. All three now say *Every export* / *the export history*.

#### What passed

after the upgrade: `user_version = 25`; all three pre-existing Todos at `exportKind = 'webhook'`;
the one pre-existing List — switched off — at `exportKind = 'inherit'`, so it went on following its
Todos rather than coming back to life; the pre-existing history row at `kind = 'webhook'`; and
`lists.webhookUrl` still present and untouched. This is the first time the migration has run against
a database nobody wrote for a test.

Item 8's second clause — a List that *was* switched on reading *Webhook* in the dropdown — could not
be walked: the only List on this phone was switched off, and the criterion has no instance here. What
the pass does fix is the half that matters more: a switched-off List is not silently promoted to
exporting, which is the failure a migration is actually at risk of.

**Item 5 passed.** A List set to **Txt** over two items produced **one** file holding both:
`Download/Listea/txt/20260918-220643-list.completed-Demo.txt`, with the version line, the header and
one `item` line per row, matching the store's own record of the round.

**Item 3 passed.** With the List on **Same as the Todos** over a Todo set to `webhook`, completing it
raised the confirmation naming the **default** URL's host — the user's n8n — and delivered
`Success · HTTP 200`, recorded as `webhook / SENT`.

**Item 9 passed as far as it can be walked.** The List has no Post URL field and no Test webhook
button, and the round above went to the Default URL with no per-List value in sight.

**Item 6 passed.** With the List on **Export nothing**, completing a round produced no dialog, left
*Last export* untouched, and wrote **no history row** — while the Todos kept their own kinds.

**Item 7 passed.** The List card read *Txt · On · Written* after the file, and *Success · 22:21* on
the card's own line; it read the failure before that, and the history records the mechanism per row.
The split round read *Success · 22:56* on the same line, and both Lists read *Automatic · On ·
Success* on the Lists screen.

**Item 1 passed in shape.** Settings carries an **Exports** card with *Open*, leading to a full
screen — Methods, the three export-wide switches, History — and the Method dropdown carries all four
choices in one order. Two things it shows were read off the screen on the second pass and are worth

· n8n.ashikoki.me* and *Txt · Download/Listea/txt/* — the amended destination, in the UI — and
**History** counts "8 records · 4 not delivered" over both kinds rather than over webhooks, with the

that was sent."*

#### Item 4, walked on a second pass — the round that exports twice

The first pass could not reach it: a Todo's kind is stored on `sources.exportKind`, one per Upstream,

#### The third pass — a folder round never found its Todo, and the split never happened

**The user's report.** Two Quick Review rounds — one over the 4-task *Demo* folder, one over the
139-task *2026-09-11* folder — **both posted webhooks**, and the second was wrong: that folder's Todo
is set to **Txt**. A POST to the default URL where a file should have been written.

**The evidence, read back from the phone.** Rows 9 and 10 of the export history are both
`webhook / review.exited / Selected folder`, sized 4 items and **139** items. The 139 items resolve —
`legacy_task_ids → assets.taskId → task_imports` — to Tasks whose `task_imports` row points at the
`2026-09-11` Todo with `exportKind = 'txt'`. The round had every fact it needed to route itself
correctly, and did the one thing that was wrong.

**The cause is one field, and it is not in the split.** A List round's rows come out of `list_items`,
where the Task is a stored column. A folder round has no `list_items` rows at all: it resolves files,
and its payload rows are **minted** from `ReviewItem`s. The function that minted them hard-coded
`taskId = ""` — reasoned out in its own KDoc as harmless, because *the foreign key that makes a stored
membership name a real Task is the only thing that would care, and it never sees this row*. That
reasoning is about the row's **writer** and missed its two **readers**, both of which are the round's
routing:

- `deliverPayload` groups a round with `planExports(items, listChoice) { row -> sources[row.taskId] }`,
  where `sources` is `dao.getExportSources(items.map { it.taskId })`. With every id empty, the lookup
  returned nothing for every item, so the whole round landed in **one group with no source** — and a
  group with no source is, by the rule for items no Todo owns, a **webhook**. A folder round over a
  *Txt* Todo posted instead of writing.
- `assetControls[row.taskId]` is keyed the same way, so the same empty field is why a folder round's
  payload reported `"actions": []` for **every** item. Row 9's Tasks carry
  `assetControls = 'builtin.media.asset-control\t2'` and marks, and the payload showed nothing; row 12
  — the List path, which was never broken — showed `["favorite","cust1","cust2"]`.

The first of those is the reported symptom; the second is a second defect on the same line that the
report did not mention, found by following the field to its other reader.

**Why 803 green tests did not see it.** `ExportDispatchTest` holds the headline rule and asserts it
hard — but every row it builds already carries a Task id, because it builds `ListItemEntity`s
directly. The seam between `ReviewItem` and `ListItemEntity` was crossed by no test at all: the rule
was covered, the rows were covered, and the bridge was assumed. The suite was green and the app was
wrong, in the one mode that has no stored rows to fall back on.

**The fix carries the field, and lifts the function to where a test can reach it.** `taskId = taskId`,
and `toPayloadRow` moves out of `ListsViewModel` to a top-level `internal` beside `exportItemView` in
`Exporters.kt` — pure, no view model, no Context, so the seam is assertable. `FolderRoundRowTest`
asserts it three ways, and it is a **tripwire rather than a description**: with the field reverted to
`""` the round splits into one group and the test fails with
`expected:<[TXT, WEBHOOK]> but was:<[WEBHOOK]>` — the user's bug, in one line.

#### The fourth pass — a List exports in the middle of another List's review

**The user's report.** Reviewing the `export test` List, **one swipe** produced an export before the
queue had ended and without leaving the review. Their reading was *"滑动完成了某个 todo，然后触发了
那个 todo 的 export"*, and the shape of it is right — but what fires is **not a Todo's** export.

**Reproduced.** The Task swiped past was the last unfinished item of the **Demo List**, which shares
that Task. The swipe completed it; Demo reached 2/2 and completed; and Demo's own rule — *Export when
this list is completed*, on **Same as the Todos** — ran at that instant, with the review still open:

> **Txt written** — *Demo* — `20260919-090936-list.completed-2026-09-11.txt` — **List completed · 2
> items · 09:09:36**

Recorded as row 25: `txt / list.completed / Demo / 2 items / WRITTEN`. The `export test` progress
went 2/4 → 3/4 and stayed there; **the review never ended and its own round never ran.**

**The mechanism is one line, and it is deliberate.** The swipe is `TaskAction.CompleteTask` →
`ListsViewModel.submitItemReview` → `dao.submitReview`, which returns **every List that transitioned**
— and the caller fires on all of them:

```kotlin
val (transitioned, inRound) = writeOrder.withLock {
    val ids = dao.submitReview(item.taskId, response, …)
    ids to ids.filterTo(mutableSetOf()) { it in openReviewRounds }
}
transitioned.forEach { onCompletionTransition(it, true, it in inRound) }
```

`onCompletionTransition`'s suppression exists for one case only — *the List this round is reviewing*,
which is about to report the same moment itself. **A List that is not the one being reviewed has no
such protection**, and Demo is not: it holds the same Task, so the round completes it too. A Task in
two Lists is a Task whose completion is two Lists' business, and both of them answer.

**What the user sees depends on the other List's own items.** A group whose kind is **Txt** writes and
says so; a group with a **webhook** item raises *Send this webhook?* — **on top of the review screen**,
which is the thing that reads as *the review just posted a webhook*. The user reported the webhook
form; this data no longer reproduces it, because the Demo List's two remaining items both come from
the `txt` Todo, so its group is Txt and delivers without asking. The condition for the prompt is
exactly *the completing List holds an item from a webhook Todo* — which is what Demo was while it
still held its third item, the one its card still reports as **"3 items removed when a Todo was
deleted"**.

**Bug or design?** Neither, and the honest answer is the third thing: **an undecided case, behaving
the way the code happens to.** Nothing is misrouted — Demo genuinely completed, its own switch said
to export when it does, and its items went where their Todo said. What was never decided is what the
completion **of a different List** should do while a round is open on another. The two candidate
answers are both defensible and this release does not choose between them:

- **It is the List's own rule and fires when it happens.** Suppressing it would mean a List could
  complete and say nothing, which is the state `Decision 1` and item 6 both treat as the one that
  looks identical to a silent failure.
- **A round in progress owns the moment.** Nothing should leave while the user is mid-review on
  something else, and the delivery can be made when that round ends — which is what the suppression
  already does for the reviewed List, applied one level wider.

**The user's decision: option C, which is neither of the two above.** Made on 2026-09-19, and it is
the shape of *it is the List's own rule* with the *asking* removed rather than the *delivery*:

> 用户在一个 list 里动作，不要反馈给用户另一个 list 的结果 … 假设在浏览 list A 的过程中触发了
> list B 的完成。不要再显示的跳弹窗 export，而是在背后完成 list B 的对应 payload 的构建，但是
> 不发送。退出或者完成 list A 之后，用户会看到：1. 在 list 界面：last export - not sent（类似
> 于用户在某次 export 弹窗里选择 not now）2. 在 history 界面，看到刚才 list B 的 payload

Implemented in this pass — see below.

#### The fix — a completion nobody is present for is *answered*, not cancelled

**The decision in one line: the app gives the dialog's safe answer on the user's behalf, at the
moment it would have been asked.** B's payload is built exactly as it would have been, and then
nothing leaves, nothing is shown, and the two places the user can look both say so.

**Which completion changes is decided in one place, and it is a value rather than a boolean.** A
completing List is in one of three scopes, read under the same `writeOrder` lock as the write that
completed it — the exit that closes a round is a separate coroutine racing that write, and only the
lock keeps a round that was open when the item was checked from having closed by the time the
decision is made:

| scope | when | what happens |
| --- | --- | --- |
| `Unattended` | nothing is being reviewed | unchanged: the round is put to the user |
| `ThisRound` | the completing List is the one under review | unchanged: the round reports it, narrowed |
| `AnotherRound` | a round is open on **something else** — another List, or a folder | **new: built, kept, not sent, not shown** |

`ThisRound` is the suppression that already existed, now named; the release changed only the third
row. A folder round counts as *another round* too, which is why `onFolderReviewStarted` exists at
all: until this pass there was a start marker for a List's round and none for a folder's, so the
question *is somebody reviewing something* had no answer for Quick Review — and the Tasks are often
literally the same Tasks, so a List completing under a folder round is reached by ordinary use
rather than by a corner case.

**The folder marker is paired by the screen, and finding out that it had to be was the second bug of
this pass.** Quick Review ends two ways — its queue runs out, or the user leaves — and only the
second goes through `onFolderReviewExited`, so a marker closed there would have leaked on the first:
one Quick Review run to its end, and *a folder round is open* would stay true for the rest of the
process, quietly keeping every completion in the app instead of asking about it. It is the failure
mode that hides itself — nothing on screen, no record, just a dialog that stops appearing — and it
sits on the one Quick Review path the device section above records as unwalked. Start and end are
now one `DisposableEffect` on the queue's session key, so the round is exactly as long as the screen
is, and no future exit path has to remember.

**Not sent, and deliberately not *silent*.** The quiet branch sits after the three checks that
precede the confirmation — a URL that cannot be used, an exporter that could not be built, a webhook
that is switched off — and not before them. Those three are *facts* about the configuration, and a
List whose URL is blank is a List the user has to go and fix; answering *not now* for them would
file a broken setting under a choice nobody made. So a disabled or unusable mechanism is still
recorded as the failure it is, even in a round nobody was present for. What the app answers for the
user is the delivery decision, and only that.

**The record is a third outcome, in its own words.** `NoticeOutcome.DEFERRED` — headline *Not sent*,
detail *Nothing was sent · you were in another review* — is written into the history with B's own
title, event and item count, and it is never raised as a notice: a dialog about a List the user is
not looking at is the same interruption the confirmation was, one step later. It is not the decline's
sentence either, which would tell the user they chose something they were never offered. *Resend* is
offered on the row as it is on every other, so the payload is not merely kept but reachable.

**And the List's own line says so too.** A List that was kept has `lastDeliveryStatus = NOT_SENT`,
which reads *Not sent* on the card and `Last export: Not sent · <time>` in its header — the third
answer beside Success and Failed that `exportStatusLabel` gained in this pass. **This reverses a
rule the third pass recorded and this document asserted above**: a round the user *declines in the
dialog* is now written against its List the same way. The reason is the same one, one step earlier —
*Last export* should name the last thing that happened to that List's exports, and when the most
recent thing that happened was a payload that did not leave, having the line go on naming an earlier
success is the line being wrong about the List. The history still holds both rounds.

**The dialog now says what caused it.** The last of the user's requests — *"每次跳窗说明 export 也
多带一点点信息，至少清晰表明是谁触发的这次 export"* — was the other half: the asking dialog opened
on the bare word *Demo*, over the review of a different List, with nothing saying what Demo had to do
with anything. It now leads with a sentence naming the event and its subject (*The List Demo just
completed*, *The review of export test ended*, *The Quick Review of 2026-09-11 finished*) and follows
it with the facts the two dialogs share (*2 items · example.com*). `review.exited` is the one phrased
carefully: it is emitted both when a queue finishes on screen and when one is backed out of, so its
sentence says the review *ended* rather than that the user left it, which would be wrong every time
it is raised on the completion screen — where this dialog most often appears.

**Four tests, in `ExportQuietRoundTest`, and one of them is a control.** A List completing under
another List's round is kept, not sent and not shown; the same completion with no round open still
asks; a List whose *own* round is open is unaffected; and a completion is kept only for as long as
the folder round is open, which is the marker above asserted as the pair it is. The control is the
one that matters — without it, a branch that had stopped asking altogether would pass the first
test. They are the first tests in the suite to drive a delivery through the ViewModel rather than the
DAO, and they document the trap that comes with it: `advanceUntilIdle()` runs what is queued and
returns, while a Room suspend query resumes from Room's own executor, so an assertion placed after it
reads a ViewModel that has not finished thinking. The tests wait on the flow they are asserting
about, which is the same reason `ConsentGateViewModelTest.settled` exists. The Compose half of the
marker — that the composition really does pair the two — is not reachable from a unit test and is
walked on the device.

**Not yet walked on the phone.** The device was not reachable over wireless ADB on 2026-09-19 — no
cable, and `adb mdns services` discovered nothing — so everything above is verified by the suite and
by reading the code, not by the phone. What the device pass still has to confirm is exactly the half
a unit test is worst at: that no dialog opens over List A's review, that B's card reads *Not sent*,
that B's payload is in the history with *Resend* on the row, that an ordinary completion's dialog now
leads with its trigger sentence — and, for the marker above, that **a Quick Review run to the end of
its queue** leaves the app still asking about later completions, which is the one path where a leak
would show. Item 10 of the acceptance list is unwalked in the same sense.

#### Not walked

#### Decision 1 — a round with nothing configured to export

**The hole is real, and it lives at one line.** The delivery path returned in silence when every Todo
the round touched said nothing exports: no file, no POST, no record, no word. Quick Review's promise
is that finishing a round *produces a result* — that is what "send when leaving a review" is for — so
such a round was indistinguishable from one that exported and failed to report, and the user had no
way to learn which.

**The user's decision: a notice, not a reworked history.** In their words, the app is *not yet
connected to a real business*, so what is needed now is a word saying that no export happened — not
a history broad enough to hold a result before an export is chosen and re-export it later. That
larger design is **not built and not scheduled**; it is recorded here as the open question, to be
revisited when the webhook is wired to something that actually consumes it.

`NoticeOutcome.UNCONFIGURED` therefore raises *Nothing exported · Nothing was sent · no Todo this
round covers is set to export*, and **nothing is recorded** — there is no payload whose kind would
mean anything, and a row reading *exported by nothing, to nowhere* would be a record of an attempt
that was never made. It is not a failure and must not read as one; it is not an attempt, so it is not
counted against a list as a delivery.

Note the asymmetry, which is deliberate: a *List* that says nothing still produces no notice at all,
because that is an answer the user gave on the List they were just looking at, while this is a
configuration gap they cannot see from the screen they finished on.

#### Two things this pass could not have found, and one it changed

**A Todo's export method is settable but not *shown*, and an earlier draft of this very section
called it immutable — that was wrong, and the correction is the finding.** The method is chosen in the
import dialog, and *Refresh Import* reopens that same dialog seeded from the Todo's stored answer
(`requestSourceRefresh` → `ImportOptions.exportChoice`), so a Todo that picked *Txt* by mistake can
have it changed, by the same dialog that set it.

What is actually missing is a place to **read** it. The Todo card shows the templates and the content
policy, and nothing about exports; the only way to see how a Todo leaves the app is to open the import
dialog, and opening it is a write. That bites hardest right after `MIGRATION_24_25`, which put every
pre-existing Todo on `webhook` — a user who wants to know what a Todo inherited has to run an import
to ask. Not built; recorded.

cleartext traffic here and the app sets `usesCleartextTraffic=false`, so the validator promises
something the network configuration forbids. Left as it is rather than changed: a debug build may
legitimately want a LAN address, and the honest fix is a network-security-config decision rather than
a tightened regex. Recorded.
