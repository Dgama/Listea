# Listea v0.8.2 — Implementation plan: Packages, Prompts, and the dating acceptance

> **Status:** **Implemented; accepted on device 2026-10-24; unreleased.** The protocol, the
> vocabulary, and the three open decisions were settled with the user before this plan; the code is
> committed on `main` and no tag or release is published. Minor issues found during acceptance are
> deferred to v0.8.3.
> **Spec:** [`v0.8.md`](v0.8.md) — the framework arc. This is the version in which the
> dating-profile acceptance first becomes runnable end to end.
> **Protocol:** [`package-protocol.md`](../package-protocol.md) — `listea.package/1`.
> **Builds on:** v0.8.1 (schema 31, stored Task Reviews, viewer events, `review_event_answers`).
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md) — *Framework evolution — v0.8.x*.
> **Branch:** `main`. **No release tag.**

## 1. The goal in one sentence

A folder containing a Package is imported as a catalog of **Prompts**; each Prompt becomes a Task
whose Viewer renders its description and Resources; a single-choice answer is caught by a stored
Headless Template, committed through the normal primary submission path, stored as one event plus
its answer row, and exported as a v5 body — without changing the meaning of Task, Asset, List,
Add-on, ReviewEvent, or export history.

## 2. Decisions settled before this plan

| # | Decision | Why |
|---|---|---|
| D1 | The stored unit of a Package is a **Prompt**, not a Task. A Task is the decision-maker's undertaking to make one judgment in one Todo; under a Package it answers one Prompt. | The user's distinction: `.listea` stores questions, not the act of answering them. A Task always carries the decision-maker's intent; media Tasks have no stored Prompt but are still Tasks. |
| D2 | Commit **modality** and **revisability** are two independent template fields. `commit` is `immediate:<intent>` or `confirm:control:<id>` / `confirm:intent:<intent>`; `revisable` is a boolean. | One-tap final (vocabulary), one-tap overwrite (dating with regret), and choose-then-confirm are combinations, not three separate enum values. |
| D3 | The Prompt body is a **member JSON file** referenced by the manifest, not inline in it. | The protocol will be upgraded often; a description can grow and its schema can move without rewriting the manifest envelope. |
| D4 | v5 exports through **both** Webhook and Txt, from one `ExportMapping`. | The mapping is shared; the two writers differ only in serialization. |
| D5 | Commit and Template compatibility are resolved by declared capability, not by a 1:1 kind→viewer or response→template map. | A questionnaire Viewer may render a single-choice Prompt; a tag Template may answer on images and video. |
| D6 | The Package body is **not** exported into v5. v5 carries content identity and the chosen option, not the profile text or the photo. | Export is a record of decisions; the profile body is personal content with no need to leave the app. |
| D7 | A new `ImporterKind.PACKAGE` is added. File-as-Task and folder-as-Task remain unchanged. | Import is the print shop; the Package is a third printing convention, not a detection rule under the old two. |

## 3. Vocabulary and the model (recorded in ARCHITECTURE)

The full vocabulary is in [package-protocol.md](../package-protocol.md#vocabulary-v082). The two
distinctions the code must not blur:

- **Question-setter intent vs decision-maker intent.** The upstream Package says what is asked and
  what the legal answers are. The Todo says which Prompts are taken on, in what scope and order,
  with which printing convention and answer tool. A List orders the resulting Tasks; it owns no
  template and no question.
- **Prompt vs Task.** A Prompt is stored in a Package. A Task is created when a Todo takes it on.
  The same Prompt may become two Tasks under two Todos. "An image" is never a Task; "tag this
  image" is a degenerate free-form Prompt, and doing it is the Task.

The exam/print-shop analogy (upstream = question source, Package = exam paper, import = print shop,
viewer = printer, template = pen/eraser, Todo = candidate's intent, Task = answering one question)
is recorded in ARCHITECTURE as a **working analogy**, explicitly not a source of rules.

## 4. Domain types (pure, JVM-testable)

New in `domain/` (names provisional):

```text
PromptKey, PackageKey, ResponseContract
PromptDeclaration            // key, kind, schema, response, title, description, assets, resources
ResourceDeclaration         // key, kind, member
PackageManifest             // protocol, packageKey, revision, title, prompts, resources
PromptBody                  // parsed description, kind/schema-specific
PackageDiagnostic           // scope, code, message
PlannedPrompt / PlannedResource / PackagePlan
ViewerCapability            // id, version, supported (kind, schema range, response), emitted intents
ViewerIntent                // key + payload
ViewerEvent.Choice          // optionId + label snapshot, new event type
```

`ViewerEvent.Choice` extends the existing value grammar:

```text
type = choice.select
value = <optionId>\t<label>
```

`ViewerEventType` gains `CHOICE_SELECT`, and `assetUri()` returns null for it: the event is about
the Task, not about a file. The child table `review_event_answers` already stores any `type`/`value`,
so the schema supports this event without a change. The label is snapshotted into the event and
bounded to 200 characters; the prompt body is not. This is what lets a Like/Dislike answer remain
interpretable after the Package revision moves on.

### Commit policy

`TaskReviewDefinition` gains `revisable: Boolean` and the generalized commit forms:

```text
CommitPolicy.Immediate(intent: String)        // the answer intent commits
CommitPolicy.Confirm(controlId: String)       // template control confirms a pending answer
CommitPolicy.ConfirmIntent(intent: String)    // viewer intent confirms a pending answer
```

`Explicit` is renamed to `Confirm` and every surface that exhaustively matches the sealed type
follows; the stored v1 key `explicit:` stays readable and is never rewritten by a read.

The definition encoding moves to `v=2`:

```text
v=2
viewer=builtin.viewer.profile@1
accepts=choice.select
commit=immediate:choice.select
revisable=true
completes=true
advance=true
```

`v=1` rows remain readable: their `explicit:<id>` reads as `Confirm(<id>)`, and a missing
`revisable` reads as `true` (the media rapid review has always allowed re-review). A `v=2` row is
unreadable to an older build, which is the fail-closed direction the definition decoder already
takes.

A refused commit (non-revisable Task already committed, or any write-boundary validation failure)
writes neither an event nor a state change.

## 5. Storage: schema 32

Additive. Five tables and no changed column.

```text
task_payloads(
  taskId TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  schemaVersion INTEGER NOT NULL,
  payload TEXT NOT NULL,             -- canonical JSON of the Prompt body
  revision INTEGER NOT NULL,
  updatedAt INTEGER NOT NULL,
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE
)

package_checkpoints(
  sourceId TEXT NOT NULL,
  packageKey TEXT NOT NULL,
  rootUri TEXT NOT NULL,
  relativePath TEXT NOT NULL,
  protocol TEXT NOT NULL,
  title TEXT NOT NULL,
  revision INTEGER NOT NULL,
  fingerprint TEXT NOT NULL,
  lastSeenAt INTEGER NOT NULL,
  PRIMARY KEY(sourceId, packageKey),
  FOREIGN KEY(sourceId) REFERENCES sources(id)
)

package_prompt_tasks(
  taskId TEXT PRIMARY KEY,
  sourceId TEXT NOT NULL,
  packageKey TEXT NOT NULL,
  promptKey TEXT NOT NULL,
  present INTEGER NOT NULL,          -- 0 when the current Package revision no longer names it
  UNIQUE(sourceId, packageKey, promptKey),
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE,
  FOREIGN KEY(sourceId) REFERENCES sources(id)
)

package_resources(
  id TEXT PRIMARY KEY,               -- opaque internal identity, not a path
  sourceId TEXT NOT NULL,
  packageKey TEXT NOT NULL,
  resourceKey TEXT NOT NULL,
  kind TEXT NOT NULL,
  rootUri TEXT NOT NULL,
  relativePath TEXT NOT NULL,
  missing INTEGER NOT NULL,
  updatedAt INTEGER NOT NULL,
  UNIQUE(sourceId, packageKey, resourceKey),
  FOREIGN KEY(sourceId) REFERENCES sources(id)
)

task_resources(
  taskId TEXT NOT NULL,
  resourceId TEXT NOT NULL,
  required INTEGER NOT NULL,
  PRIMARY KEY(taskId, resourceId),
  FOREIGN KEY(taskId) REFERENCES tasks(id) ON DELETE CASCADE,
  FOREIGN KEY(resourceId) REFERENCES package_resources(id) ON DELETE CASCADE
)
```

Notes:

- `sourceId` is the Todo's id. The protocol document says `todoId`; the storage uses the existing
  table's name, and the two mean the same thing.
- `task_payloads` is one-to-one and content, not identity. A media Task simply has no row.
- `package_checkpoints` is provenance, not a Package entity. There is no `packages` table.
- `package_prompt_tasks` carries the reconciliation key and a `present` flag. A Prompt that leaves a
  revision is marked absent; the Task, its payload, its events, and its List memberships stay.
- `package_resources` rows are kept when a member goes missing (`missing = 1`), exactly as an Asset
  source is marked missing rather than deleted. `task_resources` carries per-Task requiredness.
- Foreign keys to `sources` are `NO ACTION`, mirroring `task_imports`: a Todo's removal must not
  take provenance or history with it. The Todo deletion policy already decides what happens to
  Tasks; these tables follow it rather than inventing a second rule.
- `groupPath` for a Package Prompt is `"<packageKey>/<promptKey>"`, a catalog key and **not** a
  filesystem path. `task_imports` carries no locator of its own, so a payload-only Task fabricates
  none; an Asset member keeps its real locator on the Asset row.

Migration `31 → 32` creates the tables and indexes. It consumes no existing data; migration tests
load a populated v31 fixture and assert that tasks, states, marks, Add-on answers, events, Lists,
and export history are byte-identical after the step.

## 6. Import and reconciliation

### 6.1 Typed input

The pure planner gains a Package input beside `FolderSnapshot`:

```text
ImportInput = FolderSnapshot | PackageSnapshot
PackageSnapshot = package root + manifest bytes + description bytes + member presence
```

The platform adapter reads bytes and checks members; the planner is pure and validates protocol,
keys, limits, references, and response contracts. A `PackagePlan` carries planned Prompts (with
normalized payload), planned Resources, and diagnostics.

### 6.2 Planning

- Discover `.listea/manifest.json` under the selected scope, up to depth 4.
- Parse strictly; reject the whole Package on envelope/unsafe/limit errors. Two directories
  declaring the same `packageKey` in one run are a conflict and neither writes.
- Diagnose individual Prompts for unknown kinds/schemas, unsupported responses, missing members,
  and malformed descriptions; keep the valid rest.
- Normalize each description to canonical JSON for storage.
- A Prompt with an unsupported kind/schema is still planned, with its payload, so a later build can
  make it reviewable without a re-import. It is marked unavailable for review.

### 6.3 Applying

Inside the existing import transaction:

1. Read the checkpoint by `(sourceId, packageKey)` and classify the run. A fingerprint conflict at
   the same revision or a lower revision writes nothing and ends the Package here.
2. For each planned Prompt: find the Task by `(sourceId, packageKey, promptKey)`. Create it if new;
   otherwise reconcile it — keep the Task id, re-stamp display name, payload, revision, assets, and
   resources.
3. Write `task_payloads`, `package_prompt_tasks`, `package_resources`, `task_resources`.
4. Mark unseen Prompts `present = 0`; mark missing Resources `missing = 1`.
5. Upsert the checkpoint and record the run result and diagnostics.

Reconciliation rules are in the protocol doc: same revision + same fingerprint is a no-op; same
revision + different fingerprint is a conflict and writes nothing; higher revision reconciles;
lower revision is stale. Two Todos over one Package produce independent Tasks.

### 6.4 Catalog and eligibility

- A Package appears as a catalog scope at `packageKey`, titled by the checkpoint's title. In a flat
  Todo it adds no browsing level: its Tasks appear in the Todo's flat list and stay selectable by
  Task id.
- `CatalogRow` gains `packageKey`, `promptKey`, `payloadKind`, `payloadSchema`, `payloadRevision`,
  and a derived `contentBlocked` reason.
- A zero-Asset Task with a compatible payload is eligible. A zero-Asset Task with an unsupported
  kind/schema is `NO_VIEWER`, never vacuously eligible. A legacy manual item with no Assets and no
  payload keeps its current eligibility.
- Quick Review and Create List select Tasks from a Package scope exactly as from a folder scope;
  incompatible Templates are excluded with an explanation, and the selection remains one
  review configuration, per the architecture's rule.

## 7. Page model and surfaces

The typed page list is the cross-cutting change. One source for page count, page entries, resume
identity, and the queue guide:

```text
ReviewPage = Content(taskId) | Asset(ReviewAsset) | AddOnPage
ReviewItem.pages: List<ReviewPage>   // content first, then Assets, then the optional Add-on
```

- A Prompt with a description gets a Content page at index 0. Its payload is read by taskId when
  the page is composed, so a large queue does not carry every body.
- Assets follow in the Prompt's declared order. The Add-on page, when present, stays last.
- `taskPageCount`, `pageStep`, the navigator, the two-level guide, resume, and the five viewing
  surfaces read `pages`. The old `assets.size + addOn` arithmetic is removed.
- `ReviewItem` carries the payload's kind, schema, and revision as the review opened them, so the
  submission boundary can compare the stored payload against what was shown.
- `DecisionTarget` gains a Task-level case for a Prompt whose decision is not about a file.

Surfaces to wire: `ReviewScreen` / `ReviewSession`, `QuickReviewScreen`,
`ListItemViewerScreen`, `CatalogTaskPreviewScreen`, and the catalog/list selection paths.

## 8. Viewer and Headless Template

### 8.1 The first structured Viewer

`builtin.viewer.profile@1`:

- supports `kind = profile`, `schema = 1`, `response = choice.single`;
- renders the stem, profile fields, and the photo Resource;
- emits `choice.select` with the chosen option id and label;
- resolves the photo through a Resource adapter; a missing required photo blocks, a missing
  optional one shows a placeholder and leaves the choices usable;
- calls no DAO and owns no navigation or completion.

The capability is a pure declaration in `domain/`; the renderer is a Compose surface beside the
media viewer. Resolution picks the most specific compatible Viewer; no compatible Viewer means the
Prompt is unavailable, with a named reason.

The Template's stored `viewer` reference names the Viewer it was authored against; it does **not**
select the renderer. The renderer is selected from the payload's kind/schema/response, and the
Template is usable when its `accepts` covers that Viewer's emitted intents. With one structured
Viewer in v0.8.2 the two coincide; the rule exists so a second Viewer is additive rather than a
template edit.

### 8.2 The first Headless Template

`builtin.structured.single-choice@1`:

```text
viewer      = builtin.viewer.profile@1
accepts     = choice.select
commit      = immediate:choice.select
revisable   = true
completes   = true
advance     = true
```

The dating fixture uses `revisable = true` to exercise regret: Like, then Dislike appends a second
event and the latest answer is current. A second built-in or a test definition with
`commit = immediate:choice.select`, `revisable = false` proves the final-answer policy used by
vocabulary.

### 8.3 Submission

The existing `submitItemReview` path gains write-boundary checks:

- a compatible Viewer is registered for the stored payload's kind/schema/response, and the
  definition's `accepts` covers the intent the commit carries;
- the events satisfy the response contract — exactly one `choice.select` for `choice.single`, the
  declared cardinality for a later contract — and name only options the payload declares;
- the payload revision equals the revision the review opened with;
- every required Resource is present;
- `revisable = false` refuses a second primary commit for that Task;
- a commit with accepted events missing is refused (v0.8.1 rule, unchanged).

A failure writes neither the event nor the state. A success writes the primary event, its
`review_event_answers` rows, and the permitted state in one transaction. The current answer is the
latest valid primary event; history is append-only.

## 9. Export v5

- Introduce `ExportMapping` as a pure stage between the round snapshot and either writer. Webhook
  and Txt both consume it; neither builds fields independently.
- v5 is chosen only for a round that carries at least one structured Task. Media-only rounds stay
  at v2/v3/v4, byte-for-byte.
- Per structured Task, v5 adds:
  - `content`: `kind`, `schema`, `revision`, `promptKey`;
  - `result`: `completed` and, for a choice, `{ id, label }`.
- The Prompt body and the Resource bytes are not exported. This is D6 and is documented in the
  export contract.
- Golden tests pin v2, v3, and v4; a v5 golden asserts key order, the option id and label, and the
  absence of the profile body.

## 10. Acceptance fixture — the dating Package

`docs/assets/fixtures/dating/`:

```text
.listea/manifest.json
prompts/alice.json, bob.json, carol.json
media/alice.png, bob.png, carol.png      (small generated images, committed)
```

- Three profiles, each `kind = profile`, `schema = 1`, `response = choice.single`, options exactly
  Like and Dislike, and one photo Resource. Alice's and Bob's photos are required; Carol's is
  optional, so the walk can remove it and still choose. This is the only difference between the
  three, so a missing-required refusal cannot be confused with a viewer failure.
- The photos are generated colour blocks or simple portraits with a checked-in generator; the
  walk must not depend on a local tool.
- The manifest's revision is 1 in the committed fixture; the walk creates a revision-2 copy to
  prove reconciliation without rewriting the committed bytes.

## 11. Acceptance script (device walk)

Run on the OnePlus PGP110 (`edbb363e`), installed with `adb install -r`. Never
`connectedDebugAndroidTest`.

1. Push the fixture to the phone's Pictures tree; create a Todo with the **Package** importer over
   its parent folder, attach the single-choice Template, no Add-on.
2. The Todo's catalog shows the Package scope and three Prompts; no per-file Tasks appear.
3. Open Quick Review or a List over the Package:
   - each candidate shows one Content page: stem, profile fields, photo;
   - the Asset count is zero and the photo never appears as a page or a file chip;
   - only Like and Dislike are offered.
4. Tap Like on Alice: exactly one primary event, one `choice.select` answer row, completed state,
   advance to Bob.
5. Return to Alice and tap Dislike: a second event is appended, the latest answer is Dislike, and
   the first event is still in history. This proves `revisable = true`.
6. Reopen and confirm both the latest answer and the Info sheet's Recorded section.
7. Re-import the same Package: no duplicate Tasks, the same Task ids, judgments preserved, no new
   events.
8. Import a revision-2 copy with a changed bio: the payload updates, the Task id and judgment
   remain, and old events are untouched.
9. Import a copy with an unknown `kind` or `schema`: the Prompt is stored as unavailable, excluded
   from the queue with a named reason, and the valid Prompts still import.
10. Remove or rename Alice's required photo and re-import: submission is refused with the
    missing-content reason. Do the same to Carol's optional photo: a placeholder shows and the
    choice remains available.
11. Export a completed round by Txt and by Webhook: both carry v5 content identity and the chosen
    option; the profile body and photo are absent.
12. A media-only round still produces its v2/v3/v4 body unchanged.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| The page-model refactor touches every viewing surface. | Land it as its own phase with the existing navigation/page/queue suites as the regression net; no viewer work until it is green. |
| A hand-written JSON parser is a security surface. | The protocol needs depth/size limits, duplicate-key rejection, unknown-field rejection, and canonical output. A small pure `JsonValue` reader/writer in `domain/` gives exact control, keeps the no-`org.json` boundary, and adds no build plugin; a malformed/oversized/deep corpus and round-trip tests are part of phase 1. Using `kotlinx-serialization` was rejected because its reader does not reject duplicate keys by default, which the protocol requires. |
| Zero-Asset Tasks become vacuously eligible. | Eligibility requires a payload with a compatible Viewer; only legacy manual items with no payload keep the old path. A test pins both. |
| `groupPath` is mistaken for a file path. | Package Tasks use a namespaced catalog key and carry no fabricated locator; no code may feed the key to a file resolver. A test asserts a payload-only Task has no Assets and no file-backed target. |
| Export v5 lands late and destabilizes v2–v4. | Build the mapping seam in phase 5 before the v5 writer; goldens for v2–v4 run on every change. |
| Revisability is confused with history rewriting. | The definition policy refuses or accepts a commit; the event table stays append-only and the latest valid event is current. Tests cover both policies. |
| The protocol grows workflow-specific branches in Core. | Core knows keys, response contracts, intents, and capabilities; it never parses profile fields. `kind` is opaque to Core. |
| Package import writes partially on a bad record. | Envelope rejects before writes; record diagnostics skip that record; the DAO transaction commits only the plan. A test asserts no rows on a rejected Package. |

## 15. Out of scope

- No migration of image tagging or PDF marks onto the Package protocol. They are recorded as
  degenerate free-form Prompts conceptually, not moved.
- No `choice.multiple` or `freeform` Viewer/Template end to end. The protocol value exists and is
  rejected clearly until a Viewer ships.
- No vocabulary, scheduler, or recall products; no multiple Add-ons or Add-on changes.
- No archives, embedded binaries, remote fetching, code execution, or cross-Todo Resource
  deduplication.
- No `packages` table, no Package entity, no garbage-collection lifecycle.
- No release tag and no published release.

## 16. Deviations recorded during implementation

- **`package_resources.rootUri` holds the Resource file's own document URI**, not the Package
  tree's root, so a Content page opens the photo without re-walking the tree. `relativePath` keeps
  the Package-relative member. Recorded in
  [the storage note](../package-protocol.md#resource-declaration).
- **The selected scope may be the Package root.** Joining an empty root with the scope produced
  `"dating/"` and Resources named `"dating//media/alice.png"`; found on the first device walk. The
  scope path is stored unchanged and members stay Package-relative, as the protocol promised.
  Pinned by `PackagePlanningPathTest`.
- **Deleting a Package Todo clears checkpoint, Prompt-link, and Resource rows before the Source.**
  Their `sourceId` foreign keys are NO ACTION, so deleting the Todo failed with *Nothing was
  changed*; Prompt links may also outlive their Task after an absent-Prompt revision. Found on
  device; pinned by `PackageImportTest` and stated in
  [the protocol's Todo lifecycle](../package-protocol.md#deleting-a-package-todo).
- **A Prompt's Content page turns on a horizontal swipe on the read-only previews.** The card
  scrolls vertically and had no swipe of its own, so tapping a dating item on a List felt locked
  even though the arrows worked. The List item viewer and the Todo preview now wrap the card in a
  page-turn gesture that walks pages and then Tasks; Review is deliberately unchanged, where a tap
  is the judgment. Recorded in
  [the viewing surfaces](../review-and-actions.md#the-viewing-surfaces).
- **The built-in Task Reviews are named as headless stationery.** The first acceptance walk could
  not find the pen for a single-choice Prompt: the template existed but was called *Single Choice*,
  so nothing said it was the matching stationery. The three seeds now read *Headless Template for
  File Decisions / Sampling a Point / Single Choice*; each picker row says what it catches; a
  Package import starts on single choice until the user picks another and warns if file decisions
  is chosen. A row still carrying an earlier seeded name is repaired on open, while a user rename is
  kept. Recorded in [Templates → The built-in Task Reviews](../templates.md#the-built-in-task-reviews).
