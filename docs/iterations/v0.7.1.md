# Listea v0.7.1 — Add-ons: a questionnaire that follows the Task

> **Status:** **Implemented (2026-10-21) on `feature/add-ons`; device verification recorded below.**
> The model, the storage shape and the export contract below are what shipped in this branch: schema
> 29 with `MIGRATION_28_29`, export version 4, and the Task page. Nothing is tagged or published.
> **Audience:** User and coding agent
> **Depends on:** v0.7.0 — schema 28, export v3, the mark that points at a passage, and the split
> between the static frame and a template's dynamic components
> **Series:** the second round of **v0.7.x**, the template series
> **Plan:** [`v0.7.1-plan.md`](v0.7.1-plan.md) — how this document is built and verified
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)

## Why this round

v0.7.0 made a file reviewable in two directions: a whole picture or video through its chip row, and
a passage inside a PDF through a mark. Both answer a question about **one Asset**. Neither can say
anything about the **Task** the Asset belongs to.

The gap is easiest to see at the end of a Task. A folder of drawings is one Task with six files.
The reviewer opens it, judges file 1 through file 6, swipes left off the last one, and the app
immediately shows the first file of the next Task. There is no moment in which the Task itself is
looked at. The one Task-level fact the app records is the completion checkbox, which answers *done*
and nothing else.

The user's scenario for this round is exactly that moment:

> 这一组画（这一个 task）总体 3 分，属于生活类照片，备注，拍摄的时候心情不错。

A rating for the group, a classification, a note about the circumstances. None of it belongs to
file 3. All of it belongs to the Task.

**The hard part is not drawing a questionnaire.** A sheet of questions is a layout problem this
codebase has already solved several times. The hard part is deciding where the answer lives, so
that paging, missing-file detection, the Info sheet, file counts and the export do not acquire a
second meaning of the word *Asset*. This round's central decision is that they do not: the
questionnaire is a **third layer** beside the Task and the Task–Asset pair, and the app says so in
its storage, its screens and its payload.

## What the round adds

### 1. An add-on is its own thing

The entity is called an **add-on**. It is not a template and not an Asset:

| | Template | Add-on | Asset |
|---|---|---|---|
| What it is attached to | a Todo and a Task, by file kind | a Todo and a Task, whole | a Task, one file each |
| What it governs | buttons on files of some kinds | questions about the whole Task | — |
| Has a scope | yes, a conjunction of kind rules | **no** | — |
| Produces | per-file actions, per-passage marks | Task-level answers | the file itself |
| Position | wherever its buttons apply | **fixed after the Task's last Asset** | a page in the Task |

**An add-on is not modelled as an Asset.** `assets` in this codebase means *files the Task
presents*: they are paged through, counted, checked for missing sources, given a chip row and a
file Info sheet, referenced by PDF marks, and exported as `assets[]`. A questionnaire is not a file.
Making it a special Asset would make every one of those facts ask *except the questionnaire*, and
the exceptions would spread into the importer, the catalog, the queue, the export and the file
counts. The one apparent convenience — that it would page itself — is a single branch in one
screen.

**An add-on is not a row in `templates`.** It shares the shape that matters — a lineage with
immutable versions, an edit that appends rather than revises, a name that lives on the lineage — but
not the vocabulary: templates have scopes and buttons, add-ons have questions and no scope. Storing
both in one table would mean a nullable scope, a nullable button payload and a nullable question
payload, and every reader deciding which half of the row is real. The two share the Settings screen
and the versioning behaviour; they do not share a row.

**Names are kept apart everywhere.** `AddOnId`, `AddOnVersionRef`, `StoredAddOnVersion`,
`AddOnQuestion`, `addons`, `addon_versions`, `task_review_answers`. The word *template* in this
round never means an add-on. On the wire the object is `addOn`.

### 2. The questionnaire, at the end of the Task

A Task whose import carried an add-on has **one extra page after its last Asset**. The page is a
Task-level page, not a file page:

- Swiping left off the last Asset shows the questionnaire instead of leaving the Task.
- Swiping left off the questionnaire completes the Task and advances the queue, exactly as leaving
  the last Asset does today.
- Swiping right off the questionnaire returns to the last Asset.
- The navigator counts it as a page: a three-file Task with an add-on reads
  `1(1/4)`, `1(2/4)`, `1(3/4)`, `1(4/4)`.
- The completion checkbox is unchanged and remains a direct completion path. The questionnaire is
  **not mandatory**: a reviewer may tick the Task without answering anything, or swipe past it.
- A Task with no add-on has no extra page and behaves byte for byte as it does today.
- The page is browsable even when the Task is blocked from submission, but forward completion stays
  inert, like every other end of a blocked Task.

The page's **static frame is the existing one** — navigator, completion bar, dismissible bar with
Info. What the page adds is its content: the questions. There is no file-level chip row, because
there is no file on this page; the bar carries only **Info**, which lists the Task's stored answers.

**Three question types in v0.7.1**, and no others:

| Type | What the reviewer does | Stored value | On the wire |
|---|---|---|---|
| **Rating** | picks a score from 1 to 5 | `1` … `5` | number |
| **Yes / No** | picks one of two answers | `yes` / `no` | boolean |
| **Text** | types a free-form answer | the text, trimmed | string |

The questions are the user's. The round's own example is three questions:

1. *图片好看程度* — Rating.
2. *图片是否包含绿色* — Yes / No.
3. *有没有什么想说的话* — Text.

A fourth question, *这一组画属于生活类照片吗*, is the same Yes / No type and is how the scenario's
classification is expressed; the app does not ship a separate "category" type in v0.7.1.

**An answer is written when it is given, with no Save button.** Rating and Yes / No write on tap;
tapping the selected answer again clears it, so a mistaken tap is undoable. Text saves when the
field loses focus or Done is pressed, and a blank field clears the answer. Nothing on the page
announces a required field, because there are none.

**No add-on attributes exist in v0.7.1.** There is no start-of-Task position, no required flag, no
"ask only when complete". These are real future questions — the user named both — and the data
shape leaves room for them. The round does not implement them.

### 3. One add-on per Todo, stamped on every Task

**A Todo holds at most one add-on.** The import dialog gains a foldable section, **Add an add-on**,
drawn like **Add a template**: one row per add-on, a radio-like single choice, a **New add-on**
link, and a summary line that reads *None* until one is chosen. It appears on Create Tasks and on
Refresh Import, because both runs re-stamp every Task they touch.

- At most one, so the picker is a choice rather than a set. There is no scope to overlap and no
  first-match rule to explain.
- The Todo stores the chosen reference in `sources.addOn`; each imported Task stores the copy it was
  stamped with in `task_imports.addOn`. The format is one line, `addOnId \t version`, or empty.
- A Task imported before this round has `""` and therefore no questionnaire. No migration invents
  one.
- A List may hold Tasks from several Todos. Some Tasks have an add-on, some do not, and the queue
  shows the extra page only on those that do. Nothing is List-wide.
- Unticking the add-on on a refresh removes it from the Todo and from every Task that run touches.
  The answers already given stay stored and become hidden; they are not deleted.
- A refresh adopts the add-on's offered current version, exactly as it does for templates, and says
  so before confirming: answers to a question the new version removed are kept but no longer shown
  or sent; a question it added starts unanswered. A new question's answer is **not** required.

### 4. Where an answer lives

Answers live in a table keyed by the Task, not by an Asset:

```text
task_review_answers(taskId, questionId, kind, value,
                    authoredAddOnId, authoredAddOnVersion, createdAt, updatedAt)
primary key (taskId, questionId), foreign key taskId -> tasks(id) ON DELETE CASCADE
```

- **One row per question per Task.** A rating is one fact, not a version of one; re-answering
  replaces the row and updates `updatedAt`. There is no history of answers in this round, because
  the questionnaire records the current judgment rather than a conversation.
- **The row stores what was asked and who asked it.** `kind` is the question type at authoring
  time, and `authoredAddOnId` / `authoredAddOnVersion` are the version that offered the question.
  That is what lets an old answer still be explained after the add-on has moved on, and it is the
  same authored-reference rule PDF marks already follow.
- **The prompt is not copied into the row.** It lives in the add-on version, which is immutable, so
  editing a prompt changes what is displayed and sent, and removing a question hides its answer
  without rewriting it. The authored reference is what lets the Info sheet recover the prompt of a
  question the current version no longer offers.
- **Hidden, not deleted.** An answer is visible while the Task is still attached to **the add-on
  that asked it** and that add-on's current version offers a question with the same id **and the
  same type**. Removing the question, changing its type, removing the add-on, or attaching a
  different add-on hides the answer; restoring the same add-on, question id and type brings it
  back. Hiding is a reading of the rows, never a write.
- **The write path validates.** A tap is accepted only if the Task's attached version offers that
  question with that type and the value fits the type. A stale screen that submits a removed
  question writes nothing. Text is trimmed; blank text deletes the row, as does tapping a selected
  rating or Yes / No again.

### 5. The add-on editor

**Settings → Templates & Add-ons** is the existing Templates screen with both kinds in it, because
an add-on is authored the same way a template is: name it, give it content, confirm, and an edit
appends a version. The section is renamed but not split.

- The list shows templates and add-ons together, by name; an add-on's subtitle says
  *Add-on · 3 questions* where a template's says its scope and button count.
- **New** asks which kind to create, then asks for a name. A new add-on starts with one Rating
  question, *Overall rating*, so it is immediately attachable; an add-on with no questions would be
  a name with nothing behind it.
- An add-on's page edits its name and its questions: prompt text and type (Rating, Yes / No, Text),
  add and remove. **Update** appends a version when the questions changed, renames in place when
  only the name changed, and writes nothing when nothing changed. **Cancel** discards the draft.
- A name is required. Every question prompt is required and kept to one line; a blank prompt
  refuses to save, and the page says which row is blank. There is no delete for an add-on, for the
  same reason there is none for a template: Tasks reference it.
- Question order is the draft order and is not reorderable in v0.7.1; removing and adding appends
  at the end. Questions have opaque ids that are never shown.

The add-on's questions are encoded as one line per question, `questionId \t type \t prompt`, with
`questionsVersion = 1` beside the payload. A payload this build cannot read — an unknown version,
an unknown type, a duplicate id — makes the **whole version unreadable**, exactly as an unreadable
button payload makes a template version unreadable. Rendering the readable part of a questionnaire
would silently drop a question and leave its answer unexplained.

### 6. What an add-on exports

An add-on's answers are a **sibling of `assets`**, never inside it. The Task gains an `addOn`
object, written after `assets`:

```json
{
  "id": "task-…",
  "title": "Six drawings",
  "isCompleted": true,
  "templates": [ { "id": "…", "name": "Media control", "version": 1 } ],
  "assets": [ … ],
  "addOn": {
    "id": "…",
    "name": "Task review",
    "version": 2,
    "answers": [
      { "questionId": "…", "type": "rating", "prompt": "How good are these?", "value": 3 },
      { "questionId": "…", "type": "yes-no", "prompt": "Is there green?", "value": false },
      { "questionId": "…", "type": "text", "prompt": "Anything to say?", "value": "Felt good." }
    ]
  }
}
```

- **The body's `version` becomes 4 only when at least one Task carries an `addOn` object.** A round
  with no add-on answers says 3 if it carries a mark and 2 otherwise, and is byte for byte what
  v0.7.0 sent. A round that carries both marks and add-ons says 4; 4 is a superset, not a
  combination code.
- The key is written **only when at least one answer is visible**. A Task that has an add-on but
  no answers exports nothing for it, and its body is unchanged. This is the same rule `marks` uses.
- Answers appear in **question order**, not in answer order, so the array reads as the
  questionnaire does and is stable across deliveries.
- Only **visible** answers are sent: the question must still be offered by the version that governs
  the Task now, as the same type. A hidden answer is omitted, never sent with a stale prompt.
- The `prompt` is the current version's text. The `type` is the current question's key. The `value`
  is typed: number for `rating`, boolean for `yes-no`, string for `text`.
- `templates[]` stays exactly what it is — the file templates attached to the Task. The add-on is
  **not** a template entry and does not appear there.
- The txt method writes the same body, so a round with answers is a version 4 file; History shows
  both without changes.

### 7. The Info sheet

The add-on is a Task-level fact, so its answers belong in the **Task's** Info sheet, which is
reachable on every page of the Task. The sheet gains an **Add-on** section: the add-on's name and
version, then each stored answer with its prompt and value.

Answers the current version no longer offers are listed under the same section as
*no longer asked*, with their stored value and, when the authored version can still be read, the
prompt they were given. This is the only surface that names a hidden answer; the page itself shows
only current questions. It is the same rule a detached PDF mark follows.

There is no Save or Share for the add-on section itself: the file offers belong to a file, and on
the add-on page the sheet is opened with no file, so those offers are absent rather than pointed at
the wrong Asset.

## Storage

Schema **29**. The migration adds three tables and two columns and changes no existing row's
meaning:

- `addons(id TEXT PRIMARY KEY, name TEXT NOT NULL, createdAt INTEGER NOT NULL)`
- `addon_versions(addOnId TEXT, version INTEGER, questions TEXT, questionsVersion INTEGER,
  createdAt INTEGER, PRIMARY KEY(addOnId, version), FOREIGN KEY addOnId → addons(id) CASCADE)`
- `task_review_answers(...)` as in §4, cascading from `tasks`
- `sources.addOn TEXT NOT NULL DEFAULT ''`
- `task_imports.addOn TEXT NOT NULL DEFAULT ''`

`MIGRATION_28_29` creates the tables and adds the columns; every existing row reads empty, so no
Todo acquires an add-on and no Task acquires a page. Fresh installs create the same schema through
Room. `29.json` is committed; `27.json` and `28.json` do not change.

## Implementation notes and deviations

**The model, the encoding, the storage and the wire are as written above.** What follows is where the
built branch differs from `v0.7.1-plan.md`, and what the device walk changed. The first four are
test-shape or verification changes; the rest are what the walk found — three defects this branch now
fixes, and one promise the editor could not keep until it gained a way to keep it. The affected pages
under `docs/` describe the shipped behaviour.

- **No Compose instrumentation tests were added.** The plan named `AddOnSettingsTest` and
  `AddOnReviewTest`; this repository has no Compose UI-test harness (its `androidTest` sources are
  the PDF renderer spikes and their fixtures), and adding one was not part of the round. The same
  claims are pinned at the levels the suite does have — `AddOnDraftTest` and `AddOnStoreTest` for the
  editor and its versions, `ReviewPageTest` for the page model, `AddOnAnswerWriteTest` for the writes,
  `AddOnInfoTest` for the sheet, and the acceptance walk below for the surface itself.
- **`AddOnAnswerWriteTest` replaces the plan's `AddOnAnswerDaoTest`.** The write path's validation —
  the attached version offers the question, the value fits the type, a blank text clears — lives in
  `ListsViewModel`, not in the DAO, so the test drives the ViewModel. The DAO's own insert-or-replace
  preserving `createdAt` is still what those writes assert.
- **`AddOnInfoTest` is new.** The plan folded the Info section into the instrumentation test; the
  mapping from resolver plus stored answers to sheet rows (including the authored prompt of a hidden
  answer) is pure and is pinned on the JVM instead.
- **Migration fixtures learned schema 29.** `subtractV29Additions()` rebuilds `sources` and
  `task_imports` without the two `addOn` columns and drops the three tables;
  `subtractV28Additions()` calls it first. Every migration chain registers `MIGRATION_28_29`, and
  `MigrationV28ToV29Test` asserts the tables and columns, that existing rows read `""`, both
  cascades, and that a pre-existing Task gains no answers.
- **The add-on picker is not part of the dialog's gate**, exactly as specified: it is drawn after the
  Review section, defaults to *None*, and a Create whose only missing answer is an add-on proceeds.
- **A queue built from catalog rows carried no add-on.** The device walk found it first: in Quick
  Review, swiping left off the last Asset went straight to the next Task, while the same Task opened
  from a List drew its page. The catalog projection never selected `task_imports.addOn`, so
  `CatalogRow`, the queues built from it and every `ReviewItem` they made were pageless. The column is
  now selected, carried on `CatalogProjection` and `CatalogRow`, and copied onto the item in
  `reviewItemFor`. `QuickReviewQueueTest` and `ReviewItemAddOnTest` drive the whole path; the List
  test alone could not have caught it, because `observeDetail` reads the column separately.
- **The editor's draft decoder is lenient.** A draft is re-written and re-read on every keystroke, so
  strict decoding rejected the whole version while a prompt was half-typed — every edit after the
  first keystroke would have started from an empty questionnaire. `decodeAddOnDraftQuestions` keeps
  the lines it can read; the strict decoder still rejects a whole version on save, so what is stored
  is never lenient.
- **A text answer commits when the page is disposed, as well as on Done and on focus loss.** The plan
  said answers write without a Save button and did not say what leaving the page should do; the
  system Back only hides the keyboard, so a `DisposableEffect` commits the field — or clears it, when
  blank — as the page goes. The walk confirmed the row appears when the user swipes away and the row
  is deleted when a blanked field is left.
- **The editor gained a Removed questions list.** The plan's checklist promised that removing and
  re-adding a question hides and restores its answer, and the page already printed that promise, but
  *Add question* mints a fresh id, so the built editor had no way to keep it. `restorableAddOnQuestions`
  reads every earlier version of the lineage and offers questions the draft no longer holds back,
  with their original ids and their newest earlier wording; restoring appends the question to the
  draft, and Update writes it like any other change. The walk restored the Yes / No removed in
  version 3 and got the answer given under version 2 back under version 4 (below).

### Acceptance walk

**Device:** OnePlus PGP110, API 33, serial `edbb363e`. The branch was installed over the existing
app with `adb install -r`; logcat showed `28 -> 29` and no `SQLiteException` or `AndroidRuntime`
entry. Every write below was read back from the device's database, pulled with `adb exec-out run-as`
**together with its `-wal` and `-shm`** and queried by `sqlite3`.

- **The editor.** Settings is an index and **Templates &amp; Add-ons** reads *2 templates · 1
  add-on*; the page lists *Media Asset Control* (v1), *PDF Marks* (v2) and the add-on. The add-on was
  created with all three types — a rating (*Overall rating*), a Yes / No (*Contains green*) and a
  text question — and edited twice: cutting the questionnaire down to the rating wrote version 3, and
  renaming it (to *Task review A* and back) changed no version at all, while the name's helper says it
  would not. A blank name, a blank prompt and an empty question list are refused on save; that rule is
  pinned by `AddOnDraftTest` rather than walked again here.
- **Attaching.** Both Create Tasks and Refresh Import show an **Add an add-on** section, closed with a
  *None* summary; opening it offers *None* plus *Task review · Add-on · 1 question*, and choosing one
  closes it with that summary. At most one is chosen, and Create proceeds with *None*, because nothing
  here is required.
- **The page.** The one-Asset Task imported with the add-on read `1(1/2)/6` on its Asset — the `(1/2)`
  says the Task has two pages — and `1(2/2)/6` on the questionnaire, which carried the page slot
  label **Add-on** and the helper line *Answers are kept as you go · nothing here is required*.
  Swiping left again advanced to the next Task; right returned to the Asset, and an add-on-free Task
  showed no page level at all.
- **Answers.** Rating 4 / 5, then No, then a text note all wrote with no Save button. The database
  held `rating|4`, `yes-no|no` and `text|third look` under the Task, authored version 2. Re-tapping
  the score cleared it, re-tapping *No* cleared it, and blanking the text and leaving the page deleted
  the row. Leaving and reopening the Task showed the answers again. A text answer commits on **Done**,
  on focus loss, or when the page is left — the system Back only hides the keyboard, so a Back that is
  not followed by leaving the page commits nothing.
- **Info.** The sheet read **Task review · version 2 · 3 answers** and listed `4 / 5`, `No` and
  `third look` in question order.
- **A mixed List.** A List holding one Task from the add-on Todo and one from an add-on-free Todo read
  `1(1/2)/2` on the first and `2(1/6)/2` on the second. The add-on-free Task has no page level at all,
  and swiping off its last Asset moves to the next Task.
- **Refresh and visibility.** Refresh Import after the version-3 edit stamped every Task `@3` and kept
  the stored rows (`rating|4|2`, `yes-no|no|2`). The page then offered only *Overall rating*, and Info
  said **version 3 · 1 answer · 1 no longer asked**, showing the stored `No` as an answer no longer
  asked. Unticking the add-on cleared every stamp, kept every row, and Quick Review dropped to
  `1 / 6`; re-ticking restored the stamps, the page and the rating of 4.
- **Restoring a removed question.** The editor's **Removed questions** list offered *Contains green*
  (Yes / No) and *Anything to say* (Text) back. Restoring the Yes / No kept its id
  (`cb33b524…`) and Update wrote version 4. Refresh Import stamped the Tasks `@4`; the page then
  showed *Contains green* again, and Info read **Task review · version 4 · 1 answer** with `No` —
  the answer given under version 2 came back rather than being asked again.
- **Export.** The txt method wrote `"version":4` with `addOn` **after** `assets`:
  `{"questionId":"f4158444-…","type":"rating","prompt":"Overall rating","value":4}`. The hidden
  Yes / No answer was absent, and the other Tasks in the same round carried no `addOn` and kept
  version 3. A round of Tasks with no add-on at all stayed at version 3. `docs/exports.md` matches
  the body observed on the device.

## Not in this round

- **Position attributes** — *at the start of a Task*, *only at the end*, *only when complete*.
  The position is fixed after the last Asset.
- **A required flag**, per question or per add-on.
- **More than one add-on per Todo**, or an add-on attached to a List.
- **A category/choice question type beyond Yes / No.** The scenario's classification is a Yes / No
  question in this round.
- **Question reordering**, conditional questions, branching, and question-level help text.
- **Answer history.** A re-answer replaces the row; there is no log of earlier answers.
- **Deleting an add-on or a question lineage.** Questions may be removed from a new version; the
  lineage stays, and old answers stay readable.
- **An add-on page in the read-only List viewer.** This round's page belongs to the review surface.
  The stored answers are visible there through Info only where that surface already shows Info.
- **Add-ons on manual items.** A manual Task has no import and therefore no attachment.
- **Any new export method or delivery behaviour.** The add-on rides in the existing body.

## Questions still open

- Whether a future add-on should be able to say *this question is required before the Task can be
  completed*. The storage supports it; the completion path deliberately does not implement it.
- Whether a Task should be allowed more than one add-on (for example an intake questionnaire and an
  exit questionnaire). One is the round's scope; several would need a position/ordering model,
  which is deferred with the position attributes.
- Whether answers should have an edit history. The current table records only the latest answer,
  and `updatedAt` is the only trace of an earlier one.
