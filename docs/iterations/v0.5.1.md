# Listea v0.5.1 — The template's instance belongs to the file

> **Status:** Iteration, implemented. **Shipped.** Acceptance #1–#9 were waived by the maintainer
> on 2026-09-18, who had already exercised part of the list while using the release; the defects
> that use did find — the List that lost its rows, and the dissolved history that carried no marks —
> are recorded below rather than in a separate review document. The second is repaired in
> [v0.5.2](v0.5.2.md).
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.5.0 (the template; the three bands)
> **Supersedes:** [v0.5.0](v0.5.0.md) acceptance #5, second sentence — "The video's tag is
> still set on the Task"
> **Superseded in part by:** [v0.5.2](v0.5.2.md) — the known defect below, which this release shipped
> on purpose and that one repairs

## The change in one paragraph

v0.5.0 made the **lookup** per file and left the **record** per Task. So a Task's marks were one
set, shared by every file it presents: tagging the first photograph of `Camera` tagged the second,
because both were reading the same row. v0.5.1 moves the record down to the **Task–Asset pair**.
Each file a Task presents carries its own instance of the template, resolved by that Task's own
control and that file's own kind.

## Why

### The bug, as reported

> 路径：todo->demo->quick review->camera
>
> 我在 camera 里第一张图片打上的 tag：p2,p5 被继承到了第二张图片，这个继承不仅是显示上的继承，
> 还是 info 里 actions 的继承

`Camera` is one folder-as-Task Task holding three photographs. Ticking `p2` and `p5` on the first
photograph ticked them on the second — in the chip row, and in the Info sheet.

### Where it comes from

Not a slip in the wiring; the wiring is faithful to what v0.5.0 said. The record is a column on a
row whose primary key is the Task:

| Step | Where | What it says |
|---|---|---|
| The chip is tapped | `ReviewScreen.kt:658` | `viewModel.setItemAction(item, action, enabled)` — the **item**, never the page |
| The item is written to | `ListsViewModel.kt` `setItemAction` | `dao.setTaskAction(item.taskId, action, enabled, now())` |
| The Task is the key | `TaskEntities.kt:141` | `@PrimaryKey val taskId: String` — one `task_state` row per Task |
| Every page reads it | `ReviewScreen.kt:585` | `settings.controlFor(item.assetControls, kind)` — the *control* is per kind, the *record* is not |
| Both surfaces draw it | `MediaUi.kt:705`, `MediaUi.kt:781` | `action.isSetOn(item.decisions)` |

One row per Task, read by every page of it. **v0.5.0 changed what was offered per file, and left
what was recorded per Task** — and acceptance #5 stated that as the intended behaviour rather than
noticing it.

It is also older than v0.5.0: the record has been Task-level since v0.2's `task_state` was
introduced, because until v0.3 a Task had exactly one Asset and the two were indistinguishable.
Multi-Asset Tasks are what made them distinguishable.

### The model the record should have

The chef from [v0.5.0](v0.5.0.md#the-chef-standing-in-the-market), at the end of the round he
started there. He goes to the East Market with two intentions over the same eggs — one for the
tomato dish, one for the pepper dish — and the two Todos load **different templates for the eggs**,
so the same file is written down twice and differently, once per intention. Then he goes to the
West Market with one intention that reaches two things, and writes down something different about
each.

| Todo | Task | File | Recorded |
|---|---|---|---|
| 东市买西红柿炒蛋鸡蛋的材料 | 买鸡蛋 | 鸡蛋 | `cust1, cust2` |
| 东市买辣椒炒蛋鸡蛋的材料 | 买鸡蛋 | 鸡蛋 | `cust3, cust4, cust5` |
| 西市买辣椒炒蛋和西红柿炒鸡蛋的材料 | 买辣椒和西红柿 | 西红柿 | `cust6` |
| 西市买辣椒炒蛋和西红柿炒鸡蛋的材料 | 买辣椒和西红柿 | 辣椒 | `cust7, cust8` |

The first two rows are the record being per **intention**: one file, two Tasks, two answers. The
last two are the record being per **file**: one Task, two files, two answers. The reported bug is
the third case in the same shape — one Task, three photographs, and the answer of one applied to
the others.

> **The unit is the Task–Asset pair, and what is stored on it is the template's instance.**

`Camera`'s three photographs are the same table with three rows.

## The rule

Everything follows from which band a value lives in:

| Band | Depends on | Recorded at |
|---|---|---|
| **Navigation + task control** — name, position, checkbox | the Task, and nothing else | **the Task** |
| **Asset control** — `★` and the configured tags | intention × file kind | **the Task–Asset pair** |
| **Media control** — transport, zoom, page | the file kind, and nothing else | nothing |

Or, in one line:

> **Everything the template carries is recorded per Task–Asset pair. Everything else stays per
> Task.**

`★` Favourite is carried by the template — `Templates.kt`'s built-in declares it, and
[v0.5.0](v0.5.0.md#the-built-in-definition) put it there deliberately so a future control may omit
it. So `★` is recorded per pair, exactly like the tags beside it. Completion is the outer band's
and is not the template's, so completion stays on the Task: checking `Camera` still completes the
Task, not three files.

### The record still belongs to the Task

This is the part that matters for the architecture, and it is why the new row is named the way it
is. [ARCHITECTURE.md:157](../ARCHITECTURE.md) says an Asset:

> does not own Task completion, review responses, Task navigation, webhook configuration, or
> downstream workflow rules.

and [ARCHITECTURE.md:183](../ARCHITECTURE.md):

> Current state belongs to the Task, not to an Asset and not to a List membership.

**Neither is overturned, and no amendment to `ARCHITECTURE.md` is needed.** The new record is the
Task's own current state — it is *about* one of the Task's Assets, and it is *owned* by the Task.
The Asset is the key the state is filed under, not the object that holds it. That is visible in
three places:

- the table is `task_asset_state`, not `asset_state`;
- it is written by the same funnel family as `task_state`, addressed by Task, and its writes go
  through the Task's own state row's transaction;
- deleting the Asset takes the record with it — the pair has nothing left to be about — which is
  the same reason a Task's state cascades from the Task.

The alternative — decision columns on `assets` — reads more simply for a moment and is rejected for
the reason [ListsDao.kt:1552](../../app/src/main/java/com/example/listea/data/ListsDao.kt) gives:

> `runImport` is the sole writer of `tasks`, `task_state` and `assets`

An `assets` row describes a file: its locators, its measurements, its presence. Putting a person's
judgment in it would make the import run the co-owner of a column it must never write, and would
make "the file was re-measured" and "somebody changed their mind" the same kind of event.

## What a user sees

**Paging inside one Task now shows each file's own record.** On `Camera`, tick `p2` and `p5` on the
first photograph, page forward: the second photograph's row is empty. Page back: still ticked. The
same on the `Whatsapp` Task, whose three files are two photographs and a video — three records,
each under its own kind's control.

**The badge row under the Task's name becomes the current file's.** It was "what the Task is marked
with"; it is now "what this file is marked with", resolved over every kind the Task is under so
that an id set under a configuration the current kind no longer defines is still nameable. It is
the same record the chip row draws, named more widely — which is what
[ItemActionTags](v0.5.0-plan.md) already is for the List's own rows, where no file is on screen at
all.

**The Info sheet follows the file on screen**, as its `actions` rows always claimed to.

**The checkbox is unchanged.** It completes the Task; on `Camera` it still completes all three
files' Task at once, and a review submission is still one submission about the Task.

**The webhook is unchanged in shape.** One entry per Task, as
[Webhook.kt:327](../../app/src/main/java/com/example/listea/Webhook.kt) documents, with its `actions`
array carrying the union of the Task's pairs — the same rule by which the payload has always been
able to name a tag set on a file that is not the one on screen. A Task with three files submits one
judgment carrying all three records, because that is what a Task-level payload is for.

**A Task with no Asset loses the middle band.** A legacy manual item has no file, so it has no
pair, so there is nowhere for the template's instance to be stored and nothing for the band to
record. It keeps its checkbox and its completion. See [Out of scope](#out-of-scope) — this is a
deliberate, flagged consequence rather than an oversight, and it is the one user-visible loss this
release makes.

## Acceptance

1. Open `Demo` → `Camera` → review. Tick `p2` and `p5` on the first photograph.
2. Page forward to the second photograph. **Nothing is ticked.** The Info sheet lists no actions.
3. Page back to the first. `p2` and `p5` are still ticked, and the Info sheet lists them.
4. Tick `p3` on the second photograph, page to the third: nothing ticked. Page back: `p3` only, on
   the second.
5. Check the completion box on any page. The Task is complete, and **stays complete** as you page
   through all three files — the checkbox is the Task's and does not move per file.
6. Open `Whatsapp` (one Task, two photographs and a video). Tick a video tag on the `.mp4`, page
   back to a photograph: the video's tag is **not** on the photograph's badge row or in its Info
   sheet, and it **is** still on the video when you page forward to it again.
7. Submit the `Whatsapp` Task. The webhook's single entry for the Task carries `actions` for all
   three files' records together.
8. **A Task imported before this release behaves exactly as it did.** The migration copies each
   Asset's record from its Task's state, so every file of every existing Task keeps the marks it
   was showing.
9. **The same file under two Todos keeps two records.** Tag a shared file through one Todo, open
   the other Todo's Task over the same file: the tag is not there.

## The second bug, reported during acceptance

> 我现在在 quick review 可以正确记录每个 asset 单独的 actions。但是当我用这些 review 过的 task
> 构建 list 的时候，这些属性似乎全都又丢失了

Reported against the build that fixed the first bug, and a genuine regression of this release rather
than a survivor of it. Quick Review recorded per file correctly; the List built from those Tasks
showed every chip unticked.

**The two answers to "what does this Task carry".** A List asks that question in two places, and
v0.5.1 gave each its own fold over the pairs:

- **The membership row**, which has no file on screen, so one row must answer for all of them —
  folded in SQL by `observeItems` / `getItems` into `MAX(tas.isFavorite)` and
  `GROUP_CONCAT(tas.customActions)`.
- **The item the screens draw**, which does have the files — folded in Kotlin by
  `ReviewItem.taskDecisions = unionOf(assets.map { it.decisions })`.

Both are correct. The defect was that only the first was ever fed. `ListsViewModel.observeDetail` —
which `ListDetailScreen` and the List's `ReviewScreen` both read — resolved each Task's files through
`observeAssetsForList`, the bare `assets` rows, and never through `observeAssetStatesForList`, the
query written for exactly this job. **That query had no call site anywhere in the app.** So every
`ReviewAsset` arrived with no record attached, took `toReviewAsset`'s deliberate *nothing recorded*
default, and the fold over nothing was nothing. The folded SQL answer was right the whole time and
simply was not the one on screen.

This is the same failure the earlier defect list describes — a read left on the wrong side of the
change — and it is worth noticing *why the tests missed it*: every per-pair test asserted through the
DAO, where the question can only be asked one way, while the defect lived in the wiring between the
two answers. It is now asserted through the ViewModel, in `ListDetailRecordTest`, and the test was
checked against the unfixed code before being kept.

It also had a second face that no screen would have shown: `submitItemReview` reads the same
`item.taskDecisions`, so a judgment submitted from a List's review surface would have recorded an
empty `favorite` and no actions, into `review_events` and into the payload beside it. Nothing was
delivered during the window, so no receiver was told anything wrong.

**Verified on the device** against the data that was reported, not only in tests. The List holds
`Wechat`, `Camera` and `Whatsapp`; the row now reads `★` for the first, `★ C1 C2` for the second and
`★ C1 C5` for the third — each of them the union of that Task's own pairs, taken from the rows the
Quick Review session wrote.

## Known defect: a dissolved history no longer carries the marks

Not deferred — **shipped broken, and recorded here rather than left to be found.** Dissolution and
recovery read and write `task_state`'s `isFavorite` / `customActions`, the two columns this release
retired. So a Todo dissolved after the upgrade snapshots the frozen pre-migration value rather than
what is marked now, and a recovery writes its answer into a column no surface reads: the marks a user
asked to keep are gone while the picker reports them carried. Completion is unaffected — that column
stayed live.

It is stated at length, with the reason it needs a schema step of its own rather than a two-line
repoint, in [the plan](v0.5.1-plan.md) §9. It is out of this release's acceptance on purpose: the
camera and the Todo are what v0.5.1 is answerable for, and dissolve → recover is the next release's
first item.

**How it will be repaired is already decided** — see §9's *the rule, now made*: one row per Task, with
the pair records kept as an encoded payload rather than as more columns. The point of deciding it now
is that the repair must not add a second model of the record to maintain, which is what the defect
itself is made of.

**Repaired in [v0.5.2](v0.5.2.md)**, which is that decided shape built: the two retired columns come
off `dissolved_task_state` in a schema step (21 → 22), a snapshot writes each of a Task's files as a
line of an encoded payload, and a recovery matches those lines onto the new import's Assets by path
and writes each through the pair's existing funnel. Nothing in *this* release changes because of it —
the section above stands as the record of a release that shipped knowing what it was leaving behind.

## Out of scope

- **Typed fields, the other two bands, splitting `jpg` from `png`, making an `OTHER` file
  reviewable, and non-kind-keyed templates** — all still deferred, on [v0.5.0](v0.5.0.md)'s terms.
- **Per-pair completion.** The outer band's master is the Task, so a Task is complete or it is not.
  A separate question — "this Task is complete in List A but incomplete in List B" — is already
  reserved by [ARCHITECTURE.md:177](../ARCHITECTURE.md) and is not this.
- **Re-recording history per pair.** `review_events` stays Task-level and append-only. A submission
  is one judgment about one Task; the records it carried are snapshotted into the response, and
  which pair each was set on is not reconstructed afterwards.
- **Moving the middle band for a Task with no Asset.** Flagged above. If manual items turn out to
  matter, the fix is to give them an Asset, not to give the band a second home.
