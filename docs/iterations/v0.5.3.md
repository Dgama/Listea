# Listea v0.5.3 — What the acceptance found

> **Status:** Iteration, implemented. **Not yet shipped.** Both defects are fixed and pinned by
> tests that were watched going red first; the repair was run against a copy of the maintainer's own
> pulled database. The device pass is outstanding — see [Verification](#verification).
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.5.2 (the per-file history)
> **Supersedes:** nothing, and no architecture is touched. Both defects are code that disagrees with
> what [core-concepts.md](../core-concepts.md) and [v0.3.0](v0.3.0.md) already say.

## The change in one paragraph

Two defects, found by the maintainer on 2026-09-18 while using the v0.5.2 build as a new user
rather than against an acceptance list. **A Todo whose scope holds only folders offers no way into
selection**, so the folders it is made of cannot be picked — the screen hid Select by the same rule
it correctly hides Quick Review by, and the rule is only correct for one of them. **A List built
from Tasks that are already done is not recorded as complete**, because the four writes that change
a List's membership do not all re-answer the question "are all of this List's Tasks done". Neither
is a design question; both are the code having one rule in one place and not in the other.

## 1. The Select that was not offered

### As reported

> 对于 file as task 的 demo 这个 todo。我选择了保留了文件树结构，所以点击 todo card 进去以后是有
> 三个文件夹的。这里，我本来是想 select，然后点击每个 folder，把文件夹内任务都选中然后 create
> list。发现不行。这个界面没有 select 选项（没有 quick review 是正确的，因为下面没有完整 task）。
> 同样的功能在 list 里单独 create list 是可以做到的（即选文件夹）。请查看这是 bug 还是刻意的
> 设计。

### It is a bug, and the documents say so

`CatalogScreen`'s top bar offers `Select` behind `view.tasks.isNotEmpty()`
(`app/src/main/java/com/example/listea/CatalogScreen.kt:221`). At the root of a Todo that kept its
folder tree, `catalogAtScope` returns `tasks = emptyList()` and `scopes = [three folders]`, so the
button is never drawn and there is no way into selection mode at all.

The gate is right for the button above it and wrong for this one. Quick Review queues the Tasks that
lie **exactly** here and does not descend, so at a folders-only root a round would open on an empty
queue — [core-concepts.md:260](../core-concepts.md) says so in as many words. A *selection*, by
contrast, is meant to reach all the way down:

> A **List** is a persistent queue, made from **Tasks you pick**. Open a Todo and tap **Select**. The
> catalog becomes a selection surface; tick the Tasks to include — **a folder's box takes the whole
> folder** — and tap **Create List** in the bar along the bottom.
> — [core-concepts.md:195](../core-concepts.md)

and the acceptance criterion this was written against:

> Inside a Todo, **Select → Create List** builds a List from the Tasks ticked, including folders as
> selection units.
> — [v0.3.0.md:520](v0.3.0.md)

A folder is a selection unit. A scope made of folders is therefore the one place where a selection
is *most* useful, and it is the one place the button is missing. The reason it works from the Lists
tab is not a different rule: **New list** asks which Todo and then opens this same screen with
`startSelecting = true` (`MainActivity.kt:215`), so the button is drawn because it is already on.

### The rule

> **Select is offered wherever a selection can be made** — a Task here, or a folder below — and
> Quick Review keeps its own, narrower rule.

The two questions look alike and are not. "Is there something here to review" is about this scope
alone. "Is there something here to pick" includes everything under it, because a folder's checkbox
takes the whole folder.

## 2. The List that was complete and said so in one place only

### As reported

> 现在有一个 list 已经是全部完成了，但 list 没有显示在 completed 的 list 里，而是显示在 in
> progress。

### Two answers to one question

`ListSummary` carries both:

| Field | Source | Used for |
|---|---|---|
| `completedItems` / `totalItems` | counted live from `list_items` joined to `task_state` | the row's `"3 / 3"` label |
| `isComplete` | the stored `lists.completedAt` column | **which section the row is drawn in** |

`ListFilter.Completed` accepts `summary.isComplete`, which is `completedAt != null`
(`ListsScreen.kt:366`, `ListEntities.kt:909`). So a List can read `3 / 3` and sit under *In
progress*, which is exactly what was seen: the label was computed from the rows, the section was
read from a flag, and nothing had updated the flag.

### Why the flag was stale

`refreshCompletion` is the one thing that answers it:

```kotlin
if (itemCount(listId) > 0 && unfinishedItemCount(listId) == 0) markCompleted(listId, now)
else clearCompleted(listId)
```

It has to run whenever the question's answer can change — which is whenever a membership moves, or
a member's Task changes completion. Eight writes can do that, and **four of them call it**:

| Write | Calls `refreshCompletion` |
|---|---|
| `setTaskCompleted` / `submitReview` — via `refreshAffected` | yes |
| `removeItem` | yes |
| `removeMissingSourceItems` | yes |
| `applyReconcile` | yes |
| **`createListFromTasks`** | **no** |
| **`addTasksToList`** | **no** |
| **`deleteTodo`** | **no** |
| **`dropTask`** | **no** |

The four that do not are one defect wearing four hats: a List whose membership just changed is left
carrying the answer to a question nobody re-asked.

Both of the reported symptoms come out of the first two. The maintainer dissolved a Todo, re-imported
it — which **restores the Tasks' completion from the history** — and built a List from Tasks that
were already done. `createListFromTasks` inserted the memberships and stopped. Every row reads
`N / N`; `completedAt` is `NULL`; the List is filed under *In progress* and stays there until some
later write happens to refresh it.

The other two are the same fault reached from the other end, and they are worse for being invisible:
dissolving a Todo removes its Tasks' memberships, so a List that was waiting on one unfinished Task
can become fully complete the moment that Task is deleted — and nothing re-asks. The reverse holds
too: a completed List can be emptied by a dissolution and go on claiming completion over no rows.

### The rule

> **Every write that changes a List's membership, or the completion of a member, ends by calling
> `refreshCompletion`.**

The consequence for an emptied List is deliberate and is not new: `refreshCompletion` already
refuses to call a List with no members complete, and `applyReconcile` and `removeMissingSourceItems`
already put Lists into that state. A List that lost everything shows `0 / 0` under *In progress*
beside the note saying what it lost, which is the honest reading — an empty List is not a finished
one.

### The Lists that are already wrong

Four call sites fix the bug. They do not fix the databases it has already been through — a stored
flag stays wrong until something writes it again, and the List this was reported from reads `3 / 3`
with `completedAt` null **on the reporter's own device**, checked rather than inferred.

So the release carries **one data-only schema step, 22 → 23**, which repairs every List: one with
rows and none unfinished is completed, one with no rows or any unfinished row is un-completed. Those
two statements are `refreshCompletion` written as SQL, because a migration cannot call a DAO, and
they mirror the joins behind `itemCount` and `unfinishedItemCount` so a reader can diff them.

**No table changes shape.** `23.json` is `22.json` with a different version number in it, which the
build exports and the test suite asserts. The step costs a version number and nothing structural —
which matters, because [v0.5.1](v0.5.1.md) and [v0.5.2](v0.5.2.md) both had to rebuild a table and
this does not.

A repaired row is stamped with the upgrade time. The moment it really became complete was never
written down, and `completedAt` is not only read for null-ness — it is sent in webhook payloads — so
an invented earlier value would be a worse answer than an honest "as of now". Rows that were already
right are not touched at all, which is what keeps a real completion time intact.

## 3. Two things confirmed, and recorded

Neither is a change. Both were asked about during the same session and answered *yes, as intended*,
and they are written down here because the answer is a rule rather than an accident.

### A restored mark follows the action's **id**, not its name

> 假设原始的 template 是 C1：a, 新的是 C1：b, 那我 re-import 是还原 C1，但记录 b，还是还原 C1，但
> 记录 a? 按道理应该是根据 action name 匹配？比如原来 template 是 C1：a, 新模板是 C2：a, 那恢复后
> 应当记录 C2 被选择？

A record holds `ItemAction`s, and a `CustomAction`'s **id** is the only part of it an item ever
holds — `displayName` and `webhookValue` are resolved at draw time and stored nowhere. So:

| | Result |
|---|---|
| The same action **renamed** (same id, new name) | restored, and shown under the **new** name |
| The old action **deleted** and a new one given the same name | not shown — a different id, which this configuration does not define |
| The same name in a **different** action | not shown — a name is not an identity |

Matching by name is the thing the storage deliberately refuses. A display name is not unique and is
the one part of an action expected to change; matching on it would make renaming an action silently
re-label every record made under it, and would let a name that moved to another action drag history
with it. `★` has no id at all — it is carried by the definition — so it comes back whatever the tags
became.

This is now pinned by `app/src/test/java/com/example/listea/TemplateMatchAfterRecoveryTest.kt`,
whose middle case asserts the discriminating thing: the label matches and the row is still unticked.

### A file-as-Task re-import inherits nothing from a folder-as-Task history

> file-as-task 的新 todo，即使选择了从历史恢复，但由于 task 语义上已经改变，根据数据始于
> task-asset pair 的原则，这是一次没有任何可继承的信息。相当于与历史无关。我认为现阶段是合理的
> 处理。

Agreed, and it is what the code does rather than something it should stop doing. A recovery matches
**Tasks**: a dissolved row names the Task it was about by its `groupPath`, and a folder-as-Task Task
is the folder (`photos/alice`) where a file-as-Task Task is the file (`photos/alice/a.jpg`). The two
never name the same thing, so no row matches and the picker's offer is honestly declined. The
completion and the per-file records a folder-as-Task history does give back go to a **folder-as-Task**
re-import, which is the shape they were recorded in.

## What a user sees

1. Open a Todo whose top level is folders. **Select** is offered. Turn it on, tick a folder, and
   *Create List* takes every Task under it — the same answer the Lists tab's **New list** gives.
2. Build a List from Tasks that are already done. It is filed under **Completed**, and it says so
   on the row.
3. Dissolve a Todo that a List was waiting on, so that List's last unfinished row goes with it. The
   List moves to **Completed** on its own.
4. **Upgrade**, and a List that was already in the state the defect left behind — finished, filed
   under *In progress* — is filed correctly without anything being tapped.
5. Nothing else moves. Quick Review is still offered exactly where it was, and a selection is still
   the only way to make a List.

## Acceptance

1. Import a folder with **keep the folder tree**, so the Todo's root is folders. Open it. **Select
   is there.**
2. Turn it on, tick two folders, *Create List*. The List holds every Task under both folders.
3. Complete every Task of that List. The Lists tab files it under **Completed**, with `N / N ✓`.
4. Build a second List from a Todo whose Tasks are **already** complete. It is also under
   **Completed** — this is the reported defect and it must not need a tap to settle.
5. Dissolve the Todo behind a partially complete List, taking the last unfinished Task with it. The
   List moves to **Completed**, and carries the note saying what it lost.
6. Dissolve a Todo behind a List that was complete. The List reads `0 / 0` and sits under *In
   progress* — empty is not finished.
7. Open a Todo whose root holds Tasks as well as folders: **Select** is where it always was, and so
   is Quick Review. Open a Todo with neither (an empty folder): neither button.
8. **Upgrade over the database that has the defect in it**, rather than over a fresh one. A List
   reading `3 / 3` under *In progress* is under **Completed** afterwards, and a List still holding
   an unfinished Task has not moved.

## Verification

**Done.** The two defects were reproduced in unit tests before they were fixed — the reported List
defect goes red in four of `data/ListCompletionTest.kt`'s five cases against the old code — and the
full suite is green at **678 tests across 75 classes, 0 failures** (660/72 before this release, the
+18 being this release's new cases). The migration's tests were checked for non-vacuity by mutation:
with `MIGRATION_22_23`'s body short-circuited, exactly the three cases that need a real repair fail
and the three guards stay green. `23.json` was diffed against `22.json` and differs only in the
version number, which is what `the step changes no table` asserts from the other side.

**The repair was run against the reporter's own data, off the device.** The acceptance database was
pulled and the two statements extracted from `ListeaDatabase.kt` by regex — so what ran cannot drift
from what ships — and applied to a copy: `list 2 'Demo' 3/3 completedAt=None` became
`completedAt=1789703766116`, `list 3 'Demo' 0/6` was left alone, and `user_version` went 22 → 23.
That is acceptance #8, on the exact rows the defect left behind.

**Not done: the device pass.** The phone dropped off `adb` during the install and did not come back
across eight reconnect attempts, so the on-screen half of the acceptance list — Select drawn at a
tree Todo's root (#1, #2, #7), and the upgrade running on the phone itself (#8 end to end) — has
**not** been walked. The repair is proven on the same data by the run above and the screen change is
one predicate with four tests on it, but neither has been seen on a device, and this paragraph is
the record of that.

## Out of scope

- **A List's completion as something the user can set.** The flag stays derived from the rows; this
  release only makes every write ask the question.
- **The `task_state` completion of a Task that is not in any List.** Unchanged, and still the only
  thing the checkbox writes.
- **Everything [v0.5.2](v0.5.2.md) deferred** — pruning and retention, reading a history as a
  listing, and [v0.5.0](v0.5.0.md)'s list of bands and typed fields.
