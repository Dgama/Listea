# Listea v0.4.0 — Ownership, and a List that spans Todos

> **Status:** Iteration, shipped in two steps. **Steps 1, 2a and 2b are implemented**
> **Audience:** Coding agent and maintainers
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)
> **Depends on:** v0.3.0 (the Upstream/Todo split, the Task catalog)
> **Supersedes:** the "disjoint import roots" rule of v0.2.5 and v0.3.0

## The change in one table

v0.3.0 shipped two `UNIQUE` indices that between them said a file belongs to exactly one Task and a
folder belongs to exactly one Todo. Both are gone.

| Was | Is |
|---|---|
| `sources (rootUri, relativePath)` unique | Any number of Todos over one folder |
| `assets (rootUri, relativePath)` unique | `assets (taskId, rootUri, relativePath)` unique |

What that moves is the **sharing boundary**. It used to sit at the file; it now sits at the Task:

| Reached through | Is | State |
|---|---|---|
| Two Todos, one file | **Two Tasks** | Independent |
| Two Lists, one Task | **One Task** | Shared |

This is the whole of step 1, and everything below is either the schema that says it or the reads
that had been written on the assumption it could not happen.

## Why

The model has three layers, and only the middle one was missing:

```text
Upstream   a folder Listea may read          (a market)
Todo       one intent + one grouping rule    (a dish the cook means to cook)
Task       the thing judged, owned by one Todo, carrying checked/tags
List       an order over Tasks, nothing else (the shopping list)
```

The chef cooks two dishes, so two Todos. Market one sells eggs; market two sells tomatoes and
peppers. The shopping list holds the Tasks from both, because a List is an order over Tasks and the
chef wants one list to shop from. Nothing in that story needs a file to belong to one Todo: the eggs
are bought once and the fact that two dishes wanted them is not a relationship between the dishes.

Where it showed up as a defect rather than a missing feature:

- **Two intentions for one image.** One picture, categorised twice and sent to two different
  webhooks, is two intents and two Todo cards. Under the old rule the second import was refused
  outright — the app had no way to say the thing the user meant.
- **A List from one Todo only.** A shopping list spanning two markets had no gesture. There was a
  way to select Tasks and a way to create a List, but no way to put a second Todo's Tasks into a
  List that already existed.

## Step 1 — 归属 (ownership)

### Schema

Room `version = 17`, one step, no table rebuild:

```sql
DROP INDEX IF EXISTS index_sources_rootUri_relativePath;
CREATE INDEX IF NOT EXISTS index_sources_rootUri_relativePath ON sources (rootUri, relativePath);
DROP INDEX IF EXISTS index_assets_rootUri_relativePath;
CREATE UNIQUE INDEX IF NOT EXISTS index_assets_taskId_rootUri_relativePath
    ON assets (taskId, rootUri, relativePath);
CREATE INDEX IF NOT EXISTS index_assets_rootUri_relativePath ON assets (rootUri, relativePath);
```

The `sources` index is rebuilt rather than dropped: it stops being a uniqueness constraint but is
still how a folder'''s Todos are found. The `assets` index is rebuilt twice for the same reason —
`(taskId, rootUri, relativePath)` is what a run looks a locator up by, and `(rootUri, relativePath)`
is still what every file-state read joins on.

Existing rows already satisfy the new index, so there is nothing to backfill. `MigrationV16ToV17Test`
writes a raw v16 fixture and asserts both halves: that every row of every table survives with the
same ids and the same decisions, *and* that the relaxed constraints really are relaxed while the one
worth keeping — one Task holds at most one Asset per file — is still enforced. Asserting only the
first half would pass on a migration that dropped the indices and forgot to build the replacement.

The rule kept is the one that was load-bearing: two Assets of one Task at one path would be two
answers to the same question — which URI to render, which size to show.

### Registration mints, always

`registerSource` used to consult the covering-Source index and reuse a row when one covered the
folder, which is what made "this folder is already imported" enforceable and is why the refusal and
the registration were the same code. With nothing to enforce, the reuse arm was unreachable in every
real path, so `registerSource` is now a plain mint: one call, one row, whatever is already there.

Four functions became one. `registerNewSource`, `registerSourceInternal`, `mintSource` and the old
`registerSource` were consolidated into a single always-minting `registerSource`, and
`RegisterSourceResult` — a sealed interface whose `Overlaps` variant was the refusal — was deleted.

Reuse is still a thing a caller can want, and now it is a decision each caller makes with a reason
rather than a rule hidden inside registration: `TaskFixtures.taskIdOf` asks for it explicitly, and
`confirmResyncImport` reuses the one Source at a path after refusing when there is more than one.

### A locator another Todo holds is not a collision

`resolveNewTask` looked every planned locator up globally and, finding it owned, returned an
`ImportConflict` naming its owner. That check has to change with the schema or the release would be
invisible: the second import would report conflicts instead of writing Tasks. The lookup is now
scoped through `task_imports` to the importing Source.

- A locator held by **another** Todo is not a conflict. The run mints its own Task beside it.
- A locator held by **this** Todo is still a conflict, because that is the grouping rule disagreeing
  with itself.
- The `legacy_source_tasks` adoption branch is unchanged, and with two Todos the first to run adopts
  and the second mints its own.

### The reads that assumed one Asset per path

`file_review_state` joins `assets` on `(rootUri, relativePath)`, so two Assets at one path emitted
two rows and the decisions in them were whichever the query happened to return first.

| Read | Now |
|---|---|
| `observeFileCompletion` | `GROUP BY` the file, `MAX(isCompleted)` |
| `observeFileStates`, `getFileStates` | the same aggregation over every decision column |
| `getCheckedFilePaths` | `DISTINCT relativePath` |
| `observeCheckedFileCount` | `COUNT(DISTINCT relativePath)` |

The rule is **one row per file, ticked when any Task over it is ticked**. That is a collapse and not
an answer, which is why a second read exists beside it: a file the Todos disagree about is shown
ticked *and* marked, rather than quietly reported as the vote of whichever row came first.

The count is of files and not of Assets because of what it feeds — the card offering to delete
checked files. A file two Todos call done is still one file, and counting rows would have offered to
delete `a.jpg` twice.

### Which Todo holds a row, and in what capacity

The browser has to say who holds a row, and there turned out to be **two ways to hold one**. A Todo
either made its Task *of* this path — a file-as-Task run's file, a folder-as-Task run's folder — or
made its Task of a folder above it, in which case the path is one of the files that Task covers.
`task_imports.groupPath` is the whole of the distinction, because `Importer.plan` rebases every
planned path through the import root (`Importer.kt:104-116`), so `groupPath` and `assets.relativePath`
are already in the browser's own path space:

| | |
|---|---|
| `groupPath == relativePath` | the row **is** that Todo's Task |
| `groupPath != relativePath` | the row is **content** of that Todo's Task |

Two reads, both keyed by path:

- `observeFileClaims(rootUri)` — every claim under the root, `UNION ALL`ed from `task_imports` (the
  Tasks themselves) and from `assets` (the files they cover, excluding the rows the first arm
  already carries). Every held path appears, not only the contended ones.
- `getSharedFileStates(rootUri, relativePath)` — one row per Todo over one file, with that Todo's
  own decisions and its capacity. Read on demand rather than observed, because it is asked one file
  at a time.

A row names its holder in a line under the filename; a file more than one Todo holds *also* carries
the count as a tappable label beside its tick, and the drill-in behind it lists each Todo, its Task
and what it decided. Keeping the collapsed tick *and* the mark is the point: the tick has to say
something, and what it must not do is pretend the two Todos agreed.

**An earlier cut of this section marked only files with more than one owner** (`HAVING COUNT
(DISTINCT sourceId) > 1`). That was wrong in the field for two reasons, both of which the user hit at
once. It was silent about every file in a folder imported once — an entire 140-file directory showed
nothing — and because it joined only `assets`, it drew a file-as-Task Todo and a folder-as-Task Todo
holding the same file identically, while the drill-in asserted *"Each has a Task of its own"* for
both. The count is now a summary of the line rather than a substitute for it.

Two deliberate asymmetries worth knowing:

- **`Asset` is browser vocabulary now.** It was already user-visible in the import report and on a
  catalog row; the browser's rows say it too, which is why the hint is the plain word rather than a
  symbol.
- **Todo ownership does not propagate to ancestors, though List ownership does.** A folder that
  merely contains somebody's Task shows nothing, the same way `FolderType.NONE` refuses to call
  ancestry a relationship a folder *has*. `folderListStatus` still walks upwards for Lists, so a
  sublist is named on every folder beneath its scope; a Todo is named only where it made its Task.

### The wire name

`assignLegacyItemIds` copies a registration's `publicId` onto the Asset at that path, which was the
same thing as onto the file while a file was one Task. Left alone it would hand two Tasks one id and
a receiver two rows it could not tell apart.

It now names **one Asset per file** — the first to be named, guarded by `NOT EXISTS` so a later run
cannot hand out a second copy — and every later Task over that file takes its own name from
`legacyTaskId`, the same mechanism a multi-Asset Task already used. The file's own name is unaffected
either way: the file-state reads fall back to the registration's `publicId`, which is the same
string.

### Lists that span Todos

A List is an order over Tasks, so making one is picking Tasks and picking a List, in either order.
Both orders now exist:

- **In a Todo, with a selection.** The selection bar carries **Add to list…** beside **Create List**.
  It opens a picker of existing Lists and commits through `ListsDao.addTasksToList(listId, taskIds,
  now)`, which appends each Task as a membership built by the same `listItemForTask` a created List
  uses. A Task the List already holds is skipped rather than added twice — one Task at two positions
  is not a second opinion about it, and it would put the review queue at the same Task twice.
- **From the Lists tab.** **New list** asks which Todo to take Tasks from, then opens that Todo's
  catalog with picking already on, so the rest is the gesture that was already there. Leaving — by
  Back or by creating the List — returns to Lists rather than stranding the user on the Todo tab,
  which they never chose to be on.

The second is the first half of a two-step gesture rather than a constraint: start a List from one
Todo, then open another and use **Add to list…** to put its Tasks into the same one. A picker that
browsed every Todo at once would need a second set of rules about what a folder covers, and the two
would drift.

### The re-import prompt

`ImportFolderRequest.Confirm` carries the names of the Todos already at that folder, and the dialog
prints them: *"This folder already has 2 Todos: "Holiday", "Everything". Creating Tasks here makes
another, with Tasks of its own."* A notice, not a refusal — the whole point is that making another
is a legitimate thing to want.

## Step 2 — lifecycle

**Step 2a — dissolution — and step 2b — the two per-import policies — both shipped 2026-09-17.**
The split is the plan's: 2a is the half with the sharp edges, and 2b's `drop` tier is built out of its
machinery, so shipping it first is what makes the tier an assembly rather than a second design.
[`v0.4.0-step2-plan.md`](v0.4.0-step2-plan.md) is the reference for both.

### Dissolution

*Deleting an intention is abandoning what it meant.* A **Delete Todo** behind the Todo card's
overflow takes the Todo, its Tasks, their Assets, their state and their provenance rows — and the
List memberships that named those Tasks — after a confirmation that names every List about to lose
rows.

The ordering is not a preference. `list_items.taskId` and `task_imports.sourceId` are both
`NO ACTION`, so the memberships and the provenance rows must go before the Tasks, and the schema
says so rather than a comment. Leaving a membership behind is not the tidier option that was
declined; it is a bug: the Lists index counts memberships through a `LEFT JOIN` to `task_state` and
the detail screen resolves them through an inner one, so a List would read *"3 items, 2 checked"*
over two rows. The schema rules that state out entirely — an orphan row cannot be inserted either.

What survives is the point of the operation. `review_events` stays, because it records what
happened and a delete that rewrote it would be editing the past. `file_review_state` is keyed by
path and is never touched, so a file deleted and re-imported is the same file to the wire, keeping
the public id it had.

### Keep the decisions

The confirmation carries a **Keep the decisions** checkbox, preselected from
`sources.keepStateOnDelete` — which defaults to **off**, the behaviour-preserving answer rather than
the friendly one: before this release nothing could delete a Todo at all, so a Todo that started
keeping a snapshot would have begun doing something the user never asked for.

On, it writes `dissolved_task_state` before the delete: one row per Task, keyed by the path the
judgment was made over, with the folder the intention was made at, the Todo's name and its grouping
rule. It records the **absence** of a judgment as readily as a judgment — a recovery that invented
`false` would be indistinguishable from one that copied a real "no".

### Recovery

A Todo created at a folder where something was dissolved is offered the histories left there, newest
first, at most one at a time: a run that took some Tasks from one history and some from another
would produce a Todo that never existed as an intention. It is a **copy into the new Todo, not a
resurrection of the old Tasks** — they had no ids worth keeping — so nothing missing from the old
List comes back, and a file the new run did not produce has nothing to receive a judgment.

The match is `(rootUri, groupPath)` and nothing else. **A history whose grouping rule differs
recovers nothing at all**: dissolve a folder-as-Task Todo and re-import the same folder
file-as-Task, and the paths will not line up. That is honest rather than broken — the judgments were
about *groups*, and the new Todo has no such groups — and it is said in two places rather than
nowhere: the picker reports how many Tasks each history carries, and the import report names the
history it drew from, including when the answer is that it drew nothing.

Two properties worth stating because they are visible. **Recovery is offered on Create Tasks and
never on Refresh Import**, because a refresh runs over a live Todo and would overwrite the
judgments made since. And **histories are not consumed**: a history says *the eggs were bought
once*, and two later dishes both knowing that is correct.

### What a List says afterwards

The List survives — a List is an order over Tasks, and an order nothing satisfies is empty rather
than gone — and it says what happened: *"3 items removed when a Todo was deleted · 2026-09-17
15:31"*, on the detail screen and in the index. Two `lists` columns beside the existing delivery
quartet is the schema's proven shape for "what happened last", and it is deliberately not an audit
log: a second dissolution replaces the first note. The note is cleared when the List next gains a
membership, which is to say when it has moved on — and only then, so a re-sync that found what it
already had leaves it standing.

### Step 2b — the two per-import policies

**Shipped.** Both are **a statement about a Todo**, and both are stored per Todo rather than app-wide:
the Settings entry is only what a *new* Todo is seeded with, and the Todo card's overflow menu is
where a Todo's own behaviour is changed afterwards.

- **`contentPolicy`** — *keep* / *reset* / *drop*, on `sources.contentPolicy`, defaulted from
  Settings. `keep` is today's behaviour; `reset` clears the Task's *current state* while its identity
  stands; `drop` deletes a non-single-Asset Task and mints a fresh one in the same pass. Only `drop`
  reaches lifetime, and it is admitted **only** as an explicit, user-named policy — never as an
  inference drawn from a Task's structure.
- **Following the upstream** — `sources.followUpstream`, whether opening a Todo syncs new material in
  on its own. It is the only thing that makes the app write without being asked, so it is off
  everywhere by default and the write it triggers is gated twice: `sourceHasChanges` must say there
  is something to do before an import is even applied.
- **`ImportResult.tasksReset` / `tasksDropped`**, so the report says which tier did what.

**A Task the run found unchanged is under no policy at all**, and that is the rule the whole section
turns on. All three tiers describe what a *change* means, so a run that finds the material as it left
it has nothing to answer — which is what stops a `reset` Todo from clearing its Tasks' judgments on
every refresh, and a `drop` Todo from replacing them on every refresh. An Asset already flagged
missing is not a change either, and a partial re-import only judges what it scanned.

**A Task's lifetime is still not decided by how many Assets it has.** The original sketch had a Task
deleted when its Asset count reached zero, and that clause is **dropped**: a folder-as-Task Task over
a folder that empties and is later given a file must still be the same Task, and deleting at zero
makes the return impossible. Every tier reads a *change to the set*, never its size. The one place a
count is read is `drop` on a Task holding a single Asset, and it decides the *means* rather than the
policy — replacing a one-file Task would mint a Task holding that same file under a new id with its
judgments and memberships gone, so it is started over instead. `ARCHITECTURE.md` carries the
amendment this rested on.

**One departure from the plan, recorded in place there.** The plan had `drop` reuse 2a's List note
verbatim; a drop deletes no Todo, so the sentence would name an operation that never happened.
`lists` gained a third column, `lastDissolvedReason`, holding which of the two took the rows, and the
note above each List is written from it — *"3 items removed when a Todo was deleted"* against
*"3 items removed when their content moved"*. It is not cleared when the List moves on, because
nothing reads it unless a count is standing next to it.

## Also in this iteration

**The folder-List machinery is now provably dead.** `requestListForFolder` → `createFolderList` →
`PendingFolderList` → `FolderListRequest` → `commitPendingFolderList` → `FolderListImportConflict` →
`folderListStep` → `registerOrReuseSource` → `fileAsTaskPlan` has no caller in `app/src/main`:
`QuickReviewTarget` is only ever built with a non-null `sourceId`, and `createListFromTasks` writes a
List with a null `sourceRootUri`, so the Resync card never renders for a v0.3.0 List. They were kept
compiling rather than deleted — deleting them is a follow-up decision, and `FolderListGateTest`,
`ConsentGateViewModelTest` and `ConsentTest` are behind them.

`requestResync` and `coveringSourceOf` now serve legacy folder-backed Lists only, and both refuse
rather than guess when more than one Todo covers the folder: it is a write target, and picking wrong
is worse than declining.

## Acceptance

1. Import one folder twice. Two Todo cards, named differently, both opening onto Tasks.
2. Check a Task in one Todo. The other Todo's Task over the same file is untouched — same file, not
   the same Task.
3. Build a List holding Tasks from both Todos. Checking one of them in the List changes it in the
   Todo it came from, and in any other List that shows it.
4. Open the Upstream browser at a folder holding a shared file. The row is ticked, carries a third
   line naming the Todos that hold it, and is marked with the count when more than one does; tapping
   the mark names them and what each decided, distinguishing the ones that have a Task of their own
   from the ones that merely cover it. Open a folder a single Todo was imported over: every row
   names it, and a file that Todo's Task only *covers* says `· asset`. A folder that is itself a
   Task names its Todo; a folder that merely contains one says nothing.
5. Select Tasks in one Todo and use **Add to list…** to put them into a List made from another Todo's
   Tasks. A Task the List already holds is not added twice.
6. From the Lists tab, **New list** → pick a Todo → tick Tasks → **Create List**. Back out instead,
   and it returns to Lists.
7. Create Tasks on a folder nested inside an existing Todo. It runs, names the Todos already there,
   and makes Tasks of its own.
8. Upgrade an installed v16 database. Todos, Tasks, Assets, state and Lists are all still there, and
   step 1 of the above now works on it.
9. Delete a Todo from its card's overflow. The confirmation names every List that will lose
   memberships and how many each loses. Confirm, and the Todo, its Tasks and their Assets are gone,
   while any List that held them survives, empty.
10. Delete a Todo whose files were ticked, with **Keep the decisions** on. Each affected List says
    how many rows it lost and when. In the Upstream browser, a file whose only Task was the deleted
    one loses its tick — deleting an intention is abandoning what it meant — though only files a
    folder Quick Review has registered have a tick to lose. Create Tasks at the same folder afterwards and the
    dialog offers the history; choose it, and the Tasks come back with the judgments they had.
11. Delete a Todo with **Keep the decisions** off, then Create Tasks at the same folder. No history
    is offered, because none was written, and the report says nothing about a recovery.
12. Choose a history and get nothing. A history written by a folder-as-Task Todo has no group paths
    in common with the file-as-Task Tasks a later run mints, so the recovery reaches nothing — and
    the report says so rather than reporting a run in which nothing happened.
13. Refresh Import a Todo that has a history at its folder. No history is offered: a refresh runs
    over a live Todo, and loading one would overwrite the judgments made since.
14. Upgrade an installed v17 database. Every row survives unchanged, no List has a dissolution to
    report, and `dissolved_task_state` arrives empty.
15. Delete a file outside Listea, then **Refresh Import** a Todo set to **Keep it**. Nothing is
    removed and nothing is cleared: the file's Task survives, is flagged missing, and any tick it
    carried is still there. Refresh again — nothing has changed since, so it stays where it is.
16. Set a Todo to **Start it over**, tick one of its Tasks, then Refresh Import after deleting that
    Task's file. The Todo refreshes, the Task is still the same Task holding a List membership it
    had, the tick is gone, and the gone file is still flagged missing. Its List does not report
    losing a row.
17. Set a Todo to **Start it over** and tick a Task the refresh finds *unchanged*. Refresh Import.
    The tick survives: no policy applies to a Task nothing changed about, which is what stops the
    switch from clearing every judgment on every refresh.
18. Set a Todo to **Replace the Task** whose Tasks are one file each, tick one, and refresh after
    deleting that Task's file. The Task is **started over rather than replaced** — same Task, same
    List memberships, tick gone — and its List says nothing. Then do the same on a **One Task per
    folder** Todo: the Task really is replaced, the List that held it loses the membership, and it
    says *"1 item removed when their content moved"* rather than naming a Todo deletion.
19. Turn on **Follow the upstream** for one Todo from its card's overflow, put a new file in its
    folder, and open the Todo. It scans and reports without being asked. Turn it back off, add
    another file, and open it again: nothing is written, and a refresh is only what you ask for.
20. Change **When a Task's content changes** in Settings, then create a new Todo. It starts with the
    new answer. Change the setting back, and the Todo created a moment ago keeps the answer it was
    made with — the Settings entry seeds new Todos and never reaches an existing one.
21. Upgrade an installed v18 database. Every row survives, the Todo keeps its content the way it
    always did (`keep`, not following), and a List that already had a note keeps the sentence it
    had — the reason arrives holding the delete's own key, not the drop's.
