## 0. Decision log

| # | Decision | Why |
|---|---|---|
| 1 | An **export** is the act and an **`ExportKind`** is how it happens, as a closed enum with a stored key | §The model. Closed because a kind is code — a renderer plus a destination — and neither is data. The list of kinds is the list of exporters this build ships, so it cannot be a table |
| 2 | A stored kind this build cannot read is **`Nothing`** — export nothing, write no file, send no request | [v0.5.3](v0.5.3.md)'s rule one level up. A rule this build cannot evaluate must not be quietly dropped, because a drop *widens* what the app does on the user's behalf, and here it would widen it all the way to the network |
| 3 | The choice is **a single value on both sides**, never a set: `selections.exportKind` and `lists.exportKind` each hold one key | The user's correction in as many words: *"todo创建（import的时候）和list里的export方式都是单选"*. The plural case is a **sum over the Todos a round touched**, computed at delivery time, so nothing has to be kept in sync because nothing is held |
| 4 | `webhookUrl` is **deleted from the List**, and every webhook reads `settings.defaultWebhookUrl` | The List's copy is the exact defect v0.5.4 removed from `assetControls`: seeded once at creation (`ListsViewModel.kt:1987-1988`, `:2047-2048`) and never read again, so changing the default reaches no existing List. **The column is not dropped** — that needs SQLite 3.35 and minSdk is 24 — it is left in place, unreferenced, as `list_items.isCompleted` and `task_state.isFavorite` already are |
| 5 | The List's choice is encoded as a **word** (`none` / `inherit` / `webhook` / `txt`), not as NULL-or-empty | A List has a state a Todo does not — *having said nothing* — and `""` is already spoken for by *nothing was ever chosen* in `sources.assetControls` (v0.5.4 decision 8). Three states need three words, and a reader should not have to know which column it holds to tell them apart |
| 6 | `inherit` decoded **on a Todo** is also `Nothing` | A Todo has nothing above it to follow. The same decoder serves both columns; the flag is where the asymmetry lives, and the answer that fails closed is the one that exports nothing |
| 7 | `webhook_history` **keeps its name** and gains `kind`; the Kotlin names generalise | v0.5.4 decision 8's argument: renaming a table is a rebuild for a word, and the word is in the migration's history either way. The user chose *两种都记* — the row's home moves to Exports, but the table it lives in does not move |
| 8 | **A txt export is recorded too**, with a new terminal outcome `WRITTEN` | Without it a txt export is unfalsifiable: the user cannot tell whether the file was written, and the *Last export* line on the List card would have nothing to say exactly when the effective kind is txt. `observePendingWebhookCount`'s `outcome != 'SENT'` becomes `outcome NOT IN ('SENT','WRITTEN')` — the query was already asking *is this still unfinished*, and now there are two ways to be finished |
| 9 | The three export-wide switches **move to Exports and keep their DataStore keys** | The keys are frozen literals in the same sense a migration is: renaming `quick_review_webhook_enabled` silently resets it for every install that has it. Kotlin field names and user-visible labels change; the strings on disk do not. **Deviation: the Kotlin field names did not move — see §10** |
| 10 | **Only a kind that leaves the device asks for confirmation**, expressed as `Exporter.asksBeforeDelivering` | Today's `awaitConfirmation` (`ListsViewModel.kt:2915-2931`) exists because a POST is outward-facing and hard to take back. A file write to the user's own album is neither, and asking every round would train the user to tap through the one dialog that matters. It is a property of the kind, not a special case for txt |
| 11 | **The import dialog offers a third option, *Don't export*, that the spec did not name** — flagged, not smuggled | The user asked for *"请放webhook和txt两个选项"*. A two-option radio group has no way to say *this Todo exports nothing*, and *nothing* has to be sayable: it is the default for a new Todo, the answer for an unreadable key (decision 2), and the only way to correct a choice made at import. Every other choice in that dialog — importer, grouping, content policy — carries its neutral answer, so a group without one would be the only control in the dialog you cannot unset |
| 12 | An existing Todo migrates to **`webhook`**, a new one starts at **`none`** | Asymmetry on purpose, and the two are not the same question. Migration is preservation: a Todo that webhooked before the upgrade must webhook after it, or the release silently stops work the user set up. A new Todo is a choice being made, and a choice the user did not make should not send anything anywhere |
| 13 | An existing List migrates on **`webhookEnabled = 1`**, not on a non-empty `webhookUrl` | The URL is not a signal: it is seeded from the settings default at creation (`:1987-1988`), so **every** List created while a default was set holds one, whether or not the user ever switched it on. `webhookEnabled` is the switch the user actually touched. A List that had it on becomes `webhook` — which preserves what it did, since it webhooked regardless of its Todos |
| 14 | An item with **no source Todo** exports by `webhook` | Today's behaviour, kept: `deliverFolderReview` passes `useDefaultWebhook = true` (`ListsViewModel.kt:2588`) and is gated by the webhook default. A default *kind* in Settings is the obvious next step and is deliberately not taken — this release names the mechanism, it does not invent a policy for unowned items |
| 15 | The exporter is an **interface with `render` separate from `deliver`** | `render` is pure — no context, no network, no clock — so both the JSON body and the txt body are assertable in a unit test without a device, which is what makes the txt format a thing the suite can hold rather than a thing the user finds out about. Configuration goes in at construction, so `deliver` takes only the payload; the payload is the seam the next kinds need |
| 16 | The **field escaper is shared with `DissolvedRecords`**, by lifting it out of private | `escapeDissolvedPath` (`data/DissolvedRecords.kt:106`) already solves exactly this problem — a user's filename may hold a tab or a newline, and a renderer that lets one through produces a file that reads as two records. Two escapers would be two rules for one problem, and the existing one is already covered by `DissolvedRecordsTest`. Lifting it changes where the function lives and nothing about what it writes, and that test staying green is the proof |
| 17 | A txt export **never reports `AlreadySaved`** | `MediaSave` treats a name collision as *nothing to do* (`MediaSave.kt:181`, `:252`), which is right for a photograph the user already has. It is wrong here: a payload is not a thing the user holds, it is a report of a round, and two rounds can legitimately share a second. A collision takes a `-2` suffix instead |
| 18 | **A completion that lands while a round is open on something else is built, kept, and neither sent nor shown** — the app answers *Not now* on the user's behalf | The fourth device pass found the case: swiping a Task two Lists share completes the other List, which then asks *Send this webhook?* **over the review of the first**. The user's decision, 2026-09-19: *"用户在一个 list 里动作，不要反馈给用户另一个 list 的结果 … 在背后完成 list B 的对应 payload 的构建，但是不发送"*. A value (`CompletionScope`: *unattended* / *this round* / *another round*), read under `writeOrder` with the write that completed the List, because the round-closing exit is a separate coroutine racing it. Option C — the two the pass had left open were *fire it now* and *hold it until the round ends*, and this is neither |
| 19 | The three checks **before** the confirmation — unusable URL, no exporter, switched-off webhook — still run, and still record | The app answers the user's *decision*, not the user's *facts*. A blank default URL is a setting to go and fix; dismissing it as *not now* would file a broken configuration under a choice nobody made |
| 20 | **A declined round now writes `NOT_SENT` against its List too** — reversing the rule the third device pass recorded | Decision 18's reason one step earlier: *Last export* names the last thing that happened to that List's exports, and when it was a payload that did not leave, the line going on naming an earlier success is the line being wrong about the List. New third value in the vocabulary: `DeliveryStatus.NOT_SENT` beside `SUCCESS` and `FAILED` |
| 21 | Every dialog that asks about an export **names what caused it** | The same pass, in the user's words: *"每次跳窗说明 export 也多带一点点信息，至少清晰表明是谁触发的这次 export"*. `webhookTriggerLabel(event, subject)` is the sentence; a folder round has one too, since its subject is the folder |
| 22 | A folder round's *is one open* marker is **paired by the composition** — `DisposableEffect(sessionKey)` on Quick Review's queue — and not by the leave gesture | Quick Review ends two ways and only one of them calls `onFolderReviewExited`, so closing the marker there would leak it on the other. A leaked count does not fail locally: *a folder round is open* is what makes a completing List keep its payload instead of asking, so one finished Quick Review would leave every later completion in the app answering for itself. The screen **is** the round, so the composition's lifetime is the honest owner, and no future exit path has to remember |

## 1. Schema — 24 → 25

Three columns, no new tables. `MIGRATION_24_25` in `data/ListeaDatabase.kt`, after `MIGRATION_23_24`,
added to `addMigrations`, and `version = 25`.

```sql
ALTER TABLE `sources`         ADD COLUMN `exportKind` TEXT NOT NULL DEFAULT 'webhook';
ALTER TABLE `lists`           ADD COLUMN `exportKind` TEXT NOT NULL DEFAULT 'inherit';
ALTER TABLE `webhook_history` ADD COLUMN `kind`       TEXT NOT NULL DEFAULT 'webhook';

UPDATE `lists` SET `exportKind` = 'webhook' WHERE `webhookEnabled` = 1;
```

**The literals are frozen**, as every migration here is: `'webhook'` and `'inherit'` are written out
rather than interpolated from `ExportKind.WEBHOOK.key`, because a migration records what it did on
the day it ran and a later release that renames a key must not retroactively change what an old step
wrote.

**Three columns and one `UPDATE`, and the `UPDATE` is the whole asymmetry of decision 12/13.** The
column defaults carry the *Todo* answer for `sources` and the *not yet chosen* answer for `lists`; the
`UPDATE` is the one place a prior meaning is read and re-stated. `lists.webhookEnabled` is **not**
dropped and **not** rewritten — it keeps its column, gains a Kotlin name that says *when* rather than
*how* (decision in §5), and stays the switch behind *Export when this list is completed*.

**`lists.webhookUrl` is left in place, unreferenced.** Room's schema validation will keep it in the
entity (a `@ColumnInfo`-annotated field that nothing reads) so that `ALTER TABLE` chains written by
earlier steps still match; the DAO stops selecting it and the two `createListFromTasks` /
`createFolderList` writes (`ListsDao.kt:500-501`, `:519-520`, `:549-550`, `:557-558`) stop setting
it. v0.2.0's `list_items.isCompleted` is the precedent for a dead column that stays.

**A `MigrationV24ToV25Test` follows `MigrationV23ToV24Test`'s method**, not `MigrationV12ToV13Test`'s:
the fixture is the current schema wound back — the three columns removed, `user_version` put to 24 —
rather than a hundred lines of DDL written out by hand, and the test asserts each half of the
subtraction so the shortcut is checked rather than trusted. It carries the case the `UPDATE` exists
for: a List with `webhookEnabled = 1` and an empty `webhookUrl` (the common shape — the user switched
it on and never typed a URL) arrives at `'webhook'`, and a List with `webhookEnabled = 0` and a
**non-empty** URL (seeded from the default, never touched) arrives at `'inherit'`. That second case
is the one a naive `webhookUrl <> ''` rule would get wrong, and it is why decision 13 reads the way
it does.

## 2. The model — `domain/Exports.kt`, and `Exports.kt` beside it

**Two files, split on the layering rule the package already keeps.** `domain/` imports nothing from
`data/` — checked, not assumed — so the pure vocabulary goes there:

`domain/Exports.kt`, new, beside `domain/Templates.kt`, for the reason that file exists: it holds
what is true about exports independent of any screen or database.

```kotlin
/** How decisions leave the app. Closed: a kind is a renderer plus a destination, and neither is data. */
enum class ExportKind(val key: String) {
    WEBHOOK("webhook"),
    TXT("txt");

    companion object {
        /** A key this build cannot read is `null`, and every caller turns that into *export nothing*. */
        fun fromKey(key: String): ExportKind? = entries.firstOrNull { it.key == key }
    }
}

const val EXPORT_CHOICE_NONE = "none"
const val EXPORT_CHOICE_INHERIT = "inherit"

/** What a Todo or a List does about exporting. One value, never a set. */
sealed interface ExportChoice {
    data object Nothing : ExportChoice
    data object Inherit : ExportChoice          // Lists only
    data class By(val kind: ExportKind) : ExportChoice
}

fun encodeExportChoice(choice: ExportChoice): String
fun decodeExportChoice(encoded: String, inheritable: Boolean): ExportChoice
```

`decodeExportChoice` is tolerant in the house style: an unrecognised key is `Nothing`; `inherit`
with `inheritable = false` is also `Nothing` (decision 6). `Txt` and `None` are the only two values
`encodeExportChoice` can be handed for a Todo, which the Todo's call site enforces by construction —
the dialog never builds an `Inherit`.

`ExportKind` carries a `label` as well as a `key`, following `ContentPolicy` and `ImporterKind`:
the word a user reads is named once, so the import dialog, the List card's dropdown and the Settings
list cannot call one kind three things. `LIST_EXPORT_CHOICES` and `listExportChoiceLabel` hold the
List's four entries in their display order — the Todo's chooser names its own three, because it is
asking a different question (*Don't export*, where the List says *Export nothing*).

**`Exports.kt`** — top level, beside `Webhook.kt` — holds everything that needs the data layer,
because everything below does:
/** One round's payload for one effective mechanism. */
data class ExportPayload(
    val event: String,
    val listId: Long,
    val listTitle: String,
    val completedAt: Long,
    /** The Todo this group came from, or null for an item no Todo owns. */
    val sourceId: Long?,
    val sourceTitle: String?,
    val items: List<ListItemEntity>
)

/** What one attempt did, in the four states a caller has to tell apart. */
sealed interface ExportAttempt {
    data class Delivered(val detail: String?) : ExportAttempt
    data class Failed(val detail: String?) : ExportAttempt
    /** Nothing was attempted — a missing URL, a disabled switch. Recorded, but never a failure. */
    data object Skipped : ExportAttempt
}
```

`ExportPayload` carries **structured items, not a rendered string**, and that is the abstraction being
real rather than a rename: the txt renderer needs `title`, `isCompleted`, `relativePath` and the marks
individually, and the next kinds will need more than the current wire shape holds. The JSON body is
produced from the same payload by `buildWebhookPayload`, unchanged in shape and still the single
builder for every event.

```kotlin
/** One way of getting decisions out of the app. */
interface Exporter {
    val kind: ExportKind

    /** Whether this kind asks the user before it acts. See decision 10. */
    val asksBeforeDelivering: Boolean get() = true

    /** The bytes this kind writes. **Pure** — no context, no network, no clock. */
    fun render(payload: ExportPayload): String

    /** Does whatever the kind does with those bytes. Never throws; a failure is a result. */
    suspend fun deliver(payload: ExportPayload, body: String): ExportAttempt
}
```

Two implementations, both in `Exporters.kt`:

- **`WebhookExporter(url: String)`** — `render` calls `buildWebhookPayload`; `deliver` calls the
  existing `postWebhook` (`Webhook.kt:388`) and maps `DeliveryResult` onto `ExportAttempt`. It is a
  move: the network code is not touched, and neither is the payload.
- **`TxtExporter(context: Context)`** — `render` produces §4's text; `deliver` writes it to
  `DCIM/Listea/txt/`.

**Deviation, as built: `render` takes no resolver.** The draft signature was
`render(payload, resolver: TemplateResolver)`, on the theory that the renderer would resolve action
names itself. It does not, and it should not: `exportItemView` already resolves them into
`ExportItemView.actions` *before* the payload exists, so a renderer holding a resolver would be a
second place the two mechanisms could disagree about what is on the wire. The payload is the seam,
so the payload carries the answers.

`exporterFor(kind, url, context)` is a **`when` over the enum, not a map**, so the compiler's
exhaustiveness check is what keeps a third kind from being added without a branch. `null` for
`WEBHOOK` when the URL is empty — the caller records `Skipped`, which is exactly today's
`NoticeOutcome.DISABLED` path (`ListsViewModel.kt:2836`).

## 3. The dispatcher — one body, three triggers

`deliverPayload` (`ListsViewModel.kt:2780-2789`) is the single place every event already funnels
through. It is rewritten in place; its callers barely move.

**Unchanged**, in place and re-pointed rather than redesigned:

| Site | Trigger |
|---|---|
| `onQuickReviewFinished` (`:2530-2534`) | Quick Review queue finished, gated by `quickReviewWebhookEnabled` (`:2535`) |
| `onReviewExited` (`:2655-2665`) | leaving a List review, gated by `webhookOnReviewExit` (`:2657`) |
| `onFolderReviewExited` (`:2673-2677`) | leaving a folder review, gated by both (`:2679`) |
| `onCompletionTransition` (`:2687-2691`) | a List completed, `requireEnabled = true`, plus the `webhookOnReviewExit` de-duplication at `:2703` |
| `testWebhook` (`:2513`) | the explicit button |

**Changed**: inside the body, in the order the user gave —

```
1. items = webhookItems(rows, current)          ← `webhookCompletedItemsOnly`, unchanged, first
2. choice = decodeExportChoice(list.exportKind, inheritable = true)
3. if (choice is Nothing) return                                                  ← silent, see below
4. if (requireRoundEnabled && !list.exportOnCompletion) → NoticeOutcome.DISABLED,
                                                          record the round, return
5. if (items.isEmpty()) → NoticeOutcome.EMPTY, record nothing, return
6. sources = dao.getExportSources(items.map { it.taskId }.distinct())             ← one query
7. groups = planExports(items, choice) { row -> the row's Todo's sourceId, name, and kind }
     choice is By(k)      → one group, sourceId = null, kind = k
     choice is Nothing    → []                                                  → nothing at all
     choice is Inherit    → items grouped by their Task's sourceId              (folder rounds always
                                                                                 land here — there is
                                                                                 no List)
8. if (groups.isEmpty()) return
9. for each group:
     kind = the group's Todo kind, or WEBHOOK when the group has no owner (decision 14)
     url = the settings default, always — there is no per-List URL any more
     urlProblem → record(FAILED) + keepRound; continue
     exporter = exporterFor(kind, url, context) ?: record(FAILED) + keepRound; continue
     if (kind is WEBHOOK && !defaultWebhookEnabled) → record(DISABLED) + keepRound; continue
     if (exporter.asksBeforeDelivering && confirm)
         roundAnswer ?: awaitConfirmation(...)   → at most one prompt per round (below)
         DECLINED → keepRound; continue
     attempt = exporter.deliver(payload, bodyOf(kind, url, payload))
     record(kind, attempt); keepRound(kind, payload, body, notice)
10. if (confirm && any notice) offer deletion of the round's items
```

**Deviation, as built: the gates moved, and two of them changed meaning.** The draft put the empty
check at step 2, before the choice was read. As built, the choice comes first, for two reasons:
a List that chose *Nothing* is **silent** (it is a configuration, not a round that failed to find
anything), and a List that is switched off still **records the round it would have sent**, which the
history's own docstring calls the question people actually have. The empty check then has to come
after, and it reports `EMPTY` only when there is a group to report it against — so an inheriting
List over an empty round is silent where a chosen List is not. That asymmetry is deliberate: the
List's own configuration has to answer for itself, and a List that inherits has no answer of its
own to give.

**Deviation, as built: `defaultWebhookEnabled` is per group, not per round.** The draft left the
default switch as a round gate. That would mean a user with a Todo set to *txt* gets no file when
their webhook default is off — a txt export suppressed by an HTTP switch. As built it gates webhook
groups only, which is what lets the Webhook page and the Txt page each describe themselves honestly.

**Grouping is one query, not N.** `list_items` rows already carry `taskId`, and `task_imports`
already maps `taskId → sourceId`; the group key is read from the same joined row the List screen
already reads. The folder rounds' rows are synthetic `ListItemEntity`s with real task ids (the
same shape `deliverFolderReview` builds today), so the same grouping works with no second path.

**Deviation, as built: a folder round passes `requireRoundEnabled = false`.** `deliverFolderReview`
has no List, so there is no *Export when this list is completed* for it to be gated on. It passes
`ExportChoice.Inherit`, which is what routes each item to its own Todo's method, and it says in a
comment that a folder round defers to nothing because there is nothing above the Todos to defer to.
The alternative — refusing to export a folder round at all when no List is involved — would have
made the Quick Review switch a switch that does nothing.

**One confirmation per round, at most.** Today a round can ask once. Under grouping, a round with two
webhook groups could ask twice, so the queue keeps at most one outstanding prompt for a round and the
second POST proceeds on the first answer. Recorded here because it is a behaviour change, not an
implementation detail.

**`useDefaultWebhook` is deleted.** A group with `sourceId == null` takes `WEBHOOK` and the settings
default URL, because *list URL* no longer exists (decision 4) — the parameter has nothing left to
choose between. `recordAgainstList` becomes *the group's `sourceId` is null or the List has chosen*,
which is what decides whether the row is attributable to a List.

**`lastDelivery*` follows the same collapse.** `dao.recordDelivery` (`ListsDao.kt:1318-1328`) is
written once per round with the **first** group's outcome, and per group when a round split — the
column set is per-List and a split round has more than one answer, so the frame records the round and
the history records each group. Recorded as a known limit rather than solved: a List's `lastExport*`
is one row and a two-kind round has two outcomes.

## 4. The txt writer

`TxtExporter.render` produces §The model's format; `deliver` writes it.

```text
listea-export	1
event	quickreview.completed
list	Demo
source	Demo
at	1789726376530
items	3
item	3f2a…	one.jpg	1	Attach	custom1,favorite
```

- **Version line first**, `listea-export\t1`, following `DISSOLVED_RECORDS_VERSION` and
  `TEMPLATE_BUTTONS_VERSION`: a payload is never read without knowing what wrote it, and this one will
  gain a field the first time an action carries a value rather than a presence.
- **One line per item**, fields tab-separated in the JSON body's own order, so the two renderings can
  be read side by side and a disagreement is visible rather than plausible. `source` is empty for an
  unowned group, matching the body's null.
- **Escaping**: `escapeDissolvedPath` / `unescapeDissolvedPath` (`data/DissolvedRecords.kt:106`, `:123`)
  are lifted to `internal` and shared (decision 16). Applied to `title` and `relativePath` only —
  every other field is machine-generated and cannot hold a tab.
- **Path**: `MediaSave.ListeaAlbumRelativePath` + `"/txt"`, i.e. `DCIM/Listea/txt`. A **new** constant
  in `MediaSave.kt` rather than an inline string, because the two places that name the album should be
  one lookup. Writes through the same `MediaStore` / legacy split `saveToListeaAlbum` already makes
  (`MediaSave.kt:137-155`) — including the `RELATIVE_PATH` for API ≥ Q and the
  `Environment.getExternalStoragePublicDirectory` walk below it — because the album is scoped storage
  and the second path exists for the reasons it exists.
- **Name**: `<yyyyMMdd-HHmmss>-<event>-<source>.txt`, with `-2`, `-3` on collision (decision 17). The
  suffix loop is bounded and its exhaustion is a `Failed`, not a silent overwrite.
- **`FileProvider` is not involved** — the file is written to the album, not handed to another app.
- `SaveToAlbumResult` is **not** reused: it carries `Unsupported` and `PermissionDenied`, which are
  media-shaped answers, and an export has one failure — the write did not happen — with a reason. The
  `ExportAttempt.Failed(detail)` carries the same information without a type that names the wrong
  problem.

## 5. The record, and the word "webhook" after this release

The query renames are mechanical and confined to `ListsDao.kt:50-52, :450-452, :500-501, :519-520,
:549-550, :557-558, :1265-1292, :1303-1328` and their callers in `ListsScreen.kt:323-325` and
`FolderListStatus.kt:328-330`. They are done in this release and not deferred **because the point of
the release is that the word means one thing**; leaving `webhookEnabled` on a screen that also offers
*Txt* would be the confusion the release exists to remove.

**Deviation, as built: one row of that table did not happen.** `lastDelivery*` kept its name. The
rename was in the plan for the same reason the others were — the word should mean one thing — but
these four are *not user-visible*: nothing renders the identifier, and the only surface that reads
them says *Last export* already (`deliveryLabel` → `exportLabel`). Renaming a private field that no
one quotes buys a migration-shaped risk (Room validates column names, and `ListEntity` is the
`SELECT *` target of half the queries in the app) for a consistency no user can see. The screen
names, the labels, the query aliases and the type names all moved; this one did not, and that is the
record of it.

`folderStatusWebhookLabel` → `statusExportLabel` moved too, for the same reason as the rest: it

## 11. Order of work

Each step compiles and the suite runs green at its end.

1. **`domain/Exports.kt` + `ExportChoiceTest`.** The model, with no caller. It is step one because
   everything else is named by it, and because a decoder is where a wrong decision is cheap to find.
2. **Schema 24 → 25 + `MigrationV24ToV25Test`.** The columns exist and nothing reads them. Additive,
   so it lands alone.
3. **`Exporters.kt` — `TxtExporter` + `TxtExportTest`.** The renderer, pure and asserted, before
   anything writes a file. The escaper is lifted here, and `DissolvedRecordsTest` is the proof it did
   not move.
4. **`WebhookExporter`, and `deliverPayload` rewritten as the dispatcher.** The riskiest step: the
   existing webhook suite must stay green through it, which is what says the refactor was a refactor.
   `WebhookCompatTest`, `WebhookBodyTest`, `SentCheckedFilesTest` and `ReviewRoundTest` are the guards.
5. **The record**: `ExportRecordEntity` and `kind`, the `WRITTEN` outcome, the DAO renames,
   `ExportHistoryScreen`. Now a txt export is visible in history and the *Last export* line has an
   answer for both kinds.
6. **The import dialog.** `ImportOptions`, the radio group, the four seeding/writing sites including
   `syncTodoUpstream`.
7. **Settings → Exports.** The new section, the two screens, the three switches moved, the old Webhook
   section deleted.
8. **The List card split**, and every `webhookEnabled`/`lastDelivery*` rename left over.

Steps 6, 7 and 8 are independent of each other; 1–5 are a chain.

**Then the device pass**, which is the acceptance list in [the spec](v0.5.6.md). It is not optional and
it is not replaced by the suite: a green unit run did not catch an app-launch crash on this project
before, and the two acceptance items that matter most — *a List over two Todos exports twice in two
mechanisms*, and *an upgraded database still webhooks* — are exactly the kind of thing a Robolectric
test can be built to agree with rather than to catch. §Acceptance items 2–8 are walked on the phone,
and what the walk finds is recorded in [`v0.5.6.md`](v0.5.6.md) under §Acceptance, as run.

**Nothing is committed until the release is whole.** The user's standing instruction is that the
big-version commit comes after the webhook change lands, and this is the webhook change.
