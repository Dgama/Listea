# Listea v0.7.0 — Implementation plan: a PDF viewer, and a mark with a quote

> **Status:** **Agreed (2026-10-21); implementation in progress on `spike/pdf-selection`.** The
> renderer, the template/model changes, the mark anchor, the storage shape and the export contract
> are settled below. Nothing is on `main` and no schema has changed yet.
> **Spec:** [`v0.7.0.md`](v0.7.0.md) — what the round is for. This document is how it is built.
> **Builds on:** v0.6.2 (schema 27, the v2 export contract, the per-Todo address model), v0.5.4 (a
> template is a version; stored results reference it rather than copy it)
> **Spike branch:** `spike/pdf-selection`
> **Architecture:** [`ARCHITECTURE.md`](../ARCHITECTURE.md)

## 0. Decision log

Every row is settled for this round. The review that produced most of them is
[`v0.7.0-reviewed.md`](v0.7.0-reviewed.md); its AndroidX recommendation is superseded by the
measurement in decision 2.

| # | Decision | Why |
|---|---|---|
| 1 | PDF rendering comes from **Nucleus PDFium 158.0.8111.0** (`dev.nucleusframework:pdfium`) | The platform's `PdfRenderer` exposes pixels only. The round's acceptance bar is *select a passage*, and a viewer that cannot name the characters under a pointer cannot offer that. Nucleus wraps PDFium and exposes `PageTextLayout`: per-character boxes and codepoints in PDF points, plus page size and text. One library, not a renderer beside a text extractor. Its manifest declares `minSdk 24`, the app's own floor |
| 2 | **AndroidX PDF is a deferred candidate, not a comparison this round** | `1.0.0-beta01` offers selection only on API 35+, or API 30+ with SDK extension ≥ 13. The OnePlus PGP110 (API 33) reports extension level 3, so `PdfDocumentRendererFactoryImpl` falls back to `PdfRendererCompatAdapter`: rendering works, but `selectPageText`, `getPageTextContents` and `searchPageText` throw `UnsupportedOperationException`. Adopting it would mean a device-class change or two renderers. The re-evaluation gate is in the spec: stable API, **full text capability across the device range Listea promises**, and an adapter/anchor already renderer-neutral. If the capability cannot cover that range, the product must raise its documented floor explicitly — not ship a feature that silently differs by device |
| 3 | Kotlin moves **2.2.10 → 2.3.20** and KSP **2.2.10-2.0.2 → 2.3.12** | The artifact's Kotlin metadata is 2.3.20 and a 2.2 compiler refuses it. AGP 9.3 carries built-in Kotlin, so the change is the version catalog and nothing else. The JVM suite passes after the move |
| 4 | The viewer is **template-independent and records nothing** | The spec's boundary. It is the `SwipeCard` the image and video renderers already sit in: a vertical page list, the card's pinch/pan transform, edge swipes still stepping between sibling Assets. Reading produces no event, no mark and no completion |
| 5 | **Selection is Listea's**, with the full reading order, handles and word snapping; **cross-page selection is deferred** | Nucleus's selection layer is mouse-only on touch. Long-press-then-drag is the platform's gesture on a phone, so the interaction is ours. Reading order (y-bands, column splitting, RTL) is taken from Nucleus's MIT algorithm because a quote must read the way the document does. A drag stops at the page edge; the anchor is versioned so a later page range is an extension, not a rewrite |
| 6 | **`AssetKind.PDF` and `MediaKind.PDF` are added**, and `assetViewerAvailable` answers true for PDF | A template scoped to `OTHER` would also govern text files and every unsupported archive. Kind must be answerable from the name at import time, so MIME cannot become its resolver. `configurableAssetKinds()` becomes an explicit `IMAGE, VIDEO, PDF`, because the built-in Media Asset Control's scope stays `IMAGE, VIDEO` and derivation from it would now omit PDF. A PDF also becomes selectable by the media filter, which is the honest consequence of the filter and the viewer sharing one vocabulary |
| 7 | A PDF template is **the existing Asset Control, scoped to PDF**; its `COMMENT` and `TAG` buttons are passage tools; a `BOOLEAN` button on a PDF is inert | No new template category and no parallel tool list. `COMMENT` is free text; `TAG` resolves its value from the current template, exactly as a file-level tag does. Passage tools live in the selection menu, so the review surface **hides the file-level chip row for a PDF**; completion and the rest are unchanged. Hiding `BOOLEAN` from the editor would be a type that changes when scope moves; documenting inertness is the smaller lie |
| 8 | The button encoding gains **version 2**, written **only when a comment is present**; the decoder reads 1 and 2 | Version 1's four fields can describe `boolean` and `tag`; `comment` needs the new type but no extra field, so the row shape is unchanged and the version announces the vocabulary. Writing 1 for a comment-free list keeps ordinary templates readable by builds that predate this round. `TemplateStore` must accept both supported versions when editing, or a v1 template could never be opened again |
| 9 | A mark is **one tool, one selection, one opaque id**: `toolId`, `authoredTemplateId`/`authoredTemplateVersion`, creation `kind`, optional `value`, a versioned quote anchor, timestamps | A mark is one statement with one identity. Applying a second tool to the same passage is a second selection. The authored reference is history and never moves; it is deliberately not a foreign key |
| 10 | Visibility and export resolve through the Task's **current attachments**, first match wins, and require the tool id **and the same kind** to still exist; hidden marks are kept, not deleted | The resolver rule already used by the chip row. Removing a template or a tool hides a mark and stops sending it; restoring the same id brings the same row back. Deleting a template must therefore never cascade into marks (decision 11) |
| 11 | Marks live in **`task_asset_marks`, schema 28**, keyed to the Asset; FK to `assets` with `CASCADE`; **no FK to templates or tools** | The Asset is the pair; a deleted Asset is no longer a file to point at. Template and tool ids are plain columns so template deletion cannot delete the record of what somebody said. Current version is resolved when shown or sent, never copied into the row |
| 12 | Anchor **authority vs hint**: fingerprint, page, `exactText`, prefix/suffix are authoritative; the PDFium character range and parser id are a **hint** | The hint makes the common case cheap; it never decides meaning. On reopen the hinted range's text is verified; otherwise the page reading order is searched, prefix/suffix break ties, and a unique match may span pages. No unique match → **detached**: kept, listed, not drawn, **not exported**. A successful relocation onto changed bytes rewrites the anchor's authoritative fields and fingerprint so the mark remains true and sendable |
| 13 | Export: `actions` is unchanged; a new per-Asset `marks` collection; **body `version` 3 only when a mark is present**, otherwise 2 | Images and videos keep their exact v2 bodies. A PDF's `actions` stays `[]` because its tools are passage-scoped. Hidden tools, kind-mismatched tools and detached marks are omitted. A tag's `value` is resolved from the current tool; a comment's is stored text. Export additionally verifies the file's current SHA-256 against the anchor's fingerprint; a mismatch, missing file or unreadable file omits the marks rather than asserting a stale page |
| 14 | Large-file policy: **64 MiB cap**, whole-file `ByteArray`, SHA-256 computed once per open off the UI thread, reader disposed on leave, errors mapped to placeholders | Nucleus opens only from `ByteArray`; this is the honest way to bound it. A larger file is refused with its name and a reason — never an `OutOfMemoryError`, a blank page or a crash. Password-required, damaged, unreadable and oversized are distinct messages |
| 15 | **No renderer type crosses the adapter boundary** | Domain, Room and export know `PdfPageText`, `PdfChar`, `QuoteAnchor`; only `PdfSession.kt`/`PdfPreview.kt` import `dev.nucleusframework`. Swapping to AndroidX PDF later changes the adapter and nothing stored or sent. The exported anchor contains no PDFium object or encoded implementation detail |
| 16 | License notices ship in the APK, and AAB packaging is verified per ABI | **Corrected in implementation (2026-10-21):** the wrapper is MIT, **pdfium-binaries is MIT (© 2014–2025 Benoit Blanchon)** and **PDFium itself is BSD-3-Clause**; the plan's "PDFium … / Apache-2.0" was wrong, and the Apache-2.0 text in the notices is **Listea's own LICENSE**. 25.58 MB of natives across four ABIs. The release AAB must split by ABI; the debug APK carrying all four is expected |

## 1. What the spike proved, and what it does not

The spike is deliberately not product code: `PdfPreview.kt`, `PdfSelection.kt` and three
instrumentation files (fixture, real document, text probe). It is evidence, not a design.

| Claim | Evidence |
|---|---|
| The document renders and pages scroll | On the phone, across the five real PDFs in the `pdftest` Upstream: English prose, Chinese prose, tables and an image-bearing page all render; the page list scrolls; edge swipes still step `2/5 … 4/5` |
| A PDF with no template opens and records nothing | Same walk: the viewer is reached from the Upstream's file browser, no Todo or template involved |
| Text is extractable from the real documents | Probe over all five: every page reports `pageText` with the same character count as the layout, and every character carries a non-zero codepoint — English, Chinese and Latin-script body text alike |
| Long-press and drag select text | Instrumentation on the phone against a generated fixture and a real Chinese document; the latter selected `中关村两院2026年博士后招聘` |
| Multi-line selection reads in order | Fixture across a heading and real-document across two body lines; the quote joins lines with a newline |
| Selection does not break browsing gestures | The same test scrolls the page list with a plain vertical drag after a selection, and pinches to zoom |
| Selection cannot be proven through adb | `input motionevent` and `input draganddrop` were unreliable for long-press-drag on this device (no root; production build). Instrumentation tests are the honest evidence |
| The PDF file is untouched | The preview reads through `contentResolver.openInputStream`; nothing opens the file for writing. Checksums before and after are part of the acceptance walk |
| AndroidX PDF cannot do the round here | Measured, not inferred: extension level 3 on the API 33 device; text APIs throw (decision 2) |

Known limits the product must remove:

- **Reading order is single-column.** The spike groups y-bands and sorts left-to-right; a table or
  two-column page quotes across cells.
- **No handles, no word snapping.** A press hits the nearest character, so a drag can start inside
  a word.
- **No mark UI.** `onQuote` logs; nothing stores, draws or exports.
- **Whole file into memory, no cap, no fingerprint, no disposal.** Fine for ≈1 MB fixtures only.
- **Spike labels and logging.** Removed with the view's promotion.

## 2. Boundaries and the new files

### Domain and storage (renderer-free)

- `domain/Domain.kt` — `AssetKind.PDF`.
- `domain/TemplateButtons.kt` — `ButtonType.COMMENT`, version 2 and its support rules.
- `domain/AssetMarks.kt` — `MarkKind`, `QuoteAnchor`, `AssetMark`, `normalizeQuote`, relocation
  helpers that work on `PdfPageText`-shaped values.
- `data/AssetMarkEntity.kt` — the Room row.
- `data/AssetMarkDao.kt` (or the mark queries on `ListsDao`) — observe/insert/update/delete.
- `TemplateResolver.governingFor(attachments, kind): StoredTemplateVersion?` — the first matching
  attachment, from which both the tool list and the authored reference come.

### The renderer adapter

- `PdfSession.kt` — the only file that imports `dev.nucleusframework` besides the page composable:
  - `data class PdfChar(index, codepoint, left, right, top, bottom)`
  - `data class PdfPageText(pageIndex, widthPoints, heightPoints, chars)`
  - `interface PdfSession { val pageCount: Int; suspend fun pageText(i): PdfPageText?; fun close() }`
  - `NucleusPdfSession(PdfReaderState)` implementation, and `rememberPdfSession(uri)` that loads,
    fingerprints, opens and disposes.
  - `PdfPageCanvas(session, pageIndex, modifier)` — the rendering half.
- `PdfLoader.kt` — bounded read, size policy, SHA-256, error mapping; pure enough to test without
  Android for the policy, instrumented for the stream.
- `PdfReadingOrder.kt` — port of Nucleus's MIT reading order (y-bands, column split, RTL), with
  `text(lo, hi)`, `positionAt(point)`, `wordRangeAt(position)`, `rangeOfWord`.
- `PdfSelection.kt` — rewritten product selection (press → drag → handles → word snap → menu),
  consuming `PdfReadingOrder`.
- `PdfMarks.kt` — anchor creation, resolution against a `PdfSession`, overlap hit-testing.
- `PdfPreview.kt` — the page list, per-page selection and mark layers; no `SPIKE` text or logging.

## 3. Implementation phases

Each phase ends with its tests green before the next begins.

### Phase 1 — Vocabulary, template scope and button encoding

Files: `domain/Domain.kt`, `FileArrange.kt`, `Catalog.kt`, `Settings.kt`, `SettingsScreen.kt`,
`TemplateDetailScreen.kt`, `domain/TemplateButtons.kt`, `TemplateStore.kt`, `TemplateResolver.kt`,
`data/ListeaDatabase.kt`, tests.

1. `AssetKind.PDF("pdf")`, declared between `VIDEO` and `OTHER`. `MediaKind.PDF("pdf", "PDFs",
   setOf("pdf"))` before `TEXT`; `assetKindOf` maps it to `AssetKind.PDF`. `Importer`'s
   supported-content rule becomes `kind in PICTURE, VIDEO, PDF`.
2. `assetViewerAvailable` answers true for PDF. `reviewBlockFor` therefore stops blocking a
   PDF-only Task. `configurableAssetKinds()` becomes the explicit `listOf(IMAGE, VIDEO, PDF)` and
   its KDoc stops claiming it is derived from the built-in. `assetControlHeading(PDF)` and the
   scope chip label gain "PDF".
3. `ButtonType.COMMENT("comment")`; labels and helper text. In `CustomActionFields`, a comment has
   no webhook value: hide that field and write `recordValue = ""`. Existing types unchanged.
4. **As implemented:** `TEMPLATE_BUTTONS_VERSION` stays **1** — it is the base shape, and the
   migration, the seed fixture and a dozen tests read it as *what a build that has never heard of a
   comment writes*. Version 2 gets its own constant, `TEMPLATE_BUTTONS_COMMENT_VERSION = 2`; add
   `SUPPORTED_TEMPLATE_BUTTON_VERSIONS = TEMPLATE_BUTTONS_VERSION..TEMPLATE_BUTTONS_COMMENT_VERSION`
   and `buttonsVersionFor(buttons)` (2 iff any comment). Redefining the one constant to 2 was the
   plan's first wording and was dropped: a single constant would have made every v1 writer and
   fixture claim to write v2. `encodeTemplateButtons` stays four tab-separated fields.
   `decodeTemplateButtons` accepts 1 and 2 and drops a `comment` line from version 1 (a row v1
   could not have written). Unknown versions still return null.
5. `TemplateStore.create`/`update` write `buttonsVersionFor(...)`; the edit guard becomes
   `latest.buttonsVersion in SUPPORTED…`. `ListeaDatabase`'s seed writes the computed version too.
6. Tests:
   - `FileArrangeTest`: `assetKindOf("a.pdf") == PDF`, `"a.txt" == OTHER`, viewer true for PDF
     (replacing the two `assertFalse` cases in `CatalogTest`/`FileArrangeTest`).
   - `TemplateScopeTest`: PDF round-trips; old scope payloads decode unchanged; overlap sees PDF.
   - `TemplateButtonsTest`: v1 payloads decode as before; v2 comment round-trips with an empty
     fourth field; writer chooses 2 only with a comment; unknown version null; v2-only build
     reading v1; a v1 comment line is dropped.
   - `TemplateStoreTest`: a v1 template can be edited; the appended version is 1 without a comment
     and 2 with one; an unreadable latest version still refuses.
   - `TemplateResolver` test: a PDF-scoped control governs PDFs and nothing else; `governingFor`
     returns the same first match.
   - Catalog/import tests: a PDF Asset is viewable and a PDF-only Task is eligible.

### Phase 2 — Product viewer and selection

Files: `PdfSession.kt`, `PdfLoader.kt`, `PdfReadingOrder.kt`, `PdfSelection.kt`, `PdfPreview.kt`,
`MediaPreview.kt`, `ReviewScreen.kt` (plumbing only), instrumentation tests.

1. **Loader and lifecycle.** Resolve length via `openAssetFileDescriptor` when available; reject
   `> 64 * 1024 * 1024` before reading. When unknown, stream at most cap + 1 and reject if it
   overflows. Hash while reading (one pass), close every stream. Map failures:
   `TooLarge("This PDF is too large to open (64 MB limit)")`, `Password("PDF is
   password-protected")`, `Damaged("This PDF is damaged")`, `Unreadable("PDF could not be
   opened")`. Read and hash on `Dispatchers.IO`; open the reader on the main/confined thread the
   library requires, then hand the session to composition. `DisposableEffect` closes it on leave
   or URI change; `state.error` still surfaces mapped.
2. **Adapter.** `NucleusPdfSession` wraps `PdfReaderState`, converts each page's `PageTextLayout`
   into `PdfPageText`/`PdfChar`, and exposes `pageCount`. `PdfPageCanvas` keeps using `PdfPage`.
   Nothing else imports Nucleus.
3. **Reading order.** Port Nucleus's algorithm from its published source at the pinned version
   (MIT; notice in Phase 6): banding by vertical overlap, splitting a band into columns at
   horizontal gaps, per-line direction from the script, RTL runs emitted in logical order. Public
   shape: ordered character ids plus lines with geometry; `text(lo, hi)` joins lines with `\n`;
   `wordRangeAt` uses Unicode word boundaries within a line.
4. **Selection UI.** Long press selects the nearest position; drag extends; release shows two
   handles at the line ends. A handle drag updates its end continuously and snaps to word
   boundaries. Selection rects are drawn per line. A tap outside clears; a tap inside a stored
   mark opens the mark sheet (Phase 4). Dragging is consumed once selection has begun; ordinary
   drags still reach `LazyColumn`. Pinch and edge swipes are unchanged.
5. **Menu.** One small floating menu at the selection: **Copy** always; each `COMMENT`/`TAG`
   tool from the governing control when there is one, in template order. Copy writes the quote to
   the clipboard. No Select all.
6. **No-text pages.** `chars.isEmpty()` → no selection layer and no menu; the page still renders.
7. **Review-surface plumbing.** `ReviewScreen` resolves the page kind; for a PDF it hides the
   file-level `assetBand` and passes the tool list down. `ItemPreview`/`MediaPreview` gain an
   optional PDF overlay parameter defaulting to null, so the read-only List viewer is unchanged
   and draws no marks this round.
8. Tests:
   - Pure JVM `PdfReadingOrderTest` over synthetic pages: prose, two columns, a table-like grid,
     overlapping bands, RTL, word snapping, `text()` newlines.
   - Pure `PdfSizePolicyTest`: exact cap passes, cap + 1 fails, unknown length bounded.
   - Instrumentation `PdfViewerTest`: open each real fixture; scroll; pinch; edge-swipe back and
     forth; a scanned page offers no selection; a selected passage copies.
   - Instrumentation `PdfSelectionTest`: handles appear, word snapping, multi-line quote order.
   - Fixtures for two-column and RTL generated in `androidTest` with
     `android.graphics.pdf.PdfDocument` (`PdfFixtureFactory`) so no binary is committed unless the
     existing `androidTest/assets` already covers them; verify extraction first, because a
     generator without a usable ToUnicode map proves nothing.

**As implemented.** The device run of `PdfViewerTest` and `PdfSelectionTest` found three real
defects that synthetic boxes could not, all fixed in Phase 2 and pinned by JVM tests:

- **`quoteFor` lost the newline at a selection boundary.** It concatenated `text(before)` +
  `text(selected)` + `text(after)`, and `text()` only joins lines *inside* a range. A quote on the
  first line therefore had suffix `betatwo` where the page says `alphaone\nbetatwo`, and every
  position after it in the anchor was one character short. The newlines are now re-inserted from
  the line indices at the selection's edges; `PdfQuoteTest` pins prefix, suffix and text at each
  boundary.
- **PDFium's layout reports the line break as characters.** It emits `\r` and `\n` as point-sized
  characters at the end of every line; kept as text they became two zero-height lines, so every
  pair of lines quoted with three newlines between them. ISO control characters are dropped as
  structure, not content.
- **A synthetic space can be a point, not a box.** Zero-width spaces (and zero-height ones) were
  either dropped — `"alpha beta"` quoted as `"alphabeta"` — or, when kept, became a line of their
  own and broke the line above them. A degenerate whitespace glyph now joins the band whose
  vertical span contains it, and at equal x it sorts before the glyph it separates.

Generated fixtures draw Hebrew **one character per `drawText` call**: a whole string is shaped
and bidi-reordered by the platform, so the bytes no longer say which character was drawn where.
The RTL test also asserts the extractor's raw output first; on this device PDFium reports an RTL
run in logical order with right-to-left boxes, which is why the reading order must trust geometry
rather than the stream index. `PdfPreview` pages carry a `pdf-page-<index>` test tag so a scan's
rendered page can be asserted without waiting for a selection layer that will never appear.
`PdfPreviewSpikeTest` is kept as the original spike; `PdfViewerTest` is the product test.

### Phase 3 — Mark domain, anchor, schema 28

Files: `domain/AssetMarks.kt`, `domain/PdfAnchor.kt` (or same file), `data/AssetMarkEntity.kt`,
`data/ListsDao.kt`, `data/ListeaDatabase.kt`, `app/schemas/…/28.json`, `ListsViewModel.kt`,
`TemplateResolver.kt`, tests.

1. Domain types (decision 9/12):
   ```kotlin
   enum class MarkKind(val key: String) { COMMENT("comment"), TAG("tag") }
   const val ANCHOR_FORMAT_VERSION = 1
   const val PDF_CHAR_PARSER = "nucleus-pdfium/158.0.8111.0"   // one constant, used at creation

   data class QuoteAnchor(
       val version: Int,
       val documentFingerprint: String,
       val pageIndex: Int,
       val exactText: String,
       val prefix: String,
       val suffix: String,
       val charStart: Int,
       val charEnd: Int,
       val charParser: String
   )

   data class AssetMark(
       val id: String,
       val assetId: String,
       val toolId: String,
       val authoredTemplateId: String,
       val authoredTemplateVersion: Int,
       val kind: MarkKind,
       val value: String,
       val anchor: QuoteAnchor,
       val createdAt: Long,
       val updatedAt: Long
   )
   ```
2. **Entity** `task_asset_marks` exactly as the spec lists, with `Index("assetId")` and
   `ForeignKey(AssetEntity, ["id"], ["assetId"], onDelete = CASCADE)`. No template FK.
3. **Migration 27 → 28**: `CREATE TABLE` with the same columns and the FK/index; log `27 -> 28`;
   register in the migration chain; bump `@Database(version = 28)`; commit `28.json`. New installs
   use Room's create path.
4. **DAO**: `observeMarksForAsset(assetId): Flow<List<AssetMarkEntity>>`,
   `getMarksForAssets(assetIds)`, `insertMark`, `updateMarkValue(id, value, updatedAt)`,
   `updateMarkAnchor(id, …authoritative fields…, updatedAt)`, `deleteMark(id)`. All single-row
   writes; no template joins.
5. **Resolver**: `governingFor(attachments, kind)`; `controlFor` delegates to it. `PdfTools`
   helper: a control's buttons of type COMMENT/TAG, keeping order, plus `toolFor(id, kind)`.
6. **Mark resolution** (`PdfMarks.kt`, pure over `PdfSession`):
   - `anchorFrom(selection, pageText, order, fingerprint)`: quote text from the reading order,
     prefix/suffix up to 24 characters of normalized reading-order text, PDFium char ids,
     `PDF_CHAR_PARSER`.
   - `resolve(marks, session, tools)`: visible marks only; try the fast path when
     `anchor.fingerprint == session.fingerprint` and `anchor.charParser == PDF_CHAR_PARSER` and
     the hinted range's verified text equals `normalizeQuote(anchor.exactText)`; otherwise search
     every page's normalized reading-order text for `exactText`, break ties with prefix/suffix,
     require exactly one match. A match on a different fingerprint persists the relocated anchor
     in the background after the session is open. No match → `Detached`.
   - `Rect` geometry per line, converted to page points, shared with the selection drawing code.
7. **ViewModel**: `observeAssetMarks(assetId)`, `createPdfMark(...)` (validates non-blank comment,
   mints a UUID, `now()`), `editMarkValue(id, value)`, `deleteMark(id)`, and the relocation update.
   Writes use `launchDb`/`writeOrder` like every other record.
8. Tests:
   - `AssetMarkAnchorTest`: hint verified vs mismatched; repeated quote disambiguated by prefix and
     suffix; no unique match → detached; relocation across pages; changed fingerprint relocates
     and rewrites; never resolves to a range whose text differs.
   - `AssetMarkVisibilityTest`: tool missing, template missing, kind changed, version upgraded with
     the same id, authored reference never consulted for visibility.
   - `MigrationV27ToV28Test` and updates to every existing chain (`MigrationChainTest`,
     `MigrationSmokeTest`, `MigrationV26ToV27Test`, fixtures `CURRENT = 28`, `subtractV28…`):
     table shape, index, FK cascade on Asset deletion, template deletion leaves marks,
     `27.json` untouched, `28.json` committed.
   - DAO test: create/edit/delete; deleting an Asset removes its marks; deleting a template does
     not.

### Phase 4 — Marks in the review surface

Files: `PdfPreview.kt`, new `PdfMarkLayer.kt`/`PdfMarkSheet.kt`, `PdfSelection.kt`,
`MediaPreview.kt`, `ReviewScreen.kt`, `ListsViewModel.kt`.

1. `ReviewScreen` collects `viewModel.observeAssetMarks(page.assetId)` (only for a PDF page) and
   passes marks, the governing `PdfTools`, the governing ref and the callbacks into `AssetRun` →
   `ItemPreview` → `MediaPreview` → `PdfPreview`. No ViewModel inside the renderer.
2. Draw visible marks over the page: comment and tag use distinct translucent colours; every
   overlapping mark is drawn. Tapping a highlight opens a sheet listing every mark under the
   point — tool name, quote, comment text or configured tag value, page — with **Delete**
   (confirmation) and **Edit** for comments. Detached marks appear in a banner ("N marks not
   found in this document") and the same sheet, without geometry; they can be deleted.
3. Selection menu: Comment opens a dialog with a multiline field; Save is disabled for blank text
   and creates one mark. Tag creates one mark immediately. Both close the selection. The mark
   appears in the same frame through the Flow.
4. When the template, tool or kind disappears while the viewer is open, the Flow/resolver
   recomposition hides the marks and their menu entries; Copy remains. Nothing is deleted.
5. No-template PDF: no tools, no marks, Copy only; the chip row stays hidden.
6. Tests: visibility/kind logic is covered in Phase 3; instrumentation covers tap-to-sheet,
   overlap listing, edit, delete, and the "template removed while open" state.

### Phase 5 — Export

Files: `data/PayloadRows.kt`, `data/ListsDao.kt`, `Exporters.kt`, `Webhook.kt`, `ListsViewModel.kt`,
tests.

1. **Rows.** Add `getPayloadMarks(assetIds): List<PayloadMarkRow>` with mark id, tool id, kind,
   value, page, exact text and anchor fingerprint; group by asset in `PayloadFacts`. Add
   `fingerprintByAsset: Map<String, String>` computed for Assets with marks by hashing the file
   on IO, bounded by the same 64 MiB cap; missing/unreadable/oversized → absent.
2. **Views.** `ExportAssetView` gains `marks: List<ExportMarkView>` (id, kind, toolId, page, text,
   value). In `exportAssetView`:
   - resolve the governing control as today; for a PDF it is the PDF control;
   - keep a mark only when `control.buttons` has its `toolId` **and** that tool's type key equals
     the mark's creation kind;
   - require `mark.fingerprint == fingerprintByAsset[asset.assetId]`;
   - `value` = stored text for COMMENT, current tool `recordValue` for TAG;
   - order by creation time then id, stable.
   `actions` is untouched and is `[]` for a PDF because it has no file-level selections.
3. **Version.** `EXPORT_VERSION = 2` remains the base; add `EXPORT_VERSION_MARKS = 3`.
   `buildWebhookPayload` writes 3 iff any Task has an Asset with a non-empty `marks`, else 2. An
   Asset writes `"marks"` only when non-empty, after `"actions"`; key order otherwise unchanged.
   `TxtExporter` carries the same body, unchanged.
4. Tests:
   - `ExportMarksTest`: comment and tag shapes; tag value follows the current tool; hidden tool,
     kind mismatch, changed/missing fingerprint and detached marks omitted; stable order.
