# Listea v0.2.0 — Task, Asset, and Review Foundations

> **Status:** Executable iteration specification  
> **Audience:** Coding agent and maintainers  
> **Architecture:** [`ARCHITECTURE.md`](../../ARCHITECTURE.md)  
> **Release principle:** Same Listea outside, different Listea inside.

## 1. Purpose

v0.2.0 is the foundation release that separates the media-specific implementation from Listea's general review model without expanding the product into candidate review, PDF review, vocabulary, or a template-building platform.

The release succeeds when today's image/video workflow behaves as before but is represented internally as:

```text
List -> ListEntry -> Task -> Image/Video Asset
                         -> current TaskState
                         -> ReviewEvent history

Task Review Template Version -> rapid media judgment
Asset Viewer Template Version -> image/video presentation
```

This iteration changes meaning and ownership before it adds new capability.

## 2. Mandatory first step: inspect, map, and propose

**Do not modify production code or the database as the first action.**

Before implementation, inspect the current repository, schema, migrations, tests, and state flows. Then write a concise implementation/migration plan for maintainer review. The plan must include:

1. the current database version and every persisted entity involved;
2. the current identity spaces: Room row IDs, root-relative file identity, queue identity, resume identity, and webhook public IDs;
3. how List Review and Quick Review resolve an item and read/write checked, favourite, and custom-action state;
4. how review rounds, filtering, resume position, List completion, and webhook triggers currently work;
5. how source-backed rows and manual file-less rows differ;
6. the proposed mapping from every legacy entity/field to Task, Asset, ListEntry, TaskState, ReviewEvent, Template, and TemplateVersion;
7. the migration sequence, backfill rules, rollback/failure risks, and validation queries/tests;
8. the minimum UI/state refactor needed to show Task and Asset navigation as separate concepts;
9. any conflict between the repository as found and this specification.

The plan may challenge mechanisms in this document. It may not silently change the semantic invariants. If a conflict affects identity, data preservation, webhook compatibility, or user-visible review behavior, stop and report it before coding.

Do not infer the final schema merely by renaming the current `item` types. The existing model deliberately combines several responsibilities; the purpose of the inspection is to separate them without losing behavior.

## 3. Verified baseline at specification time

The following describes the public `main` branch inspected on 2026-09-15. Re-verify it before implementation because the repository may have changed.

- The app is Android/Kotlin/Compose with Room.
- `ListeaDatabase` is version 12 and persists `lists`, `list_items`, `file_review_state`, and `webhook_history`.
- A folder-backed `list_items` row stores List membership and source metadata. Its projected review decision comes from `file_review_state`.
- `file_review_state` is unique by Storage Access Framework root URI plus root-relative path. This makes checked/favourite/custom-action state shared across Quick Review and List Review.
- A manual item has no file and keeps its decision fields on its own `list_items` row.
- Checked, favourite, and custom actions are independent current values. Custom action rows store internal action IDs, not mutable display labels or webhook values.
- Quick Review creates no List and directly resolves a folder's files.
- A review queue is a snapshot. Checked items remain in the active round; filters narrow the round without redefining whole-List progress.
- A List stores a resume item row ID rather than a position index.
- Legacy webhook public item IDs are stable for a row/registration and identify one arrival. Reintroducing the same file may produce another public ID.
- Webhook behavior is coupled to Lists/settings today, with fixed events/payloads and retained delivery history.
- Existing media behavior includes image/GIF/video viewing, zoom, video controls, a left-swipe completion flow, backward review navigation, action controls, filtering/sorting, resume, source refresh, and explicit file-management operations.

This baseline is a regression contract, not the target architecture.

## 4. Normative invariants

Every implementation plan and code change must preserve these statements:

1. `Task != Asset != List != ListEntry`.
2. A Task has `0..N` Assets.
3. Existing media becomes one Task with one Image or Video Asset.
4. Domain identities are stable, opaque, globally unique, and independent of path, filename, row order, or List position.
5. Task and Asset have different IDs even in the one-Task/one-Asset media case.
6. Checked/current state and review history are separate.
7. Current review state belongs to the Task, not to an Asset or ListEntry.
8. Review history permits repeated review and is not erased when current state changes.
9. Asset Viewer Templates and Task Review Templates are different template kinds.
10. Template versions are immutable once referenced by a review; edits produce a new version.
11. Core contains no workflow-specific semantics.
12. Task Navigator is outside the Task Review Surface and every Asset Viewer.
13. Asset Navigator changes Assets within one Task and never changes the Task.
14. Raw gestures map to semantic review actions; gesture names are not domain actions.
15. Generic Task navigation does not steal gestures required by an Asset Viewer.
16. Existing webhook behavior remains a compatibility concern and does not enter Task, Asset, or Template.

## 5. Required scope

### 5.1 Establish the domain boundary

Introduce a clear domain representation for at least:

- Task;
- Asset and Asset kind;
- List membership/ListEntry;
- TaskState or an equivalently explicit current-state model;
- ReviewEvent;
- Template, TemplateVersion, and TemplateKind;
- review-round/queue identities needed by the current UI.

Names may differ only when the plan explains why they preserve the same meanings. Avoid a generic `Item` at the core boundary. Legacy persistence/UI types may temporarily retain their names behind mapping code.

Domain logic should not depend on Compose, Android URI types, Room annotations, webhook payload classes, or profession-specific models. Platform/source references can be represented behind appropriate boundary values or adapters.

Do not introduce architecture layers only for symmetry. Add the minimum mapping/repository/use-case seams needed to stop UI, persistence, media rendering, and webhook code from sharing one ambiguous model.

### 5.2 Add stable domain identity

Create and persist stable IDs for new durable domain entities. UUID or an equivalent collision-resistant opaque scheme is acceptable.

Required properties:

- a Task keeps its ID when renamed, reordered, reviewed again, reopened, or reached from another review context;
- an Asset keeps its ID when presentation state changes;
- Task ID and Asset ID are never interchangeable;
- Template and TemplateVersion identities are distinct;
- every newly recorded ReviewEvent has its own ID;
- no domain ID depends on a filesystem path or Room autoincrement sequence.

Preserve legacy webhook public IDs separately. Do not reuse them as Task IDs, rewrite them during backfill, or change their on-wire meaning.

### 5.3 Migrate legacy media and manual data

The migration plan must account for every existing row and decision.

For source-backed media, the conceptual target is:

```text
existing source/file identity
    -> one stable Task
    -> one stable Image or Video Asset
    -> preserved current TaskState

existing List membership row
    -> ListEntry pointing to that Task
```

For a manual item, the conceptual target is:

```text
existing manual item
    -> one stable Task
    -> zero Assets
    -> preserved current TaskState
    -> preserved ListEntry
```

The exact tables and staging sequence must follow repository inspection. However, migration must:

- preserve titles, ordering, List membership, source links, missing-source flags, cached metadata, current decisions, List progress, and usable resume behavior;
- deterministically avoid creating duplicate Tasks for the same legacy source identity during one migration;
- keep manual Tasks distinct even when their titles match;
- preserve orphaned/missing-source decisions rather than dropping them;
- preserve old webhook records and the public IDs used in future legacy payloads;
- be transactional where supported and fail rather than silently discard ambiguous data;
- include an upgrade test from the current shipped schema and representative older migration paths supported by the app.

Legacy data contains current values but no trustworthy sequence of past reviews. Backfill TaskState, but **do not fabricate ReviewEvents or a fake review count**. New review events begin when the v0.2 event-writing behavior is active. If a migration marker or provenance is needed, it must not be counted as a human review.

### 5.4 Separate current state from review history

Preserve `checked` as current Task state with the meaning “dealt with in Listea.” It remains independent of favourite and custom actions.

For new v0.2 interactions:

- a semantic judgment/state transition updates the current TaskState;
- the same operation appends an appropriate ReviewEvent when it represents a human review action;
- changing or clearing current state does not delete prior events;
- review count, if exposed internally or in tests, is derived from qualifying ReviewEvents;
- repeated review of one Task is valid;
- all state/event writes that form one user action are atomic from the caller's perspective.

Before coding, the implementation plan must state exactly which existing interactions create events: swipe completion, checkbox completion/uncompletion, favourite changes, custom-action changes, and any revisit with no submitted action. Avoid counting incidental screen opens or navigation as reviews. If current product semantics are insufficient to decide an event boundary, report the choice rather than guessing invisibly.

v0.2 does not require a review-history screen, editing historical events, analytics, or exposing review count in the UI.

### 5.5 Introduce minimal versioned templates

Implement only the template structure necessary to express the existing media workflow without media assumptions in Core.

At minimum there must be two explicit kinds:

1. **Asset Viewer** — presents compatible Image/Video Assets and owns content-specific interactions such as zoom and playback.
2. **Task Review** — defines the rapid-media review actions/completion behavior over the Task and composes the selected Asset viewer.

Each review event/result must be able to reference the exact Task Review Template Version that gives it meaning. Viewer selection/configuration must likewise be version-addressable where persisted meaning depends on it.

Built-in, code-defined template definitions are sufficient. It is acceptable for v0.2 to ship only the template(s) required by existing media review. Do not build:

- a template editor or builder;
- a marketplace or sharing system;
- a database table per UI component;
- a universal component registry/schema language;
- recruitment, vocabulary, quiz, or check-in templates;
- user-authored layout logic.

The persistence design should allow later template versions and kinds to be added without reinterpreting completed reviews. It does not need to model every possible future component now.

### 5.6 Make Task and Asset navigation visibly separate

Refactor the review composition to reflect this ownership:

```text
Task Navigator
└── Task Review Surface
    ├── Asset Navigator
    │   └── Asset Viewer
    └── Task Review Controls
```

Requirements:

- Task Navigator provides explicit previous/current/next context and a route back to the List/review origin.
- Task Navigator is outside the viewer and does not use the filename as its control entry point.
- Asset Navigator selects the current Task's Asset without changing Task.
- Keep Task Navigator present in the one-Asset media case.
- Keep Asset Navigator structurally present in the one-Asset media case for v0.2; a simple `1 / 1` or equivalent is acceptable.
- A zero-Asset manual Task must not crash or be coerced into a fake Asset. Preserve its existing usable behavior; a minimal empty/no-asset presentation is acceptable if it enters the review surface.
- Do not undertake a broad visual redesign. The current rapid-review experience remains the regression baseline.

Task and Asset navigation state must use stable IDs, not array indices as durable identity.

### 5.7 Route gestures through semantic actions

Keep physical interaction handling at the UI/template boundary. Define semantic intents such as complete/check, set action, select Asset, previous Task, and next Task as appropriate; do not send `swipeLeft` into the domain layer.

Preserve the current rapid-media left-swipe behavior by binding it to the semantic checked/completion operation and advancing only as the review flow's consequence of that successful operation. Preserve backward navigation and viewer behavior as found in the repository unless the pre-code plan identifies a conflict.

Do not add universal swipe-based Task navigation. Task navigation must not intercept image zoom/pan or video controls, and the design must leave future PDF scroll/selection gestures available to a PDF viewer.

Buttons, shortcuts, accessibility actions, and gestures that mean the same thing must invoke the same state transition path, including event creation and legacy webhook completion checks.

### 5.8 Preserve webhook behavior behind a compatibility boundary

v0.2 does not redesign webhook configuration, events, payloads, history, confirmation, resend, failure handling, or post-delivery file-management behavior.

Preserve, subject to tests against the repository as found:

- per-List webhook configuration and app-default Quick Review configuration;
- existing UI status and enable/disable behavior;
- the four current event names and trigger timing;
- current payload field names, inclusion/filter rules, ordering, and null behavior;
- existing public item IDs and their arrival semantics;
- webhook history records and resend behavior;
- confirmation before data leaves the device;
- deletion offers only after actual successful delivery, where currently configured.

Implement translation from the new domain/read models to the legacy payload at the webhook boundary. Forbidden examples include:

```text
Task.webhookUrl
Asset.webhookAction
Template.webhookEvent
Task.id = legacyWebhookItemId
```

Do not create a general Exporter abstraction in this release. A small compatibility adapter/seam is enough.

### 5.9 Preserve Quick Review and List Review semantics

Both entry paths must resolve to the same Task identity and TaskState for the same source-backed media.

Preserve these behaviors:

- Quick Review works without creating a List.
- Checking/actioning from either path is visible from the other.
- Deleting a List does not erase Task state.
- Review queues remain snapshots for the duration of a round.
- Filtering/sorting narrows the active round but not whole-List progress or completion.
- “unchecked only” behavior remains independent from payload filtering.
- source refresh/missing/restored behavior preserves recorded judgment.
- List completion and webhook triggering remain based on the same user-observable conditions as before.

## 6. Explicit non-goals

The following are out of scope for v0.2.0:

- PDF rendering, parsing, caching, annotation, highlighting, or any PDF-specific code;
- candidate/recruitment workflows or business vocabulary in Core;
- vocabulary, quiz, check-in, insurance, or other new Task types;
- ZIP/folder/filename grouping for multi-Asset Tasks;
- generalized Importer or Task Builder implementation;
- generalized Exporter framework, JSON/CSV/XLSX export, or webhook redesign;
- template builder, component table, low-code layout system, marketplace, sharing, or user-authored templates;
- evidence/annotation model;
- review-history UI, event editing, metrics, or analytics;
- mixed-template Lists;
- per-List or per-ListEntry completion for the same Task;
- cloud sync, accounts, collaboration, permissions, iOS, or a chosen multiplatform framework;
- a comprehensive repository-layer rewrite unrelated to the required boundaries;
- broad visual redesign or optimization that hides navigators for single-Asset Tasks;
- changing file-management safety rules.

Do not add placeholder tables, empty interfaces, or configuration screens for these items. Preserve a boundary that lets later work add them naturally.

## 7. Implementation sequence

After the required inspection plan is accepted, use this sequence unless repository evidence justifies a safer alternative:

1. Pin existing behavior with regression tests where coverage is missing.
2. Add pure domain types, typed IDs, semantic actions, and template definitions/version references.
3. Add persistence/mapping and a tested Room migration without changing UI behavior.
4. Route List Review and Quick Review through the new Task/Asset/TaskState read and write paths.
5. Add ReviewEvent writes atomically with qualifying current-state changes.
6. Separate Asset Viewer composition from Task Review and Task navigation.
7. Add the minimal Task Navigator and Asset Navigator presentation.
8. Adapt legacy webhook/file-management paths at the boundary.
9. Run unit, migration, instrumentation, and manual regression checks; fix regressions before cleanup.
10. Remove obsolete duplicate state paths only after proving no active caller reads or writes them.

Keep commits or change sets reviewable by concern. Do not combine the schema migration, a large visual rewrite, and unrelated cleanup into one opaque change.

## 8. Acceptance criteria

### Domain and identity

- [ ] Production review flow uses distinct Task, Asset, and ListEntry concepts.
- [ ] A media Task and its single Asset have different stable IDs.
- [ ] The model and tests permit zero, one, and multiple Assets without special-casing Task identity.
- [ ] No domain identity derives from path, filename, row number, or List position.
- [ ] Reordering, reopening, and repeated review do not change Task or Asset IDs.
- [ ] Core/domain code contains no recruitment or other workflow-specific branching.

### State and history

- [ ] Existing checked, favourite, and custom-action values survive migration.
- [ ] Checked/current state is stored or exposed as Task state, not Asset or membership state.
- [ ] Qualifying new human review actions append ReviewEvents linked to Task and exact TemplateVersion.
- [ ] Unchecking or changing the current result leaves earlier ReviewEvents intact.
- [ ] Repeated review produces a valid history independent of the final checked value.
- [ ] Migrated current state does not create fake human ReviewEvents.
- [ ] State transition and event append cannot visibly diverge after one successful user action.

### Templates and presentation

- [ ] Asset Viewer and Task Review are explicit, different template kinds.
- [ ] The existing image/video workflow runs through versioned built-in template definitions.
- [ ] Referenced TemplateVersions are immutable.
- [ ] Task Navigator wraps the review surface and is not owned by the Asset Viewer.
- [ ] Asset Navigator changes Assets only.
- [ ] Task and Asset navigators remain structurally present for a one-Asset Task.
- [ ] A zero-Asset Task is representable and does not crash resolution or rendering.
- [ ] Viewer gestures remain available to the viewer; no universal Task swipe intercept is added.
- [ ] Swipe/button paths for the same semantic action share domain behavior.

### Migration and compatibility

- [ ] An automated migration test upgrades a populated v12 database to the v0.2 schema.
- [ ] The test covers source-backed media, manual items, checked and unchecked state, favourite/custom actions, missing sources, ordering, resume, Lists, webhook config, public IDs, and webhook history.
- [ ] No legacy public item ID is regenerated or repurposed as a Task ID.
- [ ] Same-source Quick Review and List Review resolve the same Task state.
- [ ] Deleting/rebuilding a List preserves shared review state as before.
- [ ] Webhook payload snapshot/golden tests pass unchanged unless a separately approved compatibility change is documented.
- [ ] Existing older-to-current Room migrations still pass before the new migration is applied.

### Regression

- [ ] Folder browsing and Quick Review still work.
- [ ] Persistent Lists, progress, refresh, missing/restored source handling, and resume still work.
- [ ] Images, animated GIFs, and video render as before.
- [ ] Pinch/zoom and video transport controls are not degraded.
- [ ] Left-swipe checking/advancing, backward review navigation, checkbox, favourite, and custom actions behave as before.
- [ ] Filters, sorting, unchecked-only rounds, and fixed queue snapshots behave as before.
- [ ] List completion and all existing webhook trigger paths behave as before.
- [ ] Webhook confirmation, history, retry, error display, and post-success deletion offer behave as before.
- [ ] Explicit file deletion/save/share safety behavior is unchanged.
- [ ] App process restart preserves IDs, current state, history, and resume behavior.

## 9. Required tests and evidence

At minimum, provide:

- pure unit tests for typed identity, Task/Asset cardinality, state/history independence, semantic action routing, and template version immutability;
- DAO/query tests for shared Task state across review contexts and List progress projection;
- Room migration tests using a representative populated v12 fixture;
- tests proving legacy webhook public IDs and payloads remain unchanged;
- tests proving a left swipe and the equivalent explicit control reach the same semantic state/event path;
- UI or instrumentation coverage for navigator ownership and gesture non-interference where practical;
- a manual regression checklist with results for image, GIF, video, Quick Review, List Review, webhooks, and manual items.

The final implementation report must include:

1. the accepted mapping and final schema/domain relationships;
2. migration behavior and how ambiguous/legacy cases were handled;
3. tests run and their results;
4. any known limitations or deferred cleanup;
5. confirmation that every non-goal remained out of scope.

## 10. Completion gate

v0.2.0 is complete only when the internal model no longer equates a reviewable Task with a file or List row, all existing user data and visible media-review behavior are protected, and a future PDF Asset Viewer could be added as an Asset-side extension without redesigning Task, List, review history, identity, or webhook compatibility.

Passing compilation alone is not completion. A migration without regression evidence is not completion. New abstractions that the active media workflow bypasses are not completion.
