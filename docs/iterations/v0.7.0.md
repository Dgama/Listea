## Why this round

The v0.6.x rounds were about making the model visible and trustworthy: an export that is a
contract, a destination that belongs to the Todo, a history grouped by the round that produced it.
None of them changed what Listea can review. **v0.7 is about that.**

Today Listea reviews pictures and videos. A PDF is already imported and catalogued — the folder
importer counts one as supported content, and it shows up in a Task's files — but it is
deliberately not reviewable: the queue says this build has no viewer for it. So a PDF in a Todo is
a Task the user can tick but never see, and the only honest thing they can do with it is leave it
alone.

PDF is the first content kind to change that, and it is first for two reasons. It is the most
common non-media file Listea already accepts, and it is the first one that is not merely **looked
at** but **read**. A picture is judged as a whole; a document is judged in sentences. That
difference is the round.

## What the round adds

### 1. A PDF viewer, with no memory of its own

A PDF Asset opens in a viewer that can actually be read: pages scroll vertically, pinch zooms in
on a passage, and a horizontal swipe at the edge still means *previous file* / *next file*, the
same as on a picture. Reading is reading — panning, zooming and turning pages are browsing, not
decisions.

The viewer is **not a template**. Like the video player, it exists to show the file and produces
nothing of its own. A PDF whose Task carries no PDF template is browsable and nothing more: no
Listea tools, no marks drawn, no marks exported.

Text selection is **reading**, not reviewing, so it exists whether or not a template does:

- long-press starts a selection, dragging extends it;
- two handles at the ends can be dragged after release, and the selection snaps to word
  boundaries;
- the selection menu always offers **Copy**; Listea's review tools are added to that menu only
  when the governing template offers them;
- the reading order is the document's own: y-bands, column splitting and RTL, not the spike's
  single-column reduction. A table or a two-column page must quote in the order a person reads it;
- tapping a stored highlight opens the mark behind it; tapping elsewhere clears the selection.

**Select all is not added this round.** Copying the passage in front of the user is the reading
function the viewer owes; selecting the whole document is an editor feature with no review use
here. **Cross-page selection is explicitly deferred**: a drag stops at the page edge. This round's
acceptance names a passage, not a range across pages.

The viewer also states what it cannot do: a password-protected, malformed, unreadable or oversized
file becomes a placeholder with the file's name and a reason, never a crash or a blank sheet.

### 2. A template that governs PDFs

A PDF template is **the existing Asset Control, scoped to PDFs** — not a new template category and
not a parallel tool list. It is created, scoped, edited and attached exactly as a media control is,
and its version history works the same way.

Its buttons become **passage tools** on a PDF:

| Tool | What it records | What it exports |
|---|---|---|
| **Comment** | The reviewer's free text, attached to a passage | `kind: "comment"`, `value`: the text |
| **Tag** | The configured tag value, attached to a passage | `kind: "tag"`, `value`: the configured value |

A PDF-scoped template's **On / off** buttons are not passage tools and are not offered on a PDF.
The template editor still allows them, because a template can be re-scoped; on a PDF they are
inert. Documenting this is kinder than hiding the type from the editor and then changing the type
when the scope moves.

For a PDF Asset the review surface's **file-level chip row carries no tools**: the tools live in the
selection menu, because a PDF tool is applied to a passage rather than to the file as a whole. The
frame's dismissible file bar still exists — it is the frame's, not the template's — and holds only
its trailing **Info** icon, exactly as it does over a picture. The completion checkbox and the rest
of the review surface are unchanged.

**The frame is fixed and the components are the template's.** A review surface has two kinds of
part. The **static frame** — the navigator, the completion bar, and the file's dismissible bar with
its Info icon — belongs to every template and to no template: it cannot be added, removed or
customised. The **dynamic components** are what a template version records: chip rows for media,
passage tools for PDFs. This round writes that boundary down in [Templates](../templates.md); it is
what lets the Info icon keep working when a template is removed, and it is the foundation later
template work grows on.

**The button encoding gains version 2.** Version 1 rows are four fields and can only describe
`boolean` and `tag` buttons; version 2 adds `comment`. A version is written as **2 only when the
button list actually contains a comment**, so a template edited in this build but holding no
comment stays readable by a build that has never heard of version 2. A decoder that meets a version
it cannot read still fails closed, as every payload in this codebase does.

### 3. A mark that points at a passage

This is the change worth the round. Today an action is a word attached to a file: *this picture is
favourite*. A PDF produces many marks, each attached to a sentence somewhere inside it, and each
carrying both what the document said and what the reviewer said about it.

**One tool per selection.** A selection offers Copy and the template's tools; choosing one creates
one mark. Applying a second tool to the same passage is a second selection, not a second item in one
menu. That keeps a mark one statement with one identity, and it keeps the menu the size of the
template rather than the size of the interaction.

A mark holds:

- an **opaque id** of its own, minted when it is made;
- the **tool id** it names — the same stable id a template button has, never its label;
- **the template version it was authored under** (`authoredTemplateId` + `authoredTemplateVersion`);
- its **kind** at creation (`comment` or `tag`) and, for a comment, the reviewer's **text**;
- a **quote anchor** (below);
- timestamps.

**Authored-under and currently visible are two different facts.** The authored reference records
what was in force when the mark was made; it is history and never moves. What is **shown and sent**
is resolved through the Task's **current attachments** and the version each Task holds: the first
attached template whose scope admits PDF, and the tool with the mark's id in that version. That is
the same first-match resolver the chip row uses. A mark whose template or tool is no longer there
is **hidden, never deleted**; a later version that offers the same id brings it back. This is the
template rule already used for buttons, applied to a passage.

Marks are stored in Listea, next to the Asset, and **the PDF is never modified**: the viewer reads
the file and draws marks over it. Deleting a mark deletes it for good; a comment's text can be
edited; a tag mark is corrected by deleting it and applying the tag again. Overlapping marks are
all drawn; tapping an overlap lists every mark under the point rather than guessing which one was
meant. A comment or tag can be read from that sheet without reopening the PDF's tools.

### 4. The quote anchor

An anchor is what lets a mark survive leaving and reopening the Task — or a PDFium upgrade, a
renamed file, or a document that changed. It stores two kinds of fact, and the difference matters:

**Authoritative**

| Field | Why |
|---|---|
| `anchorFormatVersion` | A later build may add a field; this says how to read the row |
| `documentFingerprint` | SHA-256 of the file's bytes, so *same path, different bytes* is detectable |
| `pageIndex` | The page the passage was on |
| `exactText` | The quote as the reviewer saw it, the thing a person can verify |
| `prefix`, `suffix` | The characters on either side, for choosing between repeated quotations |

**Non-authoritative, a hint only**

| Field | Why |
|---|---|
| `startChar`, `endChar` | PDFium page-local character indices |
| `charParser` | The parser that produced them, e.g. `nucleus-pdfium/158.0.8111.0` |

On reopening:

1. **Same bytes, same parser** — the character range is used as a fast path, and the text it names
   is *still verified* against `exactText`. A match restores the original geometry directly.
2. **Anything else** — the page's reading order is rebuilt and searched for `exactText`; when the
   quotation occurs more than once, `prefix` and `suffix` must pick exactly one. Searching spans
   pages, because a changed document may move a passage.
3. **No unique match** — the mark becomes **detached**: it is kept and **not drawn**, but it is
   **listed in the file's Info sheet** with its stored quotation, tool and value, under
   *Not in this document*. Nothing over the page announces it. It is also **not exported** while
   detached, because a quotation the receiver cannot find in the document is a false statement
   about the document. A later edit that brings the text back makes it visible again.

The character range is never trusted on its own. It exists to make the common case cheap, not to
decide what the mark means.

### 5. What a PDF exports

Pictures and videos keep exactly what they have today: `actions` is an ordered array of strings,
one set per file, contract version 2.

A PDF Asset adds a **`marks`** collection beside `actions`. `actions` itself does not change type
and is not overloaded; a PDF's `actions` stays an empty array because its tools are passage-scoped.
The body's `version` becomes **3 only when the payload actually carries a mark**; every payload
without one — including every image and video payload — stays version 2, byte for byte.

```json
{
  "version": 3,
  "event": "list.completed",
  "list": { "id": 7, "title": "Reading", "completedAt": 1790000000000 },
  "tasks": [
    {
      "id": "task-public-id",
      "title": "Paper.pdf",
      "isCompleted": true,
      "templates": [ { "id": "tpl", "name": "PDF review", "version": 2 } ],
      "assets": [
        {
          "id": "asset-public-id",
          "title": "Paper.pdf",
          "relativePath": "papers",
          "sourceMissing": false,
          "actions": [],
          "marks": [
            {
              "id": "mark-id",
              "kind": "comment",
              "toolId": "comment-1",
              "quote": { "page": 3, "text": "the sentence the reviewer selected" },
              "value": "I think this overstates the result"
            },
            {
              "id": "mark-id-2",
              "kind": "tag",
              "toolId": "funny-1",
              "quote": { "page": 4, "text": "another passage" },
              "value": "funny_sentence"
            }
          ]
        }
      ]
    }
  ]
}
```

- A mark is sent only when its tool resolves through the Task's **current** attachments; a hidden
  mark is omitted, not sent with a stale value.
- A tag's `value` is the configured value of the tool in that current version, resolved at export
  time exactly as a file-level tag is.
- A comment's `value` is the stored text; editing it changes the next export and nothing already
  sent.
- `quote.page` and `quote.text` are the stored anchor. Detached marks are not sent.

## Storage

A new table, **schema 28**, keyed to the Asset:

- `task_asset_marks(id, assetId, toolId, authoredTemplateId, authoredTemplateVersion, kind, value,
  anchorVersion, documentFingerprint, pageIndex, charStart, charEnd, charParser, exactText, prefix,
  suffix, createdAt, updatedAt)`.
- A foreign key to `assets` cascades when the Asset itself goes — an Asset deleted by an import is
  no longer a file to point at. **There is no foreign key to a template or a tool.** Deleting a
  template, or a button from one, never deletes a mark; it hides it, which is the whole rule.
  `authoredTemplateId` and `authoredTemplateVersion` are plain columns for that reason, and the
  current version is resolved when shown or sent rather than copied into the row.
- The quote's authoritative fields and the character hint are columns of the same row; the anchor
  format version says how to read them.

## Implementation notes and deviations

**Status when this section was written (2026-10-21):** the round is implemented on
`spike/pdf-selection`. The full JVM suite is green (985 tests in 111 classes), the Compose
instrumentation suite compiles, and `assembleDebug`/`bundleDebug` succeed. The device acceptance
walk was started on the maintainer's OnePlus PGP110 (API 33, schema 28) the same day; what it has
covered so far is appended under [Acceptance](#acceptance-walk--2026-10-21), and the status line at
the top stays *acceptance walk under way* until the whole checklist is.

- **The licences are not what the plan said.** Phase 6 verified the actual artefacts rather than the
  plan's line: the **Nucleus wrapper is MIT** (© 2025 kdroidFilter), **pdfium-binaries is MIT**
  (© 2014–2025 Benoit Blanchon), and **PDFium itself is BSD-3-Clause** (© 2014 The PDFium Authors).
  The plan's *"PDFium BSD-3-Clause / Apache-2.0"* was wrong: no PDFium component is Apache-2.0. The
  Apache-2.0 text in the notices is **Listea's own `LICENSE`**, included so the About page states
  the whole licensing picture. The plan's decision log and Phase 6 are amended to say so.
- **An About page had to be added.** The plan said to surface the notices "where the app already
  shows About/licences". There was no such surface — the app had never shown its version or any
  licence. So v0.7.0 adds **Settings → About Listea**: one index row under History, naming the
  running `BuildConfig.VERSION_NAME` and displaying the notices from a raw resource. It is a new
  screen rather than a move, and `docs/settings.md` describes it.
- **`quote.page` is a zero-based page index** — the stored `pageIndex`, written unchanged. The
  example body's `"page": 3` therefore names the **fourth** page. The plan did not say which
  convention the wire used; [Webhooks](../webhooks.md#passages-and-why-they-are-version-3) and
  [Exports](../exports.md#pdf-passages) now state it, because "page 3" in a receiver's log is
  otherwise ambiguous.
- **The viewer does its own reading order and selection.** Nucleus's selection layer is mouse-only
  on touch, so long-press-drag, the handles and word snapping are Listea's; the reading order
  (vertical bands, column splitting, RTL) is a port of the wrapper's MIT algorithm rather than a
  call into it. The plan's §0 records this; it is repeated here because it is the reason the
  selection tests are ours rather than the dependency's.
- **A missing mark is silent, and the banner is gone.** The first implementation reported a mark the
  document could not place through a banner pinned over the top of the page list, which on a real
  document partly covered the text the reviewer had opened. The banner was removed. The PDF's file
  bar now carries the frame's **Info** entry, and the Info sheet lists every visible mark — the
  quoted passage, the tool, the page, and *Not in this document* for a detached one — beside the
  file's basic facts. Nothing over the page says a mark is missing. This follows the explicit
  product decision: missing marks are handled silently, with no proactive prompt; a badge dot on the
  Info icon was considered and deliberately deferred, because the icon is already a shared
  component and no other template has an entry point for such a prompt yet. The frame/component
  boundary is written down in [Templates](../templates.md).
- **A quote made only of whitespace cannot carry a mark.** A long press that lands between two words
  selects the gap alone, and the resolver normalises a quote down to its words; a space normalises
  to nothing, so a mark anchored to one could never be drawn and would be reported not found on the
  document it was made from. The selection menu withholds the template's tools in that case and
  keeps **Copy**, which copying a gap still deserves. Pinned by `PdfQuoteTest`, verified on device.
- **A Comment button is never a file-level action.** The template editor offers the type on any
  template, for the same reason it still offers On / off to a PDF template: a template can be
  re-scoped, and hiding a type would change what an existing button means when the scope moves. The
  chip row, the Task's badge row and the exported `actions` array therefore **omit Comment
  buttons** rather than drawing a control that can record nothing: `ResolvedAssetControl.actions`
  filters them, while `buttons` keeps them so the PDF selection menu can offer them. One filter at
  the point where all three consumers already agree is what keeps a Comment from becoming a chip
  on a picture or an empty string in an export. Pinned by `SettingsTest`.
- **The List's webhook address applies only to a List that chose Webhook.** v0.6.2 let a stored List
  address override every webhook group of an inheriting round while the List page showed the field
  under *Same as the Todos* too. v0.7.0 narrows both sides: the field is drawn only under
  **Webhook**, and `planExports` ignores it under **Same as the Todos**. This is a deliberate
  semantic change from v0.6.2: a setting the page does not show must not redirect a round, and
  *same as the Todos* means exactly that — each Todo's own address, including on a List that once
  held an override. The stored value is not cleared; it applies again if the List chooses webhook.
  `WebhookAddressPlanTest` pins the new rule, and `docs/exports.md` / `docs/webhooks.md` are amended.
- **Doc correction: inheriting rounds key by Todo, not address.** `docs/exports.md` had said two
  Todos sharing an address merge under *Same as the Todos*; the planner and
  `WebhookAddressPlanTest` have always kept them as two payloads, because the Todo is what is being
  inherited from. Merging by address is the **Webhook** choice's behaviour. The doc now says so.
- **Acceptance gained a mixed-kind folder Task.** The user added a `test` Upstream whose
  `ListeaAcceptance_folder` holds three PDFs, two JPGs and an oversized PDF, and asked for exactly
  one Task to be created from it by **folder-as-task**, added to a List, and reviewed beside Tasks
  that hold a single kind. It is the first fixture where one Task's files resolve through two
  different templates, so it is the case that proves per-file resolution and the exported shapes
  together. It is part of the walk below.

## Acceptance

The round is accepted when, on the device, with the real fixtures:

- A PDF Asset in a Todo or a List can be opened and read: pages scroll, pinch zooms a passage, and
  edge swipes still step the queue.
- A passage can be selected with handles, word-snapped, and copied; a comment can be attached to
  one passage and a tag to another, in one PDF and repeatedly; one selection produces one mark.
- Two-column, table, Chinese and RTL fixtures produce quotations in reading order.
- The marks survive leaving and reopening the Task: they are drawn over their passages again, and
  they appear in the exported body as `marks` with the right kind, tool and quote.
- A comment can be edited; a mark can be deleted; an overlap can be read and the intended mark
  chosen.
- Removing the template, or the tool from it, hides the marks and stops sending them without
  deleting them; restoring the same id brings the same mark back. A changed document never draws a
  mark over different text; an unmatchable anchor is listed as detached in the file's Info sheet,
  is silent on the page, and is not exported.
- The PDF's file bar appears and disappears with a tap on a part of the page that carries no
  highlight, and its Info icon lists the file's marks — comments and tags, placed and missing —
  beside its basic file facts. Tapping a highlight opens that mark and does not toggle the bar.
- A Task holding both a PDF and a JPG loads the PDF template for the PDF and the media template
  for the picture; a review of it alongside single-kind Tasks records the right decisions and
  produces the right exported `marks` and `actions` in History.
- A PDF with no PDF template remains viewable, offers no Listea tools, renders no marks and exports
  none; Copy still works.
- Opening a document with no text layer (a scan) succeeds and offers no selection.
- A PDF above the viewer's size limit (64 MiB) is refused with a clear message rather than an
  unbounded heap copy or a crash.
- The PDF file on disk is unchanged by any of it (checksum before and after).
- Pictures and videos review, export and behave exactly as they did in v0.6.2 — their payloads are
  still version 2 and their `actions` are unchanged.
- The AndroidX PDF decision is recorded as deferred, and the re-evaluation gate below is written
  down where the next round can find it.

## Not in this round

- **Cross-page selection.** Deliberate; see §1. A later round that needs a mark spanning pages
  extends the anchor with page ranges, which is the reason the anchor is versioned.
- **Reading annotations made by other PDF readers.** Feasible in principle; deliberately not part
  of this round.
- **Writing Listea's own marks back into the PDF file.** Marks live in Listea.
- **OCR of scanned pages.** A scan is browsable and offers no selection, because the selection
  layer comes from the text the PDF already carries.
- **More content kinds or more template types.** They are the rest of v0.7.x.

## Renderer decision and the AndroidX gate

The round uses **Nucleus PDFium 158.0.8111.0**. The measurement that decided it: AndroidX PDF
`1.0.0-beta01` can render on Android 12–14 only through the platform PDF module, and its selection
and text APIs require **Android 15, or API 30+ with SDK extension ≥ 13**. The maintainer's API 33
device reports extension level 3; on it AndroidX PDF falls back to a renderer that throws
`UnsupportedOperationException` for `selectPageText` and every text-content call. Adopting it today
would mean either a different device class or two renderers, and both are worse than one renderer
that works on every device Listea supports.

**Re-evaluation gate.** AndroidX PDF may replace Nucleus only when **all** of the following hold:

1. it is a stable (non-beta, non-experimental at the API Listea uses) release;
2. its full text-selection capability is available across the device range Listea promises to
   support at that time — not merely on the maintainer's next phone;
3. the viewer adapter boundary and the renderer-neutral anchor are in place, so the swap changes no
   Room column and no exported field.

If (2) cannot hold, the product must **explicitly raise its documented capability/API floor**
rather than shipping a feature that silently differs by device. "The maintainer's phone is new"
is not a gate: a single device says nothing about the users Listea supports.

## Questions still open

1. **Third-party annotations.** Whether a highlight or note made in another PDF reader should be
   read and turned into marks. Not this round.
2. **What happens when the file changes or disappears.** The anchor now detects and represents both;
   what the *reviewer* should be offered (re-attach? discard?) remains open at the product-policy
   level. Detached marks are the safe default until it is decided.
3. **What a receiver sees.** Version 3 introduces `marks`. The receiver has to live with the
   contract version; the shape above is the proposed one. If the receiver guarantees that unknown
   fields are ignored, an additive v2 extension remains a possible simplification — but the
   version line is the honest place to announce a new shape, and the round ships v3.

**Decided since the first draft:** marks live in Listea and the PDF is never modified; the viewer
browses and only selection is a reading feature; a template's absence hides marks without erasing
them; tags are configured by the template and comments carry free text; the anchor has
authoritative text and non-authoritative character hints; deletion and comment editing are part of
the lifecycle; Copy survives without a template and Select all does not; cross-page selection is
deferred.
