## The change in one paragraph

Ten iterations have been spent getting the model right, and they succeeded: an Upstream, a Todo, a
Task, a List, a Template and an Export now mean different things, and each can be named on its own.
The cost is that the screens carry the model instead of the work. This round does one thing: it
re-specifies what a round **leaves the device as** — the JSON a webhook POSTs and the tab-separated
body a `txt` export writes — so downstream automation can be built on it. The presentation pass that
takes the model back out of the **surface** moves to **0.6.2**, where it can be judged against a
format that is no longer in flux. Nothing is removed: the complexity stays in the data and the code.

## Why

### 1. The output is an interface now

The user's words:

> 我注意到当前保存到txt或者输出的webhook格式与第一个release的版本有所不同。由于我webhook后续会接上
> 一些自动化工作流，所以我们需要重新设计一下输出的webhook格式。

An export used to be *the thing that leaves*. Since it is about to feed real workflows, it is a
**contract**: one shape, one vocabulary, one version, and tests that pin it. A contract is not
allowed to be a rendering detail that changes when the internals do.

Two consequences follow, and both are in scope:

- **Webhook and `txt` must move together.** v0.5.6 made them two renderings of one payload
  (`ExportPayload` → `buildWebhookPayload` / `TxtExporter.render`). A new format that only one of
  them speaks would recreate the disagreement the export model was built to remove. The same facts,
  in the same order, spelled for two receivers.
- **The routing is not renegotiated.** v0.5.6's rules — a round splits by its source Todos, a List's
  own choice overrules the split, *export nothing* is a real answer — describe **which** payloads a
  round produces. This round changes only what one payload **looks like**. If the format needs a
  field the routing cannot supply, that is a finding for the plan, not a licence to change routing
  quietly.

### 2. 无痛 is a presentation problem, not a feature problem — deferred to 0.6.2

The user's words:

> 当前版本很多功能在ui上还是比较厚重的堆叠。我们需要进行一些整理和优化，让信息呈现更有层次。

The first release felt simple because every screen answered one question at a time. The model was
smaller then, so the property came for free. Now it does not, and the work is to restore it
deliberately — **primary, secondary, on demand** — without shrinking what the app can do.

The pass is not a hunt for new ideas. Earlier iterations already recorded concrete instances of the
same defect, and they are the starting inventory rather than a complete list:

| Recorded where | The instance |
| --- | --- |
| [v0.5.4](v0.5.4.md) | The dissolved-history picker shows several identical `Demo` rows, told apart only by *N Tasks judged*. |
| [v0.5.6](v0.5.6.md) | Settings says **Ask to delete after webhook** while it fires after *any* export. |
| [v0.5.6](v0.5.6.md) | A Todo's export method is settable but nowhere readable; you must open the import dialog to ask. |
| [v0.5.6](v0.5.6.md) | `review.exited` is announced as **Review left** whether the queue finished or was backed out of. |

They are different sentences with one cause: the information is present but not **ordered**. The
pass is a hierarchy pass — what a screen leads with, what it explains once, and what it keeps one tap
away.

The first of those was already pencilled in as **0.5.7's** business by the iteration that found it
([v0.5.4](v0.5.4.md): *"presenting it is the next release's question"*). The user has now moved the
pass to **0.6.2**: the output contract is the prerequisite for the acceptance test, and moving
screens while the format is still settling would move them twice. The inventory above is kept here
as 0.6.2's starting list, not as this round's work.

## This round's job, and the one after it

### A. The output (first, because it is a contract)

The user supplies the target format. This round writes it down, implements it once, and makes both
renderings obey it.

- Decide the wire vocabulary: fields, nesting, event names, id and timestamp semantics, what a
  receiver may key on, and what is deliberately absent.
- Decide **versioning**: whether the body carries its own version, and what a receiver built on the
  previous shape sees after the upgrade. The `txt` body already has a version line; the JSON does
  not. That asymmetry is a decision to make, not a detail to inherit.
- Render once: keep `ExportPayload` as the single intermediate, and change the two spellings
  together.
- Pin the shape in tests at the seam where it matters — the bytes a receiver parses, not the helper
  functions around them.
- Walk a real round against the user's n8n endpoint on the attached phone.

#### relativePath: the material's folder, not the Task's packaging

The first concrete requirement of this half, stated by the user after a real round:

> 1. 对齐初版release，是指，原来的初版输出的relativepath会是cos, danbooru而非空字符串
> 2. 不依赖task，是指，不管我这里选择file-as-task，folder-as-task，这个relativepath输出都是上面1里的结果

The round that prompted it reviewed the Upstream folder `2026-10-07`. On the phone that folder
holds `cos/`, `danbooru/`, `jable/`, `reddit/`, `rule34video/`, `x/`, `xasiat/` and
`xvideo-jp/`; the eight items in the body are files from inside `cos/`. Every one went out as
`"relativePath": ""` — the field said the Upstream root while the material sat one folder down.

The requirement is:

- **`relativePath` is a property of the material's location**, resolved from the file or folder's
  path in the Upstream. It is not read from the Task, from the import run, or from
  `task_imports.groupPath`.
- It is **relative to the Upstream's linked folder** — the root the user added — not to whichever
  folder a review round happened to open. A round scoped to `cos` and a round scoped to
  `2026-10-07` must report `cos` for the same file.
- For a file it is the containing folder: `cos`, `danbooru`, and `cos/2026` for a nested one. A file
  directly under the Upstream root is `""`; a manual item with no source file stays `null`.
- For a folder-as-Task the item is the folder, and its `relativePath` is that folder's own path
  (`cos`), so the two packagings say the same thing about the same material.
- Therefore packaging changes only *which items exist*, never what any item's `relativePath` says
  about where its material is. The same files report the same values under file-as-Task and
  folder-as-Task.
- A **task-defined** path is a different field for a later round. It is not this one, and adding it
  must not change these values.

This section recorded the requirement only when it was written; the format rewrite implemented it.
`webhookRelativePath` and the bare-name path are gone. The value is now
`assetFolderOf(AssetEntity.relativePath)`, a split-and-drop of the path the Asset already stores
relative to the Upstream's linked root, so packaging cannot influence it.

#### The hierarchy: event → list → task → asset

The v0.1 body has no Task. It is one flat `items` array in which each entry is a file and the thing
judged at the same time. The model has not believed that since v0.2, and the user's target is a body
that describes the model it actually has:

> 新输出的webhook，应当完整，且结构化的展示整个task和审批（具体指action和以后其他模板的人工信息输入以及判断）的信息。换句话说，要能从webhook完整还原某次审批流
>
> 结构类似于：event->list->task->asset
>
> 比如，上面的relativepath应当属于asset本身的属性。而iscompleted原来属于item，但现在应当属于task。另外，还会要记录新内容，比如，template。template应当属于task级别的信息。

Where each level comes from:

| Level | Carries | Lives today in |
|---|---|---|
| event | what happened | `ExportPayload.event` |
| list | id, title, completedAt | `ListEntity` / `ExportPayload` |
| task | identity, display name, `isCompleted`, `template` | `tasks`, `task_state`, `task_imports.assetControls` |
| asset | identity, name, `relativePath`, its own decisions | `assets`, `task_asset_state.selections` |

- **`relativePath` is the asset's**, because it describes where a file sits and a folder-as-Task
  Task may present several files.
- **`isCompleted` is the task's**, because completion is one judgment about one Task however many
  files it presents.
- **`template` is the task's**, because the attachment is stored on the Task: `task_imports`
  names the template versions the Task was imported under.
- **The decisions are the asset's**, because a mark lives on the Task–Asset pair
  (`task_asset_state`). A task-level union cannot say *which* file carries *which* mark, which is
  exactly what reconstructing a round needs. This last placement follows from the model rather
  than from the user's words and is to be confirmed with the field-level shape.
- "Complete" means the body carries everything needed to rebuild the round: every Task, every
  Asset under it, the template version(s) governing it, and each Asset's decisions.

#### The field-level decisions

Settled in conversation, and the plan builds to them:

- **Snapshot, not history.** The body describes what the round saw and decided as it stands when the
  round ends. The export filters decide membership exactly as they do today (*export checked items
  only*, *review unchecked items only*). `review_events` is not read this round; a timestamped
  history would be an additive `reviews` array later.
- **`actions` stays an array of strings** — the wire values of the selected buttons. Objects with
  `id`/`value` were considered and deferred: the future template types are not clear enough to
  commit the shape, and the cost of adding them later is low.
- **`templates` carries identity only** — `id`, `name`, `version`. The control definitions
  (`controls`) are deliberately omitted; they can be added later without restructuring the level.
- **Two ids.** `task.id` is a public id minted per Task; `asset.id` is the existing per-file public
  id. The old `items[].id` therefore lands on `assets[].id`, and a receiver's key moves with the
  hierarchy.
- **The body is versioned.** `"version": 2` is this contract; the unversioned v0.1 body is 1. The
  txt body's `listea-export` line moves to 2 with it.
- **A task with no Assets** (a legacy manual item) is still a Task. Its `assets` is `[]`; the shape
  does not invent a file for it.

The shape the plan starts from:

```json
{
  "version": 2,
  "event": "review.exited",
  "list": { "id": 0, "title": "Selected folder", "completedAt": null },
  "tasks": [
    {
      "id": "…",
      "title": "Shiina_01.webp",
      "isCompleted": true,
      "templates": [
        { "id": "builtin.media.asset-control", "name": "Media Asset Control", "version": 4 }
      ],
      "assets": [
        {
          "id": "…",
          "title": "Shiina_01.webp",
          "relativePath": "cos",
          "sourceMissing": false,
          "actions": ["favorite", "cust1"]
        }
      ]
    }
  ]
}
```

A folder-as-Task keeps the same shape: the Task's `title` is the folder (`cos`) and its `assets` are
the files inside it. The txt body is a linearisation of the same levels — a `task` line followed by
one `asset` line per asset — rather than a second flat item list.

### B. The presentation — deferred to 0.6.2

Deferred by the user's direction. These bullets are its scope when it comes, not this round's.

- Inventory every screen: what it shows, what it leads with, what is really an explanation the user
  reads once and should not have to read again.
- Apply one hierarchy across the app: a primary line, a secondary line, and detail on demand.
- Resolve the recorded instances above where they fall in this scope.
- Acceptance is behavioural: the core flows — add an Upstream, Create Tasks, review, complete a
  List, see the export — are walkable without leaning on the explanatory paragraphs the current
  screens added to compensate for the model.

## Rough plan

1. **Build the payload model** — the Task/Asset views the wire needs, and the database reads that
   assemble them for both a List round and a folder round.
2. **Implement the format** in both renderers, bump both version lines, and re-pin the wire tests at
   the bytes a receiver parses.
3. **Add the missing second-template creation path**, because the acceptance test cannot run
   without it (see below).
4. **Walk the acceptance round on the phone**, including the user's real endpoint and a txt export.
5. **Record what the phone says** and package `0.6.0`.

The detailed plan should decide, at minimum: the exact DAO reads and the id-minting path for Tasks
and shared Assets; how a Task with no Assets is rendered in each body; the txt line vocabulary; and
what happens to the old body (a hard cut at version 2, as agreed by the version field).

## Acceptance (v0.6.0)

The user's definition, over the Upstream `10-17`:

a. **Create the first Todo**: enter the `cos` subfolder and create it **file-as-Task**, attached to
   **template 1, version 4**.
b. **Create the second Todo**: create it over the whole `10-17` folder **folder-as-Task**, attached
   to **template 2, version …** (to be created).
c. **Create a List** containing some Tasks from both Todos.
d. **Review part of the List** — the part that includes Tasks from both Todos — and leave the
   review, which fires the webhook.
e. **Finish the rest of the List**, which completes it and fires the second webhook.

The round passes when the flow completes without a detour and both bodies have the agreed shape.
The standing invariants still hold:

1. A webhook POST and a `txt` export of the same round describe **the same facts, in the same
   order**, and both match the agreed format.
2. A downstream workflow keyed on the new format needs **no transformation** to consume it.
3. Every v0.5.6 export-routing behaviour still holds: a round splits by source Todo unless the List
   chooses, and *export nothing* still exports nothing.
4. An upgrade over an existing database loses nothing, and the phone reports the new packaged
   version (`0.6.0`).

## What had to be settled before implementation

Both findings below were resolved in the plan and are in the build: a minimal **New template** entry
was added (Settings → Templates, `TemplateStore.create`), and both Asset ids are minted at row
creation and backfilled on upgrade. The paragraphs are kept as the record of what was asked.

**A second template lineage cannot be created today.** The review and export pipeline is already
per-Task: `task_imports.assetControls` holds each Task's attachments; every read path resolves by
Task id (`getAssetControlsForList`, `observeAssetControlsForList`, `CatalogRow.assetControls`,
`exportItemView`); and `TemplateResolver` holds every lineage. So two Todos with different templates
in one List already resolve independently. What is missing is the authoring path: `TemplateStore`
has no create, the Templates screen only lists and opens, and the import dialog's **New template** is
a placeholder. The acceptance test's template 2 therefore needs a minimal creation flow as part of
this round — or the test runs with two *versions* of one lineage, which does not exercise two
templates.

**A shared file makes two Assets.** The acceptance test imports `cos` twice: once under Todo 1
(file-as-Task over `cos`) and once under Todo 2 (folder-as-Task over `10-17`). The model allows the
two Tasks and their two Assets, but the compatibility side table `legacy_item_ids` names only one
Asset per path. The new asset-level ids need a public id for both Assets; that is a plan item, not a
blocker.

## What was implemented

**The contract.** `EXPORT_VERSION = 2`; JSON keys `version, event, list, tasks`; a Task carries
`id, title, isCompleted, templates, assets`; an Asset carries `id, title, relativePath,
sourceMissing, actions`; a template carries `id, name, version`. The txt body's `listea-export` line
says `2` and its records are `task` (6 fields), `template` (5), `asset` (7) and `action` (2). Both
renderers read one `ExportPayload` built by one assembly function (`exportTaskViews`), and the tests
pin the bytes a receiver parses rather than the helpers around them.

**The ids.** `publicId` columns were added to `tasks` and `assets` (schema 25 → 26), minted at row
creation so both delivery paths and both renderers see the same name. The migration backfills from
`legacy_task_ids` and `legacy_item_ids`, gives a single-Asset Task's List id to its file, refuses to
copy a multi-Asset Task's List id onto an arbitrary file, and mints the rest at the row's own
creation time. It fails rather than shipping an empty id.

**The second template.** Settings → Templates gained **New**: a name prompt creates a lineage with
version 1 seeded from the shipped media control, so it is attachable immediately. That is what makes
the acceptance test's "template 2" possible.

**The path.** `relativePath` is `assetFolderOf` over the Asset's stored Upstream-relative path, so
the same file reports `cos` under file-as-Task and folder-as-Task alike.

### The phone walk

The acceptance round ran on a OnePlus PGP110 (API 33), installed **over** the previous build so the
25 → 26 migration ran on the existing database; the app reported `0.6.0` and nothing was lost. The
walk used the Upstream already on the phone, `2026-10-07`, because **no `10-17` folder exists
there**; it has the same shape the acceptance needs (a root holding `jable` and `cos`). Template 1
was at **version 2**, not 4 — the phone's lineage has no version 4 — so the first Todo attached v2.

What the walk established, on real data:

- **The two packagings did not change the path.** Folder-as-Task over the root produced Tasks
  `jable` and `cos` holding their folders' files; file-as-Task over `cos` produced single-file
  Tasks. Every Asset in both reported the folder it sits in — `jable` or `cos` — never the Task's
  own name or the List's.
- **Two templates ran side by side.** The folder Tasks carried the newly created *Folder control*
  (v1); the file Tasks carried the built-in *Media Asset Control* (v2), each Task naming its own
  attached version.
- **Both events carried the whole round.** `review.exited` went out with 4 Tasks and 51 Assets and
  the one unchecked Task marked `isCompleted: false`; `list.completed` carried the same four Tasks
  all completed and set `completedAt`. Both POSTs answered HTTP 200, and the history kept both
  bodies verbatim.
- **The txt body matches the JSON.** A one-Task round left in the same List wrote
  `listea-export 2` with `task` at 6 fields, `template` at 5, `asset` at 7 and its `action` line —
  the same facts in the same order as the JSON, including the Asset's `cos` path and the
  `favorite` mark on one file.
- **Item counts stayed Task counts.** Every dialog and history row said *4 items* for a round of
  4 Tasks and 51 Assets.

### Deviations from this document, and why

- **Actions are per Asset, resolved by kind.** The field-level section above placed decisions on the
  Asset but left the resolution *"to be confirmed"*. It is confirmed, and against the Task-wide
  union the old builder used: a Task holding an image and a video sends the image's mark on the
  image only. The chip row already resolved this way, and a union cannot reconstruct which file a
  mark was on, which is this round's stated goal. An Asset whose kind no attached template admits
  sends `[]`.
- **The wire ids live in columns.** Keeping the existing registration tables for the backfill was
  necessary, but they cannot name two Assets over one path or a Task no List registered. Storing
  `publicId` on the row — beside the domain id, never replacing it — makes both stable. The
  registration tables remain, read only by the migration.
- **`task.title` is the row's title**, falling back to the imported display name. A List membership
  may be named differently from the Task it holds, and the snapshot describes what the user saw in
  this List or review. This is the *"what you saw is what you get"* rule applied at the Task level.
- **Template creation is a list-screen action, not a dialog in the import path.** The import
  dialog's template picker is a snapshot; a template created from it would not appear in the open
  picker. **New** on Settings → Templates is one place to create, and the picker says to reopen.
- **Resend is verbatim.** A v0.1 history row replays its old unversioned body; a v2 row replays v2.
  The history records what was sent, and rewriting it during an upgrade would make *resent* mean
  something other than *sent again*.

## Out of scope

- New export kinds, and any change to how a round chooses one.
- The data-model work in [Roadmap](../roadmap.md): review templates for the Review page, the
  cross-platform boundary, and the check-in task type.
- The presentation hierarchy pass, now **0.6.2** — deferred, not cancelled.
- Removing features to make the app feel simpler. When 0.6.2 comes, it may hide explanation; it may
  not hide capability.
